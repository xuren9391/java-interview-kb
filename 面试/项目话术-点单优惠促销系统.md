## 二、STAR 完整版（面试讲 3-5 分钟）

### S - 背景

- **业务**：前司是餐饮 SaaS 头部，服务近百万家门店（茶饮连锁为主）。
- **我的模块**：点单流程里的**优惠促销**——用户下单时算"这单能用哪些券、怎么叠加最划算、最终付多少钱"，以及营销侧的促销活动配置（满减/折扣/买赠/秒杀）。
- **团队**：后端 50+ 人，我是优惠促销模块的**核心开发，负责模块设计**。

### T - 任务/挑战

这个模块最难的地方：

1. **优惠叠加计算极其复杂** 🔴：一单可能同时有"门店满减 + 平台券 + 会员折扣 + 新人立减"，**怎么叠加、按什么顺序、互斥规则**，算错一分钱就是资损或客诉。
2. **金额一致性**：优惠券抵扣、会员资产（积分/储值）扣减、实付金额，三方必须**分毫不差**对得上账，否则财务对账炸锅。
3. **退款回滚** 🔴（最难的场景）：用户退款时，用掉的券要还回去、扣的积分要退、满减要重算——**逆向流程比正向复杂 3 倍**，最容易出不一致。
4. **高并发超卖**：秒杀券（首杯免费、1 元抢）瞬时几万并发，不能超发；库存（杯数）不能超卖。

### A - 我做了什么（核心行动）

#### 行动 1：设计价格计算引擎（策略 + 责任链）⭐ 最大亮点

**问题**：原来优惠计算散落在代码各处 if-else，加一个新活动类型要改 5 个地方，经常漏改出 bug。

**我的方案**：
- 用**策略模式**抽象 `DiscountCalculator` 接口，每种优惠（满减/券/会员折扣）一个实现类。
- 用**责任链 + 模板方法**控制叠加顺序和互斥规则：`链 = [互斥校验 → 优先级排序 → 逐个计算 → 兜底校验]`。
- **叠加规则可配置**（运营在后台配，不写死代码）：通过规则引擎（或配置化的互斥矩阵）决定"哪些能叠加、谁先算"。

**效果**：新增促销类型从"改 5 处代码 + 测试 3 天"降到"加 1 个实现类 + 配规则 + 半天"，计算逻辑集中可测，金额 bug 下降 80%。

#### 行动 2：金额一致性保障

**问题**：优惠券抵扣、会员资产扣减、实付金额对不上，财务对账天天找。

**我的方案**：
- **金额全用分（long）**，绝不用 double（浮点误差）。
- 建立**金额恒等式**：`商品原价合计 = 优惠抵扣合计 + 实付金额 + 资产抵扣`，每单计算完做校验，不平则告警 + 拒绝下单。
- **资金流水全留痕**：每笔优惠/抵扣/退款记资金流水表，可追溯，对账兜底。

#### 行动 3：退款回滚（最难，重点讲）🔴

**问题**：用户退款时，券要还、积分要退、满减要重算。原来的逻辑是"各模块自己回滚"，经常出现：券还了但订单状态没变 / 积分多退 / 满减重算后金额对不上 → **数据不一致，客诉 + 资损**。

**我的方案**：
- **基于 MQ 事务消息**编排退款流程：退款发起 → 发事务消息 → 各资源模块（券/积分/储值）订阅消费、各自回滚 → 全部成功才认为退款完成。
- **幂等**：每个回滚操作带 bizId（退款单号），重复消费直接返回成功，防重复退。
- **补偿 + 对账**：定时任务扫描"退款超时未完成"的订单，触发补偿；每日对账兜底（订单退款状态 vs 资源回滚状态）。

**效果**：退款不一致率从 X% 降到 Y%（你填真实值），客诉显著下降。

#### 行动 4：高并发超卖防护

**问题**：秒杀券（首杯免费）瞬时几万并发，DB 扛不住且会超发。

**我的方案**（三道防线）：
1. **Redis + Lua 预扣**：领券/扣库存先在 Redis 原子扣减（拦 99%），扣到 0 直接拒。
2. **MQ 异步落库**：Redis 扣减成功后发 MQ，消费者按 DB 能力落库，削峰。
3. **DB 兜底**：`UPDATE stock SET num=num-1 WHERE id=? AND num>0`，影响行数 0 即超卖，回滚。

**效果**：秒杀活动 0 超发，高峰 DB 压力下降 70%。

### R - 结果

- 下单核心接口 RT **2s → 400ms**。
- 高峰缓存命中率 **85%**。
- 金额 bug 下降 80%，退款不一致率显著下降（你补真实值）。
- 秒杀活动 0 超发。
- 系统服务**近百万家门店**稳定运行。

## 三、技术决策追问应对（高频）

### Q：为什么用策略模式 + 责任链？不用 if-else？

> "原来 if-else 散落，加活动改 5 处。策略模式让每种优惠独立（开闭原则），责任链控制叠加顺序和互斥。新增类型只加一个类 + 配规则，不动老代码。代价是类多了点，但可维护性远胜。"

### Q：优惠叠加顺序怎么定？谁先算？

> "按业务规则：先算**商品级**优惠（单品折扣），再**订单级**（满减），最后**支付级**（券/积分）。同级有互斥（如同品类券不能用两张）。规则配置化，运营在后台调，不写死。"

### Q：为什么金额用分不用 BigDecimal？

> "分（long）性能好、无精度问题。BigDecimal 也行但慢且易忘 setScale。关键是**统一单位 + 恒等式校验**，用什么都行，我们选了 long。"

### Q：退款为什么用 MQ 事务消息不用 Seata？

> "退款涉及券/积分/储值多个模块，且允许**最终一致**（不用强一致锁定资源）。MQ 事务消息 + 幂等 + 对账兜底，比 Seata AT（全局锁、性能差）更适合这种长链路、可异步的场景。"

### Q：Redis 预扣丢了怎么办（Redis 宕机）？

> "三道防线：Redis 预扣（拦 99%）→ MQ 异步落库 → DB 兜底（WHERE stock>0）。Redis 挂了请求落到 DB，DB 乐观锁兜底防超卖，只是性能降级，不会超卖。"

### Q：价格计算引擎的规则怎么配置？

> "运营在后台配置活动时选叠加/互斥规则，存 DB + 缓存。计算时加载该门店生效的规则集，按优先级和互斥矩阵编排责任链。新规则上线不用发版。"
