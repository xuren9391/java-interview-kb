## 一、高并发总纲

### Q1 🔴🔴 高并发三板斧？你做过的最高 QPS 系统怎么设计？

**三板斧**：
1. **垂直提升**：单机硬件（CPU/内存/SSD/网卡）。
2. **水平扩展**：分布式（加机器、分区、分片）。
3. **架构优化**：异步化、缓存、削峰、批量化、池化、无状态。

**回答套路**（结合项目）：
- 量级：QPS、用户量、数据量。
- 架构：CDN → LB → 网关 → 服务（无状态弹性）→ 缓存/DB/MQ。
- 关键优化：多级缓存命中率、MQ 削峰、分库分表、读写分离。
- 稳定性：限流熔断降级、监控告警、压测。

---

### Q2 🔴 Little's Law（利特尔法则）？容量怎么估？

**并发数 = QPS × 平均 RT**

例：QPS=1000，RT=0.1s → 并发 100。

**容量评估**：
1. 估峰值 QPS（DAU × 人均 × 系数 ÷ 86400 × 峰均比）。
2. 单机容量 = 总 QPS ÷ 机器数，留 30% 余量。
3. 找瓶颈（CPU/IO/DB）。
4. 评估依赖（DB 连接、Redis、下游）。

## 二、限流

### Q3 🔴🔴 漏桶 vs 令牌桶？怎么选？

| | 漏桶 | 令牌桶 |
|---|------|--------|
| 原理 | 固定速率**漏出** | 固定速率**发令牌** |
| 突发 | 不允许（恒定速率） | 允许（一次取多个） |
| 适用 | 整形（匀速，保护下游） | 允许突发 |

- **秒杀**：令牌桶（允许瞬时突发）。
- **MQ 消费**：漏桶（匀速不压垮 DB）。

---

### Q4 🔴 限流算法有哪些？

- 计数器（固定窗口）：简单，临界问题。
- 滑动窗口：细分窗口，解决临界。
- 漏桶：匀速。
- 令牌桶：允许突发。

---

### Q5 🔴 分布式限流怎么实现？

**Redis + Lua**（原子）：
```lua
local c = redis.call("incr", KEYS[1])
if c == 1 then redis.call("expire", KEYS[1], ARGV[1]) end
if c > tonumber(ARGV[2]) then return 0 end
return 1
```
或 Sentinel 集群限流（Token Server）。

## 三、熔断降级

### Q6 🔴🔴 熔断器三个状态？

```
        失败率超阈值
CLOSED ─────────→ OPEN（熔断，直接拒绝）
  ↑                   │ 探测成功   │ 等待
  └──── HALF-OPEN（放少量探测）
```
- **CLOSED**：正常。
- **OPEN**：直接拒，不调下游（保护 + 快速失败）。
- **HALF-OPEN**：放少量探测，成功回 CLOSED，失败回 OPEN。

---

### Q7 🔴 熔断 vs 降级 vs 限流 vs 隔离？

- **限流**：控制流量大小，超出拒绝。
- **熔断**：下游故障快速失败，防级联雪崩。
- **降级**：保核心弃非核心（返回默认/缓存）。
- **隔离**：资源隔离（线程池/信号量），故障不扩散。

## 四、幂等

### Q8 🔴🔴 幂等怎么实现？UPDATE balance+10 幂等吗？

**方案**：唯一约束 / 乐观锁 / 状态机 / Token / 分布式锁 / 去重表。

**UPDATE balance+10 不幂等**（每次执行都+10）。
**UPDATE balance=100 幂等**（绝对值）。

## 五、秒杀系统（综合题）

### Q9 🔴🔴 设计秒杀系统，怎么防超卖？

**分层架构**：
```
前端：按钮置灰、验证码错峰、静态化 CDN
网关：限流（用户/IP 维度）、黑名单、鉴权
服务：
  - 活动未开始/结束 → 直接拒
  - 库存预热 Redis
  - Redis Lua 预扣（原子判断>0→扣，扣到 0 拒 99%）
  - 扣成功发 MQ
MQ：消费者按 DB 能力处理，写订单、扣真实库存
DB：UPDATE stock SET num=num-1 WHERE id=? AND num>0（兜底）
```

**防超卖核心**：
1. **Redis 预扣**（Lua 原子）拦 99%。
2. **DB 乐观锁** `WHERE num>0` 兜底。
3. **库存预热 + 回滚**（订单超时延时回滚）。

## 六、缓存

### Q10 🔴🔴 缓存一致性？先更新 DB 还是先删缓存？

**推荐：先更新 DB，再删缓存**（Cache-Aside）。
- 异常（删失败）→ 重试（MQ）/ 订阅 binlog 异步删。
- **为什么删不更新**：① 避免并发写冲突 ② 懒加载 ③ 删幂等。
- **延迟双删**（先删场景）：删 → 更新 DB → sleep → 再删。

---

### Q11 🔴 多级缓存设计？

```
浏览器 → CDN → Nginx → 网关 → 本地缓存(Caffeine) → Redis → DB
```
每层拦截一部分流量，命中率 90%+ 是目标。

## 七、稳定性与排查

### Q12 🔴🔴 接口变慢怎么排查？

```
全局慢 → 机器资源（CPU/内存/GC/网络）
单接口慢 → 链路追踪每个 Span 耗时：
  - DB 慢查询（慢 SQL + 锁 + 大结果集）
  - 下游接口超时
  - Redis/MQ 慢
  - GC 频繁
  - 网络（带宽/RTT）
  - 锁竞争（BLOCKED）
```

---

### Q13 🔴🔴 一个服务挂导致雪崩，怎么止血？

**止血**：
1. **限流**（网关 + 应用双层）。
2. **降级**非核心。
3. **隔离**故障服务。
4. **扩容**。

**根因**：补熔断、超时、重试策略、舱壁隔离。

---

### Q14 🔴 DB 慢查询优化？

```
1. 慢日志 + explain（type/key/rows/Extra）
2. 加索引 / 联合索引 / 避免失效
3. 大分页改游标
4. 避免 SELECT *，覆盖索引
5. 拆 join
6. 分库分表
7. 验证
```

## 八、容灾

### Q15 🔴 异地多活怎么做？单元化架构？

**单元化**：
- 按用户维度（userId）路由到固定"单元"。
- 每单元完整闭环（应用+DB+缓存），核心数据按用户分片。
- 跨单元调用最小化。
- 单元间双向同步（DTS/Canal+MQ）。
- 故障切流量。

**挑战**：同步延迟、全局唯一数据、跨单元事务。

## 九、实战场景（结合项目讲）

### Q17 🔴 你做过哪些性能优化？

**回答模板（STAR）**：
- **S 背景**：接口 RT 从 200ms 涨到 2s，用户投诉。
- **T 任务**：排查并优化。
- **A 行动**：
  - 定位：链路追踪发现 DB 慢查询（无索引）+ 序列化耗时。
  - 优化：① 加联合索引（覆盖）② Redis 缓存热点（命中率 85%）③ 改 Protobuf 序列化 ④ JVM 调 G1 减 FullGC。
- **R 结果**：RT 降到 100ms，QPS 提升 3 倍。

**加分**：讲取舍、量化数据、踩过的坑。

---

### Q18 🔴 怎么保证订单数据一致性？（跨服务）

- **同步**：Seata AT / TCC（核心交易）。
- **异步**：本地消息表 + MQ + 幂等（互联网主流）。
- **对账**：日终对账兜底。
- **补偿**：定时任务扫描异常订单。

### Q19 🔴 大促前你们怎么准备？

- **容量评估 + 压测**（全链路，影子库隔离）。
- **扩容**（应用、DB、Redis、MQ）。
- **预热**（热点缓存、JVM）。
- **降级预案**（开关、限流阈值）。

---

### Q20 🔴 分布式系统如何保证高可用？

- **冗余**：多副本、主从、集群。
- **故障转移**：心跳检测 + 自动切换（哨兵、Raft）。
- **限流熔断降级**：防雪崩。
- **无状态 + 弹性扩缩**。
- **多机房容灾**：同城双活 / 异地多活。
- **监控告警 + SOP**：快速发现恢复。
