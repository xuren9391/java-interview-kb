# 面试题 - 中间件与分布式

> 🔴 高频 · 配套知识点：`资料/04-中间件与分布式.md`

---

## 一、消息队列

### Q1 🔴 MQ 的作用？

1. **解耦**：生产者消费者互不依赖。
2. **异步**：写入即返回，提升响应速度。
3. **削峰填谷**：突发流量先入队，消费端按节奏处理。

---

### Q2 🔴🔴 Kafka 为什么这么快？（必背）

1. **顺序写磁盘**（append，磁盘顺序写 >> 随机写）。
2. **页缓存 PageCache**：写 OS 缓存，OS 异步刷盘。
3. **零拷贝 sendfile**：数据内核到网卡，不进用户空间。
4. **批量发送** + 压缩（攒批发送）。
5. **分区并行**：水平扩展，分区=并发。
6. **Pull 模式**：消费者按能力拉，不压垮消费端。

---

### Q3 🔴 MQ 选型？Kafka / RocketMQ / Pulsar / RabbitMQ？

| | Kafka | RocketMQ | Pulsar | RabbitMQ |
|---|-------|----------|--------|----------|
| 吞吐 | 极高 | 高 | 高 | 中 |
| 顺序 | 分区有序 | 严格顺序 | 分区有序 | 不保证 |
| 事务 | 弱 | 强（半消息+回查） | 支持 | 弱 |
| 延时 | 无原生 | 原生（18 等级） | 支持 | 插件 |
| 存算 | 耦合 | 耦合 | 分离 | 耦合 |
| 适用 | 大数据/日志 | 电商业务 | 云原生/多租户 | 中小项目 |

---

### Q4 🔴🔴 MQ 怎么保证消息不丢失？

**三环节**：
- **生产端**：acks=all（Kafka）/ 同步发送 + 重试 + 回调确认。
- **Broker**：min.insync.replicas≥2 + acks=all / 同步刷盘 + 主从复制。
- **消费端**：关闭自动 ack，业务处理完手动 ack。

---

### Q5 🔴🔴 消息重复消费怎么解决？幂等？

**重复原因**：ack 丢失 → 重发；重启 offset 未提交。**MQ 只能 at-least-once，要 exactly-once 必须业务幂等**。

**幂等方案**：
1. **唯一约束**：业务 ID 唯一键，重复插报错忽略。
2. **乐观锁**：`UPDATE ... WHERE version=v`。
3. **状态机**：校验状态流转。
4. **去重表**：msg_id 去重。
5. **Redis 锁**：`SET msg_id NX EX`。

---

### Q6 🔴🔴 消息顺序怎么保证？

- **单分区有序**：同一业务 key（如 orderId）hash 到**同一分区/队列**，单线程消费。
- **生产端**：key hash 分区（RocketMQ MessageQueueSelector）。
- **消费端**：单分区单线程；并发则按 key 分发到内存队列各自串行。
- **代价**：牺牲并行度，热点 key 瓶颈。

---

### Q7 🔴 消息积压怎么处理？

1. 临时扩容消费者（注意 Kafka 消费者数 ≤ 分区数）。
2. 紧急：先转发到新 topic（分区更多），更多消费者处理。
3. 根因：消费慢（DB 慢/外部接口慢）→ 优化/异步/批量。
4. 监控告警。

---

### Q8 🔴 RocketMQ 事务消息原理？

```
1. 发半消息（消费者看不到）→ Broker 存储
2. 执行本地事务
3. 成功 → commit（可见）；失败 → rollback（删除）
4. 异常（无 commit/rollback）→ Broker 回查 Producer → 根据本地事务状态决定
```
**本质**：解决"本地事务 + 发消息"的原子问题。

## 二、分布式理论

### Q9 🔴🔴 CAP？为什么注册中心选 AP？

**CAP**：一致性 C、可用 A、分区容错 P，三选二。P 不可避免，实际是 CP / AP 间选。

**注册中心选 AP**：
- 核心是**可用性**（服务发现不能阻塞）。
- 短暂不一致（旧的下线数据）可被客户端容错（重试/熔断）。
- CP（ZK）leader 选举期**整个不可用**，对服务发现是灾难。

**注意**：CAP 的 C 是**线性一致**（强一致），不是 ACID 的 C（事务一致）。

---

### Q10 🟡 BASE？

CAP 在 AP 的延伸：基本可用 + 软状态 + 最终一致。大多数互联网业务（电商、社交）用 BASE。

---

### Q11 🔴 Raft 选举流程？

1. 节点状态：Follower / Candidate / Leader。
2. 心跳超时 → Follower 变 Candidate，term++，发投票请求。
3. 获多数票 → Leader，开始发心跳。
4. **一个 term 每节点只投一票** → 防多 leader。
5. 日志复制：Leader 写 → 复制 Follower → 多数确认 → commit。

---

## 三、分布式事务

### Q12 🔴🔴 分布式事务方案对比？

| 方案 | 一致性 | 性能 | 复杂度 | 适用 |
|------|--------|------|--------|------|
| 2PC（XA） | 强 | 差（阻塞） | 中 | 传统数据库、银行 |
| TCC | 强（业务） | 好 | 高（3 方法） | 金融核心 |
| SAGA | 最终 | 好 | 中 | 长事务 |
| 本地消息表 | 最终 | 好 | 低 | 互联网主流 |
| 事务消息 | 最终 | 好 | 中 | 解耦场景 |
| Seata AT | 最终 | 好 | 低 | 微服务主流 |

---

### Q13 🔴 Seata AT 模式原理？

- **一阶段**：拦截 SQL → 执行本地事务 + 记 undo log（前后镜像）+ 记全局锁。
- **二阶段提交**：异步删 undo log。
- **二阶段回滚**：按 undo log 反向补偿。
- **隔离**：全局锁实现写隔离；读默认 RC（要 RR 加 @GlobalLock）。
- **角色**：TC（协调器）/ TM（发起方）/ RM（参与方）。

---

### Q14 🔴🔴 本地消息表怎么实现？

```
1. 业务表 + 消息表 同一本地事务写入
2. 定时任务扫描消息表，投递 MQ
3. 消费方处理完 ack，更新消息状态
4. 失败重试 + 业务幂等
```
**优**：简单可靠、最终一致。**劣**：消息表耦合业务、扫描有延迟。

---

### Q15 🟡 TCC 的坑？

- 业务侵入大，每操作写 3 方法。
- **幂等**：Confirm/Cancel 可能重试。
- **空回滚**：Try 未执行但 Cancel 调用（要识别）。
- **悬挂**：Cancel 先于 Try 到达（要拦截）。

## 四、分布式锁

### Q16 🔴🔴 Redis 分布式锁怎么做？Redisson 看门狗？

- **基础**：`SET key value NX PX 30000`，value 用 UUID 标识自己。
- **解锁**：Lua 脚本（判断 value 一致才删，保证原子）。
- **Redisson 看门狗**：默认锁 30s，后台线程每 10s 续期（持有者活着）。可重入（hash field=线程ID value=计数）。
- **Redlock**：多 Master 多数成功。**争议**（GC 暂停、时钟漂移），强一致用 ZK。

---

### Q17 🔴 ZK 分布式锁原理？为什么临时顺序节点避免羊群效应？

- **临时顺序节点**：`/lock/seq-0001`、`/lock/seq-0002`...
- 最小序号获锁。
- 其余**监听前一个节点删除**（不是监听所有），避免羊群效应（一个节点释放，所有等待者被唤醒争抢）。
- 客户端断开 → 临时节点自动删 → 通知后继。
- CP 强一致，可靠但写性能不如 Redis。

---

### Q18 🔴 Redis 锁 vs ZK 锁怎么选？

- **Redis（AP）**：高并发性能好，主从切换极小概率丢锁。适合性能优先、容忍极小失败。
- **ZK（CP）**：强一致可靠，但性能稍逊。适合金融等强一致场景。
- **etcd**：CP，K8s 同款 Raft，也适合。

## 五、分布式 ID

### Q19 🔴🔴 雪花算法？时钟回拨？

**64 位**：1 符号 + 41 时间戳(ms) + 10 机器 + 12 序列。可用 69 年、1024 台机器、单机 ms 内 4096 个。

**时钟回拨**（NTP 同步/人为调）→ 时间戳变小 → 可能重复 ID。**解决**：
- 拒绝服务（回拨超阈值报警）。
- 等待（睡眠到回拨后）。
- 用历史最大时间戳。
- Leaf-snowflake 用 ZK 分配 workerId + 记录上次时间戳。

---

### Q20 🔴 分布式 ID 方案对比？

| 方案 | 优 | 劣 |
|------|----|----|
| UUID | 无依赖 | 无序、长、索引差 |
| DB 自增 | 简单 | 单点瓶颈 |
| 号段（Leaf-segment） | 高性能、趋势递增 | 依赖 DB |
| 雪花 | 极高、递增 | 时钟回拨 |
| Redis INCR | 高 | 持久化风险 |

**美团 Leaf**：segment（双 buffer 预加载）+ snowflake（ZK 分配 workerId）。

## 六、ZooKeeper

### Q21 🟡 ZK 数据模型？四种节点？

- 树形 Znode：持久/临时 × 顺序/非顺序 = 4 种。
- 临时节点：会话结束自动删（锁、注册）。
- 顺序节点：自动加序号（选主、队列）。

### Q22 🟡 ZK 经典场景？

- 注册中心（Dubbo 早期、Kafka 元数据）。
- 分布式锁。
- Leader 选举（Curator InterProcessMutex）。
- 配置中心（小规模）。
- ZAB 协议（类 Raft）。

## 七、综合场景

### Q23 🔴 如何保证接口幂等？

- 插入：唯一约束。
- 更新：乐观锁（version）/ 状态机。
- 通用：Token 机制 / 分布式锁 / 去重表。
- UPDATE 绝对值（balance=100）幂等；相对值（balance+10）**不幂等**。

---

### Q24 🔴 订单 30 分钟未支付自动取消，怎么实现？

- **方案 1 延时消息**：RocketMQ 延时消息，到点消费取消（推荐）。
- **方案 2 定时任务**：扫描超时订单（简单，有延迟）。
- **方案 3 Redis ZSet**：score=到期时间戳，扫描到期。
- **方案 4 时间轮**：单机高效但易丢。
- 生产：延时消息 + 兜底定时任务双保险。
