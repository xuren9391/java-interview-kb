## 二、STAR 完整版

### S - 背景

- **业务**：为不同餐饮品牌（租户）提供门店、商品、库存、价格的管理能力。
- **架构**：**共享数据库 + tenant_id 行级隔离**（MyBatis-Plus 多租户插件自动注入 tenant_id 条件）。
- **规模**：服务近百万家门店，**头部品牌（大租户）单租户就有上万家门店、数十万 SKU**。
- **我的角色**：业务开发，负责门店/商品/库存模块开发，并解决性能问题。

### T - 挑战

多租户共享库模式下，最大的痛点是**数据倾斜**：

1. **大租户性能差** 🔴：所有租户数据混在一张表，头部品牌数据量占 60%+。查某大租户的商品列表，扫描大量数据，**慢查询频发（2s+）**，甚至拖慢整张表影响其他租户。
2. **海量数据列表查询** 🔴：门店/商品/SKU 数据量大，分页查询深翻页慢（`LIMIT 100000, 20`），模糊搜索、多维筛选性能差。
3. **租户个性化**：不同品牌有差异化字段/规则，不能为每个租户改表结构。

### A - 我的行动

#### 行动 1：大租户性能优化（分库分表）⭐ 核心亮点

**问题**：共享表里大租户数据倾斜，查询慢且影响其他租户。

**我的方案**：
- 对**门店/商品/SKU 等大表按 tenant_id 做 Hash 分库分表**（ShardingSphere）。
- 大租户的数据分散到多个分片，单分片数据量降下来；小租户数据也均匀分布。
- 分片键统一用 `tenant_id`，保证**同一租户的数据在同一分片**（避免跨分片 join/事务）。

**难点与解决**：
- **跨租户查询**（平台运营要看全局数据）：走单独的汇总表/ES，不走分片表。
- **分页**：分片后深分页更复杂，改**游标分页**（`WHERE id > last_id`）避免 `LIMIT offset`。

**效果**：大租户的查询从 2s+ 降到 200ms 以内；单表数据量从千万级降到单分片百万级。

#### 行动 2：海量数据列表查询优化

**问题**：商品/SKU 列表的分页、搜索、多维筛选慢。

**我的方案**（分层优化）：
- **索引优化**：explain 分析慢查询，建合适的**联合索引**（覆盖索引避免回表），消除 `Using filesort` 和 `Using temporary`。
- **多级缓存**：门店/商品这种读多写少的数据，加 **Caffeine 本地缓存 + Redis**，高峰命中率 85%，DB 压力大降。
- **深分页改游标**：后台管理翻到 100 页后超时，改 `WHERE id > last_id ORDER BY id LIMIT 20`，避免深分页扫全表。
- **模糊搜索走 ES**：商品名搜索这种全文匹配，从 MySQL `LIKE` 迁移到 Elasticsearch，支持拼音/纠错/联想。

**效果**：列表查询 RT 普遍降到 100ms 内；缓存命中率 85%。

#### 行动 3：多租户数据安全（防越权）

**问题**：共享库 + tenant_id 模式下，**任何一条 SQL 漏了 tenant_id 条件，就会跨租户泄漏数据**。

**我做的**：
- 依赖 **MyBatis-Plus 多租户插件**自动注入 tenant_id（拦截器层面，开发不用手动写）。
- **Code Review 把关**：涉及租户的查询必须走插件，禁止手写 SQL 绕过。
- **测试覆盖**：上线前用 A 租户账号调接口，验证不会返回 B 租户数据。
- 曾在 review 中发现 2 处潜在越权（某报表 SQL 漏了 tenant_id），及时修复。

## 三、技术决策追问应对（高频）

### Q：为什么选共享库 + tenant_id，不用独立数据库？

> "这是架构组选的（我诚实说）。权衡是：独立库隔离好但运维/成本高（近百万门店不现实）；共享库 + tenant_id 成本低、运维简单，适合 SaaS。代价是数据倾斜和大租户性能问题——这正是我用分库分表解决的。"

### Q：分库分表按 tenant_id，跨租户查询怎么办？

> "平台运营要看全局数据（如所有门店汇总），走单独的汇总表或 ES，不走分片表。业务侧的查询都带 tenant_id，落在单分片，没有跨分片问题。"

### Q：分库分表后深分页为什么更复杂？怎么解决？

> "分片后 `LIMIT 100000, 20` 每个分片都要扫 100020 行回应用层归并，灾难。改游标分页 `WHERE id > last_id LIMIT 20`，每次只取一页。代价是不能跳页，但后台管理场景可接受。"

### Q：MyBatis-Plus 多租户插件怎么保证不漏 tenant_id？

> "插件在拦截器层自动给 SQL 的 WHERE 加 tenant_id 条件，开发正常写 SQL 不用手动加。但要防'绕过插件的手写 SQL'，靠 Code Review + 测试把关。我在 review 中抓过 2 处漏掉的。"

### Q：缓存一致性怎么保证？（通用高频）

> "Cache-Aside：先更新 DB，再删缓存（不更新，因为删幂等且避免并发写冲突）。删失败用重试（MQ）或订阅 binlog（Canal）异步删。热点 key 加互斥锁防击穿。"

### Q：门店/商品数据更新不频繁，缓存怎么刷新？

> "写少读多，用 Cache-Aside + TTL 兜底 + 主动删除。商品改了发 MQ 消息，各节点删本地（Caffeine）+ Redis 缓存。大促前预热热点商品。"
