## 二、STAR 完整版

### S - 背景

- **业务**：为品牌方提供营销玩法：限量券抢领（首杯免费、1 元抢新品）、拼团砍价（社交裂变）、邀请拉新（拉新奖励）。
- **流量特征**：活动开抢瞬间流量洪峰，**单活动 10 万+ 并发抢**，持续几秒到几分钟。
- **我的角色**：**主导秒杀模块的设计与开发**（架构选型 + 核心代码 + 落地）。

### T - 挑战（三大核心难题）

1. **防超发** 🔴：限量 1 万张券，10 万人同时抢，绝不能发超（资损 + 客诉）。
2. **防系统雪崩** 🔴：瞬时 10 万并发直接打 DB，DB 瞬间挂，整条链路雪崩。
3. **防黄牛刷** 🔴：黄牛用脚本/小号批量抢券，真实用户抢不到，营销预算被薅干。

### A - 我的行动

#### 行动 1：防超发——三道防线 🔴 核心亮点

**防线 1：Redis + Lua 原子预扣**（拦 99%）
```lua
-- 原子操作：判断库存>0 → 扣减 → 记录用户已抢（防重复）
local stock = tonumber(redis.call("get", KEYS[1]))
local userId = ARGV[1]
if redis.call("sismember", KEYS[2], userId) == 1 then return -1 end  -- 已抢过
if stock == nil or stock <= 0 then return 0 end                      -- 抢光
redis.call("decr", KEYS[1])
redis.call("sadd", KEYS[2], userId)
return 1                                                             -- 抢成功
```
- 库存预热到 Redis，Lua 保证"判断+扣减+防重"原子。
- 扣到 0 立即拦截 99% 请求，DB 几乎无压力。

**防线 2：MQ 异步落库**（削峰）
- Redis 预扣成功的请求，发 RocketMQ，消费者按 DB 能力（如 1000 TPS）慢慢落库。
- 瞬时 10 万并发被 MQ 削峰，DB 平稳处理。

**防线 3：DB 乐观锁兜底**（最后保险）
```sql
UPDATE coupon_stock SET num = num - 1 WHERE activity_id = ? AND num > 0
-- 影响行数 0 = 超发，回滚 Redis
```
- 即使 Redis/MQ 出问题，DB 层 `WHERE num > 0` 保证不超卖。

**效果**：大促 0 超发，DB 峰值 QPS 从 10 万降到几千。

#### 行动 2：防雪崩——限流 + 降级 + 异步

- **网关层限流**（Sentinel）：单 IP/单用户/单接口 QPS 限制，超限直接拒。
- **应用层熔断降级**：下游（DB/Redis）RT 飙升或错误率高时熔断，返回"活动太火爆，稍后再试"。
- **静态资源 CDN + 动态接口缓存**：活动页静态化，减少回源。
- **答题/验证码错峰**：开抢前加验证码，把瞬时洪峰拉平几秒。

**效果**：大促 0 雪崩，系统稳定。

#### 行动 3：防黄牛——多维防刷

- **用户维度**：每人限领 1 张（Redis SET NX 记录）。
- **设备维度**：设备指纹限频（同设备多账号抢 → 拦）。
- **IP 维度**：同 IP 高频请求限流。
- **行为风控**：注册时间过短、无点单历史的"小号"降权/拒绝。
- **黑名单**：历史违规账号拉黑。

**效果**：黄牛刷量下降 90%+，真实用户得券率提升。

#### 行动 4：活动配置化（工程化）

- **活动模板**：运营在后台配置（券总量、限领规则、时间窗口、适用门店、优先级），不写死代码。
- **规则引擎**：不同活动的叠加/互斥规则配置化（和旗舰项目的价格计算引擎联动）。
- **灰度发布**：新活动先小范围门店灰度，验证后全量。

## 三、技术决策追问应对（高频）

### Q：为什么 Redis 预扣 + MQ 异步，不直接 DB 扣？

> "10 万并发直接打 DB 必挂。Redis 单线程 + Lua 原子，预扣毫秒级，拦掉 99% 后只放少量到 MQ，消费者按 DB 能力落库。三道防线分工：Redis 拦截、MQ 削峰、DB 兜底。"

### Q：Redis 预扣成功但 MQ 发送失败/落库失败怎么办？

> "两种兜底：① MQ 发送失败则回滚 Redis 库存（事务性）；② 落库失败的进重试队列/补偿表，定时重试；③ 最终对账（Redis 库存 + 已发券数 + DB 库存 三方对账），不平则告警人工介入。"

### Q：Redis 挂了怎么办？

> "降级到 DB 乐观锁直接扣（防线 3 兜底），性能降级但绝不超卖。同时 Redis 用集群 + 哨兵保证高可用。"

### Q：怎么保证一人一张？

> "Redis Lua 里用 SET 记录已抢用户（sismember 判断），原子防重。DB 层加唯一约束（user_id + activity_id）兜底。"

### Q：为什么不用秒杀专门的方案（如 Tair）？

> "Redis 集群 + Lua 已够用（10 万并发），Tair 成本高。技术选型要匹配规模，不过度设计。如果到百万级再考虑。"

### Q：库存预热怎么做的？

> "活动开始前把库存量同步到 Redis。预热时机：活动创建/修改时同步 + 开始前定时校对（Redis vs DB 一致）。大促前人工复核。"

## 五、经典坑故事（准备 1-2 个）

### 故事 1：Redis 集群某个节点宕机导致部分用户超发

**现象**：某次活动后对账发现多发 50 张券。
**排查**：Redis Cluster 某节点故障切换瞬间，少量请求扣减未生效但返回成功。
**解决**：① DB 乐观锁兜底（当时部分接口漏配，补上）；② 对账机制加强（实时对账而非 T+1）；③ Redis 操作失败必须回滚。
**复盘**：三道防线缺一不可，对账是最后底线。

### 故事 2：黄牛用设备农场刷券

**现象**：某活动 80% 券被同一批设备领走。
**排查**：分析发现同 IP 段、同设备指纹、新注册小号集中抢。
**解决**：加设备指纹 + IP 频控 + 小号风控规则。
**复盘**：防刷要多维，单维度（如只限用户 ID）防不住有组织的黑产。

## 八、三件套配合策略（总结）

面试时根据岗位/轮次选讲：

| 岗位/场景 | 讲哪个 | 理由 |
|---------|--------|------|
| **业务深度 / 资损防控** | 点单优惠促销（旗舰） | 价格计算 + 金额一致 + 退款回滚 |
| **架构 / 性能 / 分库分表** | 门店商品 SaaS | 多租户 + 数据倾斜 + 查询优化 |
| **高并发 / 秒杀 / 稳定性** | 营销秒杀活动（本项目）| 10 万并发 + 防超发 + 防雪崩 |
| **冲大厂架构岗** | 三个都讲 | 业务+架构+高并发全覆盖 |
| **时间紧只讲一个** | 旗舰项目 | 业务深度最稀缺 |
| **二面深挖** | 旗舰 + 秒杀 | 一个业务一个技术，立体 |

> 💡 **核心提醒**：这个项目你**可以自信地说"我主导设计"**（和门店 SaaS 的"业务开发"定位不同）。三道防线（Redis预扣→MQ削峰→DB兜底）是标准秒杀架构，背熟 + 加上你的防刷细节，就是完整的高并发故事。
