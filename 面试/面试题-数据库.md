# 面试题 - 数据库（MySQL + Redis + ES）

> 🔴 高频 · 配套知识点：`资料/03-数据库与存储.md`

## 一、MySQL

### Q1 🔴🔴 为什么 MySQL InnoDB 用 B+ 树？不用 B 树/红黑树/哈希？

- **vs 哈希**：哈希 O(1) 但不支持范围查询和排序。
- **vs 红黑树/二叉树**：树高随数据增加，磁盘 IO 多（树高=IO 次数）。
- **vs B 树**：B 树非叶子节点也存数据 → 单节点 key 少 → 树更高。
- **B+ 树优势**：
  1. 非叶子节点只存索引，单节点容纳更多 key → **树矮**（3 层存千万级，查询 3 次 IO）。
  2. 叶子节点双向链表 → **范围查询、排序极快**。
  3. 查询稳定 O(log N)（必到叶子）。

---

### Q2 🔴🔴 聚簇索引 vs 二级索引？什么是回表、覆盖索引？

- **聚簇索引**：叶子节点存**完整行数据**。InnoDB 主键索引就是。一张表只有一个，数据按聚簇索引顺序存储。
- **二级索引**：叶子节点存**主键值**。查二级索引拿到主键 → 再查聚簇索引 = **回表**。
- **覆盖索引**：查询字段全被索引覆盖 → **不需要回表**。

**MyISAM** 的主键索引也是非聚簇（叶子存行地址）。

---

### Q3 🔴🔴 联合索引 (a,b,c) 的命中规则？最左前缀？

```sql
WHERE a=1                    ✅ a
WHERE a=1 AND b=2           ✅ a,b
WHERE a=1 AND b=2 AND c=3   ✅ a,b,c
WHERE b=2                   ❌（跳过 a）
WHERE a=1 AND c=3           ⚠️ 只 a（中间断 b）
WHERE a>1 AND b=2           ⚠️ 只 a（范围后失效）
WHERE a=1 AND b>2 AND c=3   ⚠️ a,b（b 范围后 c 失效）
WHERE a=1 ORDER BY b,c      ✅ 索引有序，免 filesort
```

**核心**：索引按字段顺序排列，**遇到范围查询后面失效**，等值不受影响。

---

### Q4 🔴 索引失效场景（10 条）？

1. 索引列做函数/计算：`WHERE YEAR(t)=2026` → `WHERE t >= '2026-01-01'`
2. 隐式类型转换：`WHERE phone=13800...`（字符串列传数字）
3. `LIKE '%xxx'` 左模糊
4. `OR` 两边不全有索引
5. 不符合最左前缀
6. `!=`/`NOT IN`/`IS NOT NULL`
7. `IN` 列表过长（优化器选全表）
8. 优化器估算成本（数据分布）
9. 范围后字段失效
10. 字符集/排序规则不一致（join）

---

### Q5 🔴🔴 事务隔离级别？InnoDB 默认？各级别解决什么？

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|-----------|------|
| READ UNCOMMITTED | 有 | 有 | 有 |
| READ COMMITTED（Oracle/PG 默认） | 无 | 有 | 有 |
| **REPEATABLE READ（MySQL 默认）** | 无 | 无 | InnoDB 用间隙锁解决 |
| SERIALIZABLE | 无 | 无 | 无 |

- **脏读**：读到未提交数据。
- **不可重复读**：同行两次读不同（别的事务 update 提交）。
- **幻读**：范围查询结果集变（别的事务 insert）。

---

### Q6 🔴🔴 MVCC 原理？RC 和 RR 的 ReadView 区别？（必精通）

**三组件**：隐藏列（trx_id + roll_pointer）+ Undo Log 版本链 + ReadView。

**ReadView 包含**：m_ids（活跃事务列表）、min_trx_id、max_trx_id、creator_trx_id。

**可见性判断**（沿版本链）：
- trx_id == creator → 自己改的，可见
- trx_id < min → ReadView 前已提交，可见
- trx_id >= max → ReadView 后才开，不可见
- 在 m_ids 中 → 活跃，不可见；不在 → 已提交，可见

**RC vs RR**：
- **RC**：每次 select 都生成新 ReadView → 读到最新已提交 → 不可重复读。
- **RR**：事务首次 select 生成 ReadView，之后复用 → 一直看首次快照 → 可重复读。

---

### Q7 🔴🔴 RR 如何防幻读？

两条路：
1. **快照读**（普通 select）：MVCC，看 ReadView 快照，天然不看到新 insert → 防幻读。
2. **当前读**（select for update / lock in share mode / update / delete）：**Next-Key Lock**（Record + Gap）锁住记录和间隙，其他事务无法 insert → 防幻读。

---

### Q8 🔴 InnoDB 行锁的几种？

- **Record Lock**：锁单行（等值命中唯一索引）。
- **Gap Lock**：锁区间（开区间，不含记录），防 insert。
- **Next-Key Lock**：Record + Gap（左开右闭），RR 默认。
- **意向锁**（IS/IX）：表级，快速判断表里有无行锁。

---

### Q9 🔴🔴 Redo Log / Undo Log / Binlog 区别？两阶段提交？

| 日志 | 层 | 作用 |
|------|----|------|
| Redo Log | InnoDB | crash-safe（持久性），WAL 顺序写 |
| Undo Log | InnoDB | 回滚 + MVCC 版本链 |
| Binlog | Server | 主从复制 + 数据恢复 |

**两阶段提交**（保证 Redo 和 Binlog 一致）：
1. InnoDB 写 Undo（prepare）
2. 写 Redo Log（prepare）刷盘
3. Server 写 Binlog 刷盘
4. Redo 改 commit

**为什么需要**：防止"Redo 有 Binlog 没"（从库没数据）或"Binlog 有 Redo 没"（主库没数据）的主从不一致。宕机恢复时看 Redo 状态 + Binlog 完整性决定 commit 或回滚。

---

### Q10 🔴 explain 重点看哪些列？

- **type**：访问类型，至少 range（理想 ref/eq_ref）。ALL=全表，要优化。
- **key**：实际用的索引。NULL=没用索引。
- **key_len**：联合索引用了几字段。
- **rows**：扫描行数，越小越好。
- **Extra**：Using index（覆盖，好）/ Using filesort（差）/ Using temporary（差）/ Using where。

---

### Q11 🔴 主从延迟原因？怎么解决？

**原因**：从库单线程重放（5.7 前）/ 从库性能差 / 大事务 / 网络 / 从库读压力大。

**解决**：
- 5.7+ 并行复制（基于组提交 / 写集合）。
- 关键业务强制读主。
- 半同步复制。
- 业务容忍最终一致。

---

### Q12 🔴🔴 分库分表怎么做？带来的问题？

**维度**：垂直分库（按业务）/ 垂直分表（宽表拆窄）/ 水平分表（hash/range/时间）。

**分片策略**：范围（易扩容，易热点）/ 哈希（均匀，扩容 rehash）/ 一致性哈希。

**带来的问题**：
1. **跨库 join** → 应用层组装 / 冗余字段 / 广播表。
2. **分布式事务** → Seata / 本地消息表。
3. **深分页** → 禁止 `LIMIT 100w, 10`，用游标 `WHERE id > last_id`。
4. **全局 ID** → 雪花/Leaf。
5. **聚合统计** → ES / 数仓。

**中间件**：ShardingSphere（JDBC/Proxy 两种模式）。

---

### Q13 🟡 一条 SQL 慢，怎么优化？

```
1. 慢查询日志 + explain 看 type/key/rows/Extra
2. 加索引 / 联合索引 / 避免索引失效
3. 大分页改游标
4. 避免 SELECT *，用覆盖索引
5. 拆 join
6. 分库分表
7. 再 explain 验证
```

## 二、Redis

### Q14 🔴🔴 Redis 为什么这么快？

1. **内存存储**：纯内存操作。
2. **单线程**（核心命令）：避免锁竞争和上下文切换。（6.0+ IO 多线程，命令执行仍单线程）
3. **IO 多路复用**（epoll）。
4. **高效数据结构**（SDS、跳表、压缩列表）。
5. **通信协议简单**（RESP）。

---

### Q15 🔴 ZSet 为什么用跳表不用红黑树？

1. **范围查询友好**：跳表叶子层是链表，ZRANGEBYSCORE 天然高效；红黑树要中序遍历。
2. **实现简单**：跳表代码远比红黑树简单，调试维护容易。
3. **并发友好**：跳表局部修改，红黑树旋转涉及多节点。
4. **内存可控**：节点层数概率分布，期望 O(log N)。

**ZSet = dict（member→score，O(1) 查）+ skiplist（按 score 排序）**，共享数据，覆盖两种访问。

---

### Q16 🔴🔴 RDB vs AOF？混合持久化？

| | RDB | AOF |
|---|-----|-----|
| 内容 | 全量二进制快照 | 写命令日志 |
| 触发 | SAVE/BGSAVE/定时 | always/everysec/no |
| 优点 | 体积小、恢复快 | 丢数据少 |
| 缺点 | 两次间数据丢失 | 体积大、恢复慢 |

**BGSAVE 的 fork + COW**：fork 子进程与父进程共享内存页；父进程写时 OS 才复制该页（Copy-On-Write）。大内存 fork 慢 + 写多内存翻倍风险。

**混合持久化（4.0+）**：AOF 重写时先 RDB 二进制存快照，后续增量命令 AOF 追加。恢复快 + 数据全。

---

### Q17 🔴🔴 缓存穿透/击穿/雪崩？

| 问题 | 场景 | 解决 |
|------|------|------|
| 穿透 | 查不存在的数据（每次打 DB） | 空值缓存 + 布隆过滤器 |
| 击穿 | 热点 key 过期，并发打 DB | 互斥锁 / 永不过期 + 异步刷新 |
| 雪崩 | 大量 key 同时过期 / Redis 宕机 | 过期时间加随机 + 多级缓存 + 限流 |

**布隆过滤器**：bit 数组 + k 个哈希。加入：k 位置 1。查询：k 位都 1 才"可能存在"，有 0 "一定不存在"。有误判无漏判，不能删除（除非计数版）。

---

### Q18 🔴 Redis 内存淘汰策略？

- noeviction（默认，不淘汰，写报错）
- allkeys-lru / allkeys-lfu / allkeys-random
- volatile-lru / volatile-lfu / volatile-random / volatile-ttl（只淘汰设过过期的）

**Redis 的 LRU 不是真 LRU**：维护双向链表开销大，用**采样近似 LRU**（随机取 maxmemory-samples 个淘汰最久未用）。

---

### Q19 🔴🔴 Redis 集群为什么是 16384 个槽？

1. **带宽**：Gossip 消息带"自己负责的槽位 bitmap"，16384 bit=2KB；65536 bit=8KB，浪费。
2. **集群规模**：建议节点 ≤1000，16384 足够。
3. **位压缩**：节点少时 bitmap 压缩后更省。

**槽定位**：`CRC16(key) % 16384`。节点变动用 ASK/MOVED 重定向，客户端缓存路由表。

---

### Q20 🔴🔴 分布式锁（Redis）怎么做？Redisson 看门狗？Redlock 争议？

**演进**：
- v1：`SET key value NX PX 30000`。问题：业务没完锁过期 → 误删。
- v2：value 用 UUID（标识自己）+ Lua 解锁（判断 value 一致才删）。
- v3：**Redisson 看门狗**。默认锁 30s，后台线程每 10s（1/3 周期）检查持有者活着就续期。可重入（hash 结构 field=线程ID value=重入次数）。

**Redlock**（多 Master）：多数成功才算成功。
**争议**（Martin Kleppmann）：GC 暂停可能让客户端持锁超时不知情；时钟漂移问题。
**结论**：强一致用 ZK/etcd，高并发用 Redis 容忍极小概率失败。

---

### Q21 🟡 大 Key / 热 Key 怎么处理？

**大 Key**（String >10KB / 集合数万元素）：
- 危害：阻塞（单线程）、网络、删除卡顿、主从同步慢。
- 解决：拆分（Hash 分桶）、压缩、4.0+ UNLINK 异步删、监控。

**热 Key**：
- 危害：单节点热点、击穿。
- 解决：本地缓存（Caffeine 多级）、多副本（key_1/key_2 随机读）。

## 三、Elasticsearch

### Q22 🔴 ES 倒排索引原理？

- 正排：文档→词。
- 倒排：词→文档列表（+ 词频 + 位置）。
- 组成：Term Dictionary（词典）+ Term Index（FST 优化查找）+ Posting List（Roaring Bitmap 压缩）。

---

### Q23 🟡 ES 写入流程？为什么近实时？

```
1. Coordinator 路由到 Primary Shard
2. Primary 写 translog + 内存 buffer
3. refresh（默认 1s）→ buffer 生成 segment → 可搜（近实时）
4. 复制到 Replica
5. flush（translog 满/定时）→ segment 落盘 + 清 translog
6. merge 合并小 segment
```
**近实时**：refresh 间隔（默认 1s），可调。

## 四、综合场景

### Q24 🔴 缓存一致性怎么保证？先更新 DB 还是先删缓存？

**推荐：先更新 DB，再删缓存**（Cache-Aside）。
- 异常（删缓存失败）→ 脏数据 → 重试（MQ）或订阅 binlog（Canal）异步删。
- **为什么删不更新缓存**：① 避免并发写冲突 ② 懒加载（写后不一定读） ③ 删幂等。
- **延迟双删**（先删缓存场景）：删 → 更新 DB → sleep → 再删。

---

### Q25 🔴 海量数据下，MySQL 单表多大要优化？怎么拆？

- 经验值：单表 **1000w 行 / 10GB** 后性能下降（B+ 树变高、索引膨胀）。
- 先优化：索引、分区、读写分离。
- 再分表：水平分表（hash/range）。
- 再分库：垂直（按业务）+ 水平（按数据）。
- 配合 ShardingSphere。
