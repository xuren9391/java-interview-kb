# 第一章 架构演进 🔴（必懂发展脉络）

## 1.1 演进路线

```
1. 单体架构（All in One）
   └─ 部署简单，但代码膨胀、迭代冲突

2. 垂直拆分（按业务拆应用）
   └─ 解耦了，但重复造轮子

3. SOA（面向服务，ESB 总线）
   └─ 服务化，但 ESB 中心化瓶颈

4. 微服务（去中心化、独立部署、独立数据）
   └─ 解耦彻底，但运维复杂、分布式问题多

5. 云原生（容器化 + K8s + DevOps + 微服务）
   └─ 弹性、不可变基础设施

6. 服务网格 ServiceMesh（治理能力下沉 Sidecar）
   └─ 业务无感治理，多语言友好

7. Serverless（FaaS + BaaS）
   └─ 按需付费，免运维，但冷启动、调试难

8. AI 原生架构（LLM + Agent + 向量库）
   └─ 智能体编排，知识驱动
```

## 1.2 什么时候该上微服务？🔴
**不该一上来就微服务**（小团队单体更高效）。判断信号：
- 团队规模 > 30 人，需要并行迭代。
- 业务领域边界清晰，可拆分。
- 单体部署相互阻塞（一个 bug 拖垮全站）。
- 性能瓶颈局部化（某模块流量集中）。

**反模式**：分布式单体（拆了微服务但还强耦合 / 共享数据库 / 同步链路过长）。

## 1.3 微服务的代价 🔴
面试官常问"微服务的缺点"，体现你权衡过：
1. 分布式复杂性（网络不可靠、CAP）。
2. 数据一致性（分布式事务）。
3. 运维成本（部署、监控、链路）。
4. 服务间通信延迟。
5. 测试难度（联调）。
6. 团队协作成本（接口对齐）。

**一句话**：微服务是用"运维复杂度"换"业务扩展性"。

## 1.4 服务拆分原则 🟡
- **单一职责**：一个服务一个业务能力。
- **限界上下文**（DDD）：按业务领域划分。
- **不同生命周期/变更频率的分开**。
- **团队 ownership 对齐**（康威定律）。
- **数据库独立**（不共享 DB，通过 API 交互）。

# 第二章 DDD（领域驱动设计）🔴🔴

## 2.1 为什么需要 DDD
微服务时代，**如何正确拆分服务、如何对齐业务与技术**是难题。DDD 提供了一套从业务到代码的方法论。

## 2.2 战略设计 🟡
- **领域 Domain**：业务问题域（如电商）。
- **子域**：核心子域（核心竞争力）、支撑子域、通用子域。
- **限界上下文 Bounded Context**：模型的边界（一个微服务对应一个上下文）。
- **上下文映射**：上下文之间的关系（合作、共享、客户-供应商、防腐层）。

## 2.3 战术设计 🔴🔴（核心概念 + 代码示例）

| 概念 | 说明 | 例子 |
|------|------|------|
| **实体 Entity** | 有唯一标识 + 生命周期 | 订单 Order |
| **值对象 Value Object** | 无标识，不可变 | 地址 Address、金额 Money |
| **聚合 Aggregate** | 一组相关对象，一致性边界 | 订单聚合（订单+订单项） |
| **聚合根 Aggregate Root** | 聚合的入口，外部只能通过它操作 | Order 是根，OrderItem 通过 Order 改 |
| **领域服务 Domain Service** | 不属于单个实体的业务逻辑 | 转账服务（涉及两个账户） |
| **领域事件 Domain Event** | 业务发生的事实 | OrderCreated |
| **仓储 Repository** | 聚合的持久化抽象 | OrderRepository |
| **工厂 Factory** | 复杂对象创建 | |
| **防腐层 ACL** | 隔离外部系统/遗留模型 | 适配老接口 |

## 2.4 🔴 贫血 vs 充血模型

**贫血模型**（传统三层架构）：
```java
// Entity 只有 getter/setter，业务在 Service
class Order {
    Long id; OrderStatus status; List<OrderItem> items;
    // getters/setters
}
class OrderService {
    public void pay(Order order) {
        if (order.getStatus() != UNPAID) throw ...;
        order.setStatus(PAID);
        // 持久化
    }
}
```
问题：业务散落在 Service，Entity 退化成数据载体，模型和行为分离。

**充血模型**（DDD 推荐）：
```java
class Order {
    Long id; OrderStatus status; List<OrderItem> items;  // 字段封装

    public void pay() {  // 业务在 Entity 内
        if (this.status != UNPAID) throw new BizException("订单状态错误");
        this.status = PAID;
        DomainEvents.publish(new OrderPaidEvent(this.id));  // 领域事件
    }
}
class OrderService {
    public void pay(Long orderId) {
        Order order = orderRepo.findById(orderId);
        order.pay();   // ← 业务在 Entity
        orderRepo.save(order);
    }
}
```
DDD 推崇充血：业务内聚到 Entity，Service 只做编排（加载 + 调用 + 持久化）。

## 2.5 DDD 落地的难点 🔴
1. **建模能力**：业务专家 + 技术共同建模（**事件风暴 Event Storming**）。
2. **贫血 vs 充血**：DDD 推崇充血，但很多人习惯贫血 + Service。
3. **聚合设计**：太大性能差，太小一致性弱。
4. **过度设计**：小项目硬套 DDD 是负担。

**面试话术**："DDD 不是银弹，适合复杂业务的核心子域。我们用 DDD 梳理限界上下文指导微服务拆分，核心域用充血模型，边缘用贫血保持简洁。"

## 2.6 📌 实战案例：用 DDD 重构订单系统

**S 问题**：传统三层架构，订单逻辑分散在 OrderService/OrderItemService/PayService，改一个业务要动多处。
**A**：
- **事件风暴**：拉产品 + 测试一起画事件流，识别"下单、支付、发货、退款"等核心事件。
- **划分限界上下文**：订单、支付、库存、营销各自独立。
- **聚合设计**：Order 为聚合根（含 OrderItem），外部不能直接改 OrderItem。
- **充血**：`order.pay()` / `order.cancel()` 业务内聚。
- **领域事件**：`OrderPaidEvent` 由支付发出，营销/积分订阅。
**R**：业务变更影响面收敛到聚合内，迭代效率提升。

# 第三章 技术选型 🔴🔴（架构师核心能力）

## 3.1 技术选型方法论

**决策维度**：
1. **业务匹配度**：能否解决核心痛点？
2. **成熟度**：生产可用？社区活跃？版本稳定？
3. **团队能力**：学习曲线、现有栈契合度。
4. **性能/功能**：基准测试验证（POC）。
5. **TCO 总拥有成本**：授权费、运维、人力。
6. **生态**：周边工具、文档、案例。
7. **风险**：闭源风险、停更风险、迁移成本。
8. **公司战略**：是否符合技术体系。

**决策流程** 🔴：
```
需求 → 列候选 → POC 验证 → 横向对比（加权打分）→ 风险评估 → 决策 → 灰度落地
```

## 3.2 经典选型对比 🔴（面试常考"为什么选 A 不选 B"）

### MQ 选型（见中间件篇）
### 注册中心（见 Spring 篇）

### 数据库选型 🔴
| | 适用 |
|---|---|
| MySQL | OLTP，事务强，关系复杂 |
| PostgreSQL | 功能强（JSON/地理/扩展），复杂查询 |
| TiDB/OceanBase | 分布式 NewSQL，HTAP，海量数据 |
| MongoDB | 文档型，灵活 schema |
| ClickHouse/Doris | OLAP，分析查询 |

### 缓存：Redis（主流）vs Memcached（纯 KV，多线程）
### 搜索：ES（主流）vs OpenSearch（AWS 分叉）
### 网关：Gateway（Java）vs Nginx/OpenResty（性能）vs APISIX/Kong（云原生）
### 调度：XXL-Job（轻量）vs ElasticJob（分布式）vs Airflow（数据）

## 3.3 🔴 自研 vs 开源 vs 采购
- **开源优先**：避免重复造轮子，但要评估维护成本。
- **自研**：核心差异化、开源不满足、安全合规。代价是长期维护负担。
- **采购**：非核心能力（如支付、短信），买比自建划算。
- **原则**：把精力投在核心子域，非核心用成熟方案。

## 3.4 📌 实战案例：MQ 选型

**背景**：电商业务消息（订单、支付、营销），需要事务消息 + 延时消息。
**候选**：Kafka / RocketMQ / RabbitMQ。
**分析**：
- Kafka：吞吐高但事务弱、无原生延时，适合日志/大数据不适合业务消息。
- RocketMQ：事务消息强、原生 18 等级延时、阿里验证过、Java 生态好。
- RabbitMQ：吞吐一般，Erlang 运维门槛。
**决策**：RocketMQ（业务消息场景最匹配）。
**代价**：吞吐不如 Kafka（但业务量够用），运维要学一套。

# 第四章 系统架构原则 🔴

## 4.1 核心原则
1. **KISS**（Keep It Simple）：简单优先，别过度设计。
2. **YAGNI**（You Aren't Gonna Need It）：别提前实现用不到的。
3. **DRY**（Don't Repeat Yourself）：抽象复用。
4. **高内聚低耦合**。
5. **面向接口编程**。
6. **SOLID 原则**（单一职责、开闭、里氏替换、接口隔离、依赖倒置）。
7. **无状态设计**（便于水平扩展）。
8. **Fail-Fast**（快速失败，早暴露问题）。
9. **Design for Failure**（为失败而设计，假设一切都会挂）。

## 4.2 康威定律 🟡
"系统架构 = 组织沟通结构"。微服务的拆分本质是团队的拆分。架构要和团队结构匹配。

## 4.3 技术债管理 🔴
- **债务分类**：有意债务（赶进度主动欠）/ 无意债务（认知不足）。
- **管理**：可视化（记录）、定期偿还（每个迭代留比例）、防恶化（Code Review + 卡点）。
- **重构**：测试覆盖 + 小步快跑 + 灰度。

# 第五章 设计模式 🟡（23 种里高频的）

## 5.1 必会的高频模式
| 模式 | 场景 | JDK/Spring 例子 |
|------|------|----------------|
| **单例** | 全局唯一 | Runtime、Spring Bean（单例） |
| **工厂** | 创建对象解耦 | BeanFactory、Calendar.getInstance |
| **策略** | 算法可替换 | Comparator、Spring 的 Resource |
| **模板方法** | 流程骨架，子类填充 | AbstractList、JdbcTemplate |
| **观察者** | 发布订阅 | Listener、ApplicationEvent |
| **责任链** | 多个处理器串联 | Filter、Interceptor、Sentinel |
| **代理** | 增强/控制访问 | AOP（JDK 动态代理/CGLIB） |
| **装饰器** | 动态增强 | IO 流（BufferedInputStream） |
| **适配器** | 接口转换 | HandlerAdapter |
| **建造者** | 复杂对象构造 | StringBuilder、Lombok @Builder |

## 5.2 设计模式原则
SOLID 五原则 + 迪米特法则（最少知道）+ 合成复用原则（优先组合而非继承）。

## 5.3 实战应用 🔴
- **策略 + 工厂消除 if-else**（支付方式路由）：
```java
// 不用 if-else，用策略模式
public interface PayStrategy { void pay(Order o); }
@Component class AlipayStrategy implements PayStrategy {...}
@Component class WechatStrategy implements PayStrategy {...}

// 工厂 + Map 注入
Map<String, PayStrategy> strategies;  // Spring 自动按 beanName 注入
strategies.get(payType).pay(order);
```
- **责任链**做风控/参数校验。
- **模板方法**做流程编排（订单创建流程）。
- **观察者**做业务解耦（下单成功发事件，各业务方订阅）。

# 第六章 技术管理与软实力（管理岗 / 专家岗）🔴

## 6.1 技术规划
- **年度规划**：技术目标对齐业务目标（支撑 N 倍增长、降本 X%）。
- **路线图**：季度里程碑。
- **投资组合**：核心攻坚 / 债务偿还 / 创新探索，按比例分配。

## 6.2 团队管理
- **招聘**：标准、面试、留人。
- **培养**：梯队建设、个人发展计划（IDP）、技术分享、Code Review 文化。
- **绩效**：目标设定（OKR/SMART）、过程反馈、公平评估。
- **激励**：物质（晋升/奖金）+ 成长（挑战项目/技术影响力）+ 氛围。

## 6.3 项目推进
- **目标拆解**：WBS（工作分解）+ 责任人 + 时间点。
- **风险管理**：识别 → 评估 → 应对（规避/转移/减轻/接受）。
- **进度跟踪**：站会、周报、里程碑评审。
- **跨团队协作**：明确边界、协议先行、定期对齐。

## 6.4 向上/向下/横向管理 🟡
- **向上**：主动汇报（进展/风险/选项），带着方案而非问题。
- **向下**：明确目标 + 授权 + 资源 + 反馈。
- **横向**：共赢思维、信用账户、定期沟通。

## 6.5 技术影响力
- 技术分享、内部 Wiki、专利论文、开源贡献、跨项目赋能、带新人。
- **专家岗**尤其看重"在多大范围内有技术影响力"。

# 第七章 职业发展 🔴（面试官会问"你的规划"）

## 7.1 发展路径
```
初级（0-3 年）→ 中级（3-5 年）→ 高级（5-8 年）
   → 资深 / 技术专家（8+ 年，个人贡献者顶点）
```

## 7.2 专家路线 vs 管理路线
- **专家/架构师**：深度 + 广度 + 技术判断力 + 影响力。不做人事管理。
- **管理**：人 + 事 + 业务理解 + 跨部门协作。
- 两者都需要**技术视野 + 业务理解**，差异在"通过代码 vs 通过团队产出"。

**好的回答**：成长驱动（更大规模/更深业务/更高挑战）+ 价值匹配（贵公司的 X 正是我想要的）。
**避免**：抱怨前东家、只谈钱、空洞的"想学习"。

# 第八章 云原生（架构师视野）🟡

## 8.1 核心概念
- **容器**（Docker）：标准化交付单元。
- **编排**（Kubernetes）：调度、自愈、弹性。
- **不可变基础设施**：不修改运行中的容器，重新部署。
- **声明式 API**：描述"期望状态"，系统自动收敛。
- **DevOps / CI/CD**：自动化构建-测试-部署。

## 8.2 K8s 核心对象
- Pod（最小调度单元，1+ 容器）。
- Deployment（Pod 副本控制器）。
- Service（稳定的网络端点 + 负载均衡）。
- Ingress（七层路由）。
- ConfigMap / Secret（配置）。

## 8.3 对 Java 工程师的意义
- 应用打包镜像、Helm Chart 部署。
- 配置通过 ConfigMap/Nacos 注入。
- **优雅上下线**（preStop hook + 就绪探针）🔴：
  - 下线：preStop → sleep（等流量排空）→ SIGTERM → K8s 移除 endpoints。
  - 上线：就绪探针（readinessProbe）通过后才接流量。
- 资源限制（requests/limits），防 JVM 误判内存（容器内 JVM 配 `-XX:UseContainerSupport`，JDK8u191+ 支持）。

# 第九章 性能优化总纲（综合实战）🔴

## 9.1 优化层次（从上到下，收益递减）
```
1. 业务优化（最大收益）
   - 减少不必要的调用、合并请求、异步化、批量化
2. 架构优化
   - 缓存、MQ、读写分离、分库分表、CDN
3. 代码优化
   - 算法数据结构、减少对象创建、连接池复用
4. JVM 优化
   - GC 调优、参数
5. OS / 硬件
   - 网络内核参数、磁盘、CPU
```

**铁律**：**先业务后技术，先架构后代码，先测量后优化**（别瞎优化，Profile 找瓶颈）。

## 9.2 📌 实战案例：订单接口优化全链路

**S**：订单详情接口 RT 2s，P99 5s。
**A 分层优化**：
1. **业务**：合并 3 个独立查询为 1 个聚合接口；非核心信息异步加载。
2. **架构**：
   - 加 Redis 缓存（命中率 80%）。
   - 热点商品本地缓存（Caffeine）。
   - 历史订单读写分离。
3. **代码**：批量化查（`IN` 一次查）；避免 N+1 查询。
4. **DB**：加联合索引（覆盖）；大字段拆分。
5. **JVM**：换 G1，调 NewRatio，Full GC 消失。
**R**：RT 2s → 150ms，P99 <500ms，QPS 提升 4 倍。
