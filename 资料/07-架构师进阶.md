# 第一章 架构演进 🔴（必懂发展脉络）

## 1.1 架构演进全景路线

### ① 为什么/痛点
业务从 0 到 1 时，速度第一；业务从 1 到 N 时，扩展性第一。**没有一种架构适用于所有阶段**，架构演进的本质是「随业务规模、团队规模、性能要求的变化而不断取舍」。面试官问「你的架构怎么演进」其实是在考：你能不能说清楚每个阶段**为什么变、变了什么、付出什么代价**。

### ② 原理图解
```
1. 单体架构（All in One）        ── 0~日 PV 万级 / 团队 <10 人
   └─ 部署简单，但代码膨胀、迭代冲突、一个 bug 拖垮全站

2. 垂直拆分（按业务拆应用）      ── 业务线并行
   └─ 解耦了，但重复造轮子（每个应用都有自己的用户/商品表）

3. SOA（面向服务，ESB 总线）     ── 服务化复用
   └─ 服务化，但 ESB 中心化瓶颈、协议重（XML/SOAP）

4. 微服务（去中心化、独立部署）  ── 团队 30+ / 日 PV 百万+
   └─ 解耦彻底，但运维复杂、分布式问题多（CAP/分布式事务/链路追踪）

5. 云原生（容器化 + K8s + DevOps）── 弹性、不可变基础设施
   └─ 标准化交付，资源利用率高，但 K8s 学习曲线陡

6. 服务网格 ServiceMesh          ── 治理能力下沉 Sidecar
   └─ 业务无感治理，多语言友好，但多一跳延迟、Sidecar 资源开销

7. Serverless（FaaS + BaaS）     ── 按需付费
   └─ 免运维，但冷启动、调试难、长任务不友好

8. AI 原生架构（LLM + Agent + 向量库）
   └─ 智能体编排，知识驱动，召回 + 推理一体化
```

### ③ 真实案例（茶饮 SaaS 场景
前司早期（2015 前后）是**单体 PHP/Java 工程**，一个 war 包打天下；2018 年随门店规模（几万家）和业务线（点单、会员、营销、供应链、财务）扩张，演进为**垂直拆分**——点单、会员、营销各一个应用；2020 年后核心域继续**微服务化**：点单、订单、支付、优惠券、促销、库存、门店、消息中心独立部署，注册中心用 Nacos，网关 Spring Cloud Gateway。目前点单/订单等核心域跑在 K8s 上（云原生），营销域因大促流量峰值会配合弹性扩缩容。

### ④ 对比：单体 vs 微服务
| 维度 | 单体架构 | 微服务架构 |
|------|----------|------------|
| 部署 | 一个包，简单 | 多服务独立部署，复杂 |
| 技术栈 | 统一 | 可异构（多语言） |
| 扩展 | 整体复制 | 按服务按需扩（点单扩、财务不扩） |
| 故障隔离 | 差（一崩全崩） | 好（熔断隔离） |
| 团队协作 | 串行冲突 | 并行（按服务分团队） |
| 性能 | 本地调用，快 | 网络调用，有延迟 |
| 一致性 | 本地事务 | 分布式事务/最终一致 |
| 运维成本 | 低 | 高（监控/链路/容器） |
| 适合阶段 | 0→1 / MVP | 1→N / 团队 30+ |

### ⑤ 面试话术
「架构演进核心是**匹配业务与团队规模**。前司从单体到微服务，是随门店数从几千到几万家、团队从十几个到上百人逐步演进的，不是为了追时髦。单体阶段我们追求速度，微服务阶段追求扩展性和团队并行。每次演进都是 trade-off——微服务解决了单体一崩全崩和迭代冲突，但带来了分布式事务、链路追踪、运维成本这些新问题，我们用 Seata/MQ 最终一致 + SkyWalking 链路 + K8s 来消化。」

## 1.2 什么时候该上微服务？什么时候不该？🔴

### ① 为什么/痛点
「**不该一上来就微服务**」是架构师最重要的判断力。过早微服务化会把简单问题复杂化：小团队单体一周上线，微服务化后光搭注册中心/网关/链路就要一个月，且分布式调试痛苦。

### ② 判断信号（该上微服务的信号）
- 团队规模 > 30 人，需要并行迭代。
- 业务领域边界清晰，可按 DDD 拆分。
- 单体部署相互阻塞（一个 bug 拖垮全站）。
- 性能瓶颈局部化（某模块流量集中，如前司点单高峰流量）。
- 不同模块变更频率差异巨大（点单天天改，财务月度改）。

### ③ 反模式（前司踩过的坑）
**分布式单体（Distributed Monolith）**：拆了微服务但还强耦合——共享数据库、同步调用链路过长（下单→营销→库存→积分一串同步 RPC）、改一个接口要联调 5 个服务。这是「拆了但没拆干净」，比单体更糟，因为既有分布式的复杂度又没获得解耦的好处。

### ④ 对比：好微服务 vs 坏微服务
| 维度 | 好的微服务 | 坏的微服务（分布式单体） |
|------|-----------|------------------------|
| 数据库 | 独立 | 共享库/共享表 |
| 通信 | 异步优先（MQ） | 长链路同步 RPC |
| 耦合 | 接口契约 | 数据库/共享 jar |
| 部署 | 真正独立 | 一改全发布 |
| 团队 | 一服务一团队 owner | 多团队改同一服务 |

### ⑤ 面试话术
「上不上微服务要看四点：团队规模、业务边界、部署阻塞、性能瓶颈局部化。前司是在门店破万、点单高峰单体扛不住、且点单和营销团队开始抢接口时才上的微服务。反例是『分布式单体』——我们早期拆了订单和库存但共享一个库，结果库存改表订单就抖动，后来强制『一服务一库 + MQ 解耦』才真正独立。我个人的判断是：宁可单体撑久一点，也别为拆而拆。」

## 1.3 微服务的代价 🔴

### ① 为什么/痛点
面试官常问「微服务的缺点」，考的是你**权衡过没有**。只吹微服务好、说不出代价，说明没真正做过。

### ② 微服务的六大代价
```
1. 分布式复杂性    网络不可靠、超时/重试/熔断、CAP 定理
2. 数据一致性      分布式事务（TCC/Saga/本地消息表）
3. 运维成本        部署、监控、链路追踪、日志聚合
4. 通信延迟        本地调用 ns → 网络 ms，链路一长 RT 翻倍
5. 测试难度        联调环境、依赖治理、契约测试
6. 团队协作成本    接口对齐、版本兼容、文档维护
```

### ③ 真实案例（茶饮 SaaS 场景
- **分布式复杂性**：用 Sentinel 做熔断限流、OpenFeign + 重试、Resilience4j 做舱壁。
- **数据一致性**：核心链路（下单扣库存）用本地消息表 + MQ 最终一致；财务对账用 TCC。
- **运维**：SkyWalking 全链路、ELK 日志、Prometheus + Grafana 监控、K8s 弹性。
- **通信延迟**：热点数据 Redis，本地缓存 Caffeine 兜底，链路上异步化（下单成功后营销/积分走 MQ）。

### ④ 对比
| 代价维度 | 单体 | 微服务 |
|---------|------|--------|
| 一致性 | 本地事务，强 | 分布式，最终一致 |
| 调试 | 本地起服务即可 | 联调环境 + 链路追踪 |
| 部署 | 一个包 | CI/CD + 容器编排 |
| 调用延迟 | ns | ms 级 |

### ⑤ 面试话术
「微服务的本质是**用运维复杂度换业务扩展性**。主要代价：分布式事务、网络不可靠、运维成本。我们公司的消化方式：一致性用本地消息表 + RocketMQ 最终一致；网络不可靠用 Sentinel 熔断 + 重试 + 超时三件套；运维用 SkyWalking 链路 + K8s 容器化。我的体会是——这些代价不是『上不上』的问题，而是『准备好没有』的问题。」

## 1.4 服务拆分原则 🟡

### ① 为什么/痛点
拆错比不拆更惨：拆太细变成纳米服务（一个接口一个服务，运维爆炸），拆太粗等于没拆。拆分原则是架构师的核心方法论。

### ② 拆分原则 + 图示
```
┌─────────────────────────────────────────────┐
│  按 DDD 限界上下文拆（首选，业务驱动）         │
│  ┌────────┐ ┌────────┐ ┌────────┐           │
│  │ 点单域  │ │ 订单域  │ │ 营销域  │  ...     │
│  └────────┘ └────────┘ └────────┘           │
└─────────────────────────────────────────────┘
拆分维度（优先级从高到低）：
1. 业务能力（限界上下文）  ── 首选
2. 变更频率/生命周期      ── 高频变更的独立
3. 性能/资源特征          ── CPU 密集 vs IO 密集分开
4. 团队边界（康威定律）    ── 一个团队 own 一个或一组服务
5. 数据所有权             ── 不同数据模型/存储的分开
```

**拆分粒度判断**：一个服务能被 2-3 个人的小团队完全掌控（开发+运维+演进），是合理粒度（"two-pizza team"）。

### ③ 真实案例（茶饮 SaaS 场景
前司按 DDD 限界上下文拆：**点单**（小程序下单）、**订单**（订单生命周期）、**支付**（多渠道）、**优惠券/促销**（营销资产）、**会员/积分**、**门店/组织**、**商品/库存**、**消息中心**（push/短信）、**财务对账**。其中**点单**和**订单**虽然相关但拆开，因为点单是高频写、订单要支持复杂查询和状态机，资源特征不同。**优惠券**和**促销**分开，因为优惠券是资产（有生命周期），促销是规则（实时计算）。

### ④ 对比
| 拆分方式 | 优点 | 缺点 |
|---------|------|------|
| 按业务能力（DDD） | 内聚高、边界清 | 建模能力要求高 |
| 按技术分层 | 简单 | 数据跨层，分布式事务地狱 |
| 按团队（康威） | 协作顺 | 可能割裂业务 |
| 纳米服务（过细） | 单一职责 | 运维爆炸、链路长 |

### ⑤ 面试话术
「我的拆分原则是『**业务驱动、DDD 限界上下文优先、康威定律对齐**』。前司按域拆成点单、订单、营销、会员等十几个服务。粒度判断标准是『一个 2-3 人团队能完整 own』。最忌讳的是按技术分层拆（一个服务只做查询、一个只做写入）——那会造成分布式事务地狱。」

# 第二章 DDD（领域驱动设计）🔴🔴

## 2.1 为什么需要 DDD

### ① 为什么/痛点
微服务时代两大难题：**怎么拆**和**拆完怎么不让代码腐化**。传统三层架构（Controller-Service-Dao）下，业务逻辑散落在多个 Service，一个业务改动要动十几个类，代码逐渐变成「大泥球」。DDD 提供了一套**从业务语言（通用语言）到代码模型（聚合/实体）再到服务边界（限界上下文）**的完整方法论，让业务模型和代码模型一致。

### ② DDD 的两层结构
```
┌──────────────────────────────────────────┐
│  战略设计（宏观：怎么划边界、怎么拆服务）   │
│  ┌────────────────────────────────────┐  │
│  │ 领域 → 子域 → 限界上下文 → 上下文映射 │  │
│  └────────────────────────────────────┘  │
├──────────────────────────────────────────┤
│  战术设计（微观：边界内的代码怎么写）       │
│  ┌────────────────────────────────────┐  │
│  │ 实体/值对象/聚合/领域服务/领域事件/   │  │
│  │ 仓储/工厂/防腐层                     │  │
│  └────────────────────────────────────┘  │
└──────────────────────────────────────────┘
```

### ③ 真实案例（茶饮 SaaS 场景
前司用 DDD 重构营销域时，先做**事件风暴**拉产品+测试+开发一起贴便利贴，识别出「领券、用券、退券、核销、过期」等核心事件，由此划分出**优惠券**（资产）和**促销**（规则）两个限界上下文，再各自做战术建模。结果是改一个促销规则不再动优惠券代码，影响面收敛。

### ④ 对比：DDD vs 传统三层
| 维度 | 传统三层 | DDD |
|------|---------|-----|
| 业务位置 | Service（散落） | 聚合根（内聚） |
| 业务与代码 | 割裂 | 通用语言对齐 |
| 拆服务 | 经验拍脑袋 | 限界上下文驱动 |
| 适合 | 简单 CRUD | 复杂核心域 |

### ⑤ 面试话术
「DDD 解决的是『复杂业务怎么不让代码腐化』。它分战略和战术两层：战略用限界上下文指导微服务拆分，战术用聚合根把业务内聚到 Entity。前司营销域用 DDD 重构后，改促销规则不再动优惠券代码。但 DDD 不是银弹，它有建模成本和学习曲线，**只适合核心子域**，边缘 CRUD 用三层架构更高效。」

## 2.2 战略设计 🟡

### ① 为什么/痛点
战略设计回答「**系统怎么划成几块、块之间什么关系**」，是微服务拆分的理论基础。不先做战略设计直接拆服务，就是拍脑袋。

### ② 核心概念 + 图示
```
领域（Domain）：整个业务问题域，如「茶饮 SaaS」
   │
   ├─ 核心子域（Core）：核心竞争力，要自己投入做精 ── 如我们公司的「点单+营销」
   ├─ 支撑子域（Supporting）：必要但不差异化 ── 如门店管理
   └─ 通用子域（Generic）：通用能力，可采购 ── 如短信、支付

限界上下文（Bounded Context）：模型的边界
   └─ 一个上下文内模型唯一、无歧义
       （「商品」在点单上下文=可点的饮品；在库存上下文=物料 SKU）

上下文映射（Context Map）：上下文之间的关系
   ├─ 合作关系（Partnership）：两个团队紧密协作
   ├─ 共享内核（Shared Kernel）：共享部分模型
   ├─ 客户-供应商（Customer-Supplier）：下游依赖上游
   ├─ 防腐层（ACL, Anticorruption Layer）：下游做隔离适配，防止上游模型污染
   └─ 开放主机服务（OHS）：上游提供开放协议
```

### ③ 真实案例（茶饮 SaaS 场景
```
┌────────┐  ACL   ┌────────┐  OHS   ┌────────┐
│ 点单    │───────▶│ 订单    │◀───────│ 支付    │
│Context │        │Context │        │Context │
└────────┘        └────────┘        └────────┘
    │  发布 OrderCreatedEvent (MQ)
    ▼
┌────────┐  ACL   ┌────────┐
│ 营销    │◀───────│ 积分    │   （营销订阅订单事件，用防腐层隔离积分模型）
│Context │        │Context │
└────────┘        └────────┘
```
前司营销域调用老的会员系统时，做了一个**防腐层 ACL**：把老系统的 `MemberVO` 转换成营销域自己的 `CustomerId` 值对象，避免老模型污染新领域。

### ④ 对比：子域类型与投入策略
| 子域类型 | 例子（前司） | 投入策略 |
|---------|-------------|---------|
| 核心子域 | 点单、优惠券计算 | 自研、投入最精锐、DDD 建模 |
| 支撑子域 | 门店管理、报表 | 自研但简化（三层即可） |
| 通用子域 | 短信、OCR | 采购/开源，不投入 |

### ⑤ 面试话术
「战略设计三件套：子域划分（决定投入策略）、限界上下文（决定服务边界）、上下文映射（决定交互方式）。前司把『点单+营销』当核心子域自己投入 DDD 建模，门店/报表当支撑子域简化做，短信/OCR 直接采购。和老的会员系统对接时用防腐层隔离，防止老模型污染新域。」

## 2.3 战术设计 🔴🔴（核心概念 + 代码）

### ① 为什么/痛点
战略设计划好边界后，**边界内的代码怎么写**才不会腐化？战术设计给了一套积木：实体、值对象、聚合、领域服务、领域事件、仓储、工厂、防腐层。

### ② 核心概念 + 图示 + 代码
```
┌──────────────────── 订单聚合（一致性边界）────────────────────┐
│                                                              │
│   Order（聚合根 Aggregate Root）                              │
│   ├─ id: OrderId（值对象）                                    │
│   ├─ status: OrderStatus（值对象/枚举）                       │
│   ├─ customerId: CustomerId（值对象）                         │
│   ├─ totalAmount: Money（值对象，封装金额运算）               │
│   └─ items: List<OrderItem>（实体，但归 Order 管）            │
│                                                              │
│   行为：pay() / cancel() / addItem() / confirm()             │
│   规则：外部只能通过 Order 改 OrderItem（保证一致性）         │
└──────────────────────────────────────────────────────────────┘
```

| 概念 | 说明 | 前司例子 |
|------|------|---------|
| **实体 Entity** | 有唯一标识 + 生命周期 | Order、Coupon（券码唯一） |
| **值对象 VO** | 无标识、不可变、可比较 | Money（金额）、Address、CouponTemplateId |
| **聚合 Aggregate** | 一组相关对象，一致性边界 | 订单聚合（Order + OrderItem） |
| **聚合根** | 聚合唯一入口，外部只能通过它 | Order 是根，OrderItem 由 Order 改 |
| **领域服务** | 不属于单个实体的业务逻辑 | TransferService（涉及两个账户） |
| **领域事件** | 业务发生的事实（已发生） | OrderPaidEvent、CouponUsedEvent |
| **仓储 Repository** | 聚合的持久化抽象 | OrderRepository（接口在领域层） |
| **工厂 Factory** | 复杂对象创建 | OrderFactory（组装聚合） |
| **防腐层 ACL** | 隔离外部/遗留模型 | 适配老会员接口 |

**代码示例（前司订单聚合根，充血模型）**：
```java
// ===== 值对象：金额（不可变，封装运算）=====
public final class Money implements ValueObject {
    private final long cents;  // 用分存储，避免浮点
    public Money(long cents) { this.cents = cents; }
    public Money add(Money other) { return new Money(this.cents + other.cents); }
    public Money multiply(int qty) { return new Money(this.cents * qty); }
    public Money subtract(Money other) { return new Money(this.cents - other.cents); }
}

// ===== 聚合根：订单（业务内聚，充血）=====
public class Order implements AggregateRoot {
    private OrderId id;
    private OrderStatus status;       // 枚举：CREATED/PAID/CANCELED/REFUNDED
    private CustomerId customerId;
    private List<OrderItem> items;    // 实体，但归 Order 管
    private Money totalAmount;
    private List<DomainEvent> events = new ArrayList<>();  // 领域事件暂存

    // 行为：支付（业务规则在聚合内）
    public void pay() {
        if (this.status != OrderStatus.CREATED) {
            throw new BizException("订单状态不允许支付");
        }
        this.status = OrderStatus.PAID;
        this.events.add(new OrderPaidEvent(this.id, this.customerId, this.totalAmount));
    }

    // 行为：加项（保证一致性，外部不能直接 add OrderItem）
    public void addItem(SkuId skuId, int qty, Money price) {
        OrderItem item = new OrderItem(skuId, qty, price);
        this.items.add(item);
        recalculateTotal();
    }

    private void recalculateTotal() {
        this.totalAmount = items.stream()
            .map(i -> i.getPrice().multiply(i.getQty()))
            .reduce(Money.ZERO, Money::add);
    }

    public List<DomainEvent> pullEvents() {  // 应用层负责发布
        List<DomainEvent> e = this.events;
        this.events = new ArrayList<>();
        return e;
    }
}

// ===== 应用服务：只做编排（加载→调用→持久化→发事件）=====
@Service
public class OrderAppService {
    @Autowired private OrderRepository orderRepo;
    @Autowired private DomainEventBus eventBus;

    @Transactional
    public void pay(Long orderId) {
        Order order = orderRepo.findById(new OrderId(orderId));
        order.pay();                          // 业务在聚合根
        orderRepo.save(order);                // 持久化整个聚合
        order.pullEvents().forEach(eventBus::publish);  // 发事件
    }
}
```

### ③ 真实案例（茶饮 SaaS 场景
前司订单域用聚合根 `Order` 内聚了 pay/cancel/refund/addItem 行为；金额用 `Money` 值对象避免 `double` 精度问题（茶饮场景满减、优惠券、会员折扣叠加，金额运算频繁）；`OrderItem` 不暴露给外部直接改，保证「下单后不能偷偷加项」的一致性。

### ④ 聚合设计边界（高频追问）
| 聚合设计 | 后果 |
|---------|------|
| 太大（一个大聚合包含订单+商品+优惠券） | 加载慢、锁冲突、性能差 |
| 太小（每个实体一个聚合） | 一致性弱、跨聚合事务多 |
| 原则 | **优先小聚合**，跨聚合用**最终一致**（领域事件 + MQ） |

### ⑤ 面试话术
「战术设计的核心是**聚合根**——它是数据 + 行为的统一体，是唯一的一致性边界。前司订单聚合 `Order` 内聚了 pay/cancel 行为，金额用 `Money` 值对象避免精度问题，`OrderItem` 只能通过 Order 改。应用层 OrderAppService 只做编排。聚合设计的原则是**优先小聚合**，跨聚合用领域事件 + MQ 最终一致，不用强一致事务，避免大锁。」

## 2.4 贫血 vs 充血模型 🔴

### ① 为什么/痛点
这是 DDD 落地最常踩的坑。**贫血模型**（Entity 只有 getter/setter，业务在 Service）是 Java 圈惯性，结果是业务散落、Service 膨胀成几千行上帝类。**充血模型**（业务在 Entity）是 DDD 的要求，但很多人不习惯。

### ② 代码对比
```java
// ===== 贫血模型（传统三层，业务在 Service）=====
class Order {  // 只有数据
    Long id; OrderStatus status; List<OrderItem> items;
    // getter/setter...
}
class OrderService {
    public void pay(Order order) {
        if (order.getStatus() != UNPAID) throw new BizException("状态错误");
        order.setStatus(PAID);
        orderRepo.save(order);
        // 业务规则散落在 Service，Order 成了数据载体
    }
}

// ===== 充血模型（DDD，业务在 Entity）=====
class Order {
    private OrderStatus status;  // 字段封装（private）
    public void pay() {           // 业务内聚
        if (this.status != UNPAID) throw new BizException("订单状态错误");
        this.status = PAID;
        this.events.add(new OrderPaidEvent(this.id));
    }
}
class OrderService {
    public void pay(Long orderId) {
        Order order = repo.findById(orderId);
        order.pay();     // ← 业务在 Entity
        repo.save(order);
    }
}
```

### ③ 真实案例（茶饮 SaaS 场景
前司不是一刀切充血。**核心域（订单、优惠券计算）用充血**——`Order.pay()` / `Coupon.use()` 业务内聚；**边缘域（门店列表、报表查询）保持贫血 + 三层**，因为查询逻辑简单，充血是负担。这是务实的做法，DDD 推崇但**不滥用**。

### ④ 对比
| 维度 | 贫血模型 | 充血模型 |
|------|---------|---------|
| 业务位置 | Service | Entity |
| 内聚 | 差（散落） | 好 |
| 可测试 | 业务难单测（依赖 Repo） | Entity 可纯内存单测 |
| 学习成本 | 低（Java 习惯） | 高 |
| 适合 | 简单 CRUD | 复杂核心域 |
| ORM 友好 | 好 | 需注意（JPA 友好，MyBatis 要自定义映射） |

### ⑤ 面试话术
「DDD 推崇充血模型——把业务行为内聚到 Entity，Service 只做编排。好处是业务可单测、模型和行为统一。但充血不是必须处处用，我们公司的实践是**核心域（订单/优惠券）充血，边缘查询域贫血**，务实优先。落地时要注意 MyBatis 对充血不友好，我们用 resultMap + 自定义 ResultHandler 把行映射到带行为的领域对象。」

## 2.5 领域事件与最终一致性 🔴

### ① 为什么/痛点
微服务下「**下单成功后要扣库存、加积分、核销优惠券、发通知**」，如果用同步 RPC 串起来，链路长、RT 高、一个挂全挂。**领域事件 + MQ** 解耦：下单服务只发事件，其他服务订阅，各自处理，最终一致。

### ② 原理图 + 代码
```
[订单服务] --publish(OrderPaidEvent)--> [RocketMQ]
                                          │
                ┌─────────────────────────┼─────────────────────────┐
                ▼                         ▼                         ▼
        [库存服务]                 [积分服务]                [营销服务]
        扣减库存                   加积分                    核销券
        （各自本地事务）            （各自本地事务）           （各自本地事务）

关键：通过 MQ 解耦 + 本地消息表保证「发事件」和「业务」原子性
```
```java
// 领域事件
public class OrderPaidEvent implements DomainEvent {
    private final OrderId orderId;
    private final CustomerId customerId;
    private final Money amount;
    private final Instant occurredAt;
}

// 本地消息表方案（保证业务+发事件的原子性）
@Transactional
public void pay(Long orderId) {
    Order order = repo.findById(orderId);
    order.pay();
    repo.save(order);
    // 同一事务写本地消息表（业务和消息要么都成功要么都失败）
    messageDao.insert(new LocalMessage("OrderPaidEvent", toJson(order.pullEvents())));
}
// 定时任务扫本地消息表 → 投递 MQ → 成功后删除
```

### ③ 真实案例（茶饮 SaaS 场景
前司下单链路：点单服务创建订单后发 `OrderCreatedEvent`，优惠券服务订阅做「占券」，支付成功后发 `OrderPaidEvent`，库存/积分/营销各自订阅。**用本地消息表 + RocketMQ** 保证不丢消息。退单时发 `OrderRefundedEvent`，优惠券回退、积分扣减。整条链路是最终一致，支付到积分到账有几秒延迟，业务可接受。

### ④ 对比：强一致 vs 最终一致
| 维度 | 强一致（2PC/TCC） | 最终一致（事件+MQ） |
|------|------------------|-------------------|
| 一致性 | 实时 | 延迟几秒 |
| 性能 | 差（锁/阻塞） | 好（异步） |
| 可用性 | 差（协调器挂全挂） | 好 |
| 复杂度 | 高 | 中 |
| 茶饮 SaaS 场景 | 财务对账（TCC） | 下单链路（MQ） |

### ⑤ 面试话术
「微服务下跨服务一致性首选**最终一致 + 领域事件**。前司下单链路用『本地消息表 + RocketMQ』：订单服务和本地消息表在同一事务，定时任务扫表投递 MQ，库存/积分/营销各自订阅本地消费，整条链路最终一致，延迟几秒业务可接受。只有财务对账这种对一致性强要求的才上 TCC。核心思想是：**业务边界内强一致，跨边界最终一致**。」

## 2.6 📌 实战案例：用 DDD 重构前司订单系统（STAR）

**Situation（问题）**：传统三层架构，订单逻辑分散在 OrderService（3000+ 行）/OrderItemService/PayService，改一个满减规则要动 5 个类，新人 2 周才能上手。

**Action（DDD 落地）**：
1. **事件风暴**：拉产品 + 测试 + 开发一起画事件流（下单→支付→制作→取餐→完成），识别核心领域事件。
2. **划分限界上下文**：订单、支付、库存、营销、会员各自独立，用 ACL 隔离老会员系统。
3. **聚合设计**：`Order` 为聚合根（含 OrderItem），外部不能直接改 OrderItem；`Coupon` 为另一个聚合根。
4. **充血**：`order.pay()` / `order.cancel()` 业务内聚到 Entity，Service 只编排。
5. **领域事件**：`OrderPaidEvent` 由订单发出，营销/积分订阅，MQ 解耦。
6. **Money 值对象**：金额统一用分存储 + 运算封装，杜绝 double 精度 bug。

**Result**：业务变更影响面收敛到聚合内，新人 3 天能上手核心链路；满减规则改动只动 `Order.calculateDiscount()`，不再波及多个 Service；单测覆盖率从 20% 提升到 70%（Entity 可纯内存单测）。

**面试话术**：「我主导了前司订单域的 DDD 重构。先用事件风暴对齐业务，识别出下单/支付/完成等核心事件；然后划分订单、支付、营销等限界上下文；订单聚合用充血模型，金额用 Money 值对象。重构后业务变更收敛到聚合内，新人上手时间从 2 周降到 3 天，单测覆盖率到 70%。核心经验是：DDD 只在核心域用，边缘域保持简洁。」

# 第三章 技术选型 🔴🔴（架构师核心能力）

## 3.1 技术选型方法论

### ① 为什么/痛点
架构师最高频的决策就是**选型**。选错轻则返工，重则拖垮业务（如选了 Erlang 的 RabbitMQ 但团队没人会 Erlang，线上问题搞不定）。选型考的是**结构化决策能力**，不是「我听过这个就选它」。

### ② 决策框架 + 决策树
```
┌─────────────────────────────────────────────────────────────┐
│  技术选型决策流程                                            │
│                                                             │
│  需求痛点 ──▶ 列候选（3-5 个）                              │
│              │                                              │
│              ▼                                              │
│  POC 验证（搭最小 Demo 跑基准）                              │
│              │                                              │
│              ▼                                              │
│  横向对比（加权打分表）                                      │
│   维度：业务匹配/成熟度/团队/性能/TCO/生态/风险/战略          │
│              │                                              │
│              ▼                                              │
│  风险评估（停更? 闭源? 迁移成本? 安全漏洞?）                  │
│              │                                              │
│              ▼                                              │
│  决策 + 灰度落地（先非核心业务灰度，再全量）                 │
└─────────────────────────────────────────────────────────────┘
```

### ③ 真实案例（茶饮 SaaS 场景
| 维度（权重） | RocketMQ | Kafka | RabbitMQ |
|-------------|----------|-------|----------|
| 业务匹配（30%）| 9（事务+延时）| 5（弱事务）| 6（功能全但弱）|
| 成熟度（15%）| 8（阿里双11验证）| 9 | 9 |
| 团队（15%）| 9（Java 栈熟）| 7 | 5（Erlang）|
| 性能（15%）| 8（10w+ TPS）| 10 | 6 |
| 运维（10%）| 7 | 8 | 5 |
| 生态（10%）| 8 | 9 | 8 |
| 风险（5%）| 7（Apache 顶级）| 9 | 8 |
| **加权总分** | **8.2** | **7.6** | **6.3** |

→ 决策：RocketMQ。

### ④ 对比：选型常见误区
| 误区 | 正确做法 |
|------|---------|
| 追新（latest is greatest） | 选稳定版，看生产案例 |
| 只看功能 | 看 TCO（运维+人力+授权） |
| 没有 POC | 必须基准验证 |
| 一人拍板 | 团队共识 + 风险评估 |
| 忽视迁移成本 | 评估未来换掉的成本 |

### ⑤ 面试话术
「我的选型方法论是『**痛点驱动 → 列候选 → POC 验证 → 加权打分 → 风险评估 → 灰度落地**』。核心维度是业务匹配度、成熟度、团队能力、TCO、生态、风险。最忌讳追新和拍脑袋。前司选 RocketMQ 就是按这套流程，加权打分胜出，然后先在非核心的消息通知灰度，再切到下单链路。」

## 3.2 MQ 选型决策树 🔴

### ① 为什么/痛点
MQ 是微服务解耦的核心，选错后果严重。Kafka/RocketMQ/RabbitMQ/Pulsar 各有适用场景。

### ② 决策树
```
                    需要消息队列？
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   日志/大数据流      业务消息          多协议/路由
   (吞吐优先)        (可靠/事务/延时)    (AMQP/STOMP)
        │                │                │
        ▼                ▼                ▼
     Kafka        需要事务消息?        RabbitMQ
                  ┌─────┴─────┐
                  ▼           ▼
                是           否
                  │      需要延时/定时?
                  ▼      ┌────┴────┐
              RocketMQ   ▼         ▼
              (事务+18级 是(RocketMQ) 否(Kafka/Redis)
               原生延时)
```

### ③ 对比表
| 特性 | Kafka | RocketMQ | RabbitMQ | Pulsar |
|------|-------|----------|----------|--------|
| 吞吐 | 极高（百万级） | 高（10w+） | 中（万级） | 高 |
| 延迟 | ms | ms | μs（最低） | ms |
| 事务消息 | 弱 | 强（原生） | 弱 | 强 |
| 延时消息 | 无原生 | 原生 18 级 | 插件 | 原生 |
| 顺序消息 | 分区有序 | 严格有序 | 队列有序 | 分区有序 |
| 协议 | 私有 | 私有 | AMQP/STOMP | 多协议 |
| 适用 | 大数据/日志 | 业务消息 | 企业集成/路由 | 云原生多租户 |
| 运维 | 中 | 中（Java） | 难（Erlang） | 难（复杂） |

### ④ 真实案例（茶饮 SaaS 场景
- **下单链路**（订单事件分发）：RocketMQ（事务消息保证下单+发事件原子，18 级延时做「下单 15 分钟未支付自动取消」）。
- **埋点日志**（小程序行为上报）：Kafka（吞吐优先，丢几条可接受）。
- **延时取餐通知**：RocketMQ 延时消息（做好后 2 分钟提醒）。

### ⑤ 面试话术
「MQ 选型看场景：大数据/日志选 Kafka（吞吐王），业务消息选 RocketMQ（事务+延时原生），企业路由集成选 RabbitMQ。前司下单链路用 RocketMQ——事务消息保证『下单+发事件』原子，18 级延时消息做超时自动取消；埋点日志用 Kafka 追求吞吐。我的原则是**不同场景可以混用多个 MQ**，不是一个 MQ 打天下。」

---

## 3.3 注册中心 / 网关 / 缓存 / 数据库选型

### 注册中心决策树
```
Java/Spring Cloud 栈? ──是──▶ Nacos（推荐，注册+配置一体）
       │否
       ▼
   多语言/K8s? ──是──▶ Consul / 直接用 K8s Service
       │否
       ▼
   老系统 ZK? ──是──▶ Zookeeper（但不推荐新项目，CP 太重）
```
- **Nacos**（前司用）：AP/CP 切换、注册+配置一体、Spring Cloud Alibaba 原生集成。
- **Eureka**：AP，但已停止维护，不推荐新项目。
- **Zookeeper**：CP，强一致但复杂，适合配置/选主而非服务发现。
- **Consul**：多语言友好，CP+AP 可选。

### 网关选型
| 网关 | 适用 |
|------|------|

| APISIX/Kong | 云原生、插件丰富、多语言 |
| Higress | 阿里开源，网关+MSE 一体 |

前司用 Spring Cloud Gateway（Java 栈统一，过滤器做鉴权/限流/日志）。

### 缓存选型
| | Redis | Memcached |
|---|---|---|
| 数据结构 | 丰富（String/Hash/List/Set/ZSet/Stream） | 纯 KV |

| MongoDB | 文档型，灵活 schema | 商品规格、自定义表单 |
| ClickHouse/Doris | OLAP，分析查询 | 报表/BI |

### ⑤ 面试话术
「选型要分场景：注册中心前司选 Nacos（AP+配置一体）；网关选 Spring Cloud Gateway（Java 栈统一）；缓存 Redis 主力 + Caffeine 多级；数据库 MySQL 做核心 OLTP，未来订单量再大考虑 TiDB。核心原则是**匹配业务 + 团队熟悉度 + 生态**，不是哪个新选哪个。」

---

## 3.4 自研 vs 开源 vs 采购 🔴

### ① 为什么/痛点
「这个我们要不要自己写？」是架构师天天被问的问题。判断错要么重复造轮子（自研一个消息队列），要么核心能力受制于人（采购了核心营销引擎）。

### ② 决策矩阵
```
                    是否核心差异化能力？
                         │
                ┌────────┴────────┐
                ▼                 ▼
               是                否
                │                 │
        开源能用?           采购成本 < 自研?
         │     │             │        │
         是    否            是       否
         │     │             │        │
         ▼     ▼             ▼        ▼
      开源+   自研         采购     开源
      二次   (投入最精锐)           (二次开发)
      开发
```

### ③ 真实案例（茶饮 SaaS 场景
- **自研**：优惠券计算引擎、促销规则引擎（核心差异化，我们公司的护城河，开源没有匹配茶饮 SaaS 的）。
- **开源**：注册中心 Nacos、MQ RocketMQ、网关 Gateway、链路 SkyWalking（成熟，社区活跃）。
- **采购**：短信（阿里云）、OCR（百度）、支付通道（聚合支付商）、地图（高德）（非核心，买比自建划算）。

### ④ 对比
| 方式 | 适合 | 代价 |
|------|------|------|
| 自研 | 核心子域、开源不满足、安全合规 | 长期维护负担、人才储备 |
| 开源 | 通用能力、社区活跃 | 需要二次开发能力、有学习成本 |
| 采购 | 非核心能力（短信/支付） | 受供应商制约、有费用 |

### ⑤ 面试话术
「我的原则是『**把精力投在核心子域**』。我们公司的优惠券计算和促销规则引擎是核心差异化，自研投入；Nacos/RocketMQ/Gateway 这类成熟中间件用开源；短信/OCR/支付等非核心能力采购。判断标准是『是否差异化 + 开源能否满足 + 采购 vs 自研 TCO』。自研的最大陷阱是低估长期维护成本——一个自研 MQ 看着省了授权费，但 3 年的维护人力可能远超。」

# 第四章 系统架构原则与分布式设计 🔴

## 4.1 核心架构原则

### ① 为什么/痛点
原则不是教条，而是**踩坑后的经验结晶**。架构师要有自己的原则清单，遇到决策时能快速判断。

### ② 九大原则
```
1. KISS（Keep It Simple）        简单优先，别过度设计
2. YAGNI（You Aren't Gonna Need It） 别提前实现用不到的
3. DRY（Don't Repeat Yourself）   抽象复用
4. 高内聚低耦合
5. 面向接口编程
6. SOLID 五原则
   - SRP 单一职责
   - OCP 开闭原则（对扩展开放，对修改关闭）
   - LSP 里氏替换
   - ISP 接口隔离
   - DIP 依赖倒置（依赖抽象不依赖具体）
7. 无状态设计                    便于水平扩展
8. Fail-Fast                     快速失败，早暴露问题
9. Design for Failure            为失败而设计（假设一切都会挂）
```

### ③ 真实案例（茶饮 SaaS 场景
- **无状态**：前司所有应用服务器无状态，Session 存 Redis，便于 K8s 弹性扩缩容。早期有过把用户上下文存本地内存的坑，扩容后丢失。
- **Design for Failure**：调用第三方支付/外卖平台接口全部加超时 + 熔断 + 降级（Sentinel），外部挂了不影响核心下单。
- **Fail-Fast**：入参校验前置（@Valid + 自定义校验器），不合法立即返回，不进业务逻辑。

### ④ SOLID 对比记忆
| 原则 | 一句话 | 反例 |
|------|--------|------|
| SRP | 一个类一个变化原因 | 上帝类（又管订单又管支付） |
| OCP | 加功能不改老代码 | 支付加新渠道要改 if-else |
| LSP | 子类能替父类 | 子类重写后抛异常破坏契约 |
| ISP | 接口细化 | 胖接口强迫实现用不到的方法 |
| DIP | 依赖抽象 | 业务依赖具体 MySQL 类 |

### ⑤ 面试话术
「架构原则我最看重三个：**KISS（简单优先）、Design for Failure（为失败设计）、无状态（可扩展）**。前司所有服务无状态存 Redis 便于弹性；调用外部接口全加熔断降级；入参 Fail-Fast 校验。SOLID 里我用得最多的是 OCP 和 DIP——开闭原则靠策略/工厂模式扩展支付渠道，依赖倒置靠接口隔离具体实现。」

---

## 4.2 康威定律 🟡

### ① 为什么/痛点
「系统架构 = 组织沟通结构」。架构和组织不匹配，再好的设计也会被组织摩擦拖垮。

### ② 四大定律
```
1. 组织设计的系统，其结构等同于组织的沟通结构
2. 把能独立完成的工作交给独立团队
3. 跨团队沟通成本高，所以要减少跨团队依赖
4. 大系统 = 多个独立小系统（微服务本质）
```

### ③ 真实案例（茶饮 SaaS 场景
前司微服务拆分对齐团队：**点单团队** own 点单+订单服务，**营销团队** own 优惠券+促销服务，**会员团队** own 会员+积分。团队边界 = 服务边界 = 数据库边界。早期有过「一个团队改多个服务」，结果接口对齐成本爆炸，后来按康威定律重组团队，效率大幅提升。

### ④ 面试话术
「康威定律讲『**架构 = 组织结构**』。前司微服务拆分对齐团队——点单团队 own 点单+订单，营销团队 own 优惠券+促销。这样做的好处是团队内高内聚、跨团队低耦合，接口对齐成本最低。逆康威定律就是『想要某种架构，就先调整组织结构』。」

---

## 4.3 分布式系统设计原则（CAP/BASE/高可用）🔴

### ① 为什么/痛点
分布式系统的三大难题：**网络不可靠、节点会挂、时钟不同步**。CAP 和 BASE 是应对这些难题的理论基础。

### ② CAP / BASE
```
CAP 定理：分布式系统三选二
   C（一致性 Consistency）
   A（可用性 Availability）
   P（分区容错 Partition tolerance）—— 分布式必须选 P
   → 实际是 CP 还是 AP 的选择

   CP：Zookeeper、etcd、Redis Cluster（部分场景）—— 强一致，牺牲可用
   AP：Nacos（默认）、Eureka、Cassandra —— 高可用，最终一致

BASE 理论：CAP 中 AP 的延伸
   Basically Available（基本可用）—— 允许降级
   Soft state（软状态）—— 允许中间态
   Eventually consistent（最终一致）
```

### ③ 高可用设计三板斧
```
1. 冗余    主从/集群/多机房/异地多活（无单点）
2. 自动故障转移  健康检查 + 自动切换（Redis Sentinel、K8s 自愈）
3. 降级/限流/熔断  保护核心（Sentinel、Hystrix）

前司高可用：
- 应用层：多副本 + K8s 自愈 + Sentinel 限流熔断
- 数据层：MySQL 主从 + Redis Cluster + MQ 多副本
- 接入层：网关集群 + 负载均衡
- 异地容灾：核心数据异地备份（RPO/RTO 达标）
```

### ④ 对比：CP vs AP 选型
| 场景 | 选 | 例子 |
|------|----|----|
| 服务发现 | AP | Nacos（注册中心要可用） |
| 配置中心 | CP | Nacos（配置要一致） |
| 数据库主键/选主 | CP | ZK/etcd |
| 购物车/缓存 | AP | Redis（可用优先） |
| 转账/扣款 | CP | 强一致（本地事务/TCC） |

### ⑤ 面试话术
「CAP 讲分布式三选二，因为网络分区 P 必选，实际是 CP vs AP。我的选型原则：**服务发现选 AP（注册中心挂了所有服务都受影响，要可用）、配置中心选 CP、转账扣款选强一致**。BASE 是 AP 的延伸——基本可用 + 软状态 + 最终一致，前司下单链路就是 BASE 实践：允许积分延迟到账（软状态），最终一致。高可用三板斧是冗余 + 故障转移 + 限流降级。」

## 4.4 技术债管理 🔴

### ① 为什么/痛点
技术债不可避免（赶进度必然欠债），但**不管理的债会指数级放大**，最终拖垮迭代速度。架构师要有「还债」意识。

### ② 债务分类与管理
```
债务分类：
- 有意债务（Reckless/故意）：赶进度主动欠，要记录 + 计划还
- 无意债务（认知不足）：不懂设计欠下的，靠 Code Review 发现
- 不可避免的债务（业务演进）：旧设计不再匹配新业务

管理四步：
1. 可视化    记录到技术债清单（Confluence/Issue），标优先级
2. 定期偿还  每个迭代留 20% 时间还债（和产品博弈）
3. 防恶化    Code Review 卡点 + 架构守护（ArchUnit）
4. 重构      测试覆盖 + 小步快跑 + 灰度
```

### ③ 真实案例（茶饮 SaaS 场景
前司重构优惠券引擎就是还技术债：老引擎是 if-else 堆砌，加一个券类型要改一周还容易出 bug。重构为策略 + 责任链（见第五章）后，加新券类型半天搞定。重构前先补单测（覆盖核心场景），灰度切流（10% → 50% → 100%），全程双跑对账。

### ④ 面试话术
「技术债管理我的方法是『**可视化 + 定期偿还 + 防恶化 + 小步重构**』。债务分有意的（赶进度）和无意的（认知不足），都要记录到清单标优先级。前司每个迭代留 20% 时间还债，重构用『测试覆盖 + 灰度双跑』。我主导的优惠券引擎重构就是还债——从 if-else 改成策略+责任链，加券类型从一周降到半天。核心是要让产品理解『不还债，迭代速度会越来越慢』。」

# 第五章 设计模式实战 🟡🔴（23 种里高频的，结合前司资产计算）

## 5.1 设计模式总览与原则

### ① 为什么/痛点
设计模式是**前人总结的套路**，解决的是「代码扩展性/可读性/复用性」。但**滥用模式比不用更糟**（过度设计）。面试考的是「你在实际项目怎么用」，不是背 23 种定义。

### ② 七大原则
```
SOLID 五原则 + 迪米特法则（最少知道）+ 合成复用原则（优先组合而非继承）
```

### ③ 高频模式速查表
| 模式 | 场景 | JDK/Spring 例子 | 前司应用 |
|------|------|----------------|---------|
| **单例** | 全局唯一 | Runtime、Spring Bean | 配置加载器 |
| **工厂** | 创建解耦 | BeanFactory、Calendar | 优惠券工厂 |
| **策略** | 算法可替换 | Comparator、Resource | 优惠券/促销计算 |
| **模板方法** | 流程骨架 | AbstractList、JdbcTemplate | 下单流程编排 |
| **观察者** | 发布订阅 | Listener、ApplicationEvent | 下单事件分发 |
| **责任链** | 多处理器串联 | Filter、Interceptor、Sentinel | 风控/校验/资产计算 |
| **代理** | 增强/控制访问 | AOP（JDK/CGLIB） | 日志/事务/限流切面 |
| **装饰器** | 动态增强 | IO 流（BufferedInputStream） | 权限包装 |
| **适配器** | 接口转换 | HandlerAdapter | 老系统接口适配 |
| **建造者** | 复杂对象构造 | StringBuilder、@Builder | 订单构造 |

### ④ 面试话术
「设计模式我重点掌握高频的 8 个：策略、责任链、工厂、模板方法、观察者、单例、代理、装饰器。前司用得最多的是**策略+责任链做优惠券计算引擎**。原则记 SOLID + 合成复用（优先组合）。我的体会是**模式要解决问题才用，不为用而用**——一个简单 if-else 硬上策略模式是过度设计。」

---

## 5.2 🔴 策略 + 责任链：前司优惠券计算引擎（重点实战）

### ① 为什么/痛点
茶饮 SaaS 平台 的优惠券/促销极其复杂：满减券、折扣券、兑换券、赠品券、会员折扣、平台活动、第二杯半价……老代码用**巨型 if-else**（一个方法 2000 行），每加一种券类型要改主流程、容易引入 bug、无法单测。需要一套**可扩展、可组合**的计算引擎。

### ② 架构设计
```
计算流程（责任链）：
┌──────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 商品  │──▶│ 会员折扣  │──▶│ 优惠券    │──▶| 平台活动  │──▶│ 满减促销  │──▶ 最终价
│原价   │   │ Handler  │   │ Handler  │   │ Handler  │   │ Handler  │
└──────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
                              │
                       优惠券内部用策略：
                       ┌─────────────────────────────┐
                       │ CouponCalcStrategy (接口)    │
                       ├─────────────────────────────┤
                       │ ├─ 满减券 FullReduction      │
                       │ ├─ 折扣券 Discount           │
                       │ ├─ 兑换券 Exchange           │
                       │ └─ 赠品券 Gift               │
                       └─────────────────────────────┘
                       工厂按 couponType 路由到具体策略
```

### ③ 代码实现

**策略模式：优惠券计算**
```java
// 策略接口
public interface CouponCalcStrategy {
    /** 计算优惠金额 */
    Money calculate(OrderContext ctx, Coupon coupon);
    /** 该策略支持哪些券类型 */
    CouponType supportType();
}

// 满减券策略（满 30 减 5）
@Component
public class FullReductionStrategy implements CouponCalcStrategy {
    @Override
    public Money calculate(OrderContext ctx, Coupon coupon) {
        Money threshold = coupon.getRule().getThreshold();  // 满 30
        Money reduction = coupon.getRule().getReduction();  // 减 5
        if (ctx.getCurrentAmount().compareTo(threshold) < 0) {
            return Money.ZERO;  // 不满门槛
        }
        return reduction;
    }
    @Override public CouponType supportType() { return CouponType.FULL_REDUCTION; }
}

// 折扣券策略（8 折）
@Component
public class DiscountStrategy implements CouponCalcStrategy {
    @Override
    public Money calculate(OrderContext ctx, Coupon coupon) {
        BigDecimal rate = coupon.getRule().getDiscountRate();  // 0.8
        Money discount = ctx.getCurrentAmount()
            .multiply(rate.doubleValue()).subtract(ctx.getCurrentAmount());
        // 封顶
        Money cap = coupon.getRule().getCap();
        return discount.compareTo(cap) > 0 ? cap : discount;
    }
    @Override public CouponType supportType() { return CouponType.DISCOUNT; }
}

// 策略工厂（Spring 自动按 bean 收集，OCP：加新券不改工厂）
@Component
public class CouponStrategyFactory {
    private final Map<CouponType, CouponCalcStrategy> strategyMap;

    // Spring 注入所有 CouponCalcStrategy 实现，按 supportType 建 Map
    public CouponStrategyFactory(List<CouponCalcStrategy> strategies) {
        this.strategyMap = strategies.stream()
            .collect(Collectors.toMap(CouponCalcStrategy::supportType, s -> s));
    }

    public CouponCalcStrategy get(CouponType type) {
        CouponCalcStrategy s = strategyMap.get(type);
        if (s == null) throw new BizException("不支持的券类型: " + type);
        return s;
    }
}
```

**责任链：多阶段价格计算**
```java
// 责任链处理器抽象（模板方法）
public abstract class PriceCalcHandler {
    protected PriceCalcHandler next;  // 下一个处理器
    public PriceCalcHandler setNext(PriceCalcHandler next) {
        this.next = next;
        return next;
    }
    public abstract void handle(OrderContext ctx);  // 模板方法
    protected void fireNext(OrderContext ctx) {
        if (next != null) next.handle(ctx);
    }
}

// 会员折扣处理器
@Component
public class MemberDiscountHandler extends PriceCalcHandler {
    @Override
    public void handle(OrderContext ctx) {
        MemberLevel level = ctx.getMember().getLevel();
        if (level == MemberLevel.GOLD) {
            ctx.applyDiscount(new BigDecimal("0.95"));  // 金卡 95 折
        }
        fireNext(ctx);  // 传递给下一个
    }
}

// 优惠券处理器（内部用策略）
@Component
public class CouponHandler extends PriceCalcHandler {
    @Autowired private CouponStrategyFactory factory;

    @Override
    public void handle(OrderContext ctx) {
        for (Coupon coupon : ctx.getCoupons()) {
            CouponCalcStrategy strategy = factory.get(coupon.getType());
            Money discount = strategy.calculate(ctx, coupon);
            ctx.applyDiscount(discount);
        }
        fireNext(ctx);
    }
}

// 责任链组装（Spring 配置）
@Configuration
public class PriceChainConfig {
    @Bean
    public PriceCalcHandler priceChain(MemberDiscountHandler m, CouponHandler c,
                                       PromotionHandler p, FullReductionHandler f) {
        // 组装顺序：会员 → 优惠券 → 平台活动 → 满减
        m.setNext(c); c.setNext(p); p.setNext(f);
        return m;  // 返回链头
    }
}
```

### ④ 效果
- **加新券类型**：只需写一个新 Strategy 类（如 `NewUserCouponStrategy`），注册到 Spring，**不改任何老代码**（OCP 开闭原则）。
- **加新计算阶段**：写新 Handler 接入链。
- **可单测**：每个 Strategy/Handler 独立测试。
- 前司重构后，加券类型从一周降到半天，bug 率下降 80%。

### ⑤ 对比：if-else vs 策略+责任链
| 维度 | if-else 巨型方法 | 策略 + 责任链 |
|------|-----------------|--------------|
| 扩展 | 改主流程，易出 bug | 加新类，开闭原则 |
| 可读 | 2000 行方法 | 单一职责小类 |
| 可测 | 难（依赖整个流程） | 每个 Strategy 独立测 |
| 灵活 | 顺序写死 | 链顺序可配置 |

### ⑥ 面试话术
「前司优惠券计算引擎我用了**策略 + 责任链 + 工厂**三个模式组合。责任链把『会员折扣→优惠券→平台活动→满减』串成链，每个阶段独立；优惠券阶段内部用策略模式——每种券类型一个 Strategy，工厂用 Spring 自动收集 bean 按 supportType 路由。好处是**加新券类型只写新类不改老代码**（开闭原则），加券类型从一周降到半天。这个组合的精髓是『责任链解决流程编排、策略解决算法替换、工厂解决路由解耦』。」

---

## 5.3 单例模式

### ① 为什么/痛点
全局只需要一个实例的场景（配置、连接池、注册中心客户端），重复创建浪费资源或导致状态不一致。

### ② 实现（枚举单例最优）
```java
// 枚举单例（最优，防反射攻击 + 天然线程安全 + 防反序列化破坏）
public enum ConfigHolder {
    INSTANCE;
    private final Properties props = load();
    public String get(String key) { return props.getProperty(key); }
}

// 双重检查锁（经典写法）
public class Singleton {
    private static volatile Singleton instance;  // volatile 防指令重排
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) instance = new Singleton();
            }
        }
        return instance;
    }
}
```

### ③ 真实案例
Spring Bean 默认单例（容器管理，不需要自己写）。我们公司的 SDK 客户端（如对接外卖平台的 Client）用单例，避免重复建连接池。

### ④ 面试话术
「单例我推荐枚举实现（防反射、防序列化破坏）。实际项目大部分用 Spring 容器单例，自己写的少。注意双重检查锁要 volatile 防指令重排。」

---

## 5.4 工厂模式

### ① 为什么/痛点
创建对象逻辑复杂或需要根据类型创建时，直接 new 会让调用方耦合具体类。工厂把创建逻辑封装，调用方只依赖接口。

### ② 代码
```java
// 简单工厂 + 策略（前司优惠券工厂见 5.2）
public class CouponFactory {
    public static Coupon create(CouponType type, CouponTemplate tpl) {
        switch (type) {
            case FULL_REDUCTION: return new FullReductionCoupon(tpl);
            case DISCOUNT:       return new DiscountCoupon(tpl);
            default: throw new IllegalArgumentException("未知类型");
        }
    }
}
```

### ③ 真实案例
Spring BeanFactory 是最经典的工厂。前司优惠券/支付都用工厂 + 策略组合（见 5.2、5.5）。

### ④ 面试话术
「工厂解决『创建逻辑复杂或按类型创建』的解耦。我推荐工厂 + 策略 + Spring 自动注入三件套，比纯简单工厂更 OCP——加新类型不改工厂。」

---

## 5.5 策略模式消除 if-else（支付路由）

### ① 痛点 + 代码
```java
// 反例：if-else
public void pay(String type, Order o) {
    if ("alipay".equals(type)) {...}
    else if ("wechat".equals(type)) {...}
    else if ("balance".equals(type)) {...}  // 每加一个渠道改这里
}

// 正例：策略 + 工厂
public interface PayStrategy { void pay(Order o); }
@Component("alipay")  class AlipayStrategy implements PayStrategy {...}
@Component("wechat")  class WechatStrategy implements PayStrategy {...}
@Component("balance") class BalanceStrategy implements PayStrategy {...}

// Spring 按 beanName 注入 Map
@Autowired Map<String, PayStrategy> strategies;
strategies.get(payType).pay(order);  // 加新渠道只加 Strategy 类
```

### ② 前司案例
前司支付网关对接微信、支付宝、会员余额、聚合支付商，用策略 + Spring Map 注入，加渠道只加一个 @Component 类。

### ③ 面试话术
「策略 + Spring Map 注入是消除 if-else 的经典套路。加新支付渠道只加一个 @Component 类，符合开闭原则。前司支付网关、优惠券计算都用这套。」

---

## 5.6 责任链模式

### ① 痛点 + 代码
多个处理器串联（风控、参数校验、限流、业务），每个只关心自己的事。
```java
// Servlet Filter / Spring Interceptor / Sentinel Slot 都是责任链
public interface Handler { void handle(Request req, Chain chain); }
// 前司风控链：黑名单 → 频次限制 → 风险评分 → 业务处理
```

### ② 前司案例
下单链路前置校验用责任链：黑名单检查 → 门店营业状态 → 商品库存 → 营销规则校验 → 下单。每个 Handler 独立，可复用、可单测、可配置顺序。

### ③ 面试话术
「责任链适合『多个处理器串联、可灵活增删、可调整顺序』。前司下单前置校验用责任链（黑名单→营业状态→库存→营销校验），价格计算引擎也用责任链串联多个计算阶段。」

---

## 5.7 观察者/发布订阅模式

### ① 痛点 + 代码
一个动作触发多个后续处理，且不希望主流程被拖慢。观察者模式解耦「事件发布」和「事件处理」。
```java
// Spring ApplicationEvent
public class OrderPaidEvent extends ApplicationEvent {...}
publisher.publishEvent(new OrderPaidEvent(order));
@EventListener public void onOrderPaid(OrderPaidEvent e) { 加积分(); }
@EventListener public void sendNotice(OrderPaidEvent e) { 发通知(); }
```

### ② 前司案例
- 进程内：Spring `@EventListener` + `@Async` 异步发通知。
- 跨服务：领域事件 + RocketMQ（见 2.5），下单成功后库存/积分/营销各自订阅。

### ③ 面试话术
「观察者模式解决『一个事件多端响应且解耦』。进程内用 Spring ApplicationEvent，跨服务用领域事件 + MQ。前司下单成功后发 OrderPaidEvent，库存/积分/营销各自订阅，主流程不被拖慢。」

---

## 5.8 模板方法模式

### ① 痛点 + 代码
流程骨架固定，各步骤可变。父类定义骨架，子类填充细节。
```java
public abstract class AbstractOrderProcess {
    public final void process(Order o) {  // 骨架，final 防覆盖
        validate(o);
        calculate(o);
        save(o);
        afterProcess(o);  // 钩子
    }
    protected abstract void validate(Order o);
    protected void calculate(Order o) { 默认计算(); }
    protected void afterProcess(Order o) { }  // 可选钩子
}
```

### ② 前司案例
前司不同业务线（堂食、外卖、自提）下单流程大同小异，用模板方法：父类定义「校验→算价→落库→后置」骨架，子类各自实现 validate（外卖要校验配送地址）和 afterProcess（堂食要打印小票）。

### ③ 面试话术
「模板方法适合『流程骨架固定、各步骤可变』。前司堂食/外卖/自提下单用模板方法，父类定义骨架，子类实现差异步骤。Spring 的 JdbcTemplate、RestTemplate 都是经典。」

---

## 5.9 代理 / 装饰器 / 适配器 / 建造者（速记）

| 模式 | 一句话 | 前司/JDK 例子 |
|------|--------|--------------|
| **代理** | 控制访问/增强（不改变接口） | Spring AOP（事务/日志/限流）、`@Transactional` |
| **装饰器** | 动态增强（同接口多层包装） | `BufferedInputStream(new FileInputStream())`、权限包装 |
| **适配器** | 接口转换（让不兼容的协同） | 老会员接口适配到新领域模型（ACL 用） |
| **建造者** | 复杂对象分步构造 | `Order.builder().items().coupon().build()`、@Builder |

**代理 vs 装饰器**（高频追问）：代理强调「控制访问」（如远程代理、权限代理），装饰器强调「增强功能」（IO 流层层包装）。代码结构相似，意图不同。

### 面试话术
「代理和装饰器结构像但意图不同：代理是控制访问（AOP），装饰器是增强功能（IO 流）。前司用 AOP 代理做统一日志/限流；用适配器做老会员接口到新领域模型的转换（防腐层）；复杂订单用建造者分步构造。」

# 第八章 云原生（架构师视野）🟡

## 8.1 核心概念
- **容器（Docker）**：标准化交付单元。
- **编排（Kubernetes）**：调度、自愈、弹性。
- **不可变基础设施**：不修改运行中的容器，重新部署。
- **声明式 API**：描述「期望状态」，系统自动收敛。
- **DevOps / CI/CD**：自动化构建-测试-部署。

## 8.2 K8s 核心对象
- Pod（最小调度单元，1+ 容器）。
- Deployment（Pod 副本控制器）。
- Service（稳定网络端点 + 负载均衡）。
- Ingress（七层路由）。
- ConfigMap / Secret（配置）。

## 8.3 🔴 对 Java 工程师的意义：优雅上下线

### ① 痛点
K8s 滚动更新时，老 Pod 被删但流量还在进来 → 请求失败；新 Pod 启动但 JVM 还在预热 → 接口超时。这是 Java 上云最常见的问题。

### ② 方案
```
下线流程（避免请求打到正在关闭的 Pod）：
  K8s 发 SIGTERM → preStop hook → sleep（等流量排空）→ 应用关闭 → K8s 移除 endpoints

上线流程（避免流量打到没准备好的 Pod）：
  Pod 启动 → readinessProbe 探针通过（应用就绪）→ K8s 加 endpoints → 接流量
```
```yaml
# K8s 部署片段
spec:
  containers:
  - name: order-service
    readinessProbe:        # 就绪探针：通过后才接流量
      httpGet:
        path: /actuator/health/readiness
        port: 8080
      initialDelaySeconds: 30
    lifecycle:
      preStop:             # 下线前等待流量排空
        exec:
          command: ["sh", "-c", "sleep 15"]
    resources:
      requests: { cpu: "500m", memory: "1Gi" }
      limits:   { cpu: "2",    memory: "2Gi" }
```

### ③ JVM 容器化注意
- 用 JDK8u191+，支持 `UseContainerSupport`（自动识别容器内存限制）。
- JVM 堆别设死，用 `-XX:MaxRAMPercentage=75.0` 按容器内存比例。
- G1 GC 在容器场景表现好（前司用 G1）。

### ④ 面试话术
「Java 上 K8s 最关键是优雅上下线。下线用 preStop hook sleep 15 秒等流量排空再 SIGTERM；上线用 readinessProbe 探针，应用就绪才接流量。JVM 要用 8u191+ 支持容器内存感知，用 MaxRAMPercentage 按比例设堆。前司核心服务都跑 K8s，配合 Eureka/Nacos 优雅注销，滚动更新零失败请求。」

# 第九章 性能优化总纲（综合实战）🔴

## 9.1 优化层次（从上到下，收益递减）
```
1. 业务优化（最大收益）
   - 减少不必要的调用、合并请求、异步化、批量化
2. 架构优化
   - 缓存、MQ、读写分离、分库分表、CDN
3. 代码优化
   - 算法数据结构、减少对象创建、连接池复用
4. JVM 优化
   - GC 调优、参数
5. OS / 硬件
   - 网络内核参数、磁盘、CPU
```

**铁律**：**先业务后技术，先架构后代码，先测量后优化**（别瞎优化，Profile 找瓶颈）。

## 9.2 📌 实战案例：前司订单详情接口优化全链路（STAR）

**Situation**：订单详情接口 RT 2s，P99 5s，高峰期超时严重。

**Action 分层优化**：
1. **业务**：合并 3 个独立查询为 1 个聚合接口；非核心信息（推荐商品、广告）异步加载。
2. **架构**：
   - 加 Redis 缓存（命中率 80%）。
   - 热点门店/商品用 Caffeine 本地缓存（避免 Redis 击穿）。
   - 历史订单读写分离（查走只读库）。
3. **代码**：批量化查（`IN` 一次查）；避免 N+1（用 MyBatis 关联查询或批量预加载）。
4. **DB**：加联合索引（覆盖索引）；订单详情大字段（如菜品快照 JSON）拆分到副表。
5. **JVM**：换 G1，调 `MaxGCPauseMillis=200`，NewRatio，Full GC 消失。

**Result**：RT 2s → 150ms，P99 <500ms，QPS 提升 4 倍。

### 面试话术
「性能优化我的方法论是『**先测量后优化，先业务后技术**』，按收益从高到低：业务 → 架构 → 代码 → JVM → 硬件。前司订单详情接口 RT 2s 优化到 150ms，我先 Profile 找瓶颈（发现是多次 RPC + N+1 查询），业务层合并接口 + 异步加载，架构层加 Redis+Caffeine 缓存，代码层批量化避免 N+1，DB 加覆盖索引，JVM 换 G1。最终 QPS 提升 4 倍。核心是别瞎优化，先定位再动手。」
