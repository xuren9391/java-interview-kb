# 第一篇 MySQL 深度

## 1.1 索引深度（B+ 树内核 + 聚簇/二级 + 覆盖）

### 为什么是 B+ 树？对比其他数据结构 🔴🔴

| 结构 | 查询 | 范围 | 问题 |
|------|------|------|------|
| 哈希 | O(1) | ❌ | 不支持范围/排序 |
| 二叉树/红黑树 | O(log N) | 弱 | 树高随数据增长，磁盘 IO 多（树高 = IO 次数） |
| B 树 | O(log N) | 中 | 非叶子节点也存数据 → 单节点 key 少 → 树更高 |
| **B+ 树** | O(log N) | **强** | ✅ 见下 |

### B+ 树的 4 大优势 🔴
1. **非叶子节点只存索引**（不存数据）→ 单节点容纳更多 key → **树更矮**（3 层存千万级，查询 3 次 IO）。
2. **叶子节点双向链表** → 范围查询、排序极快（`WHERE id BETWEEN`、`ORDER BY`）。
3. **查询稳定** O(log N)（必到叶子，不因数据位置变快/慢）。
4. **磁盘友好**：节点大小 = 页（默认 16KB），一次 IO 读一页。

### 一个 B+ 树能存多少行？🔴（经典估算）
假设页 16KB：
- **非叶子节点**：索引项 = 主键(8B) + 指针(6B) ≈ 14B，一页 ≈ 16384/14 ≈ **1170 个索引项**。
- **叶子节点**：一行假设 1KB，一页 ≈ 16 行。
- 3 层：1170 × 1170 × 16 ≈ **2189 万行**。
- 4 层：×1170 ≈ 250 亿。

**结论**：千万级表 3 层 B+ 树，查询只要 3 次磁盘 IO。

### 聚簇索引 vs 二级索引 🔴🔴

| | 聚簇索引 Clustered | 二级索引 Secondary |
|---|---|---|
| 叶子存什么 | **完整行数据** | **主键值** |
| 数量 | 一张表**只有一个**（InnoDB 主键） | 可以多个 |
| 数据物理顺序 | 按聚簇索引顺序存储 | — |
| 查询 | 直接拿数据 | 拿主键 → **回表**查聚簇索引 |

**回表**：查二级索引拿到主键 → 再查聚簇索引拿行数据。两次 B+ 树查询。
**MyISAM** 的主键索引也是非聚簇（叶子存行地址）。

### 覆盖索引 🟡
查询的字段全部被索引覆盖 → **不需要回表**。
```sql
-- 联合索引 (a, b, c)
SELECT a, b, c FROM t WHERE a = 1;     -- ✅ 覆盖，不回表
SELECT a, b, c, d FROM t WHERE a = 1;  -- ❌ d 不在索引，要回表
```

### 最左前缀原则详解 🔴🔴

联合索引 (a, b, c) 按 a→b→c 顺序排列：
```
(1,1,1) (1,1,2) (1,2,1) (1,2,3) (2,1,1) (2,1,3) ...
```

**命中规则**：
```sql
WHERE a=1                    ✅ 用 a
WHERE a=1 AND b=2           ✅ 用 a, b
WHERE a=1 AND b=2 AND c=3   ✅ 用 a, b, c
WHERE b=2                   ❌ 跳过 a，用不到
WHERE a=1 AND c=3           ⚠️ 只用 a（中间断 b，c 用不到索引查找，但可做过滤）
WHERE a>1 AND b=2           ⚠️ 只用 a（范围后 b 失效）
WHERE a=1 AND b>2 AND c=3   ⚠️ 用 a, b（b 范围后 c 失效）
WHERE a=1 ORDER BY b,c      ✅ 索引有序，避免 filesort
WHERE a=1 AND b IN (1,2)    ✅ 用 a, b（IN 是等值，不是范围）
```

**核心**：索引按字段顺序排列。**等值查询不影响后续字段，范围查询后字段失效**。

### 索引下推（ICP，5.7+）🟡
```sql
-- 联合索引 (a, b)，MySQL 5.6 前
WHERE a='x' AND b LIKE '%y'
-- 存储引擎按 a 取所有记录 → 回表 → server 层过滤 b（回表多）
-- 5.7+ ICP
-- 把 b 的过滤下推到存储引擎层 → 减少回表次数
```

### 索引失效 10 大场景 🔴🔴

| # | 场景 | 反例 → 正解 |
|---|------|------------|
| 1 | 列做函数/计算 | `WHERE YEAR(t)=2026` → `WHERE t>='2026-01-01'` |
| 2 | 隐式类型转换 | 字符串列 `WHERE phone=13800...`（传数字）→ 传字符串 |
| 3 | 左模糊 | `LIKE '%abc'` → `LIKE 'abc%'` 或全文索引 |
| 4 | OR 两边不全有索引 | `WHERE a=1 OR b=2`（b 无索引）→ 全表，可改 UNION |
| 5 | 不符合最左前缀 | 见上 |
| 6 | != / NOT IN / IS NOT NULL | 通常走全表 |
| 7 | IN 列表过长 | 优化器认为全表更快 |
| 8 | 优化器估算 | 数据分布倾斜（如 95% 是某值）→ 选全表 |
| 9 | 范围后字段失效 | 见最左前缀 |
| 10 | 字符集/排序规则不一致 | join 时 `utf8` vs `utf8mb4` → 索引失效 |

## 1.2 explain 详解 🔴

| 列 | 含义 | 关注 |
|----|------|------|
| id | 执行顺序 | 大的先执行；相同从上往下 |
| select_type | SIMPLE/PRIMARY/SUBQUERY/DERIVED | — |
| **type** | 访问类型 | 🔴 **核心**：system > const > eq_ref > ref > range > index > ALL |
| possible_keys | 可能用的索引 | — |
| **key** | 实际用 | NULL = 没用索引 |
| **key_len** | 索引使用长度 | 🔴 判断联合索引用了几个字段（每个字段按类型算长度） |
| ref | 索引比较来源 | const/func/字段 |
| **rows** | 估算扫描行数 | 越小越好 |
| **Extra** | 额外 | 🔴 Using index（覆盖，好）/ filesort（差）/ temporary（差）/ Using where |

**type 各级别**：
- `const`：主键/唯一索引等值。
- `eq_ref`：join 用主键/唯一索引（唯一匹配）。
- `ref`：非唯一索引等值。
- `range`：范围（>, between, in）。
- `index`：扫整个索引树（比 ALL 好，但仍是全扫）。
- `ALL`：全表扫描，要优化。

**判断标准**：type 至少 range（理想 ref/eq_ref），Extra 出现 Using index 是好事，filesort/temporary 要优化。

## 1.3 事务与隔离级别 🔴

### ACID
- 原子性 Atomicity（Undo Log）
- 一致性 Consistency（业务约束 + 其他三个保证）
- 隔离性 Isolation（锁 + MVCC）
- 持久性 Durability（Redo Log）

### 四种隔离级别 🔴🔴

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|-----------|------|
| READ UNCOMMITTED | 有 | 有 | 有 |
| READ COMMITTED（Oracle/PG 默认） | 无 | 有 | 有 |
| **REPEATABLE READ（MySQL 默认）** | 无 | 无 | InnoDB 用间隙锁解决 |
| SERIALIZABLE | 无 | 无 | 无 |

- **脏读**：读到别的事务**未提交**的数据。
- **不可重复读**：同一事务内两次读同一行不同（别的事务 **update** 提交）。
- **幻读**：同一事务内两次范围查询结果集不同（别的事务 **insert**）。

## 1.4 MVCC（多版本并发控制）🔴🔴🔴 必精通

### 为什么要 MVCC
- 普通 select 不加锁，读写不互斥，提升并发。
- 用"快照"让事务读到一致视图。

### 三个核心组件

**① 隐藏列**
每行有：
- `DB_TRX_ID`（6B）：最近修改它的事务 ID。
- `DB_ROLL_PTR`（7B）：指向 undo log 中该行的上一版本。

**② Undo Log 版本链**
```
当前行（trx_id=300） 
  → Undo Log v(trx_id=200) 
    → Undo Log v(trx_id=100) 
      → ...
```
每次 update 生成一条 undo log，roll_pointer 串成链。

**③ ReadView（读视图）**
事务执行**快照读**时生成。包含：
- `m_ids`：生成时**活跃（未提交）事务 ID** 列表。
- `min_trx_id`：m_ids 最小值。
- `max_trx_id`：下一个要分配的事务 ID。
- `creator_trx_id`：当前事务 ID。

### 可见性判断算法 🔴🔴（沿版本链找）

对每行的 `trx_id` 判断：
```
① trx_id == creator_trx_id
   → 自己改的，可见
② trx_id < min_trx_id
   → 生成 ReadView 前已提交，可见
③ trx_id >= max_trx_id
   → ReadView 后才开启的事务改的，不可见
④ min_trx_id ≤ trx_id < max_trx_id
   → 在 m_ids 中：活跃事务改的，不可见
   → 不在 m_ids：已提交，可见
```
不可见 → 沿 roll_pointer 找上一版本，继续判断。

### 🔴 RC vs RR 的 ReadView 区别（核心考点）

| | ReadView 生成时机 |
|---|---|
| **RC（读已提交）** | **每次 select 都生成新的 ReadView** → 能读到最新已提交 → 不可重复读 |
| **RR（可重复读）** | **事务第一次 select 生成 ReadView，之后复用** → 一直看首次快照 → 可重复读 |

## 1.5 锁机制深度 🔴🔴

### 锁分类
- **粒度**：表锁、页锁、行锁（InnoDB 默认行锁）。
- **类型**：共享锁 S（读锁）、排他锁 X（写锁）。
  - `SELECT ... LOCK IN SHARE MODE` / `SELECT ... FOR UPDATE`。
- **意向锁**（IS/IX，表级）：意图锁，快速判断表里有无行锁，避免逐行检查。加行 S/X 前先加表 IS/IX。

### InnoDB 行锁 3 种算法 🔴🔴 必精通

| 锁 | 范围 | 用途 |
|----|------|------|
| **Record Lock**（记录锁） | 锁单行 | 等值命中唯一索引 |
| **Gap Lock**（间隙锁） | 锁区间（开区间，不含记录） | 防 insert |
| **Next-Key Lock**（临键锁） | Record + Gap（左开右闭） | RR 默认，防幻读 |

**举例**：表 id 有 5,10,15,20，RR 下 `WHERE id=10 FOR UPDATE`：
- 锁 (5, 10]（Next-Key）+ (10, 15)（Gap）= (5, 15) 整个区间锁住。
- 其他事务无法 insert id=6~14。

**退化规则** 🔴：
- 等值**唯一索引命中** → 退化为 Record Lock（只锁记录）。
- 等值**非唯一**或不命中 → Gap Lock。
- 范围查询 → Next-Key Lock。

### 🔴 RR 如何防幻读？

两条路：
1. **快照读**（普通 select）：MVCC，看 ReadView 快照，天然看不到新 insert。
2. **当前读**（select for update / lock in share mode / update / delete）：用 **Next-Key Lock** 锁住记录+间隙，其他事务无法 insert。

## 1.6 日志体系：Redo / Undo / Binlog 🔴🔴🔴 必精通

### 三大日志对比

| 日志 | 层 | 作用 | 写入 |
|------|----|------|------|
| **Redo Log**（重做） | InnoDB | crash-safe（持久性） | 事务中持续写（循环写，固定大小） |
| **Undo Log**（回滚） | InnoDB | 回滚 + MVCC 版本链 | 修改前先写 undo |
| **Binlog**（归档） | Server | 主从复制 + 数据恢复 | 事务提交时写（追加写） |

### Redo Log 为什么存在？🔴
- Buffer Pool（内存）修改后**不立即刷盘**（随机 IO 慢）。
- 先写 Redo Log（**顺序 IO 快**），宕机后用 Redo 恢复 → **WAL（Write-Ahead Logging）**。
- Redo Log 是物理日志（"在某页某偏移改成什么"）。
- 循环写：write pos（写位置）+ check point（刷盘位置），写满就绕回。

### Undo Log 作用
- 事务回滚：根据 undo 恢复原状。
- MVCC：版本链的历史版本。
- Undo Log 是逻辑日志（"反向操作"，如 insert 的 undo 是 delete）。

### 🔴 两阶段提交（保证 Redo 和 Binlog 一致）

```
┌─────────────────────────────────────────────────┐
│ 1. InnoDB 写 Undo Log（prepare 状态）            │
│ 2. 写 Redo Log（prepare 状态）→ 刷盘             │
│ 3. Server 层写 Binlog → 刷盘                     │
│ 4. Redo Log 改为 commit 状态                     │
└─────────────────────────────────────────────────┘
```

**为什么需要 2PC？** 🔴
若不两阶段，crash 时可能出现：
- Binlog 写了 Redo 没写 → 从库有数据，主库没有（主从不一致）。
- Redo 写了 Binlog 没写 → 主库有数据，从库没有。

**崩溃恢复规则** 🔴：
- Redo 是 prepare 且 **Binlog 完整** → commit（因为从库可能已经拉了 binlog）。
- Redo 是 prepare 但 **Binlog 不完整** → **回滚**（事务无效）。

### Binlog 三种格式 🟡
- **STATEMENT**：记 SQL 语句。小，但可能不确定（NOW()、UUID()）。
- **ROW**：记每行变更（前镜像 + 后镜像）。大，但确定（推荐）。
- **MIXED**：混合。

## 1.7 主从复制 + 延迟 🔴

### 复制流程
```
主库执行 SQL → 写 Binlog
  → Binlog Dump Thread 推送
从库 IO Thread 接收 → 写 Relay Log（中继日志）
  → SQL Thread 重放 Relay Log
```

### 复制方式
- **异步复制**（默认）：主库不等从库，性能高，可能丢数据。
- **半同步复制**（semi-sync）：主库至少等一个从库 ack。
- **组复制 MGR**：基于 Paxos，多主一致性。

### 主从延迟原因 🔴🔴
1. **从库单线程重放**（5.7 前）→ 5.7+ **并行复制**（基于组提交 GROUP_COMMIT / 写集合 WRITESET）。
2. 从库性能差。
3. 大事务（一个事务卡住后续）。
4. 网络延迟。
5. 从库被业务读压力拖累。

**解决**：并行复制、关键业务强制读主、半同步、业务容忍最终一致。

## 1.8 分库分表 🔴🔴

### 拆分维度
```
垂直分库：按业务拆（订单库、用户库）—— 早期解耦
垂直分表：宽表拆窄（冷热列分离）—— 优化单表
水平分表：按规则（hash/range/时间）把数据拆到多张同构表 —— 应对数据量
```

### 分片策略
| 策略 | 优 | 劣 |
|------|----|----|
| **范围 Range**（按时间/ID 区间） | 易扩容、范围查询友好 | 易热点（最新数据集中） |
| **哈希 Hash**（hash(uid) % N） | 均匀 | 扩容要 rehash |
| **一致性哈希** | 加减节点只影响相邻数据 | 实现复杂 |
| **基因法** | 把分片键嵌入其他 ID | 解决多维度分页 |

### 分库分表带来的问题 🔴🔴

**① 跨库 join** → 应用层组装 / 冗余字段 / 广播表（小表每库一份）。
**② 分布式事务** → Seata / 本地消息表。
**③ 深分页** 🔴：
```sql
-- 单库：LIMIT 1000000, 10  → 还能
-- 分片后：每个分片都要 LIMIT 1000010，回应用层归并排序 → 灾难
```
解法：**禁止深分页**，用游标 `WHERE id > last_id ORDER BY id LIMIT 10`。
**④ 全局唯一 ID** → 雪花 / Leaf。
**⑤ 聚合统计** → ES / 数仓。

### 中间件
- **ShardingSphere**（Apache 顶级）：
  - **JDBC 模式**：客户端 jar，轻量，无需部署，但只 Java。
  - **Proxy 模式**：独立服务，多语言，多一层网络。
- MyCat（Proxy，老）、TDDL（阿里内部）。

## 1.9 MySQL 实战案例

### 📌 案例 1：慢查询优化（覆盖索引）

**现象**：订单列表查询 3s。
```sql
SELECT id, order_no, user_id, amount, status FROM orders
WHERE user_id = 123 AND status = 1 ORDER BY create_time DESC LIMIT 20;
```
**排查**（explain）：
- type = ALL（全表），rows = 1000w，Extra = Using filesort。
- 没有合适索引，回表 + 排序。

**优化**：建联合索引 `(user_id, status, create_time)`。
- 用 user_id + status 等值定位，create_time 索引有序免 filesort。
- `SELECT` 字段都是索引列 + id（主键在二级索引叶子）→ **覆盖索引**，免回表。

**结果**：RT 3s → 10ms。

### 📌 案例 2：深分页优化

```sql
-- 原：LIMIT 1000000, 20（扫 1000020 行）
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;
-- 优化：游标（前提：id 有序且不变化）
SELECT * FROM orders WHERE id > #{last_id} ORDER BY id LIMIT 20;
-- 或：延迟关联
SELECT * FROM orders o 
INNER JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) t ON o.id = t.id;
```

### 📌 案例 3：死锁排查

**现象**：`Deadlock found when trying to get lock; try restarting transaction`。
**排查**：`SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK。
```
两个事务：
T1: UPDATE account SET bal=bal-100 WHERE id=1;  → 锁 id=1
T2: UPDATE account SET bal=bal-100 WHERE id=2;  → 锁 id=2
T1: UPDATE account SET bal=bal+100 WHERE id=2;  → 等 id=2
T2: UPDATE account SET bal=bal+100 WHERE id=1;  → 等 id=1
→ 死锁（InnoDB 检测到，回滚代价小的）
```
**解决**：**统一加锁顺序**（如按 id 升序处理），或短事务。

### 📌 案例 4：主从延迟导致读到旧数据

**现象**：下单后立即查订单列表，偶尔查不到。
**排查**：写主库，读从库，从库延迟 2s。
**解决**：
- 关键业务（下单后跳订单页）**强制读主**（一段时间内）。
- 半同步复制降低延迟。
- 业务层短暂等待/重试。

# 第二篇 Redis 深度

## 2.1 数据结构与底层编码 🔴

| 类型 | 底层编码（7.0 前） | 编码（7.0+） |
|------|------------------|-------------|
| String | int / embstr / raw | 同 |
| List | ziplist / linkedlist | **listpack** / quicklist |
| Hash | ziplist / hashtable | listpack / hashtable |
| Set | intset / hashtable | listpack / hashtable |
| ZSet | ziplist / skiplist | listpack / skiplist |

**Redis 7.0 用 listpack 替代 ziplist**：ziplist 有**连锁更新**问题（一个节点变更可能引发后续所有节点级联扩展，最坏 O(n²)）。

### 重点讲两个底层结构

**① 跳表（SkipList）—— ZSet 底层** 🔴🔴 必精通

```
Level 4:  head ------------------------------> 50 ----------------------> nil
Level 3:  head ----------> 20 ----------------> 50 --------> 80 --------> nil
Level 2:  head ----> 10 --> 20 --------> 40 --> 50 --> 70 --> 80 --------> nil
Level 1:  head -> 10 -> 20 -> 30 -> 40 -> 50 -> 60 -> 70 -> 80 -> 90 -> nil
```

- **多层链表**，每层是下层的"快速通道"。
- 查找：从最高层起，向右走，走不动下降一层，直到找到。
- 每节点 level[] 数组，**层数随机生成**（p=1/2 升一级，最高 32）。
- 查找 O(log N)。

**为什么 ZSet 用跳表不用红黑树？** 🔴🔴
1. **范围查询友好**：跳表叶子层是链表，`ZRANGEBYSCORE` 天然高效（找到起点后沿链表遍历）；红黑树要中序遍历，开销大。
2. **实现简单**：跳表代码远比红黑树简单（无旋转），调试维护容易。
3. **并发友好**：跳表局部修改（改指针），红黑树旋转涉及多节点（并发控制复杂）。
4. **内存可控**：节点层数概率分布，期望 O(log N)。

**ZSet = dict（member→score）+ skiplist（按 score 排序）** 🔴
- 两者**共享同一份数据**（指针）。
- dict：O(1) 查 score（`ZSCORE`）。
- skiplist：按 score 排序（`ZRANGEBYSCORE`）。
- 空间换时间，覆盖两种访问模式。

**② listpack（替代 ziplist）** 🟡
- 紧凑的连续内存结构，存小数据集合。
- 元素少时（List <128、Hash/ZSet <128）用 listpack，省内存。
- 超阈值转 hashtable/skiplist/quicklist。

## 2.2 持久化 🔴🔴

### RDB（快照）
- 全量数据二进制 dump。
- 触发：`SAVE`（阻塞）/ `BGSAVE`（fork 子进程，COW）/ 定时规则。
- 🔴 **fork + Copy-On-Write**：
  - fork 出子进程与父进程共享内存页。
  - 父进程写时，OS 才复制该页（COW）。
  - 大内存 fork 慢（几秒到几十秒）+ 写多时内存翻倍风险。
- 优：体积小、恢复快、适合备份。
- 劣：两次快照间数据丢失、fork 慢。

### AOF（追加日志）
- 记录每条写命令。
- 刷盘策略：`always`（每条同步，安全但慢）/ `everysec`（默认，每秒，平衡）/ `no`（OS 决定）。
- **AOF 重写**：bgrewriteaof，把命令压缩（如 100 次 INCR 合并为 SET）。
- 优：丢数据少。
- 劣：体积大、恢复慢。

### 混合持久化（4.0+，推荐）🔴
- AOF 重写时，先以 **RDB 二进制**写入当前内存快照，后续增量命令以 **AOF 格式**追加。
- 恢复快（RDB 部分快）+ 数据全（AOF 补齐）。

## 2.3 集群方案 🔴

### 主从复制
- **全量同步**：从库首次连接 → 主库 BGSAVE 生成 RDB 发给从库 + 主库缓存期间新命令（repl_backlog）一起发。
- **增量同步**：`replid + offset`，主库维护 backlog 环形缓冲区。
- 全量同步代价大（fork + RDB 传输）。

### 哨兵 Sentinel
- 监控主从、自动故障转移、通知客户端。
- **主观下线**（单个哨兵判定）→ **客观下线**（quorum 个哨兵同意）→ **选举 leader 哨兵**（Raft）→ **执行故障转移**。
- 选新主：优先级 > 复制偏移量 > runid。

### Cluster 集群 🔴🔴 必精通

- **16384 个哈希槽**（slot），`CRC16(key) % 16384` 定位槽。
- 节点间 **Gossip 协议**通信（去中心化，P2P）。
- 每节点负责一部分槽。

**🔴 为什么是 16384 槽？（作者 antirez 解释）**
1. **带宽**：Gossip 消息要带"自己负责的槽位 bitmap"，16384 bit = 2KB；如果 65536 bit = 8KB，浪费。
2. **集群规模**：Redis 建议节点数 ≤1000，16384 足够。
3. **位压缩**：节点少时 bitmap 压缩后更省。

**槽迁移过程** 🔴：
- 源节点迁移中：`ASK` / `MOVED` 重定向。
- 客户端缓存路由表（Smart Client，JedisCluster/Lettuce）。

**Cluster 限制**：
- 不支持跨槽多键操作（除非 hash tag `{tag}`）。
- 不支持跨节点事务/多键。
- 客户端要 Smart Client。

## 2.4 缓存三大问题 🔴🔴 必精通

| 问题 | 场景 | 解决 |
|------|------|------|
| **穿透** | 查不存在的数据（恶意攻击），每次打 DB | ① 缓存空值（null，短过期） ② **布隆过滤器** ③ 接口校验 |
| **击穿** | 热点 key 过期瞬间，大量并发查 DB | ① **互斥锁**（只让一个查 DB） ② 热点 key **永不过期**（逻辑过期+异步刷新） |
| **雪崩** | 大量 key 同时过期 / Redis 宕机 | ① 过期时间**加随机** ② 多级缓存 ③ 集群高可用 ④ 熔断限流 |

### 布隆过滤器（Bloom Filter）🔴🔴
- bit 数组（m 位）+ k 个哈希函数。
- **加入**：k 个位置置 1。
- **查询**：k 个位置都为 1 → **可能存在**（假阳性）；有 0 → **一定不存在**。
- 特点：有误判（假阳性，可调），无漏判；不能删除（除非计数版 Counting BF）。
- 适用：缓存穿透防护、URL 去重、海量数据存在性判断。

## 2.5 内存淘汰策略 🔴

| 策略 | 范围 | 算法 |
|------|------|------|
| noeviction（默认） | — | 不淘汰，写报错 |
| allkeys-lru | 全部 | 近似 LRU（采样） |
| allkeys-lfu | 全部 | LFU（4.0+） |
| allkeys-random | 全部 | 随机 |
| volatile-lru | 设过期键 | LRU |
| volatile-lfu | 设过期键 | LFU |
| volatile-random | 设过期键 | 随机 |
| volatile-ttl | 设过期键 | 快过期的先删 |

**Redis 的 LRU 不是真 LRU** 🔴：真 LRU 要维护双向链表，开销大。Redis 用**采样近似 LRU**（随机取 maxmemory-samples 个，淘汰最久未用）。LFU 用概率衰减计数器（防历史热点永远占位）。

## 2.6 大 Key / 热 Key 治理 🟡

### 大 Key
- 定义：String >10KB、Hash/List/Set/ZSet 元素过多（数万）。
- 危害：阻塞（Redis 单线程）、网络、主从同步慢、删除卡顿（4.0+ UNLINK 异步删）。
- 解决：拆分（Hash 分桶）、压缩、异步删除、监控。

### 热 Key
- 危害：单节点热点、缓存击穿。
- 解决：本地缓存（Caffeine 多级）、多副本（key_1/key_2 随机读）、客户端计算。

## 2.7 分布式锁（详见中间件篇，这里给 Redisson 核心代码）

```java
RLock lock = redisson.getLock("orderLock:" + orderId);
try {
    if (lock.tryLock(3, 30, TimeUnit.SECONDS)) {  // 等待3s，锁30s
        // 业务
    }
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```
- **看门狗**：默认锁 30s（`lockWatchdogTimeout`），后台线程每 10s（1/3 周期）续期（持有者还活着）。
- **可重入**：hash 结构，field=线程ID，value=重入次数。
- Redlock 争议（见中间件篇）。

## 2.8 Redis 实战案例

### 📌 案例 5：大 Key 导致 Redis 阻塞

**现象**：Redis 偶发响应慢 2-3s，监控看 QPS 不高。
**排查**：`redis-cli --bigkeys` 找大 key → 一个 Hash 有 500w 字段（用户标签）。
**解决**：
- 拆分：按 uid % 100 分到 100 个 Hash。
- 异步删除：`UNLINK`（4.0+）。
- 业务侧限制单 Hash 大小。

### 📌 案例 6：缓存击穿打挂 DB

**现象**：热点商品促销，缓存过期瞬间 DB 被打满。
**排查**：缓存 key 同时过期，大量请求穿透。
**解决**：
- 热点 key **永不过期** + 后台异步刷新（逻辑过期）。
- 或 **互斥锁**（单飞，只放一个查 DB）。
- 预热大促前热点。

### 📌 案例 7：主从切换丢锁

**现象**：分布式锁偶尔失效（并发）。
**排查**：主库加锁成功后，主库宕机，从库（未同步到锁）晋升 → 锁丢失。
**解决**：
- Redis 官方推荐 **Redlock**（多 Master），但有争议。
- 强一致场景改用 ZK/etcd。
- 业务幂等兜底（锁失败也不重复扣款）。

# 第三篇 Elasticsearch 🟡

## 3.1 倒排索引 🔴

```
正排：文档 → 词
倒排：词 → 文档列表（+ 词频 + 位置 + 偏移）

结构：
  Term Dictionary（词典）  → FST（Finite State Transducer）压缩，加载到内存
  Term Index（词项索引）   → 辅助快速定位 Term
  Posting List（倒排表）   → 文档 ID 列表，用 Roaring Bitmap 压缩
```

## 3.2 ES 写入流程 🟡

```
1. 写请求到 Coordinator Node（协调节点）
2. 根据 routing 路由到 Primary Shard
3. Primary 写入：
   - 写 translog（事务日志，durability）
   - 写内存 buffer
4. refresh（默认 1s）→ buffer 生成 segment（in-memory）→ 可搜（**近实时**）
5. 复制到 Replica Shard
6. flush（translog 满/定时）→ segment 落盘 + 清 translog
7. merge：后台合并小 segment（减少段数）
```
**为什么 ES 近实时？** refresh 间隔（默认 1s），可调 `index.refresh_interval`。

## 3.3 ES vs 关系型数据库

| ES | RDB |
|----|-----|
| Index | Database |
| Type（已废弃） | Table |
| Document | Row |
| Field | Column |
| Shard | 分区 |

**适用**：全文检索、日志分析（ELK）、多维聚合、模糊搜索。
**不适用**：强事务、频繁更新、复杂 join。
