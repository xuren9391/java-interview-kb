# 第一篇 高并发总纲

## 1.1 高并发三板斧 🔴🔴 必精通

```
        ┌─ 「垂直」提升单机能力（CPU/内存/网卡/SSD）
        │
三板斧 ─┼─ 「水平」分布式扩展（加机器、分区、分片）
        │
        └─ 「架构」异步化 + 缓存 + 削峰 + 批量化 + 池化
```

**具体手段**：
1. **缓存**：多级缓存（浏览器/CDN/Nginx/本地/Redis/DB），缓存命中率是命脉。
2. **异步**：MQ 削峰填谷，同步链路改异步。
3. **拆分**：业务拆分、读写分离、分库分表、微服务化。
4. **批量化**：批量写、pipeline、合并请求。
5. **连接池化**：DB 连接池、线程池、对象池。
6. **无状态化**：服务无状态 → 随意扩容。

## 1.2 性能指标 🔴（面试要会估算）

| 指标 | 含义 |
|------|------|
| QPS | 每秒查询数（读为主） |
| TPS | 每秒事务数（写为主） |
| RT | 响应时间，分 P50/P90/P99/P999 |
| 并发数 | 同时处理的请求数 |
| 吞吐量 | 单位时间处理数据量 |

### 🔴 Little's Law（利特尔法则）
**并发数 = QPS × 平均 RT**

例：QPS=1000，RT=0.1s，则并发数=100。这是容量评估的基石。

### 为什么看 P99 而非平均？🔴
- 平均掩盖长尾。1000 个请求里 1 个 10s，平均只增加 10ms，但那 1 个用户体验灾难。
- 大厂用 **P99/P999**（99%/99.9% 请求的响应时间）。

# 第二篇 缓存深度 🔴

## 2.1 多级缓存架构

```
浏览器 → CDN → Nginx 缓存 → 网关缓存 → 应用本地缓存(Caffeine) → Redis → DB
```
每一层拦截一部分流量，越靠后压力越小。理想：90% 请求打到 Redis 或更前，DB 只扛 10%。

## 2.2 缓存模式 🟡

| 模式 | 读 | 写 | 适用 |
|------|----|----|------|
| **Cache-Aside（旁路，主流）** | 先查缓存，无查 DB 写回 | 先更新 DB，再删缓存 | 通用 |
| **Read/Write-Through** | 缓存层代理读写 DB | 同步写缓存+DB | 缓存层封装 |
| **Write-Behind（回写）** | 同 Read-Through | 只写缓存，异步刷 DB | 写多读少 |

## 2.3 缓存一致性 🔴🔴 必精通

### 🔴 Cache-Aside 下"先更新 DB 还是先删缓存"？

**方案 A：先删缓存，再更新 DB** ❌
- 问题：删缓存后、更新 DB 前，另一请求读 DB 旧值写回缓存 → 脏数据持续。
- 缓解：**延迟双删**（删 → 更新 DB → sleep 一会 → 再删），但 sleep 不好估。

**方案 B：先更新 DB，再删缓存** ✅（推荐）
- 异常：删缓存失败 → 脏数据。
- 解决：① 重试（消息队列）② 订阅 binlog（Canal）异步删缓存，可靠。

### 🔴 为什么是"删"而不是"更新"缓存？
1. **避免并发写冲突**：两个写并发更新缓存，顺序乱可能存脏。
2. **懒加载**：很多数据写后不被读，更新浪费；删是惰性的，读时再加载。
3. **一致**：删是幂等的，更新不是。

# 第三篇 限流 🔴🔴 必精通（含算法实现）

## 3.1 限流算法对比

| 算法 | 原理 | 优 | 劣 |
|------|------|----|----|
| **计数器（固定窗口）** | 单位时间内计数 | 简单 | 临界问题（窗口边界突发 2 倍） |
| **滑动窗口** | 细分窗口滑动 | 解决临界 | 内存略多 |
| **漏桶** | 固定速率漏出 | 匀速平滑 | 无法应对突发（恒定速率） |
| **令牌桶** | 固定速率发令牌 | 允许一定突发 | 实现稍复杂 |

## 3.2 🔴 漏桶 vs 令牌桶（核心区别）

- **漏桶**：**出**固定速率（水以恒定速度漏）。适合**整形流量**（让下游均匀）。
- **令牌桶**：**入**固定速率，桶满丢弃；突发可一次取多个令牌。适合**允许突发**。
- 例：**秒杀用令牌桶**（允许瞬时突发），**MQ 消费用漏桶**（匀速不压垮 DB）。

## 3.3 算法代码实现 🔴

### 滑动窗口（Sentinel 思路）
```java
class SlidingWindow {
    int windowSizeMs = 1000;   // 窗口 1s
    int sampleCount = 2;       // 2 个子桶（每 500ms 一个）
    AtomicLong[] buckets = new AtomicLong[sampleCount];
    volatile long startTime = System.currentTimeMillis();

    long currentBucketIdx() {
        long elapsed = System.currentTimeMillis() - startTime;
        return (elapsed / (windowSizeMs / sampleCount)) % sampleCount;
    }
    boolean tryAcquire(int limit) {
        // 重置过期桶 + 统计窗口内总数 + 判断
        long total = Arrays.stream(buckets).sum();
        if (total >= limit) return false;
        buckets[(int)currentBucketIdx()].incrementAndGet();
        return true;
    }
}
```

### 令牌桶（Guava RateLimiter 思路）
```java
class TokenBucket {
    long capacity = 100;           // 桶容量
    double rate = 10.0;            // 每秒产生 10 个令牌
    double tokens;                 // 当前令牌数
    long lastRefillNanos;
    synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        double elapsed = (now - lastRefillNanos) / 1e9;
        tokens = Math.min(capacity, tokens + elapsed * rate);  // 按时间补充
        lastRefillNanos = now;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;
    }
}
```
Guava `RateLimiter.create(rate)` 就是令牌桶，`acquire()` 阻塞等待，`tryAcquire()` 非阻塞。

## 3.4 限流维度
- 单机（Guava RateLimiter、Sentinel 单机规则）。
- 分布式（Redis + Lua、Sentinel 集群限流）。
- 维度：接口 QPS、用户维度（userId）、IP 维度、集群总 QPS。

## 3.5 🔴 分布式限流实现（Redis + Lua）
```lua
-- KEYS[1] = 限流 key, ARGV[1] = 过期秒, ARGV[2] = 阈值
local c = redis.call("incr", KEYS[1])
if c == 1 then
    redis.call("expire", KEYS[1], ARGV[1])  -- 第一次设过期
end
if c > tonumber(ARGV[2]) then
    return 0  -- 限流
end
return 1
```
Lua 保证原子性（incr + expire 不会被并发打断）。

# 第四篇 熔断与降级 🔴

## 4.1 概念区分 🔴
- **限流**：控制流量大小，超出拒绝。
- **熔断**：下游故障时**快速失败**，防止级联雪崩（不再调用）。
- **降级**：保证核心、牺牲非核心（返回默认/缓存）。
- **隔离**：资源隔离（线程池/信号量），故障不扩散。

## 4.2 🔴 熔断器状态机
```
        失败率超阈值
CLOSED ─────────────→ OPEN（熔断，直接拒绝）
  ↑                       │
  │ 探测成功               │ 等待一段时间（sleep window）
  │                       ↓
  └──── HALF-OPEN（半开，放少量探测请求）
```
- **CLOSED**：正常调用，统计失败率。
- **OPEN**：直接拒，不调下游（保护下游 + 快速失败）。
- **HALF-OPEN**：等待期过后放少量请求探测，成功回 CLOSED，失败回 OPEN。

## 4.3 隔离策略 🔴（Sentinel vs Hystrix）
- **线程池隔离**（Hystrix 默认）：每个资源独立线程池，彻底隔离但开销大（线程切换）。
- **信号量隔离**（Sentinel）：计数器限并发，轻量无线程切换。

## 4.4 降级方案
- 返回默认值/空列表。
- 返回缓存（旧数据）。
- 同步转异步（先返回"处理中"，后台处理）。
- 关闭非核心功能（如关闭推荐、评论）。

# 第五篇 幂等 🔴🔴 必精通

## 5.1 为什么需要幂等
网络重试、用户重复点击、MQ 重复消费 → 同一请求执行多次。幂等保证**多次执行结果一致**。

## 5.2 幂等方案
| 方案 | 实现 | 适用 |
|------|------|------|
| **唯一约束** | 业务 ID 唯一键，重复插报错 | 插入 |
| **乐观锁（版本号）** | `UPDATE ... WHERE version=v` | 更新 |
| **状态机** | 校验状态流转 | 订单状态 |
| **Token 机制** | 服务端发 token，请求带 token，处理即失效 | 表单提交 |
| **分布式锁** | `SET id NX` 抢锁 | 通用 |
| **去重表** | msg_id 去重 | MQ 消费 |

## 5.3 各操作幂等性 🔴
- SELECT、DELETE（按主键）：天然幂等。
- UPDATE 绝对值（`SET balance=100`）：幂等。
- UPDATE 相对值（`SET balance=balance+10`）：**不幂等**。
- INSERT：天然不幂等。

# 第六篇 秒杀系统设计 🔴🔴🔴（综合实战题）

## 6.1 核心挑战
- 瞬时高并发（几秒百万 QPS）。
- 防超卖（库存不能负）。
- 防黄牛（机器人）。
- 防缓存击穿。

## 6.2 分层架构 🔴

```
1. 前端/客户端
   - 按钮置灰（点一次禁用几秒）
   - 验证码（错峰 + 防机器人）
   - 答题/小游戏（错峰）
   - 资源静态化（CDN）

2. 网关层
   - 限流（用户维度、IP 维度）
   - 黑名单（黄牛）
   - 鉴权

3. 服务层
   - 活动未开始/已结束 → 直接拒绝
   - 库存预热到 Redis
   - Redis 预扣库存（Lua 原子扣减，扣到 0 拒绝）
   - 扣减成功的请求异步发 MQ
   - 限流降级

4. MQ 异步下单
   - 消费者按 DB 能力处理，写订单、扣真实库存

5. DB
   - 库存表，乐观锁 / 行锁防超卖
```

## 6.3 🔴 防超卖的核心

**① Redis 预扣（Lua 原子）**：
```lua
-- KEYS[1]=库存key, ARGV[1]=扣减数量
local stock = tonumber(redis.call("get", KEYS[1]))
if stock == nil or stock < tonumber(ARGV[1]) then
    return 0  -- 库存不足
end
redis.call("decrby", KEYS[1], ARGV[1])
return 1  -- 扣减成功
```
- 扣到 0 立即拦截 99% 请求。

**② DB 兜底（乐观锁）**：
```sql
UPDATE stock SET num = num - 1 WHERE sku_id = ? AND num > 0
-- 影响行数 0 = 超卖，回滚
```

**③ DB 性能**：分库分表（按商品 hash），热点商品单独表。

## 6.4 库存回滚
- 订单超时未支付 → 异步任务回滚库存（延时消息）。

## 6.5 防刷
- 用户限购（每人限 1 件）：Redis SETNX。
- IP/设备维度限流。
- 验证码、答题。
- 黑名单（黄牛账号）。

# 第七篇 高可用架构 🔴

## 7.1 多活/容灾

| 方案 | 说明 | 成本 |
|------|------|------|
| **冷备** | 备机不运行，故障切换启动 | 低，切换慢 |
| **热备** | 备机运行不接流量，同步数据 | 中 |
| **双活** | 两机房都接流量，互备 | 高 |
| **同城双活** | 同城两机房，低延迟，机房级容灾 | 中高 |
| **异地多活** | 不同城市多机房，城市级容灾 | 极高 |

## 7.2 🔴 单元化架构（异地多活主流）
- 按用户维度（如 userId）路由到固定"单元"。
- 每个单元是完整闭环（应用 + DB + 缓存），核心数据按用户分片。
- 跨单元调用最小化，单元内自洽。
- 单元间数据双向同步（DTS / Canal+MQ）。
- 故障切换单元流量到其他单元。

**挑战**：数据同步延迟、全局唯一数据（如库存、账号）、跨单元事务。

## 7.3 数据同步方案 🟡
- **同步**：MySQL 主从复制、DTS。
- **异步**：Canal 订阅 binlog → MQ → 异地写。
- **关键**：核心数据强一致（金融），非核心最终一致。

## 7.4 SLA 等级 🟢
- 99.9%：年停机 ≤ 8.76h
- 99.99%：年停机 ≤ 52.6min
- 99.999%（5 个 9）：年停机 ≤ 5.26min（金融级）

# 第八篇 稳定性建设（资深/架构师必备）🔴

## 8.1 全链路监控
**三大支柱**：
- **Metrics 指标**（Prometheus + Grafana）：QPS、RT、错误率、资源。
- **Logging 日志**（ELK/Loki）：详细记录。
- **Tracing 链路**（SkyWalking/Zipkin/Jaeger）：跨服务调用链。

**黄金信号**：延迟、流量、错误、饱和度。

## 8.2 全链路压测 🔴
- **影子库/影子表**：压测数据隔离，不污染生产。
- **流量录制回放**（GoReplay）：录真实流量回放。
- **目的**：找瓶颈、定容量、验证扩容。

## 8.3 容量评估 🔴
1. 估算峰值 QPS（日均 × 系数，大促再放大）。
2. 单机容量 = QPS ÷ 机器数，留 30% 余量。
3. 找出瓶颈（CPU/IO/DB）。
4. 评估依赖容量（DB 连接、Redis、下游接口）。

## 8.4 故障应急预案 SOP 🟡
- **预案**：常见故障的处理步骤（限流、降级、重启、回滚）。
- **演练**（混沌工程 Chaos Monkey）：主动注入故障验证容错。
- **快速恢复**：灰度发布、蓝绿部署、金丝雀。

## 8.5 🔴 故障复盘
**TimeLine**：发生 → 发现 → 响应 → 恢复。
**5 Why 分析**：找根因（不是甩锅）。
**改进措施**：监控告警、流程、代码、架构，跟踪到关闭。

**黄金法则**：
- 发现要快（监控告警）。
- 止血要快（限流降级回滚）。
- 根因要透（5 why）。
- 改进要落地（不复发）。

# 第九篇 经典问题排查套路 🔴

## 9.1 接口变慢排查
```
1. 是单接口慢还是全局慢？
   全局慢 → 机器资源（CPU/内存/网络/GC）
   单接口 → 该接口依赖
2. 单接口：链路追踪看每个 Span 耗时
   - DB 慢查询？慢 SQL + 锁等待 + 大结果集
   - 下游接口超时？
   - 外部依赖（Redis、MQ）？
3. JVM：GC 频繁？FullGC？
4. 网络：带宽、丢包、RTT？
5. 锁竞争：线程 BLOCKED？
```

## 9.2 数据库慢查询优化
```
1. 开慢查询日志
2. explain 看 type/key/rows/Extra
3. 优化方向：
   - 加索引 / 改联合索引 / 避免索引失效
   - 大分页 → 游标
   - 避免 SELECT *，用覆盖索引
   - 拆 SQL，避免 join 过多
   - 分库分表
4. 验证：再 explain，看 RT
```

## 9.3 雪崩排查与止血 🔴
```
现象：一个服务挂，整条链路雪崩
根因：同步调用 + 无熔断 + 资源耗尽（线程池满）
止血：
  1. 限流（网关 + 应用双层）
  2. 降级非核心
  3. 隔离故障服务
  4. 扩容
根因：补熔断、超时、重试、降级、舱壁隔离
```

# 第十篇 实战案例

## 📌 案例 1：缓存击穿打挂 DB

**现象**：热点商品促销，缓存过期瞬间 DB 被打满。
**S**：大促 0 点，商品详情接口 RT 飙升，DB CPU 100%。
**T**：紧急止血 + 根因修复。
**A**：
1. 止血：临时对该商品接口加限流（Sentinel 单机 500 QPS）。
2. 排查：链路发现 Redis miss → 全部打到 DB（缓存击穿）。
3. 修复：
   - 热点 key 改**永不过期** + 后台异步刷新（逻辑过期）。
   - 加**互斥锁**（单飞，只放一个查 DB 重建缓存）。
   - 大促前预热所有热点。
**R**：DB CPU 降到 30%，接口 RT 恢复。

## 📌 案例 2：服务雪崩

**现象**：支付服务调风控服务超时，导致整个支付链路阻塞。
**S**：风控服务 GC 抖动响应变慢，支付服务线程池打满 → 雪崩。
**T**：止血。
**A**：
1. 止血：手动降级风控（跳过风控直接放行，事后补偿）。
2. 排查：链路看风控 RT 从 50ms → 5s，支付调用堆积 → 线程池满 → 拒绝服务。
3. 根因修复：
   - 加**熔断**（Sentinel，风控 RT 超 1s 熔断 30s）。
   - 加**超时**（Feign readTimeout 1s）。
   - 加**降级**（风控挂了走默认规则）。
   - 风控服务优化 GC（换 G1，调堆）。
**R**：后续风控抖动不再影响支付。

## 📌 案例 3：Full GC 导致接口抖动

**现象**：订单接口 P99 偶发 3s。
**排查**：
1. Grafana GC 看每 10 分钟一次 Full GC，停顿 800ms。
2. dump 分析：本地缓存 `Map` 累积 2GB（没设淘汰）。
3. 对象进老年代，Mixed GC 回收慢。
**解决**：
- 缓存改 **Caffeine**（限制大小 + LRU）。
- JVM：`-XX:InitiatingHeapOccupancyPercent=35` 提前标记。
**结果**：Full GC 消失，P99 稳定 200ms。

## 📌 案例 4：分库分表后深分页爆炸

**现象**：订单后台翻到 100 页后超时。
**排查**：`LIMIT 1000000, 20` 在分片下，每片都扫 1000020 行回应用层归并 → 慢。
**解决**：改游标分页（`WHERE id > last_id LIMIT 20`），后台场景可接受。

# 第十一篇 性能优化总纲 🔴

## 11.1 优化层次（从上到下，收益递减）
```
1. 业务优化（最大收益）
   - 减少不必要的调用、合并请求、异步化、批量化
2. 架构优化
   - 缓存、MQ、读写分离、分库分表、CDN
3. 代码优化
   - 算法数据结构、减少对象创建、连接池复用
4. JVM 优化
   - GC 调优、参数
5. OS / 硬件
   - 网络内核参数、磁盘、CPU
```

**铁律**：**先业务后技术，先架构后代码，先测量后优化**（别瞎优化，Profile 找瓶颈）。

## 11.2 优化方法论
1. **量化现状**：RT/QPS/CPU/内存 baseline。
2. **定位瓶颈**：Profile（arthas、async-profiler、火焰图）。
3. **假设验证**：改一处测一处（控制变量）。
4. **回归验证**：防止优化破坏正确性。
5. **持续监控**：优化后跟踪，防退化。
