# 第一篇 高并发总纲

## 1.1 高并发三板斧 🔴🔴 必精通

### ① 为什么/痛点
单机性能有物理上限（CPU 主频、网卡带宽、磁盘 IOPS）。当业务流量从 1 千 QPS 涨到 10 万 QPS，靠"换更好机器"成本指数级上升（摩尔定律已放缓），且单点故障=系统级宕机。必须靠**分布式 + 异步化 + 缓存**横向扩展。

### ② 原理图解
```
        ┌─ 「垂直」提升单机能力（CPU/内存/网卡/SSD）—— 成本高、有上限
        │
三板斧 ─┼─ 「水平」分布式扩展（加机器、分区、分片）—— 无上限、可线性
        │
        └─ 「架构」异步化 + 缓存 + 削峰 + 批量化 + 池化 —— 性价比最高
```

**六大具体手段**：
1. **缓存**：多级缓存（浏览器/CDN/Nginx/本地/Redis/DB），缓存命中率是命脉。
2. **异步**：MQ 削峰填谷，同步链路改异步。
3. **拆分**：业务拆分、读写分离、分库分表、微服务化。
4. **批量化**：批量写、pipeline、合并请求。
5. **连接池化**：DB 连接池、线程池、对象池。
6. **无状态化**：服务无状态 → 随意扩容。

### ③ 前司真实案例
茶饮 SaaS 平台小程序大促（如"买一送一""第二杯半价"）：原本单库 MySQL 扛不住秒级万级并发下单。我们做的：
- **缓存**：商品/活动/库存预热 Redis，高峰缓存命中 **85%**。
- **异步**：下单链路从"同步写 DB"改为"Redis 预扣 → MQ 异步落库"，接口 **RT 从 2s 降到 400ms**。
- **拆分**：促销服务、库存服务、订单服务独立部署，按租户(门店品牌)分库。

### ④ 对比/边界
| 手段 | 收益 | 代价/边界 |
|------|------|----------|
| 缓存 | 10-100 倍 | 一致性、雪崩/击穿/穿透 |
| 异步 | 解耦、削峰 | 最终一致、消息丢失/重复 |
| 拆分 | 横向扩展 | 分布式事务、运维复杂 |
| 批量 | 减少网络往返 | 实时性下降 |

### ⑤ 面试话术
「高并发三板斧我总结成一句话：**能用缓存绝不打 DB，能异步绝不同步，能拆分绝不分单体**。我在前司主导秒杀活动（10 万+并发），核心就是 Redis 预扣库存削峰 + MQ 异步落库，把同步 2s 的链路压到 400ms。垂直扩容是治标，水平扩展+架构异步化才是治本。」

## 1.2 性能指标 🔴（面试要会估算）

### ① 为什么
没有量化就没有优化。面试官问"你系统多快"，答"挺快"=0 分；答"P99 200ms、峰值 10 万 QPS"=专业。指标决定容量规划、告警阈值、SLA 合同。

### ② 指标定义
| 指标 | 含义 | 前司典型值 |
|------|------|----------|
| QPS | 每秒查询数（读为主） | 商品详情 5w+ |
| TPS | 每秒事务数（写为主） | 下单 2k |
| RT | 响应时间，分 P50/P90/P99/P999 | P99 400ms |
| 并发数 | 同时处理的请求数 | ~2000 |
| 吞吐量 | 单位时间处理数据量 | — |

### 🔴 Little's Law（利特尔法则）
**并发数 = QPS × 平均 RT**

例：QPS=10000，RT=0.04s，则并发数=400。这是容量评估的基石，也是线程池/连接池大小的理论依据。

### 🔴 为什么看 P99 而非平均？
- 平均掩盖长尾。1000 个请求里 1 个 10s，平均只增加 10ms，但那 1 个用户体验灾难。
- 大厂用 **P99/P999**（99%/99.9% 请求的响应时间）。
- 前司内部标准：核心接口 P99 ≤ 500ms，P999 ≤ 1s。

### ③ 前司真实案例
大促前压测：商品详情接口 P50=50ms 看着很美，但 P99=3s（缓存击穿瞬间）。只看平均会误判，按 P99 才发现要补互斥锁。

### ④ 对比/边界
- P50 看系统"一般状态"，P99 看"用户体验下限"，P999 看"极端长尾"。
- 金融/支付场景必须看 P999 甚至 P9999。

### ⑤ 面试话术
「容量评估我靠 **Little's Law：并发=QPS×RT**。比如我系统 10 万 QPS、RT 40ms，并发约 400，单机线程池设 200，配 4 台机器正好留余量。监控我只认 P99/P999，平均值会掩盖长尾——前司大促时就因为只看平均，没发现 P99 的缓存击穿，后来全链路监控都改成 P99 告警。」

# 第二篇 缓存深度 🔴

## 2.1 多级缓存架构

### ① 为什么
单一缓存层有瓶颈：Redis 网络往返也有延迟，DB 抗压能力最弱。多级缓存让请求**逐层拦截**，越靠后压力越小，是高并发第一道防线。

### ② 原理图解
```
浏览器 → CDN → Nginx 缓存 → 网关缓存 → 应用本地缓存(Caffeine) → Redis → DB
  本地      边缘    反代       网关      进程内(JVM)          集群    持久化
```
每一层拦截一部分流量，理想：90% 请求打到 Redis 或更前，DB 只扛 10%。

### ③ 前司真实案例
- **CDN/Nginx**：商品图片、活动页静态资源走 CDN，回源率 <5%。
- **Caffeine 本地缓存**：门店基础信息（近百万家门店）、商品类目，TTL 5 分钟，命中率 90%+，避免 Redis 网络 RT。
- **Redis**：活动库存、用户优惠券，高峰**命中率 85%**。

### ④ 对比/边界
| 层级 | 速度 | 容量 | 一致性 |
|------|------|------|--------|
| 本地 Caffeine | ns 级 | MB-G | 最差（多机不一致） |
| Redis | ms 级 | GB-T | 中（需淘汰策略） |
| DB | 10ms+ | TB | 强 |

### ⑤ 面试话术
「多级缓存核心是**逐层拦截**。前司是本地 Caffeine 放门店/类目这种读多写少的数据（命中率 90%），Redis 放库存/资产这种需要强一致和高并发的，DB 只兜底。命中率 85% 意味着 DB 流量直接降一个数量级。」

---

## 2.2 缓存模式 🟡

| 模式 | 读 | 写 | 适用 |
|------|----|----|------|
| **Cache-Aside（旁路，主流）** | 先查缓存，无查 DB 写回 | 先更新 DB，再删缓存 | 通用 |
| **Read/Write-Through** | 缓存层代理读写 DB | 同步写缓存+DB | 缓存层封装 |
| **Write-Behind（回写）** | 同 Read-Through | 只写缓存，异步刷 DB | 写多读少 |

**Cache-Aside 是业界主流**：应用代码同时操作缓存和 DB，灵活可控。前司所有缓存都用 Cache-Aside。

---

## 2.3 缓存一致性 🔴🔴 必精通

### ① 为什么
缓存和 DB 是两份数据，并发读写必然产生不一致窗口。不一致=用户看到过期价格、错误库存，直接影响交易。一致性方案是缓存设计的核心难题。

### 🔴 Cache-Aside 下"先更新 DB 还是先删缓存"？

**方案 A：先删缓存，再更新 DB** ❌
- 问题：删缓存后、更新 DB 前，另一请求读 DB 旧值写回缓存 → 脏数据持续。
- 缓解：**延迟双删**（删 → 更新 DB → sleep 一会 → 再删），但 sleep 不好估。

**方案 B：先更新 DB，再删缓存** ✅（推荐）
- 异常：删缓存失败 → 脏数据。
- 解决：① 重试（消息队列）② 订阅 binlog（Canal）异步删缓存，可靠。

### 🔴 为什么是"删"而不是"更新"缓存？
1. **避免并发写冲突**：两个写并发更新缓存，顺序乱可能存脏。
2. **懒加载**：很多数据写后不被读，更新浪费；删是惰性的，读时再加载。
3. **一致**：删是幂等的，更新不是。

### ② 原理图解（先更新 DB 再删缓存 + Canal 兜底）
```
应用 ──更新DB──→ DB ──binlog──→ Canal ──MQ──→ 消费者删缓存
   └──删缓存──→ Redis (失败则靠 Canal 补偿)
```

### ③ 前司真实案例
优惠券库存这类强一致场景：先 `UPDATE` DB 扣减，再 `DEL` Redis。为防止删缓存失败，引入 Canal 订阅 binlog，落 MQ 后异步补偿删缓存。**最终一致性，延迟 <1s**。

### ④ 对比/边界
| 方案 | 一致性 | 复杂度 | 适用 |
|------|--------|--------|------|
| 先删后更新 | 差（脏读） | 低 | 不推荐 |
| 先更新后删 | 中 | 中 | 通用 |
| +延迟双删 | 中高 | 中 | 写频繁 |
| +Canal 兜底 | 高 | 高 | 强一致场景 |

### ⑤ 面试话术
「缓存一致性我用**先更新 DB 再删缓存**，删是幂等的、惰性的，比更新更安全。删失败用 Canal 订阅 binlog 异步补偿，保证最终一致。前司优惠券库存就这么做，延迟控制在 1s 内。」

# 第三篇 限流 🔴🔴 必精通（含算法实现）

## 3.1 限流算法对比 🔴

### ① 为什么
系统处理能力有上限（DB 2000 TPS、Redis 10w QPS），超量请求会拖垮整个系统。限流是**自我保护**——拒绝部分请求保住整体可用，是高可用第一道闸门。

### ② 四种算法对比表
| 算法 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **计数器（固定窗口）** | 单位时间内计数 | 实现最简单 | 临界问题（窗口边界突发 2 倍） | 资源粗粒度限流 |
| **滑动窗口** | 细分窗口滑动 | 解决临界 | 内存略多 | 精确 QPS 限流（Sentinel） |
| **漏桶** | 固定速率漏出 | 匀速平滑 | 无法应对突发（恒定速率） | 整形流量（保护下游 DB） |
| **令牌桶** | 固定速率发令牌 | 允许一定突发 | 实现稍复杂 | 突发流量入口（秒杀、网关） |

### ③ 前司真实案例
- **令牌桶**：网关层秒杀接口，允许瞬时突发（用户 0 点同时点），令牌速率=下游能扛的 QPS。
- **漏桶**：MQ 消费端，匀速消费保护 DB（DB 2000 TPS，消费速率严格限速）。
- **滑动窗口**：Sentinel 单机流控，统计每秒 QPS。

### ④ 边界
- 单机：Guava RateLimiter、Sentinel 单机规则。
- 分布式：Redis + Lua、Sentinel 集群限流。
- 维度：接口 QPS、用户维度（userId）、IP 维度、集群总 QPS。

### ⑤ 面试话术
「限流我分两层：**网关用令牌桶**（允许突发，秒杀 0 点万级并发不被一刀切死），**消费端用漏桶**（匀速保护 DB）。算法选型看场景——要突发选令牌桶，要整形选漏桶。」

---

## 3.2 🔴 漏桶 vs 令牌桶（核心区别）

### ① 为什么
两个算法常被混淆，面试必问。理解差异才能正确选型：一个"控出"，一个"控入"。

### ② 原理图解
```
漏桶 Leaky Bucket（控"出"，匀速）          令牌桶 Token Bucket（控"入"，允许突发）
                                              ┌─令牌以固定速率产生─→
  大量请求 ──→ [桶] ──固定速率──→ 出口       桶满丢弃令牌
   (入可任意快)   (匀速漏出)                  请求 ──→ 取N个令牌 ──→ 通过
                                              (突发可一次取多个)
```
- **漏桶**：**出**固定速率（水以恒定速度漏）。适合**整形流量**（让下游均匀）。
- **令牌桶**：**入**固定速率，桶满丢弃；突发可一次取多个令牌。适合**允许突发**。

### ③ 前司真实案例
- **秒杀用令牌桶**：0 点 10 万并发涌入，令牌桶允许前几秒突发放行，之后按速率限制。
- **MQ 消费用漏桶**：消费者匀速拉取（如 2000/s），保证 DB 不被瞬时打挂。

### ④ 对比
| 维度 | 漏桶 | 令牌桶 |
|------|------|--------|
| 流量形态 | 匀速 | 允许突发 |
| 队列 | 请求排队 | 令牌排队 |
| 典型库 | — | Guava RateLimiter |
| 场景 | 保护下游 | 入口限流 |

### ⑤ 面试话术
「一句话：**漏桶控出、令牌桶控入**。漏桶把任意速率的请求整形成匀速，保护下游；令牌桶按速率发令牌，桶里令牌可累积，允许突发。秒杀入口用令牌桶（0 点突发要放过），MQ 消费用漏桶（匀速保护 DB）。」

## 3.3 🔴 算法代码实现（完整可运行 Java）

### 3.3.1 固定窗口计数器
```java
import java.util.concurrent.atomic.AtomicInteger;

/**
 * 固定窗口计数器限流
 * 痛点：实现最简单，但有"临界突发"问题（窗口边界 2 倍流量）
 */
public class FixedWindowRateLimiter {
    private final long windowSizeMs;        // 窗口大小（毫秒）
    private final int maxRequests;          // 窗口内最大请求数
    private final AtomicInteger counter = new AtomicInteger(0);
    private volatile long windowStart = System.currentTimeMillis();

    public FixedWindowRateLimiter(long windowSizeMs, int maxRequests) {
        this.windowSizeMs = windowSizeMs;
        this.maxRequests = maxRequests;
    }

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        // 进入新窗口，重置计数器和起始时间
        if (now - windowStart >= windowSizeMs) {
            windowStart = now;
            counter.set(0);
        }
        return counter.incrementAndGet() <= maxRequests;
    }
}
// 用法：new FixedWindowRateLimiter(1000, 100) → 每秒最多 100 次
```

### 3.3.2 滑动窗口（Sentinel 思路）
```java
import java.util.concurrent.atomic.AtomicLong;
import java.util.Arrays;

/**
 * 滑动窗口限流（Sentinel 核心思路）
 * 把一个大窗口切成多个子桶，滑动统计窗口内总数
 * 优点：比固定窗口更平滑，缓解临界突发
 */
public class SlidingWindowRateLimiter {
    private final int windowSizeMs = 1000;   // 总窗口 1s
    private final int sampleCount = 2;       // 2 个子桶（每 500ms 一个）
    private final AtomicLong[] buckets;
    private volatile long startTime = System.currentTimeMillis();

    public SlidingWindowRateLimiter() {
        buckets = new AtomicLong[sampleCount];
        for (int i = 0; i < sampleCount; i++) buckets[i] = new AtomicLong(0);
    }

    /** 当前时间落在哪个子桶 */
    private int currentBucketIdx() {
        long elapsed = System.currentTimeMillis() - startTime;
        return (int) ((elapsed / (windowSizeMs / sampleCount)) % sampleCount);
    }

    /** 滑动到新桶时，重置该桶计数（ buckets 按时间轮转复用） */
    public synchronized boolean tryAcquire(int limit) {
        long now = System.currentTimeMillis();
        long elapsed = now - startTime;
        // 跨越整个窗口周期，全部桶重置
        if (elapsed >= windowSizeMs) {
            for (AtomicLong b : buckets) b.set(0);
            startTime = now;
        }
        int idx = currentBucketIdx();
        // 统计当前窗口内所有桶的总请求数
        long total = Arrays.stream(buckets).mapToLong(AtomicLong::get).sum();
        if (total >= limit) return false;       // 超限拒绝
        buckets[idx].incrementAndGet();
        return true;
    }
}
```

### 3.3.3 漏桶（Leaky Bucket）
```java
/**
 * 漏桶限流（匀速整形）
 * 水以任意速率流入，以固定速率漏出。桶满则拒绝。
 * 适合保护下游（让下游均匀接收）
 */
public class LeakyBucketRateLimiter {
    private final int capacity;            // 桶容量
    private final double leakRatePerSec;   // 漏出速率（请求/秒）
    private double water;                  // 当前水量
    private long lastLeakNanos = System.nanoTime();

    public LeakyBucketRateLimiter(int capacity, double leakRatePerSec) {
        this.capacity = capacity;
        this.leakRatePerSec = leakRatePerSec;
    }

    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        double elapsedSec = (now - lastLeakNanos) / 1e9;
        // 先漏水：按时间匀速漏出
        water = Math.max(0, water - elapsedSec * leakRatePerSec);
        lastLeakNanos = now;
        // 再加水：当前请求进入
        if (water + 1 > capacity) return false;  // 桶满拒绝
        water += 1;
        return true;
    }
}
// 用法：capacity=100, leakRate=10/s → 最多排队 100，匀速放行 10/s
```

### 3.3.4 令牌桶（Token Bucket，Guava RateLimiter 思路）
```java
/**
 * 令牌桶限流（允许突发）
 * 令牌以固定速率产生放入桶中，桶满丢弃。请求来取 N 个令牌，不够则拒绝/等待。
 * 适合入口限流（允许瞬时突发）
 */
public class TokenBucketRateLimiter {
    private final long capacity;           // 桶最大令牌数
    private final double ratePerSec;       // 令牌产生速率（个/秒）
    private double tokens;                 // 当前令牌数
    private long lastRefillNanos = System.nanoTime();

    public TokenBucketRateLimiter(long capacity, double ratePerSec) {
        this.capacity = capacity;
        this.ratePerSec = ratePerSec;
        this.tokens = capacity;            // 初始满桶（允许首次突发）
    }

    public synchronized boolean tryAcquire() {
        return tryAcquire(1);
    }

    /** 申请 n 个令牌（突发可一次取多个） */
    public synchronized boolean tryAcquire(int n) {
        long now = System.nanoTime();
        double elapsedSec = (now - lastRefillNanos) / 1e9;
        // 按时间补充令牌，上限 capacity
        tokens = Math.min(capacity, tokens + elapsedSec * ratePerSec);
        lastRefillNanos = now;
        if (tokens >= n) {
            tokens -= n;
            return true;
        }
        return false;                       // 令牌不足拒绝
    }
}
// Guava 等价：RateLimiter.create(rate) → 令牌桶
//   acquire() 阻塞等待、tryAcquire() 非阻塞
```

---

## 3.4 🔴 分布式限流实现（Redis + Lua）

### ① 为什么
单机限流（Guava）只能控本机，集群多台机器叠加 QPS 远超下游承受。必须**集群维度限流**，Redis + Lua 保证原子性。

### ② 实现
```lua
-- KEYS[1] = 限流 key, ARGV[1] = 过期秒, ARGV[2] = 阈值
local c = redis.call("incr", KEYS[1])
if c == 1 then
    redis.call("expire", KEYS[1], ARGV[1])  -- 第一次设过期
end
if c > tonumber(ARGV[2]) then
    return 0  -- 限流
end
return 1
```
Lua 保证原子性（incr + expire 不会被并发打断）。

### ③ 前司真实案例
秒杀接口集群总 QPS 限流：`key = "rate_limit:seckill:activity_123"`，阈值=下游 DB+Redis 总承受力（如 5 万/s）。超出部分网关直接返回"活动太火爆"。

### ④ 边界
- Redis 限流本身依赖 Redis 可用（Redis 挂了限流失效），高可用需 Redis Cluster。
- 极端高并发下 Redis 也会成瓶颈，可结合本地限流"双层兜底"。

### ⑤ 面试话术
「单机限流用 Guava RateLimiter，集群限流用 **Redis+Lua**。Lua 脚本里 `incr` 后判断阈值、首次设过期，原子执行不会被并发打断。前司秒杀就靠这个控集群总 QPS，超出直接返回'活动太火爆'，保护下游 DB。」

---

# 第四篇 熔断与降级 🔴

## 4.1 概念区分 🔴

### ① 为什么
微服务链路长（A→B→C→D），D 挂了，C 等 D 超时占线程，B 等 C 超时占线程……**线程池耗尽→雪崩**。需要四种"稳定性武器"避免级联故障。

| 概念 | 定义 | 时机 |
|------|------|------|
| **限流** | 控制流量大小，超出拒绝 | 流量超容量 |
| **熔断** | 下游故障时**快速失败**，不再调用 | 下游异常率高 |
| **降级** | 保证核心、牺牲非核心（返回默认/缓存） | 核心链路压力大 |
| **隔离** | 资源隔离（线程池/信号量），故障不扩散 | 多业务共享资源 |

### ② 原理图解（雪崩成因）
```
D 挂了 → C 调 D 超时(占线程) → C 线程池满 → B 调 C 超时 → B 线程池满 → 全链路雪崩
                          ↑ 没有"快速失败"机制
```

### ③ 前司真实案例
促销服务调优惠券服务，优惠券服务 GC 抖动 RT 飙升 → 促销线程池堆积险些雪崩。加 Sentinel 熔断（RT>1s 熔断 30s）+ 降级（返回默认优惠）后稳住。

### ④ 对比
- **限流防"自己被打挂"，熔断防"被下游拖死"，降级保"核心可用"，隔离防"故障扩散"**。四者互补。

### ⑤ 面试话术
「四个概念我分得清：**限流是流量超量拒绝，熔断是下游故障快速失败，降级是牺牲非核心保核心，隔离是资源不共享**。前司秒杀里，网关限流防入口洪水，调优惠券服务加熔断防被拖死，大促时降级评论/推荐保下单。」

---

## 4.2 🔴 熔断器状态机

### ① 为什么
下游故障时持续调用=雪崩源头。熔断器自动"跳闸"快速失败，给下游恢复时间，是**自动化保护**核心。

### ② 原理图解
```
        失败率超阈值
CLOSED ─────────────→ OPEN（熔断，直接拒绝）
  ↑                       │
  │ 探测成功               │ 等待一段时间（sleep window）
  │                       ↓
  └──── HALF-OPEN（半开，放少量探测请求）
```
- **CLOSED**：正常调用，统计失败率。
- **OPEN**：直接拒，不调下游（保护下游 + 快速失败）。
- **HALF-OPEN**：等待期过后放少量请求探测，成功回 CLOSED，失败回 OPEN。

### ③ 关键参数（Sentinel 为例）
| 参数 | 含义 | 前司典型值 |
|------|------|----------|
| 慢调用 RT 阈值 | 超过算慢调用 | 1000ms |
| 慢调用比例 | 触发熔断阈值 | 0.5 |
| 最小请求数 | 统计生效最小量 | 5 |
| 熔断时长 | OPEN 持续时间 | 30s |
| 探测请求数 | HALF-OPEN 放行量 | 1-3 |

### ④ 前司真实案例
优惠券查询接口慢调用比例 >50% 持续 5 次 → 熔断 30s，期间返回缓存优惠券（降级），30s 后放 1 个探测，成功则恢复。

### ⑤ 面试话术
「熔断器三态：**CLOSED 正常统计、OPEN 快速失败、HALF-OPEN 探测恢复**。失败率超阈值进 OPEN 保护下游，等 sleep window 过后放少量探测请求，成功回 CLOSED。前司优惠券服务 RT 飙到 1s 就熔断 30s，期间走降级缓存。」

---

## 4.3 🔴 熔断器对比：Hystrix vs Sentinel vs Resilience4j

### ① 对比表
| 维度 | Hystrix（停更） | Sentinel（阿里，主流） | Resilience4j |
|------|----------------|----------------------|--------------|
| 隔离策略 | 线程池（默认）/信号量 | **信号量**（轻量） | 信号量 |
| 熔断策略 | 异常比例 | **慢调用比例 + 异常比例** | 异常比例 |
| 实时统计 | 滑动窗口 | 滑动窗口 | 环形缓冲 |
| 动态规则 | 较弱 | **动态数据源（Nacos/ZK）** | 较弱 |
| 控制台 | Dashboard | **Sentinel Dashboard** | 无 |
| 限流 | 不支持 | **支持**（核心优势） | 不支持 |
| 维护状态 | 停更（维护模式） | 活跃 | 活跃 |

### ② 为什么选 Sentinel
- 一站式：限流+熔断+降级+系统保护。
- 信号量隔离无线程切换开销，性能高。
- 动态规则可热更新（接 Nacos）。

### ③ 前司真实案例
全公司统一 **Sentinel**，规则配在 Nacos，大促前动态调整阈值不用重启。

### ④ 边界
- Hystrix 线程池隔离**彻底但重**（线程切换开销），适合调用第三方不可控服务。
- Sentinel 信号量隔离**轻量**，适合内部服务调用。

### ⑤ 面试话术
「Hystrix 已停更，现在主流是 **Sentinel**。选 Sentinel 三理由：① 信号量隔离轻量无线程切换；② 限流熔断降级一站式；③ 规则可接 Nacos 动态热更新。前司全公司用 Sentinel，大促调阈值不用重启。」

---

## 4.4 隔离策略 🔴（线程池 vs 信号量）

### ① 为什么
多业务共享线程池，一个业务慢调用把池占满，其他业务全死。隔离=**给每个业务独立资源**，故障不扩散。

### ② 对比
| 策略 | 实现 | 优点 | 缺点 | 代表 |
|------|------|------|------|------|
| **线程池隔离** | 每资源独立线程池 | 彻底隔离、可异步超时 | 线程切换开销大 | Hystrix |
| **信号量隔离** | 计数器限并发 | 轻量、无线程切换 | 不能异步超时 | Sentinel |

### ③ 前司真实案例
- 秒杀下单、商品查询、优惠券各用独立线程池（Hystrix 风格），秒杀挂了不影响商品查询。
- 内部服务调用用 Sentinel 信号量隔离（轻量）。

### ④ 边界
- 调外部第三方（不可控、易超时）→ 线程池隔离。
- 内部服务（可控）→ 信号量隔离。

### ⑤ 面试话术
「隔离分两种：**线程池隔离彻底但重**（适合调第三方），**信号量隔离轻量**（适合内部调用，Sentinel 默认）。前司秒杀、商品、优惠券各自独立线程池，秒杀挂了不拖累商品查询。」

---

## 4.5 降级方案

### ① 为什么
系统压力极大时，保不全就**保核心**。降级是主动牺牲非核心功能换整体存活。

### ② 方案清单
1. 返回默认值/空列表。
2. 返回缓存（旧数据）。
3. 同步转异步（先返回"处理中"，后台处理）。
4. 关闭非核心功能（如关闭推荐、评论）。

### ③ 前司真实案例
大促 0 点压力峰值，主动**降级**：商品推荐、评论、浏览历史关闭，保下单+支付链路。优惠券查询降级返回本地缓存。

### ④ 边界
- 降级要有开关（配置中心），可手动/自动触发。
- 降级要可逆，压力下降要能恢复。

### ⑤ 面试话术
「降级就是保核心舍非核心。前司大促 0 点，我手动降级推荐、评论这些非核心，全力保下单。优惠券查询降级返回缓存。降级必须有开关，配在配置中心可热生效。」

---

# 第五篇 幂等 🔴🔴 必精通

## 5.1 为什么需要幂等

### ① 为什么
网络重试、用户重复点击、MQ 重复消费 → 同一请求执行多次。幂等保证**多次执行结果一致**。秒杀、支付这种**资金/库存**场景，不幂等=超卖/重复扣款。

### ② 前司真实案例
秒杀下单：用户疯狂点按钮、网络重试、MQ At-Least-Once 重复消费，没有幂等防护，同一用户可能下多单、扣多次库存。

### ③ 面试话术
「幂等就是**同一请求执行任意次结果一致**。秒杀、支付这种必须幂等，不然重复点击/重试/MQ 重复消费会导致超卖、重复扣款。」

---

## 5.2 幂等方案

| 方案 | 实现 | 适用 |
|------|------|------|
| **唯一约束** | 业务 ID 唯一键，重复插报错 | 插入 |
| **乐观锁（版本号）** | `UPDATE ... WHERE version=v` | 更新 |
| **状态机** | 校验状态流转 | 订单状态 |
| **Token 机制** | 服务端发 token，请求带 token，处理即失效 | 表单提交 |
| **分布式锁** | `SET id NX` 抢锁 | 通用 |
| **去重表** | msg_id 去重 | MQ 消费 |

### 前司组合方案（秒杀防重复下单）
1. **前端**：按钮置灰 3s。
2. **网关**：userId+activityId 维度分布式锁（Redis SETNX，TTL 5s）。
3. **DB**：订单表唯一索引（userId+activityId）。
4. **MQ 消费**：msg_id 去重表。

四道防线层层兜底，杜绝重复下单。

---

## 5.3 各操作幂等性 🔴

- SELECT、DELETE（按主键）：天然幂等。
- UPDATE 绝对值（`SET balance=100`）：幂等。
- UPDATE 相对值（`SET balance=balance+10`）：**不幂等**。
- INSERT：天然不幂等。

### ⑤ 面试话术
「幂等我用组合拳：DB 唯一索引兜底 + Redis 分布式锁前置过滤 + MQ 去重表。注意 **UPDATE 绝对值幂等、相对值( balance+10 )不幂等**，秒杀扣库存用 `WHERE num>0` 的乐观锁形式保证幂等+防超卖。」

---

# 第六篇 秒杀系统设计 🔴🔴🔴（前司核心亮点 · 综合实战题）

## 6.1 核心挑战

### ① 为什么
秒杀是**瞬时高并发 + 强一致 + 防欺诈**的极端场景，是高并发架构集大成者。面试官借此考察系统设计深度。

### ② 四大挑战
- 瞬时高并发（几秒 10 万+ QPS）。
- 防超卖（库存不能负）。
- 防黄牛（机器人）。
- 防缓存击穿。

---

## 6.2 🔴 分层架构（前司秒杀全链路）

### ② 原理图解
```
┌─────────────────────────────────────────────────────────────────┐
│ 1. 前端/客户端                                                  │
│    - 按钮置灰（点一次禁用几秒）                                  │
│    - 验证码（错峰 + 防机器人）                                   │
│    - 答题/小游戏（错峰）                                         │
│    - 资源静态化（CDN）                                           │
├─────────────────────────────────────────────────────────────────┤
│ 2. 网关层                                                       │
│    - 限流（用户维度、IP 维度、集群令牌桶）                       │
│    - 黑名单（黄牛账号/设备）                                     │
│    - 鉴权                                                       │
├─────────────────────────────────────────────────────────────────┤
│ 3. 服务层 ★三道防线                                             │
│    - 活动未开始/已结束 → 直接拒绝（前置校验）                    │
│    - 用户限购校验（Redis SETNX userId+activityId）               │
│    - ★防线1：Redis Lua 预扣库存（原子扣减，扣到 0 拒绝 99%）     │
│    - 扣减成功 → ★防线2：发 MQ 异步下单                          │
│    - 限流降级（Sentinel）                                       │
├─────────────────────────────────────────────────────────────────┤
│ 4. MQ 异步削峰                                                  │
│    - 消费者按 DB 能力匀速处理（漏桶）                            │
│    - 写订单、扣真实库存                                          │
│    - msg_id 去重保证幂等                                         │
├─────────────────────────────────────────────────────────────────┤
│ 5. DB 层 ★防线3                                                 │
│    - 库存表，乐观锁 / 行锁防超卖兜底                             │
│    - 分库分表（按租户/活动 hash）                                │
└─────────────────────────────────────────────────────────────────┘
```

### ③ 前司真实案例（核心亮点）
**我主导设计开发了前司促销秒杀活动系统，支撑 10 万+并发**。核心设计：
1. **三道防线防超卖**：
   - 防线1（Redis Lua 预扣）：99% 请求在 Redis 拦截，扣到 0 立即返回"售罄"。
   - 防线2（MQ 异步）：扣减成功的请求发 MQ，消费者匀速落库（削峰）。
   - 防线3（DB 乐观锁）：`UPDATE ... WHERE num>0` 兜底，万一前两层漏网，DB 层保证不超卖。
2. **性能成果**：接口 **RT 从 2s 降到 400ms**，高峰**缓存命中 85%**。

### ⑤ 面试话术
「我主导设计了前司秒杀系统，10 万+并发。核心是**三道防线**：① Redis Lua 预扣库存拦 99% 请求；② MQ 异步削峰落库；③ DB 乐观锁兜底防超卖。配合限流+防刷+幂等，RT 从 2s 压到 400ms。这是典型的'缓存+异步+兜底'架构。」

---

## 6.3 🔴 防超卖的核心（三道防线代码）

### 防线1：Redis 预扣（Lua 原子）
```lua
-- KEYS[1]=库存key, ARGV[1]=扣减数量
local stock = tonumber(redis.call("get", KEYS[1]))
if stock == nil or stock < tonumber(ARGV[1]) then
    return 0  -- 库存不足，扣到 0 立即拦截 99% 请求
end
redis.call("decrby", KEYS[1], ARGV[1])
return 1  -- 扣减成功
```

### 防线2：MQ 异步削峰
```java
// 服务层：Redis 扣减成功后发 MQ
public OrderResult trySeckill(Long userId, Long activityId) {
    // 1. 限购校验（防重复）
    if (!redis.setIfAbsent("bought:" + activityId + ":" + userId, "1", 24, HOURS)) {
        return OrderResult.fail("每人限购1件");
    }
    // 2. Redis Lua 预扣库存（防线1）
    Long stock = redisTemplate.execute(seckillScript, 
        Collections.singletonList("stock:" + activityId), 1);
    if (stock == 0L) return OrderResult.fail("售罄");
    // 3. 发 MQ 异步下单（防线2）
    mqTemplate.send("seckill_order_topic", new SeckillOrderMsg(userId, activityId));
    return OrderResult.success("抢购成功，订单生成中");
}

// MQ 消费者：匀速落库（漏桶保护 DB）
@RocketMQMessageListener(topic = "seckill_order_topic", ...)
public class SeckillOrderConsumer {
    public void onMessage(SeckillOrderMsg msg) {
        // msg_id 去重（幂等）
        if (dedupDao.exists(msg.getMsgId())) return;
        // 防线3：DB 乐观锁扣库存
        int rows = stockDao.deductWithOptimisticLock(msg.getActivityId());
        if (rows == 0) {
            // DB 层超卖兜底（理论上 Redis 已拦，极少走到）
            redisTemplate.opsForValue().increment("stock:" + msg.getActivityId());
            return;
        }
        orderDao.create(msg);  // 创建订单
    }
}
```

### 防线3：DB 兜底（乐观锁）
```sql
UPDATE stock SET num = num - 1 WHERE sku_id = ? AND num > 0
-- 影响行数 0 = 超卖，回滚
```

### ④ DB 性能优化
- 分库分表（按活动 hash）。
- 热点商品单独表，避免锁冲突。
- 库存表只放库存字段，行锁粒度小。

---

## 6.4 库存回滚

### ① 为什么
用户抢到不支付会"占坑不拉屎"，导致真实想买的买不到。需要超时回滚释放库存。

### ② 实现
- 订单超时未支付 → **延时消息**（RocketMQ 延时级别 / Redis ZSet 定时扫）触发回滚。
- 回滚：`stock +1`（Redis + DB 双回滚）。

### ③ 前司真实案例
秒杀订单 15 分钟未支付，RocketMQ 延时消息触发回滚 Redis + DB 库存，重新放入可售池。

### ⑤ 面试话术
「库存回滚我用 **RocketMQ 延时消息**，订单 15 分钟未支付自动触发 Redis+DB 双回滚，重新放入可售池。不用定时扫表，延时消息精准且不占 DB。」

---

## 6.5 防刷（风控）

### ① 为什么
黄牛用机器人脚本刷单，正常用户抢不到。防刷=**识别并拦截非正常用户**，是秒杀公平性保障。

### ② 多维度防刷体系
```
前端层：验证码 / 答题 / 滑块（增加脚本成本）
网关层：IP/设备维度限流、黑名单（黄牛账号库）
应用层：用户限购（每人限 1 件）Redis SETNX
风控层：行为分析（同设备多账号、下单速度异常 → 拦截/加验）
```

### ③ 前司真实案例
- **用户限购**：`SETNX bought:activityId:userId`，TTL 24h，每人限 1 件。
- **IP/设备限流**：网关层单 IP 单设备 QPS 限制。
- **验证码**：抢购前强制滑块验证。
- **黑名单**：历史黄牛账号直接拒绝。

### ⑤ 面试话术
「防刷我做了四层：① 用户限购 Redis SETNX 每人限 1 件；② IP/设备维度限流；③ 验证码/滑块增加脚本成本；④ 黑名单拦截黄牛。秒杀是 2C 场景，防刷和防超卖同等重要。」

# 第七篇 高可用架构 🔴

## 7.1 高可用设计原则（六大武器）

### ① 为什么
线上故障不可避免（硬件损坏、网络抖动、代码 bug），高可用=**故障发生时系统仍能提供服务**。目标不是"不挂"，而是"挂了用户无感"。

### ② 六大原则
| 原则 | 含义 | 实现 |
|------|------|------|
| **冗余** | 多副本，单点不致命 | 主从、集群、多机房 |
| **故障转移** | 主挂自动切备 | 哨兵、VIP 漂移、健康检查 |
| **限流** | 超量拒绝保整体 | 令牌桶、Sentinel |
| **降级** | 牺牲非核心 | 配置开关 |
| **熔断** | 下游故障快速失败 | Sentinel、Hystrix |
| **隔离** | 故障不扩散 | 线程池/信号量/物理隔离 |

### ③ 前司真实案例
- **冗余**：Redis 主从哨兵、MySQL 主从、应用多副本。
- **故障转移**：Redis 哨兵自动主从切换、Nginx 健康检查剔除故障节点。
- **限流降级熔断**：Sentinel 全链路。
- **隔离**：核心（下单/支付）与非核心（推荐/评论）独立部署、独立 DB。

### ⑤ 面试话术
「高可用我总结六个字：**冗余、转移、保护**。冗余是多副本（Redis 主从、应用多实例）；转移是故障自动切（哨兵选主）；保护是限流+降级+熔断+隔离。前司核心下单链路和非核心推荐评论物理隔离，大促时非核心降级不影响下单。」

---

## 7.2 多活/容灾

| 方案 | 说明 | 成本 | RTO |
|------|------|------|-----|
| **冷备** | 备机不运行，故障切换启动 | 低 | 小时级 |
| **热备** | 备机运行不接流量，同步数据 | 中 | 分钟级 |
| **双活** | 两机房都接流量，互备 | 高 | 秒级 |
| **同城双活** | 同城两机房，低延迟，机房级容灾 | 中高 | 秒级 |
| **异地多活** | 不同城市多机房，城市级容灾 | 极高 | 秒级 |

### ⑤ 面试话术
「容灾等级：冷备→热备→双活→同城双活→异地多活，成本递增、RTO 递减。金融级要异地多活（城市级容灾），普通业务同城双活够用。前司是同城双活+异地冷备，性价比平衡。」

---

## 7.3 🔴 单元化架构（异地多活主流）

### ① 为什么
传统异地多活全量数据同步，延迟大、冲突多。单元化按**用户维度分片**，每个单元自洽，跨单元调用最小化，是异地多活工业级方案。

### ② 原理图解
```
                      ┌─── 单元A（北京）── 用户A、C 的全链路
用户请求 → 路由层 ─────┤   （App + DB + Redis 完整闭环）
（按 userId 路由）      │
                      └─── 单元B（杭州）── 用户B、D 的全链路
                          （App + DB + Redis 完整闭环）

单元间：DTS/Canal+MQ 双向同步（仅全局数据，如商品库）
```

### ③ 核心要点
- 按用户维度（如 userId）路由到固定"单元"。
- 每个单元是完整闭环（应用 + DB + 缓存），核心数据按用户分片。
- 跨单元调用最小化，单元内自洽。
- 单元间数据双向同步（DTS / Canal+MQ）。
- 故障切换单元流量到其他单元。

### ④ 挑战
- 数据同步延迟。
- 全局唯一数据（如库存、账号）。
- 跨单元事务。

### ⑤ 面试话术
「单元化是异地多活工业级方案。核心：按 userId 路由到固定单元，每个单元是完整闭环（App+DB+Redis），单元内自洽、跨单元调用最小化。单元间用 DTS 双向同步全局数据。阿里、字节都这么搞。挑战是全局唯一数据（库存）和跨单元事务。」

---

## 7.4 数据同步方案 🟡

- **同步**：MySQL 主从复制、DTS。
- **异步**：Canal 订阅 binlog → MQ → 异地写。
- **关键**：核心数据强一致（金融），非核心最终一致。

# 第八篇 多租户架构（SaaS 核心，前司必考）

## 8.1 什么是多租户

### ① 为什么
前司是 SaaS 茶饮平台，服务**近百万家门店（品牌）**。多租户=**一套软件服务多个客户（租户），数据互相隔离**。核心矛盾：**隔离性 vs 资源利用率**。

### ② 三种架构模式
| 模式 | 说明 | 隔离性 | 成本 | 适用 |
|------|------|--------|------|------|
| **独立 DB** | 每租户独立数据库 | 最强 | 最高 | 大客户/金融 |
| **共享 DB 独立 Schema** | 同库不同 Schema | 中 | 中 | 中等客户 |
| **共享 DB 共享 Schema** | 同表加 tenant_id | 弱 | 最低 | 小客户/SaaS 主流 |

### ③ 前司真实案例（门店商品多租户）
前司采用**共享 Schema + tenant_id（品牌/门店 ID）**模式：
- 所有业务表带 `tenant_id`（品牌 ID）字段。
- MyBatis 拦截器**自动拼接 `WHERE tenant_id=?`**，避免漏写导致跨租户数据泄露。
- 大客户（如连锁头部品牌）可单独 DB/Schema 独立部署。

### ④ 边界
- 共享 Schema 必须防"租户越权"：所有 SQL 强制 tenant_id 过滤（拦截器兜底）。
- 大客户资源倾斜：独立 DB 或独立集群。

### ⑤ 面试话术
「前司是 SaaS，近百万家门店。我用**共享 Schema + tenant_id**模式，所有表带品牌 ID，MyBatis 拦截器自动拼 WHERE 条件防越权。大客户（头部连锁）独立部署。多租户核心是**隔离性 vs 成本**的权衡。」

---

## 8.2 多租户关键技术

### ② 实现

```java
    public Object intercept(Invocation invocation) throws Throwable {
        // 获取当前登录租户

        BoundSql boundSql = ...; // 改写 SQL

    }
}
```

### ③ 资源隔离维度
- **数据隔离**：tenant_id / 独立 Schema / 独立 DB。
- **资源隔离**：大租户独立线程池、限流配额（防某租户拖垮全局）。
- **配置隔离**：每租户独立配置（功能开关、限流阈值）。

# 第九篇 稳定性建设（资深/架构师必备）🔴

## 9.1 全链路监控

### ① 为什么
"没监控等于裸奔"。故障发现要快（秒级告警），定位要准（链路追踪），靠**可观测性三大支柱**。

### ② 三大支柱
- **Metrics 指标**（Prometheus + Grafana）：QPS、RT、错误率、资源。
- **Logging 日志**（ELK/Loki）：详细记录。
- **Tracing 链路**（SkyWalking/Zipkin/Jaeger）：跨服务调用链。

**黄金信号**：延迟、流量、错误、饱和度。

### ③ 前司真实案例
Prometheus + Grafana 看大盘，SkyWalking 看调用链，ELK 查日志。秒杀接口 P99 超 500ms 钉钉告警，DB CPU >80% 告警。

### ⑤ 面试话术
「监控三大支柱：**Metrics（Prometheus）、Logging（ELK）、Tracing（SkyWalking）**。黄金信号看延迟、流量、错误、饱和度。前司所有核心接口 P99、错误率、DB CPU 都有钉钉告警，故障秒级发现。」

---

## 9.2 全链路压测 🔴

### ① 为什么
线上容量不测不知道，大促前不压测=裸奔大促。压测找瓶颈、定容量、验证扩容方案。

### ② 关键技术
- **影子库/影子表**：压测数据隔离，不污染生产。
- **流量录制回放**（GoReplay）：录真实流量回放。
- **目的**：找瓶颈、定容量、验证扩容。

### ③ 前司真实案例
每次大促前全链路压测：模拟 10 万并发，压出库存服务瓶颈，提前扩容。影子库表带 `_test` 后缀，压测流量打标记路由到影子库。

### ⑤ 面试话术
「大促前必全链路压测。核心：① 影子库表隔离压测数据不污染生产；② 流量录制回放真实场景。前司每次大促前压到 10 万并发找瓶颈，库存服务每次都是重点扩容对象。」

---

## 9.3 容量评估 🔴

### ① 步骤
1. 估算峰值 QPS（日均 × 系数，大促再放大）。
2. 单机容量 = QPS ÷ 机器数，留 30% 余量。
3. 找出瓶颈（CPU/IO/DB）。
4. 评估依赖容量（DB 连接、Redis、下游接口）。

### ② 用 Little's Law
QPS=10万，单机 2000 QPS，需 50 台，留 30% 余量 → 65 台。

### ③ 前司真实案例
大促秒杀预估 10 万 QPS，按单机 2000 QPS 算需 50 台，留余量扩到 65 台。DB 连接池每机 50，Redis Cluster 10 节点。

### ⑤ 面试话术
「容量评估四步：① 估峰值 QPS（日均×大促系数）；② Little's Law 算并发；③ 单机容量÷机器数留 30% 余量；④ 评估 DB/Redis/下游依赖。前司秒杀按 10 万 QPS、单机 2000 算，配 65 台机器。」

---

## 9.4 故障应急预案 SOP 🟡

### ① 为什么
故障发生时人心慌，没有 SOP 容易乱操作扩大故障。预案让止血标准化、可执行。

### ② SOP 核心
- **预案**：常见故障的处理步骤（限流、降级、重启、回滚）。
- **演练**（混沌工程 Chaos Monkey）：主动注入故障验证容错。
- **快速恢复**：灰度发布、蓝绿部署、金丝雀。

### ⑤ 面试话术
「故障 SOP 三板斧：**限流降级回滚**。预案提前写在 runbook 里，新人都按步骤操作。蓝绿/金丝雀发布保证回滚快。前司定期混沌工程演练，主动 kill 服务验证容错。」

---

## 9.5 🔴 故障复盘

### ① 为什么
故障不复盘=还会再犯。复盘不是甩锅，是**找根因 + 落地改进**，让同类故障不再发生。

### ② 复盘四步
**TimeLine**：发生 → 发现 → 响应 → 恢复。
**5 Why 分析**：找根因（不是甩锅）。
**改进措施**：监控告警、流程、代码、架构，跟踪到关闭。

### ③ 黄金法则
- 发现要快（监控告警）。
- 止血要快（限流降级回滚）。
- 根因要透（5 why）。
- 改进要落地（不复发）。

### ⑤ 面试话术
「故障复盘四步：TimeLine 还原 → 5 Why 找根因 → 改进措施 → 跟踪到关闭。核心是**对事不对人**。我主导过几次秒杀故障复盘，每次都落地监控告警+架构改进，同类故障没再犯。」

---

# 第十篇 经典问题排查套路 🔴

## 10.1 接口变慢排查

### ① 套路
```
1. 是单接口慢还是全局慢？
   全局慢 → 机器资源（CPU/内存/网络/GC）
   单接口 → 该接口依赖
2. 单接口：链路追踪看每个 Span 耗时
   - DB 慢查询？慢 SQL + 锁等待 + 大结果集
   - 下游接口超时？
   - 外部依赖（Redis、MQ）？
3. JVM：GC 频繁？FullGC？
4. 网络：带宽、丢包、RTT？
5. 锁竞争：线程 BLOCKED？
```

### ③ 前司真实案例（RT 2s → 400ms）
商品详情接口 RT 2s，排查：SkyWalking 看到优惠券计算 Span 占 1.5s → 优惠券聚合查询 N+1 → 改批量查询 + 缓存 → RT 降到 400ms。

### ⑤ 面试话术
「接口变慢我按'单接口 vs 全局'分流。单接口靠 SkyWalking 看 Span 定位。前司商品详情 RT 2s，链路追踪定位到优惠券 N+1 查询，改批量+缓存压到 400ms。**先定位再优化，不瞎猜**。」

---

## 10.2 数据库慢查询优化

### ① 套路
```
1. 开慢查询日志
2. explain 看 type/key/rows/Extra
3. 优化方向：
   - 加索引 / 改联合索引 / 避免索引失效
   - 大分页 → 游标
   - 避免 SELECT *，用覆盖索引
   - 拆 SQL，避免 join 过多
   - 分库分表
4. 验证：再 explain，看 RT
```

### ⑤ 面试话术
「慢 SQL 优化：先 explain 看 type（要 ref/range 以上）、key（走没走索引）、rows（扫描行数）、Extra（是否临时表/文件排序）。常见坑：索引失效（函数/隐式转换/最左前缀）、大分页（改游标）、SELECT *（用覆盖索引）。」

---

## 10.3 雪崩排查与止血 🔴

### ① 套路
```
现象：一个服务挂，整条链路雪崩
根因：同步调用 + 无熔断 + 资源耗尽（线程池满）
止血：
  1. 限流（网关 + 应用双层）
  2. 降级非核心
  3. 隔离故障服务
  4. 扩容
根因：补熔断、超时、重试、降级、舱壁隔离
```

### ⑤ 面试话术
「雪崩根因：**同步调用+无熔断+线程池耗尽**。止血四步：限流→降级→隔离→扩容。根因修复必补：熔断+超时+舱壁隔离。记住：超时+熔断是防雪崩的左膀右臂。」

---

# 第十一篇 实战案例（前司 STAR 复盘）

## 📌 案例 1：缓存击穿打挂 DB

**现象**：热点商品促销，缓存过期瞬间 DB 被打满。
**S**：大促 0 点，商品详情接口 RT 飙升，DB CPU 100%。
**T**：紧急止血 + 根因修复。
**A**：
1. 止血：临时对该商品接口加限流（Sentinel 单机 500 QPS）。
2. 排查：链路发现 Redis miss → 全部打到 DB（缓存击穿）。
3. 修复：
   - 热点 key 改**永不过期** + 后台异步刷新（逻辑过期）。
   - 加**互斥锁**（单飞，只放一个查 DB 重建缓存）。
   - 大促前预热所有热点。
**R**：DB CPU 降到 30%，接口 RT 恢复。

### ⑤ 面试话术
「缓存击穿=热点 key 过期瞬间大量请求穿透到 DB。我处理过：先限流止血，根因修复用**逻辑过期+互斥锁**（只放一个请求查 DB 重建），大促前提前预热热点 key。」

---

## 📌 案例 2：服务雪崩

**现象**：支付服务调风控服务超时，导致整个支付链路阻塞。
**S**：风控服务 GC 抖动响应变慢，支付服务线程池打满 → 雪崩。
**T**：止血。
**A**：
1. 止血：手动降级风控（跳过风控直接放行，事后补偿）。
2. 排查：链路看风控 RT 从 50ms → 5s，支付调用堆积 → 线程池满 → 拒绝服务。
3. 根因修复：
   - 加**熔断**（Sentinel，风控 RT 超 1s 熔断 30s）。
   - 加**超时**（Feign readTimeout 1s）。
   - 加**降级**（风控挂了走默认规则）。
   - 风控服务优化 GC（换 G1，调堆）。
**R**：后续风控抖动不再影响支付。

### ⑤ 面试话术
「服务雪崩我经历过：风控 GC 抖动 RT 5s，支付线程池满。止血先降级风控（事后补偿），根因修复加熔断+超时+降级三件套，风控也优化 GC 换 G1。核心教训：**调用下游必须超时+熔断**。」

---

## 📌 案例 3：Full GC 导致接口抖动

**现象**：订单接口 P99 偶发 3s。
**排查**：
1. Grafana GC 看每 10 分钟一次 Full GC，停顿 800ms。
2. dump 分析：本地缓存 `Map` 累积 2GB（没设淘汰）。
3. 对象进老年代，Mixed GC 回收慢。
**解决**：
- 缓存改 **Caffeine**（限制大小 + LRU）。
- JVM：`-XX:InitiatingHeapOccupancyPercent=35` 提前标记。
**结果**：Full GC 消失，P99 稳定 200ms。

### ⑤ 面试话术
「接口 P99 偶发抖动，看 GC 日志发现每 10 分钟 Full GC 800ms。dump 发现本地缓存 Map 没 LRU 涨到 2GB。改 Caffeine 限大小 + 调 IHOP 提前标记，Full GC 消失。教训：**本地缓存必须设淘汰策略**。」

---

## 📌 案例 4：分库分表后深分页爆炸

**现象**：订单后台翻到 100 页后超时。
**排查**：`LIMIT 1000000, 20` 在分片下，每片都扫 1000020 行回应用层归并 → 慢。
**解决**：改游标分页（`WHERE id > last_id LIMIT 20`），后台场景可接受。

### ⑤ 面试话术
「分库分表深分页炸了：`LIMIT 1000000,20` 每片扫百万行。改游标分页 `WHERE id>last_id`，深分页问题根治。」

# 第十二篇 性能优化总纲 🔴

## 12.1 优化层次（从上到下，收益递减）
```
1. 业务优化（最大收益）
   - 减少不必要的调用、合并请求、异步化、批量化
2. 架构优化
   - 缓存、MQ、读写分离、分库分表、CDN
3. 代码优化
   - 算法数据结构、减少对象创建、连接池复用
4. JVM 优化
   - GC 调优、参数
5. OS / 硬件
   - 网络内核参数、磁盘、CPU
```

**铁律**：**先业务后技术，先架构后代码，先测量后优化**（别瞎优化，Profile 找瓶颈）。

### ⑤ 面试话术
「性能优化按收益排序：**业务>架构>代码>JVM>硬件**。前司 RT 2s→400ms 主要是架构层（Redis 预扣+MQ 异步），不是抠代码细节。铁律：先测量后优化，Profile 找瓶颈再动手。」

---

## 12.2 优化方法论
1. **量化现状**：RT/QPS/CPU/内存 baseline。
2. **定位瓶颈**：Profile（arthas、async-profiler、火焰图）。
3. **假设验证**：改一处测一处（控制变量）。
4. **回归验证**：防止优化破坏正确性。
5. **持续监控**：优化后跟踪，防退化。

# 高频追问清单（自测）

1. 高并发三板斧？你做过的最高 QPS 系统怎么设计？🔴🔴
   - 答：前司秒杀 10 万+并发，Redis 预扣 + MQ 异步 + DB 乐观锁三道防线。
2. Little's Law？容量怎么估？为什么看 P99？🔴
   - 答：并发=QPS×RT；P99 看用户体验下限，平均掩盖长尾。
3. 缓存一致性怎么保证？为什么删不是更新？先 DB 还是先缓存？🔴🔴
   - 答：先更新 DB 再删缓存 + Canal 补偿；删是幂等惰性的。
4. 缓存穿透/击穿/雪崩 区别和解法？🔴
   - 答：穿透=查不存在（布隆过滤）；击穿=热点 key 过期（互斥锁）；雪崩=大批 key 同时过期（随机 TTL）。
5. 漏桶 vs 令牌桶？怎么选？🔴🔴
   - 答：漏桶控出匀速（保护下游），令牌桶控入允许突发（入口限流）。
6. 限流算法实现（滑动窗口/令牌桶代码）？分布式限流怎么实现？🔴🔴
   - 答：滑动窗口子桶轮转统计；令牌桶按时间补令牌；分布式用 Redis+Lua 原子 incr。
7. 熔断器三状态？熔断和降级区别？🔴
   - 答：CLOSED→OPEN→HALF-OPEN；熔断是下游故障快速失败，降级是牺牲非核心。
8. 幂等怎么实现？UPDATE balance+10 幂等吗？🔴🔴
   - 答：唯一索引+分布式锁+去重表；UPDATE 绝对值幂等，相对值(balance+10)不幂等。
9. 秒杀系统怎么设计？怎么防超卖？防刷？🔴🔴🔴
   - 答：三道防线（Redis Lua 预扣→MQ 异步→DB 乐观锁）；防刷（限购+限流+验证码+黑名单）。
10. 异地多活怎么做？单元化架构核心？🔴
    - 答：按 userId 分片到单元，单元内闭环，跨单元同步最小化。
11. 接口变慢怎么排查？给出完整步骤。🔴🔴
    - 答：单接口 vs 全局 → SkyWalking 看 Span → DB/JVM/网络/锁。
12. 一个服务挂导致雪崩，怎么止血？🔴🔴
    - 答：限流→降级→隔离→扩容，根因补熔断+超时。
13. 你做过哪些性能优化 / 稳定性建设？（STAR 量化）🔴🔴
    - 答：RT 2s→400ms（Redis 预扣+MQ 异步）；缓存命中 85%；秒杀 10 万并发。
14. 容量评估怎么做？怎么估机器数？🔴
    - 答：Little's Law + 单机容量 + 30% 余量。
15. 多租户怎么做数据隔离？🔴
    - 答：共享 Schema + tenant_id + MyBatis 拦截器自动拼接 WHERE。
