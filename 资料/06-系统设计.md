# 第一章 系统设计方法论 🔴（先掌握框架再做题）

## 1.1 标准答题框架（7 步法）

```
Step 1 澄清需求（Clarify）—— 3-5 分钟
  - 核心功能是什么？（用户场景）
  - 用户量级？QPS？数据量？（规模）
  - 读写比例？峰值？（负载特征）
  - 一致性要求？延迟要求？（质量属性）

Step 2 估算容量（Estimate）—— 3-5 分钟
  - QPS 估算（DAU × 人均次数 ÷ 86400 × 峰均比）
  - 存储估算（每天新增 × 保留时间）
  - 带宽、连接数

Step 3 高层设计（High-level）—— 5-10 分钟
  - 画核心组件框图（客户端→网关→服务→存储）
  - 说明数据流

Step 4 详细设计（Deep Dive）—— 15-20 分钟
  - 数据模型（表结构）
  - 核心接口
  - 关键算法/流程
  - 按面试官兴趣点深入

Step 5 扩展性（Scale）—— 5-10 分钟
  - 缓存、MQ、分库分表、CDN
  - 瓶颈识别与解决

Step 6 可靠性（Reliability）—— 5 分钟
  - 单点、容灾、限流熔断、监控

Step 7 总结与权衡（Wrap up）
  - 复述方案
  - 讲取舍（为什么这么选，替代方案的代价）
```

**口诀**：**"问清楚 → 估容量 → 画框架 → 深入核心 → 扩展容灾 → 讲权衡"**

## 1.2 必背估算数字 🔴

| 操作 | 延迟 |
|------|------|
| L1 缓存 | 1 ns |
| 主存访问 | 100 ns |
| SSD 随机读 | 100 μs |
| 局域网 RTT | 0.5 ms |
| 同机房 DB 查询 | 1-5 ms |
| 跨机房 RTT | 几十 ms |
| 跨城 RTT | 几十-100 ms |

| 单机能力（粗估） |
|-----------------|
| Web QPS：1k-1w |
| MySQL QPS：1k-1w（读高写低） |
| Redis QPS：10w+ |
| Kafka 单 broker：10w+ msg/s |

**估算口诀**：
- DAU 100w，每人每天 10 次 → 日请求 1000w → 平均 QPS = 1000w/86400 ≈ 115，峰值 ×5-10 → 600-1200。
- 一条业务数据 1KB，日增 100w 条 → 1GB/天，保留 1 年 → 365GB。
- 单库千万行级别，超过就考虑分表。

## 1.3 通用架构图（背下来）🔴

```
                      ┌─ CDN ─┐
                      │       ↓
用户 → LB(高可用) → 网关 ─→ 服务集群(无状态，弹性扩缩)
                      │       ↓
                      │   注册中心 / 配置中心
                      │       ↓
                      │   ┌─ Redis 缓存
                      │   ├─ MySQL(主从/分库分表)
                      │   ├─ MQ(异步)
                      │   └─ ES(搜索)
                      │
                      └─ 监控(Prometheus+Grafana) / 日志(ELK) / 链路(SkyWalking)
```

# 第二章 经典系统设计题（详细方案）

## 2.1 🔴🔴 短链系统（经典入门）

**Step 1 澄清**：长→短生成、短→长跳转。日新增 1 亿，读 QPS 10w 写 1w。

**Step 2 估算**：5 年存储 ≈ 1亿×365×5 = 1825 亿条，每条 500B → ≈ 90TB（分库分表）。读 QPS 10w → Redis 缓存 + 多副本。

**Step 3 高层**：
```
发号器 → 生成短码 → 存(短码→长链) → 返回
访问短链 → 查缓存 → 302 重定向
```

**Step 4 核心**：

**短码生成** 🔴：
- 方案 A：**发号器**（自增 ID → 62 进制：0-9a-zA-Z）。短、有序、不重复。6 位 = 62^6 ≈ 568 亿。
- 方案 B：MD5/哈希取前 6-8 位。可能冲突，要查重。
- 方案 C：预生成池（离线批量生成存 DB，用的时候取）。
- 推荐 A。

**301 vs 302？** 🔴
- 301 永久重定向：浏览器缓存，下次不访问短链服务 → 省服务器压力，但**统计不到访问量**。
- 302 临时重定向：每次都访问短链服务 → 能统计，但压力略大。
- 业务要统计访问就用 302。

**缓存**：热点短链放 Redis，命中率 90%+。

**扩展**：布隆过滤器快速判断短码是否存在（防穿透）；分库分表（按短码 hash）。

## 2.2 🔴🔴 秒杀系统

（完整方案见 `资料/05-高并发高可用.md` 第六篇）

核心：Redis Lua 预扣（拦 99%）+ MQ 异步下单 + DB 乐观锁兜底（WHERE num>0）+ 防刷。

**架构图**：
```
用户 → 网关(限流) → 秒杀服务
                      ├─ Redis Lua 预扣库存（拦截 99%）
                      ├─ 扣减成功 → 发 MQ
                      └─ 失败 → 直接返回"抢光了"
MQ 消费者 → 写订单 + 扣真实库存（DB WHERE num>0 兜底）
订单超时 → 延时消息回滚库存
```

## 2.3 🔴 Feed 流（朋友圈/微博时间线）

**核心挑战**：如何让用户看到关注人的最新内容。

**三种模式** 🔴🔴：
| 模式 | 写 | 读 | 适用 |
|------|----|----|------|
| **拉（Pull）** | 不推，读时实时拉关注人最新 | 读时聚合，慢 | 写少读少 |
| **推（Push/扇出写）** | 发帖推到所有粉丝收件箱 | 读自己收件箱，快 | 粉丝适中（普通用户） |
| **推拉结合** | 普通人推，大 V 拉粉丝收件箱 | 大 V 粉丝读时合并 | 微博典型 |

**微博典型架构**：
- 普通人发帖 → 推送到粉丝 inbox（Redis ZSet 存 postId，score=时间戳）。
- 大 V 发帖 → 不推（粉丝千万推不动），粉丝读时拉大 V 帖子 + 自己 inbox 合并。

**收件箱设计**：Redis ZSet，score=时间戳，member=postId。读时 `ZREVRANGE` 分页。

**避免大 V 热点**：大 V 帖子存独立结构，粉丝 timeline 按需拉取合并。

---

## 2.4 🔴 排行榜

**方案演进**：
- DB `ORDER BY score DESC LIMIT`：数据量大慢。
- **Redis ZSet**：天然有序，`ZADD/ZREVRANGEBYSCORE`，单机十万级成员。
- **分桶 ZSet**：超大规模按维度分桶（地区榜、全国榜）。
- **实时更新**：用户行为（积分）异步累加 → Redis。

**Top N 高效**：Redis ZSet + 分页，亿级用户可分片（按 score 范围/用户 hash）。

## 2.5 🔴 IM / 消息推送系统

**核心难点**：
1. **消息可达性**（不丢、不重、有序）。
2. **长连接维护**（心跳、断线重连）。
3. **多端同步**。

**架构** 🔴：
```
客户端 ←→ 接入层(WebSocket/长连接网关) ←→ 消息路由
                                            ↓
                            消息存储(写库 + 离线消息) + 推送(在线推/离线存)
```

**消息可达性** 🔴🔴：
- **客户端 ACK**：服务端发出 → 客户端 ACK → 服务端删离线消息。
- **消息 ID + 序号**：客户端去重、排序。
- **离线消息**：未 ACK 的存离线消息表，下次上线拉取。
- **QoS 等级**（参考 MQTT）：0 至多一次、1 至少一次、2 恰好一次。

**多端同步**：每个会话维护一个**自增 sequence**，客户端上报 last_seq，服务端返回 > last_seq 的消息。

**长连接**：Netty/自研网关，单机维持几十万连接（epoll + 内存优化，连接对象精简）。

## 2.6 🔴 延迟任务平台

**需求**：订单 30 分钟未支付自动取消、定时推送。

**方案对比**：
| 方案 | 优 | 劣 |
|------|----|----|
| DB 轮询 | 简单 | 慢、压 DB |
| Redis ZSet | 简单 | 需扫描、重启丢 |
| **时间轮（HashedWheelTimer）** | 高效 | 单机，重启丢 |
| RocketMQ 延时消息 | 可靠 | 等级固定（RocketMQ 5.x 支持任意延时） |
| 自建延迟队列（多级时间轮 + 持久化） | 灵活 | 复杂 |

**时间轮原理** 🟡：
```
一个轮 = 数组（slot 数固定），每个 slot 挂任务链表
指针每 tick（如 100ms）走一格
任务落到 (currentTime + delay) % slotNum 格
大延迟用多层（小时轮 + 分钟轮 + 秒轮）
```
企业级：Redis ZSet（score=执行时间戳）+ 多线程扫描 + 持久化兜底；或 RocketMQ 5.x 任意延时消息。

## 2.7 🔴 抢红包

类似秒杀 + 随机金额算法。

**二倍均值法**（保证公平）🔴：
```
每次抢：金额 = random(0.01, 剩余总额 / 剩余人数 × 2)
最后一个：剩余全部
```
例：100 元 10 人，第一人 random(0.01, 100/10×2=20)，假设抢 15 元；第二人 random(0.01, 85/9×2≈18.9)...

Redis 预扣（原子扣份额 + 记录已抢用户防重复）+ MQ 异步落库 + 防刷。

## 2.8 🔴 12306 余票

**核心难点**：余票扣减防超卖 + 海量查询。

- **查询**：走缓存/ES，余票预聚合（按车次+日期）。
- **购票**：库存表分库分表（按车次 hash），Redis 预扣 + DB 行锁兜底。
- **难点**：**区间票**（A→B→C，买 A→B 影响 B→C）——按区间建模余票，每个区间一个库存。
- **排队**：高峰期（春运）用 MQ 削峰 + 排队提示。

## 2.9 🔴 监控告警系统

```
采集（Agent / Prometheus exporter）→ 传输（Kafka）→ 存储（TSDB：Prometheus/InfluxDB/Druid）
→ 计算（告警规则引擎）→ 通知（邮件/短信/钉钉/电话）
```
**重点**：
- **时序数据存储**：写多读多，按时间序列。Prometheus 自研 TSDB，InfluxDB 专用。
- **告警风暴抑制**：同一故障触发多个指标告警，需**聚合**（group by service/alert）+ **收敛**（去重、限频）。

## 2.10 🔴 分布式 ID 服务

- 雪花算法（41 时间 + 10 机器 + 12 序列）+ ZK 分配 workerId。
- 或美团 Leaf（segment 双 buffer + snowflake）。
- 时钟回拨：拒绝/等待/记录历史最大时间戳。
- 服务化：独立 ID 服务 + 本地缓存号段（降 DB 压力）。

## 2.11 🔴 限流平台

- 配置中心 + 规则下发 + 多维度（接口/用户/IP/集群）+ 监控。
- 实现：Sentinel / 自研 Redis+Lua。
- 控制台可视化 + 动态调阈值。

## 2.12 🔴 配置中心

- 长轮询推送（hold 30s，变更立即返回）。
- 多环境隔离（命名空间/Group/DataID）。
- 灰度发布、权限、版本回滚。
- 参考 Apollo / Nacos。

**架构**：
```
应用 → 配置中心客户端（长轮询）→ 配置中心服务端
                                        ↓
                                    配置存储（DB）
                                    管理后台（灰度/权限/审计）
```

---

## 2.13 🔴 抢券/优惠券系统

- **券模板**（总量、限领、有效期）。
- **领券**：Redis 预扣防超发（Lua 原子）。
- **用券**：核销幂等（唯一约束）。
- **防刷**：用户限领、IP 限流、黑名单。
- **架构**：
```
领券 → Redis 预扣（剩余量原子减）→ 写用户券表（唯一约束防重领）
用券 → 校验状态（未使用）→ 核销（状态机 + 乐观锁）→ 更新订单
过期 → 延时任务回滚库存
```

---

## 2.14 🔴 亿级数据报表

- **实时**：Flink 实时聚合 + Druid/ClickHouse 查询。
- **离线**：Hadoop/Hive T+1。
- 存储：**OLAP 引擎**（ClickHouse/Doris）远比 MySQL 适合（列存、向量化、聚合快）。

**为什么不用 MySQL？** 🔴
- OLTP 行存，聚合扫描慢。
- 亿级数据单表扛不住。
- OLAP 列存 + 向量化执行 + 预聚合，查询快几十到几百倍。

## 2.15 🔴 全局唯一订单号

- 业务前缀（平台+类型）+ 时间（年月日）+ 雪花（机器+序列）。
- 或 Leaf-segment。
- 设计：可读（前缀含义）+ 趋势递增（索引友好）+ 不暴露量（不用纯自增）+ 去中心化（不依赖单点）。

# 第四章 答题加分技巧 🔴

1. **先问需求**：不问就开画 = 减分。问"用户量级、读写比、一致性、延迟"。
2. **先估算**：体现"规模感知"。
3. **画图要清晰**：客户端→网关→服务→存储分层。
4. **讲取舍**：每个选择讲为什么 + 放弃方案的代价。
5. **主动暴露瓶颈**：识别单点/热点，主动说解决。
6. **结合实际经验**："我们 XX 场景踩过坑，所以这里用 XX"。
7. **不会就说思路**：别装懂，"这块没做过，我的思路是…"。
8. **时间管理**：按 7 步节奏走，别陷细节。
