# 第一章 系统设计方法论（先掌握框架再做题）

## 1.1 标准答题框架（7 步法）

### 为什么需要框架

系统设计题没有标准答案，面试官通过你的**思考过程**来评估。如果上来就画图，等于没问清楚需求就动手编码，是减分项。框架的价值：

1. **结构化表达**：让面试官知道你每一分钟在干什么。
2. **避免陷入细节**：先全局后局部，避免在某个点上耗死。
3. **展示工程素养**：需求→估算→设计→权衡，是真实工作的节奏。

> 「系统设计题我习惯按 7 步走：先花 3 分钟澄清需求边界，再 5 分钟做容量估算，然后画高层架构，深入核心模块，最后讲扩展性和取舍。每一步我都会主动跟面试官确认节奏，不会闷头画图。」

### Step 1 澄清需求（Clarify）—— 3-5 分钟

四个维度必问：

| 维度 | 要问的问题 | 茶饮 SaaS 场景示例 |
|------|-----------|-------------|
| **核心功能** | 用户场景是什么？哪些是 MVP？ | 设计优惠券系统：领券、核销、过期回收，要不要做券码生成、对账？ |
| **规模** | DAU/QPS/数据量？ | 近百万门店，假设 30% 日活 = 30w 门店，每门店日均 100 单 → 3000w 单/天 |
| **负载特征** | 读写比？峰值多少倍？ | 优惠券：领券读多写少（10:1），秒杀峰值 50 倍 |
| **质量属性** | 一致性？延迟？可用性？ | 券核销必须强一致（不超发不漏发），列表页可弱一致（1s 最终一致） |

**反例**：面试官问"设计一个秒杀系统"，你直接画图 → 减分。
**正例**：先问"是电商通用秒杀还是票务？峰值 QPS 大概多少？要不要排队？是否允许超卖？" → 加分。

### Step 2 估算容量（Estimate）—— 3-5 分钟

三个核心：QPS、存储、带宽。给出推导过程，不是凭空说数字。

**QPS 估算公式**：
```
平均 QPS = DAU × 人均日访问次数 ÷ 86400
峰值 QPS = 平均 QPS × 峰均比（一般 3-10 倍，秒杀场景可达 50-100 倍）
机器数 = 峰值 QPS ÷ 单机 QPS（Web 单机约 1000-5000）
```

**存储估算公式**：
```
日增量 = 日写入量 × 单条大小
年增量 = 日增量 × 365
总存储 = 年增量 × 保留年限 ÷ 压缩比（通常留 30% 冗余）
```

**带宽估算**：
```
读带宽 = 读 QPS × 单次响应大小（如 50KB 的图片列表 → 10w QPS × 50KB = 5GB/s = 40Gbps）
```

> 详见 [1.2 必背估算数字](#12-必背估算数字)。

### Step 3 API 设计（API Design）—— 3-5 分钟

定义对外接口，明确"系统提供什么能力"。RESTful 为主：

```
POST /api/v1/coupon/claim        # 领券
POST /api/v1/coupon/redeem       # 核销
GET  /api/v1/coupon/list         # 我的券列表
GET  /api/v1/coupon/{id}         # 券详情
```

每个接口写清楚：入参、出参、鉴权、幂等键、错误码。

### Step 4 数据模型（Data Model）—— 5 分钟

设计核心表结构，回答"数据怎么存"。关注：

- 主键策略（自增 / 雪花 / Leaf）
- 索引设计（查询路径反推索引）
- 分库分表键（热点避免、跨库 join 规避）
- 字段冗余 vs 范式（读多写少适当冗余）

### Step 5 高层架构（High-level）—— 5-10 分钟

画核心组件框图（客户端 → 网关 → 服务 → 存储），说明数据流。这一步先不要细节，画出主干。

### Step 6 详细设计（Deep Dive）—— 15-20 分钟

按面试官兴趣点深入：
- 核心算法（短码生成、红包算法、Feed 推拉）
- 关键流程（下单、支付回调、库存扣减）
- 数据一致性（分布式事务、最终一致方案）
- 瓶颈识别（热点 key、大 key、慢查询）

### Step 7 瓶颈与扩展（Scale & Reliability）—— 5-10 分钟

- **扩展性**：缓存、MQ、分库分表、CDN、读写分离
- **可靠性**：单点消除、限流熔断降级、容灾、监控告警
- **权衡**：复述方案，讲为什么这么选 + 替代方案的代价

**口诀**：**"问清楚 → 估容量 → 设计API → 建模型 → 画框架 → 深入核心 → 扩展容灾 → 讲权衡"**

## 1.2 必背估算数字

### 延迟数字（Jeff Dean 经典，必背）

| 操作 | 延迟 | 直观类比 |
|------|------|---------|
| L1 缓存 | 0.5 ns | 1 次心跳 |
| 分支预测错误 | 5 ns | — |
| L2 缓存 | 7 ns | 7 次心跳 |
| 互斥锁加解锁 | 25 ns | — |
| 主存访问 | 100 ns | 半分钟 |
| Zippy 压缩 1KB | 3 μs | — |
| SSD 随机读 | 150 μs | 1.5 分钟 |
| 1Gbps 网络传 1KB | 20 μs | — |
| 同机房 DB 查询 | 1-5 ms | 1 小时 |
| 局域网 RTT | 0.5-1 ms | — |
| 跨机房 RTT（同城） | 1-3 ms | — |
| 跨城 RTT | 几十-100 ms | 1 天 |
| 跨洲 RTT | 100-500 ms | — |

> 记忆口诀：内存比 SSD 快 1000 倍，SSD 比网络快 10 倍，同机房比跨城快 100 倍。

### 吞吐量数字

| 组件 | 单机能力 |
|------|---------|
| Nginx 反向代理 | 5w-10w QPS |
| Web 服务（Tomcat/Spring Boot） | 1000-5000 QPS |
| MySQL（读，命中索引） | 3000-10000 QPS |
| MySQL（写，含事务） | 500-2000 QPS |
| Redis（单节点） | 10w+ QPS |
| Kafka 单 broker | 10w+ msg/s |
| ES 单节点查询 | 1w+ QPS |

### 估算实战口诀

- DAU 100w，每人每天 10 次 → 日请求 1000w → 平均 QPS = 1000w/86400 ≈ **115**，峰值 ×5-10 → **600-1200**。
- 一条业务数据 1KB，日增 100w 条 → **1GB/天**，保留 1 年 → **365GB**（加索引冗余 → 约 1TB）。
- 单库千万行级别，超过就考虑分表；单表 5 亿行必须分。
- 1GB 内存 ≈ 1 亿个 10 字节的对象（如短链短码）。
- 千兆带宽 = 125MB/s ≈ 1.25w 次 10KB 请求/秒。

## 1.3 通用架构图（背下来）

```
                      ┌─ CDN（静态资源加速）─┐
                      │                      ↓
用户 → LB(高可用VIP/SLB) → 网关(鉴权/限流/路由) ─→ 服务集群(无状态，弹性扩缩)
                                                │
                                                ↓
                                     ┌─ 注册中心(Nacos) / 配置中心(Apollo)
                                     │
                                     ├─ Redis 集群（缓存 / 分布式锁 / ZSet）
                                     ├─ MySQL（主从/分库分表 + ShardingSphere）
                                     ├─ MQ（Kafka/RocketMQ 异步削峰）
                                     ├─ ES（全文检索 / 复杂查询）
                                     └─ 对象存储（OSS/S3 文件）

侧翼：
  监控（Prometheus + Grafana）
  日志（ELK：Filebeat → Kafka → ES → Kibana）
  链路追踪（SkyWalking / Jaeger）
```

> 「这套架构是互联网公司的标配。客户端请求先过 CDN 缓存静态资源，动态请求过 LB 到网关，网关做鉴权限流路由，后端服务无状态可弹性扩缩，存储层用 Redis 缓存热数据、MySQL 落持久化、MQ 异步解耦削峰、ES 做搜索。侧翼还有监控日志链路三件套保证可观测性。」

# 第二章 经典系统设计题（15 题详细方案）

## 2.1 短链系统

### 为什么 / 痛点分析

长链（如带 UTM 参数的营销链接）有几个问题：
1. **太长**：短信/微博字数受限，长链浪费字符（前司发券短信，一条链接就占 200 字）。
2. **丑且不美观**：影响品牌形象和点击率。
3. **无法统计**：不知道点击量、来源、转化。

短链核心难点：
- **短码生成不冲突**：海量长链都要唯一短码。
- **高并发跳转**：营销活动瞬时 QPS 几十万。
- **海量存储**：长期累积可能千亿级。

### 原理图解 + 代码

**整体架构**：

```
【生成短链】
长链 → 发号器(自增ID) → Base62编码 → 存DB(短码↔长链) → 写Redis缓存 → 返回 https://t.cn/abc123

【访问短链】
用户点击短链 → 查Redis缓存 → 命中？返回302+Location
                          ↓ 未命中
                        查DB → 命中？回写缓存 + 302
                                ↓ 未命中
                              布隆过滤器拦截(防穿透) → 404

【统计】
302跳转同时 → 异步发MQ → 消费者写统计库(点击量/UV/IP/来源)
```

**表设计**：

```sql
CREATE TABLE short_url (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  short_code  VARCHAR(10) NOT NULL UNIQUE COMMENT '短码',
  long_url    VARCHAR(2048) NOT NULL COMMENT '长链',
  long_url_md5 CHAR(32) NOT NULL COMMENT '长链MD5，用于查重',
  biz_type    TINYINT COMMENT '业务类型：1营销 2券 3商品',
  expire_time DATETIME COMMENT '过期时间，null永久',
  create_time DATETIME DEFAULT NOW(),
  UNIQUE KEY uk_md5 (long_url_md5),  -- 同一长链返回同一短码
  KEY idx_code (short_code)
) COMMENT='短链映射表';
```

**Base62 编码（核心代码）**：

```java
private static final String CHARS = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

// 10进制ID → 62进制短码（6位可表达 62^6 ≈ 568亿）
public static String encode(long id) {
    StringBuilder sb = new StringBuilder();
    while (id > 0) {
        sb.append(CHARS.charAt((int)(id % 62)));
        id /= 62;
    }
    while (sb.length() < 6) sb.append('0'); // 补齐到6位
    return sb.reverse().toString();
}
// 例：id=123456789 → "8M0kX"
```

**301 vs 302 选择** 🔴：

| 重定向 | 浏览器缓存 | 服务端压力 | 能否统计 | 适用 |
|--------|-----------|-----------|---------|------|
| 301 永久 | 缓存，下次不访问短链服务 | 低 | 不能（统计丢失） | 永久静态链接 |
| 302 临时 | 不缓存，每次访问短链服务 | 高 | 能统计点击 | 营销活动、需要数据 |

**茶饮 SaaS 场景**：发券短信里的短链必须用 302，否则统计不到点击转化。

### 真实案例

- **微博 t.cn**：日均生成短链上亿，读 QPS 几十万。
- **前司营销短信**：发券短信带短链，链接跳小程序领券页，需要统计点击率优化投放。
- **美团/抖音分享**：分享链接用短链，配合 UTM 参数统计渠道。

### 对比 / 方案演进

| 方案 | 实现 | 优 | 劣 | 适用 |
|------|------|----|----|------|
| **方案A：自增ID+Base62** | 发号器 → 62进制 | 短、有序、不重复、索引友好 | 短码可预测（可遍历，需加随机前缀） | 主流推荐 |
| **方案B：MD5取前6位** | MD5(长链) 取前6-8位 | 实现简单 | **冲突率高**（生日悖论，10亿条必冲突），要查重 | 不推荐 |
| **方案C：预生成池** | 离线批量生成存DB，用时取 | 性能好、解耦 | 存储浪费、池子耗尽风险 | 超大流量场景 |
| **方案D：随机数+布隆过滤** | 随机6位+查重 | 不可预测 | 冲突需重试、碰撞随数据增长加剧 | 安全性要求高 |

**演进路径**：方案B（简单但有冲突）→ 方案A（主流）→ 方案C+发号器服务化（超大规模）。

### 面试话术

「短链系统我分两块设计：生成和跳转。**生成用发号器+Base62**——发号器可以用雪花算法或美团 Leaf 生成全局自增 ID，再转成 62 进制（6 位能表达 568 亿，足够用 5 年）。同一长链用 MD5 查重返回同一短码，避免重复存储。**跳转走 Redis 缓存**，命中率 90%+，未命中查 DB 并回写缓存，布隆过滤器防穿透。重定向用 **302 临时重定向**，因为营销场景必须统计点击量、UV、来源，301 会被浏览器缓存导致统计丢失。容量上，日增 1 亿条、5 年 1800 多亿条，按短码 hash 分 64 库 64 表。防刷方面，加 IP 限流和黑名单。」

## 2.2 秒杀系统

### 为什么 / 痛点分析

秒杀（如前司大额满减券、双 11 限量奶茶、抢茅台）核心痛点：

1. **瞬时高并发**：10w 库存，100w 人抢，1 秒内涌入，DB 直接被打挂。
2. **绝对防超卖**：库存不能为负，超卖要赔偿。
3. **防黄牛/防刷**：脚本、机器人大批量抢。
4. **用户体验**：不能让用户长时间等待，要快速反馈。

### 原理图解 + 代码

**整体架构（多层防御）**：

```
用户 → CDN(静态页) → 网关(限流+黑名单+Token校验) → 秒杀服务
                                                      │
                              ┌───────────────────────┼───────────────────────┐
                              ↓                       ↓                       ↓
                    Redis Lua 预扣库存         风控校验(用户/设备/行为)   生成下单Token
                  (拦99%流量，单机10w QPS)       (机器学习/规则引擎)
                              │
                       扣减成功 → 发MQ订单消息
                              │ 失败 → 直接返回"抢光了"
                              ↓
                    MQ消费者(异步) → 写订单 + 扣真实库存
                                      │
                                      └─ DB: UPDATE stock SET num=num-1 WHERE id=? AND num>0 (兜底)
                    订单超时未支付 → 延时消息 → 回滚库存
```

**Redis Lua 预扣库存（原子操作，核心代码）**：

```lua
-- KEYS[1]: 库存key  KEYS[2]: 已购用户Set  ARGV[1]: userId
-- 1. 判断是否已抢过（防重复）
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -1  -- 已抢过
end
-- 2. 判断库存
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock <= 0 then
    return 0   -- 抢光了
end
-- 3. 扣减库存 + 记录用户
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1       -- 成功
```

**为什么用 Lua**：保证"判库存 + 扣减 + 记录用户"三步原子性，避免并发下两个用户同时判到库存=1 导致超卖。

**数据模型**：

```sql
-- 秒杀活动表
CREATE TABLE seckill_activity (
  id BIGINT PRIMARY KEY,
  sku_id BIGINT COMMENT '商品ID',
  total_stock INT COMMENT '总库存',
  available_stock INT COMMENT '可用库存',
  price DECIMAL(10,2),
  start_time DATETIME,
  end_time DATETIME,
  limit_per_user INT DEFAULT 1 COMMENT '每人限购',
  version INT DEFAULT 0 COMMENT '乐观锁版本号'
);

-- 秒杀订单表（分库分表，按user_id）
CREATE TABLE seckill_order (
  id BIGINT PRIMARY KEY COMMENT '雪花ID',
  order_no VARCHAR(32) UNIQUE,
  activity_id BIGINT,
  user_id BIGINT,
  status TINYINT COMMENT '0未支付 1已支付 2已取消',
  create_time DATETIME,
  KEY idx_user_activity (user_id, activity_id)  -- 防重复下单
) COMMENT='秒杀订单';
```

### 真实案例

- **前司大额满减券**：限量 1 万张满 100 减 50，10w 门店同时抢，Redis 预扣 + MQ 异步落库。
- **天猫双 11**：阿里用 Sentinel + 多级缓存 + 单元化部署。
- **茅台抢购**：京东/天猫用风控（设备指纹、行为验证码）+ 排队 + 限购实名。

### 对比 / 方案演进

| 方案 | 实现 | 优 | 劣 |
|------|------|----|----|
| **V1：纯DB锁** | `UPDATE...WHERE num>0` 或 `SELECT...FOR UPDATE` | 简单 | DB 扛不住高并发，行锁排队 |
| **V2：DB乐观锁** | 带 version 的 CAS | 无锁性能好 | 高并发下大量失败，DB 仍被打 |
| **V3：Redis预扣+MQ** | Redis Lua 拦 99%，MQ 异步落库 | DB 压力小、响应快 | 需保证最终一致、防 Redis 挂 |
| **V4：本地缓存+Redis** | JVM 本地标记（库存>0才查Redis） | 拦 90% 无效请求 | 一致性弱，需定期同步 |

**演进**：V1（DB扛不住）→ V2（乐观锁仍打DB）→ V4（本地预判减少Redis压力）→ V3（主流方案）。

### 面试话术

「秒杀核心是**分层拦截 + 异步削峰**。我会做四级防御：**第一级 CDN 缓存静态页**，活动页和商品图都不打到后端；**第二级网关限流**，按用户/IP/接口多维度限流，加黑名单和风控；**第三级 Redis Lua 预扣库存**，这是核心——Lua 脚本保证'判库存+扣减+记录用户'原子性，拦掉 99% 请求，单机 Redis 扛 10w+ QPS；**第四级 MQ 异步下单**，扣减成功的请求发 RocketMQ，消费者写订单和扣 DB 真实库存，DB 用 `WHERE num>0` 兜底防超卖。订单超时用延时消息回滚库存。防刷方面，限购（用户Set去重）、行为验证码、设备指纹、IP 限流。最后做好监控，库存归零后熔断接口快速失败。」

## 2.3 Feed 流（朋友圈/微博时间线）

### 为什么 / 痛点分析

Feed 流（关注流）核心问题：用户打开 App 要看到关注人的最新动态。难点：

1. **关注关系规模大**：一人关注几百上千人，大 V 粉丝几千万。
2. **实时性**：发帖后粉丝要尽快看到。
3. **排序**：按时间 or 按算法（互动度）。
4. **海量数据**：微博日活几亿，每天发帖上亿条。

### 原理图解 + 代码

**三种模式对比** 🔴🔴：

| 模式 | 写入 | 读取 | 适用 | 代价 |
|------|------|------|------|------|
| **拉（Pull）** | 只存发帖源，读时实时拉关注人最新 | 慢，关注人多时聚合开销大 | 写多读少、粉丝少 | 读放大 |
| **推（Push/扇出写）** | 发帖时主动推到所有粉丝 inbox | 快，只读自己 inbox | 普通用户（粉丝少） | 写放大（大V灾难） |
| **推拉结合** | 普通人推、大 V 拉粉丝 | 大 V 粉丝读时合并 inbox + 拉大 V | 微博典型 | 实现复杂 |

**微博典型架构（推拉结合）**：

```
【发帖】
普通人(粉丝<10w) 发帖 → 推到所有粉丝 inbox(Redis ZSet, score=时间戳, member=postId)
大 V(粉丝>10w) 发帖 → 只存源帖子，不推

【刷Feed】
用户打开App → 拉自己 inbox(ZREVRANGE分页) 
           → 查关注的大V最新帖子(读时拉) 
           → 合并排序 → 返回
```

**收件箱设计（Redis ZSet）**：

```
key: inbox:{userId}
score: 发帖时间戳
member: postId
读取: ZREVRANGE inbox:userId 0 20   # 倒序取最新20条，分页
```

**为什么用 ZSet**：天然有序、支持范围查询、O(logN) 插入。每个用户 inbox 限制大小（如最近 1000 条），超出淘汰旧的。

**避免大 V 热点** 🔴：
- 大 V 发帖不推（千万粉丝推不动，写放大灾难）。
- 大 V 帖子存独立结构，粉丝读 timeline 时主动拉大 V 最新帖子 + 自己 inbox 合并。
- 阈值：粉丝数 > 10w（或 50w）算大 V，动态可调。

### 真实案例

- **微博**：推拉结合，大 V（明星）不推，普通人推。早期纯推被大 V 拖垮过。
- **朋友圈**：好友数有限（一般 <500），纯推模式，发朋友圈时推到好友 inbox。
- **前司商家动态**：门店关注品牌/总部，总部发动态推到所有门店，规模小用纯推。

### 对比 / 方案演进

1. **V1：纯拉模式** → 简单但读慢，关注 500 人要查 500 次。
2. **V2：纯推模式** → 读快，但大 V 发帖推千万粉丝写放大崩溃。
3. **V3：推拉结合** → 主流，按粉丝数动态选择策略。
4. **V4：算法排序** → 不只按时间，还按互动度（点赞/评论/亲密度）加权排序（Facebook EdgeRank）。

### 面试话术

「Feed 流核心是**推拉结合**。我会按用户类型分流：**普通用户（粉丝少）发帖用推模式**，发帖时主动写到所有粉丝的收件箱（Redis ZSet，score 是时间戳），粉丝刷 Feed 时直接读自己 inbox，速度快。**大 V（粉丝几十万以上）发帖用拉模式**，不推——因为推千万粉丝是写放大灾难，会拖垮 Redis。大 V 帖子单独存，粉丝读时主动拉关注的大 V 最新帖子 + 自己 inbox 合并排序。inbox 用 ZSet 存最近 1000 条，超出淘汰。阈值（如 10w 粉丝）动态可调。这样既保证读性能，又避免大 V 写放大。如果要做算法 Feed（不按时间），可以加权重：互动度、亲密度、时间衰减加权排序。」

## 2.4 IM / 消息推送系统

### 为什么 / 痛点分析

IM（微信/QQ/钉钉/客服）核心难点：

1. **消息可达性**：不丢、不重、有序。
2. **长连接维护**：百万千万并发连接，心跳、断线重连。
3. **多端同步**：手机/PC/Web 多端消息一致。
4. **实时性**：消息秒级到达。

### 原理图解 + 代码

**整体架构**：

```
客户端A ←→ 接入层(WebSocket/长连接网关,Netty) ←→ 路由层(查用户在线在哪台)
                                                        ↓
                                               消息服务(写库/发推送)
                                                        │
                              ┌─────────────────────────┼─────────────────────────┐
                              ↓                         ↓                         ↓
                        消息存储(MySQL+HBase)      离线消息(Redis/DB)         推送通道(APNS/FCM/厂商)
```

**消息发送流程（核心）**：

```
1. A 发消息 → 接入层 → 路由层(查B在线?)
2. B在线 → 路由层找到B所在接入层 → 推给B → B回ACK → 服务端标记送达
3. B离线 → 存离线消息表 → B上线时拉取
4. 服务端始终持久化消息(无论在线离线)
```

**消息可达性保证（核心，必考）** 🔴🔴：

- **客户端 ACK**：服务端发出后**不立即删离线消息**，等客户端 ACK 才删。没收到 ACK 重发。
- **消息 ID 去重**：每条消息全局唯一 ID，客户端收到按 ID 去重（防重复推送）。
- **消息序号排序**：每个会话维护自增 sequence，客户端按 sequence 排序。
- **QoS 等级**（参考 MQTT）：
  - QoS 0：至多一次（可能丢，如状态同步）。
  - QoS 1：至少一次（可能重，靠 ID 去重，主流聊天用这个）。
  - QoS 2：恰好一次（开销大，金融场景用）。

**多端同步** 🔴：
- 每个会话维护自增 `sequence`。
- 客户端上报本地 `last_seq`。
- 服务端返回 `sequence > last_seq` 的所有消息。
- 客户端本地按 sequence 排序、增量同步。

**表设计**：

```sql
-- 消息表（按会话ID分库分表）
CREATE TABLE im_message (
  msg_id BIGINT PRIMARY KEY COMMENT '雪花ID',
  session_id BIGINT COMMENT '会话ID(单聊:小ID+大ID, 群聊:群ID)',
  sender_id BIGINT,
  receiver_id BIGINT,
  content TEXT,
  seq BIGINT COMMENT '会话内自增序号',
  send_time DATETIME,
  KEY idx_session_seq (session_id, seq)
);

-- 离线消息（用户上线拉取后清理）
CREATE TABLE offline_message (
  id BIGINT PRIMARY KEY,
  user_id BIGINT,
  msg_id BIGINT,
  KEY idx_user (user_id)
);
```

**长连接维护**：
- **心跳**：客户端每 30-60s 发心跳，服务端 90s 没收到判离线。
- **断线重连**：指数退避（1s/2s/4s/8s），避免雪崩。
- **单机连接数**：Netty + epoll，单机维持几十万连接（精简连接对象、堆外内存、零拷贝）。

### 真实案例

- **微信**：长连接网关 + 音视频单独通道，消息存 SQLite + 同步协议。
- **钉钉/前司商家版**：门店和总部客服 IM，消息可达性靠 ACK + 重试。
- **美团骑手 IM**：低延迟（订单状态变更实时推送）。

### 对比 / 方案演进

| 方案 | 实现 | 适用 |
|------|------|------|
| **短轮询** | 客户端每隔几秒 HTTP 请求 | 简单但浪费、延迟高，淘汰 |
| **长轮询** | 服务端 hold 住请求有消息才返回 | 中等延迟，兼容性好 |
| **WebSocket** | 全双工长连接 | 主流，实时性好 |
| **SSE** | 服务端单向推送 | 仅推送场景（如通知） |

**演进**：短轮询（浪费）→ 长轮询（兼容）→ WebSocket（主流）。

### 面试话术

「IM 我分四块设计：**接入层**用 Netty 实现 WebSocket 长连接网关，单机维持几十万连接，靠 epoll + 精简连接对象。**消息可达性**是核心——服务端发消息后不删离线消息，等客户端 ACK 才删，没收到 ACK 就重试；同时每条消息带全局唯一 ID 让客户端去重，每会话维护自增 sequence 保证有序。QoS 用'至少一次'+ ID 去重，平衡可靠性和性能。**多端同步**：客户端上报 last_seq，服务端返回大于 last_seq 的消息，增量同步。**离线消息**：未 ACK 的存离线表，用户上线拉取后清理。容量上，消息表按 session_id 分库分表，历史消息归档到 HBase。最后心跳保活（30s 一次）+ 断线指数退避重连。」

## 2.5 附近的人 / LBS 地理位置

### 为什么 / 痛点分析

"附近的人/门店/骑手"是 O2O 核心功能（前司找附近门店、美团找附近商家、滴滴找附近司机）。难点：

1. **二维空间检索**：经纬度二维数据，普通 B+ 树索引无法高效查询"附近 X 米"。
2. **实时性**：用户位置实时变化，司机/骑手位置秒级更新。
3. **高并发查询**：每次打开 App 都要查附近，QPS 高。
4. **距离排序**：结果要按距离从近到远排序。

### 原理图解 + 代码

**三种主流方案**：

**方案1：MySQL（适合数据量小）**：

```sql
-- MySQL 5.7+ 原生支持地理位置
CREATE TABLE store (
  id BIGINT PRIMARY KEY,
  name VARCHAR(100),
  location POINT NOT NULL SRID 4326,
  SPATIAL INDEX idx_location (location)
);

-- 查附近5km门店
SELECT id, name,
  ST_Distance_Sphere(location, ST_PointFromText('POINT(121.47 31.23)')) AS dist
FROM store
WHERE ST_Contains(
  ST_MakeEnvelope(ST_GeomFromText('POINT(121.42 31.18)'),
                  ST_GeomFromText('POINT(121.52 31.28)')), location)
ORDER BY dist LIMIT 20;
```

**方案2：Redis GEO（主流，前司推荐）** 🔴：

```
Redis GEO 底层是 GeoHash + ZSet

# 添加门店位置
GEOADD stores 121.4737 31.2304 "store:001"

# 查附近5km门店，按距离排序
GEORADIUS stores 121.4737 31.2304 5 km WITHCOORD WITHDIST ASC COUNT 20

# 单key存储：经纬度→GeoHash(52位整数)→ZSet(score=GeoHash, member=id)
```

**GeoHash 原理图解**：

```
经纬度(121.47, 31.23) → 二进制交错编码 → 52位整数 → ZSet score

二进制编码示意（GeoHash把2D变1D）：
  经度121.47 → 110100101010...
  纬度31.23  → 101011001011...
  交错(经偶纬奇) → 111001001110... → 转十进制 = GeoHash值

特点：GeoHash值相近 → 地理位置相近（但有边界突变问题，需查9宫格）
```

**方案3：Elasticsearch（复杂查询）**：

```json
// ES geo_point 类型，支持聚合、过滤
{
  "query": {
    "bool": {
      "must": [
        {"match": {"category": "茶饮"}},
        {"geo_distance": {"distance": "5km", "location": {"lat": 31.23, "lon": 121.47}}}
      ]
    }
  },
  "sort": [{"_geo_distance": {"location": {"lat":31.23,"lon":121.47}, "order":"asc"}}]
}
```

### 真实案例

- **前司找附近门店**：小程序首页按定位查 5km 内品牌门店，Redis GEO，QPS 中等。
- **美团/大众点评**：找附近商家，ES + GeoHash，支持品类筛选。
- **滴滴**：找附近司机，高并发 + 实时位置更新，自研地理索引。

### 对比 / 方案演进

| 方案 | 实现 | 优 | 劣 | 适用 |
|------|------|----|----|------|
| **MySQL 空间索引** | POINT + SPATIAL INDEX | 简单、强一致 | 数据量大慢，写入有锁 | 数据量小（<百万） |
| **Redis GEO** | GeoHash + ZSet | 性能高（10w+QPS）、轻量 | 不支持复杂过滤 | 主流，纯附近查询 |
| **ES geo_point** | 倒排 + GeoHash 树 | 支持复杂查询（品类/评分）+ 地理 | 重、写入有延迟 | 需要复合条件查询 |
| **MongoDB 2dsphere** | GeoJSON | 简单 | 生态不如ES | MongoDB技术栈 |

**演进**：MySQL（小量）→ Redis GEO（纯地理，主流）→ ES（复杂查询）。

### 面试话术

「附近的人我用 **Redis GEO** 为主。Redis GEO 底层是 GeoHash——把经纬度二维数据编码成一维 52 位整数，存到 ZSet（score=GeoHash，member=ID），这样就把二维空间检索转成一维范围查询。查询用 `GEORADIUS` 指定中心点+半径，自动按距离排序返回。单机 Redis 10w+ QPS，足够前司找附近门店的场景。**容量上**，单个 GEO key 存所有点会成大 key，按城市/区域分 key（如 `geo:store:shanghai`）。**如果需要复合条件**（如附近5km内的茶饮店，按评分排序），Redis GEO 不够，上 ES 的 geo_point + bool 查询。位置实时更新场景（如骑手），用户上报位置直接 `GEOADD` 覆盖更新。GeoHash 有边界突变问题，查询时取 9 宫格规避。」

## 2.6 排行榜 / 实时榜单

### 为什么 / 痛点分析

排行榜（积分榜、销量榜、热度榜）常见场景：游戏积分、电商销量排行、微博热搜、前司门店业绩榜。难点：

1. **实时排序**：用户行为触发积分变化，榜单要实时更新。
2. **海量数据排序**：亿级用户/商品排序，传统 DB `ORDER BY` 扛不住。
3. **多维度**：全国榜、地区榜、好友榜、周榜、月榜。
4. **Top N 高效查询**：亿级用户查 Top 100 要毫秒级。

### 原理图解 + 代码

**方案演进**：

```
V1: MySQL ORDER BY score DESC LIMIT 100  → 数据量大慢（全表扫描+排序）
     ↓
V2: MySQL + 索引(score)                   → 亿级仍慢，写入更新索引开销大
     ↓
V3: Redis ZSet                            → 天然有序，单机10w+成员，O(logN)
     ↓
V4: 分桶 ZSet（按维度/范围）              → 超大规模，地区榜、全国榜分离
```

**Redis ZSet 核心**：

```
# 更新积分（用户消费/签到/任务）
ZADD leaderboard:202608 <score> <userId>

# 查Top100
ZREVRANGE leaderboard:202608 0 99 WITHSCORES

# 查某用户排名
ZREVRANK leaderboard:202608 <userId>

# 查某用户分数
ZSCORE leaderboard:202608 <userId>
```

**为什么 ZSet 快**：底层是**跳表（SkipList）+ 哈希表**。跳表保证有序（O(logN) 范围查询），哈希表保证按 member 快速定位（O(1) 查分数）。插入/更新 O(logN)。

**多维度榜单设计**：

```
全国日榜:  leaderboard:daily:20260806
全国周榜:  leaderboard:weekly:20260632        # 周榜=每日榜聚合(定时任务合并)
全国月榜:  leaderboard:monthly:202608
城市榜:    leaderboard:city:shanghai:20260806
好友榜:    leaderboard:friend:{userId}        # 小规模，预计算
```

**分桶/分片**（亿级用户）🔴：

```
方案A：按 score 范围分片
  bucket0: 0-1000分    bucket1: 1000-5000分   ...
  查TopN：从高分桶往低查，合并

方案B：按用户 hash 分片到多个 ZSet
  各分片各自查 TopN，再合并归并排序
```

**实时更新数据流**：

```
用户行为(下单/签到/分享) → 发MQ → 消费者累加积分 → ZADD 更新ZSet
                                ↓
                          持久化到DB（异步，用于历史/对账）
```

### 真实案例

- **微博热搜**：实时统计话题出现次数，ZSet 排序 + 人工审核。
- **王者荣耀国服榜**：亿级玩家，按战力 ZSet 排序，分省/全国。
- **前司门店业绩榜**：月度销售额排行，激励门店。ZSet + 定时任务聚合。
- **抖音直播打赏榜**：实时打赏金额排序，房间榜 + 主播榜。

### 对比 / 方案演进

| 方案 | 优 | 劣 | 适用 |
|------|----|----|------|
| MySQL ORDER BY | 简单、强一致 | 慢、扛不住高并发 | 数据量小（<百万） |
| Redis ZSet | 快、天然有序 | 重启丢（需持久化）、内存限制 | 主流，单维度 |
| 分桶 ZSet | 支持超大规模 | 实现复杂 | 亿级用户 |
| ES 聚合 | 支持复合维度 | 写入延迟、重 | 多维度复杂排行 |

### 面试话术

「排行榜我用 **Redis ZSet**。ZSet 底层是跳表 + 哈希表，跳表保证有序范围查询 O(logN)，哈希表保证按用户 O(1) 查分数。`ZADD` 更新积分、`ZREVRANGE` 查 Top N、`ZREVRANK` 查个人排名，都是毫秒级。**实时更新**：用户行为（下单/签到）发 MQ，消费者异步累加积分写 ZSet，DB 异步持久化用于对账。**多维度榜单**：按维度建不同 key（日榜/周榜/城市榜），周榜月榜用定时任务从日榜聚合。**亿级用户**场景单个 ZSet 内存扛不住，按 score 范围分桶，查 TopN 从高分桶往低合并。**持久化**：Redis 主从 + RDB/AOF，关键榜单同步写 DB 兜底。」

## 2.7 抢红包

### 为什么 / 痛点分析

抢红包（微信群红包、前司营销红包雨）难点：

1. **高并发**：群红包几十人同时抢，瞬时 QPS 高。
2. **金额公平**：每人金额随机但不能太离谱（不能有人抢 0.01 有人抢 99）。
3. **防超发**：红包个数和总金额不能超。
4. **防并发重复抢**：一人只能抢一次。

### 原理图解 + 代码

**二倍均值法（核心算法，保证公平）** 🔴：

```
规则：每次抢 = random(0.01, 剩余总额 / 剩余人数 × 2)
最后一人：抢剩余全部

例：100元10人
  第1人：random(0.01, 100/10×2=20)      → 假设抢15元，剩85元9人
  第2人：random(0.01, 85/9×2≈18.89)     → 假设抢12元，剩73元8人
  ...
  第10人：抢剩余全部

为什么公平：
  每人期望 = 剩余均值 × (0~2均匀分布的期望=1) = 剩余均值
  不会出现"先抢的人一定多/少"的偏差
```

**整体架构（类秒杀）**：

```
发红包：用户发红包 → 写红包表(总额/个数/明细) → Redis预生成金额列表(LPUSH到list) → 发群消息
        ↓
抢红包：用户点抢 → Redis Lua原子操作(校验是否抢过+LPOP取出金额+记录已抢) 
        → 成功？发MQ异步落库 + 推送金额
        → 失败(抢过/抢光)？快速返回
        ↓
过期：24h未抢完 → 退回原账户
```

**Redis Lua 抢红包（原子防超发+防重复）**：

```lua
-- KEYS[1]: 红包金额List  KEYS[2]: 已抢用户Set  ARGV[1]: userId
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -1  -- 已抢过
end
local money = redis.call('LPOP', KEYS[1])
if not money then
    return 0   -- 抢光了
end
redis.call('SADD', KEYS[2], ARGV[1])
return money   -- 返回抢到的金额
```

**表设计**：

```sql
CREATE TABLE red_packet (
  id BIGINT PRIMARY KEY,
  packet_no VARCHAR(32) UNIQUE COMMENT '红包编号',
  sender_id BIGINT,
  total_amount DECIMAL(10,2) COMMENT '总金额(分)',
  total_count INT COMMENT '总个数',
  remain_count INT COMMENT '剩余个数',
  group_id BIGINT COMMENT '群ID',
  status TINYINT COMMENT '0进行中 1已抢完 2已过期',
  expire_time DATETIME,
  create_time DATETIME
);

CREATE TABLE red_packet_detail (
  id BIGINT PRIMARY KEY,
  packet_id BIGINT,
  receiver_id BIGINT COMMENT '领取人',
  amount DECIMAL(10,2) COMMENT '领取金额',
  receive_time DATETIME,
  UNIQUE KEY uk_packet_receiver (packet_id, receiver_id)  -- 防重复抢(DB兜底)
);
```

### 真实案例

- **微信群红包**：亿级用户，二倍均值法，Redis + 异步落库。
- **支付宝集五福**：红包雨，限流 + 排队。
- **前司营销红包**：满赠发红包，金额小、并发中等，DB+Redis 混合。

### 对比 / 方案演进

| 方案 | 优 | 劣 |
|------|----|----|
| **V1：DB事务+随机** | 简单 | 高并发扛不住，行锁竞争 |
| **V2：Redis预生成金额List** | 原子LPOP抢金额，快 | 需预生成、List持久化 |
| **V3：二倍均值法+Lua** | 公平+原子+高并发 | 实现稍复杂 |

**金额算法对比**：
- **随机区间法**（random(0,total)）：先抢的人可能拿大头，不公平。
- **二倍均值法**：期望公平，微信采用，主流。
- **线段切割法**（切N-1刀分N段）：金额分布更随机但实现复杂。

### 面试话术

「抢红包是**秒杀+随机金额算法**的组合。金额用**二倍均值法**：每次抢 = `random(0.01, 剩余总额/剩余人数×2)`，保证每人期望相等、不会出现极端偏差，最后一人抢剩余全部。**抢的流程**：发红包时预生成金额列表 LPush 到 Redis List；用户抢用 **Lua 脚本原子操作**——校验是否已抢（Set 去重）+ LPOP 取金额 + 记录已抢，三步原子防并发超发和重复抢。成功后发 MQ 异步落库。**过期处理**：24h 未抢完用延时消息退回原账户。**防刷**：每人限抢一次（Set 去重）、设备/IP 限流。DB 层加唯一约束（packet_id+receiver_id）兜底。」

## 2.8 点赞系统

### 为什么 / 痛点分析

点赞（朋友圈/微博/抖音/前司门店好评）看似简单，难点：

1. **高并发写**：热门内容每秒上万点赞。
2. **防重复点赞**：一人只能赞一次。
3. **实时统计**：内容要实时显示总赞数。
4. **取消点赞**：状态机管理。
5. **海量数据**：单条热门内容百万赞，全量数据千亿。

### 原理图解 + 代码

**整体架构**：

```
点赞请求 → 网关 → 点赞服务
                    ├─ Redis 计数器(实时总赞数): INCR/DECR
                    ├─ Redis Set/Bloom(用户是否赞过,去重)
                    └─ 发MQ(异步落库,削峰)
                          ↓
                    MQ消费者 → 批量写入DB(点赞明细)
                          ↓
                    定时任务 → DB计数对账(防Redis漂移)

取消点赞 → Redis DECR + SREM + MQ异步删DB明细
```

**Redis 数据结构**：

```
# 内容总赞数（计数器）
like:count:{contentId}  → INCR / DECR

# 点赞用户集合（去重，小规模用Set，大规模用Bloom）
like:users:{contentId}  → SADD/SREM/SISMEMBER
```

**为什么 Redis 计数器不直接落库**：高频写 DB 扛不住，Redis INCR 单机 10w+ QPS。

**表设计**：

```sql
-- 点赞明细表（按content_id分库分表）
CREATE TABLE user_like (
  id BIGINT PRIMARY KEY,
  user_id BIGINT,
  content_id BIGINT,
  status TINYINT COMMENT '0取消 1有效',
  create_time DATETIME,
  UNIQUE KEY uk_user_content (user_id, content_id)  -- 防重复
);

-- 内容计数表（聚合，定时同步）
CREATE TABLE content_like_count (
  content_id BIGINT PRIMARY KEY,
  like_count INT COMMENT '总赞数'
);
```

**防重复点赞（核心）** 🔴：
- **Redis Set 去重**：`SISMEMBER like:users:{cid} {uid}` 判断是否赞过。小规模内容适用。
- **Bloom Filter**：海量内容（每条百万赞 Set 太大），用布隆过滤器判重，有误判但省内存。
- **DB 唯一约束兜底**：`(user_id, content_id)` 唯一索引。

**计数漂移对账**：Redis 计数器可能因宕机丢计数，定时任务（每小时）从 DB 聚合真实计数校正。

### 真实案例

- **微博/抖音点赞**：亿级用户，Redis 计数 + Bloom 判重 + Kafka 异步落 HBase。
- **朋友圈点赞**：好友可见，Redis Set（好友数有限）。
- **前司门店好评**：评价点赞，规模中等，Redis + MySQL。

### 对比 / 方案演进

| 方案 | 优 | 劣 |
|------|----|----|
| **V1：纯DB** `INSERT+COUNT` | 强一致 | 高并发写不动，COUNT慢 |
| **V2：DB+缓存计数** | 读快 | 写仍打DB |
| **V3：Redis计数+异步落库** | 主流，高并发 | 最终一致，需对账 |
| **V4：Bloom判重+计数** | 海量数据省内存 | 有误判率 |

### 面试话术

「点赞系统我用 **Redis 计数 + 异步落库**。点赞请求先到 Redis：`INCR` 总赞数、`SADD` 用户到点赞集合（去重）。判重用 `SISMEMBER`，大规模内容（百万赞）Set 太大，换 Bloom Filter。然后发 MQ 异步批量写 DB 明细表，DB 加 `(user_id, content_id)` 唯一约束兜底防重复。**取消点赞**：`DECR` 计数 + `SREM` 用户 + MQ 删 DB 明细。**计数漂移**：Redis 可能宕机丢计数，定时任务每小时从 DB 聚合真实计数校正。**为什么不全走 DB**：热门内容每秒上万赞，DB 写不动；Redis INCR 单机 10w+ QPS。点赞明细按 content_id 分库分表。」

## 2.9 评论系统

### 为什么 / 痛点分析

评论（微博/抖音/电商商品评论/前司门店评价）难点：

1. **层级结构**：评论-回复-再回复，树形结构存储和展示。
2. **高并发读**：热门内容百万评论，分页加载。
3. **排序**：按时间 / 按热度 / 按点赞数。
4. **审核**：敏感词过滤、人工审核。

### 原理图解 + 代码

**两种评论树存储模型** 🔴：

**模型1：邻接表（parentId 关联）**：

```sql
CREATE TABLE comment (
  id BIGINT PRIMARY KEY,
  content_id BIGINT COMMENT '被评论内容ID',
  user_id BIGINT,
  parent_id BIGINT COMMENT '父评论ID, 顶级评论为null',
  reply_to_uid BIGINT COMMENT '@回复谁',
  content TEXT,
  like_count INT DEFAULT 0,
  create_time DATETIME,
  KEY idx_content (content_id, create_time)
);
```
查评论树需要递归查询，性能差。

**模型2：邻接表+根评论冗余（主流，电商常用）**：

```sql
CREATE TABLE comment (
  id BIGINT PRIMARY KEY,
  content_id BIGINT COMMENT '内容ID',
  root_id BIGINT COMMENT '根评论ID, 顶级评论=root_id自己',
  parent_id BIGINT COMMENT '直接父评论ID',
  user_id BIGINT,
  reply_to_uid BIGINT COMMENT '被回复用户',
  content VARCHAR(2000),
  like_count INT,
  state TINYINT COMMENT '0待审核 1正常 2屏蔽',
  create_time DATETIME,
  KEY idx_content_root (content_id, root_id, create_time)  -- 查询主索引
);
```

**查询逻辑（两段式加载）**：

```
1. 查顶级评论（按热度/时间排序分页）:
   SELECT * FROM comment WHERE content_id=? AND root_id=id ORDER BY like_count DESC LIMIT 20

2. 懒加载某条评论下的回复（点"展开10条回复"）:
   SELECT * FROM comment WHERE root_id=? ORDER BY create_time
```

**整体架构**：

```
发评论 → 网关 → 评论服务
          ├─ 敏感词过滤(AC自动机/DFA)
          ├─ 异步审核(机器学习+人工)
          ├─ 写DB(状态=待审核)
          └─ 发MQ → 更新内容评论数 + 推送通知

查评论 → 查Redis缓存(热门评论) → DB → 按root_id分组组装树
```

**排序策略**：
- 默认按热度（like_count DESC）：热门评论置顶。
- 可切换按时间（create_time DESC）。
- 热度算法可加权：`score = like_count + reply_count×0.5 - 时间衰减`。

### 真实案例

- **微博评论**：楼中楼结构，邻接表 + 冗余 root_id，亿级评论分库分表。
- **淘宝商品评价**：评价+晒图+追加评价，Redis 缓存热门商品评价。
- **前司门店评价**：用户评价门店，星标 + 文字 + 图，规模中等。

### 对比 / 方案演进

| 方案 | 优 | 劣 |
|------|----|----|
| **邻接表（parentId）** | 简单 | 递归查询慢 |
| **路径枚举（path）** | 查子树快 | 移动节点复杂 |
| **嵌套集（lft/rgt）** | 查树快 | 写入复杂 |
| **邻接表+根ID冗余** | 查询简单、两段加载 | 适当冗余字段 |

**演进**：邻接表（递归慢）→ 路径枚举（移动难）→ **邻接表+root_id冗余（主流）**。

### 面试话术

「评论系统核心是**树形结构存储**和**两段式加载**。我用**邻接表 + 冗余根评论ID**模型：每条评论记录 `parent_id`（直接父评论）和 `root_id`（根评论，顶级评论 root_id=自己）。**加载分两段**：先查顶级评论（按热度/时间分页，用 `content_id + root_id` 联合索引），用户点'展开回复'再懒加载某条根评论下的所有回复（`WHERE root_id=?`），前端按 parent_id 组装树。这样避免一次递归查整棵树。**写入**走敏感词过滤（AC自动机）+ 异步审核 + 发 MQ 更新评论数。**排序**支持按热度（like_count）和按时间，热度可加权时间衰减。缓存热点内容的评论列表到 Redis。分库分表按 content_id。」

## 2.10 搜索系统

### 为什么 / 痛点分析

搜索（电商商品搜索、内容搜索、前司菜品/门店搜索）难点：

1. **全文检索**：MySQL `LIKE '%xx%'` 走不了索引，全表扫描。
2. **相关性排序**：按匹配度、销量、时间排序。
3. **高亮/分词/纠错**：搜索词分词、结果高亮、拼写纠错。
4. **海量数据**：商品/内容千万到亿级。

### 原理图解 + 代码

**为什么不用 MySQL** 🔴：
- `LIKE '%奶茶%'` 不走索引（前缀通配），全表扫描。
- 没有分词能力（"珍珠奶茶"无法分成"珍珠"+"奶茶"匹配）。
- 没有相关性打分（无法按 TF-IDF/BM25 排序）。

**ES 倒排索引原理**：

```
正排索引：文档ID → 文档内容
倒排索引：词项 → 包含该词的文档ID列表

例：
  文档1: "珍珠奶茶好喝"
  文档2: "珍珠奶茶买一送一"
  文档3: "烤奶也不错"

分词后倒排索引：
  珍珠 → [文档1, 文档2]
  奶茶 → [文档1, 文档2]
  烤奶 → [文档3]

搜索"珍珠奶茶" → 分词[珍珠,奶茶] → 取交集[文档1,文档2] → 按TF-IDF/BM25打分排序
```

**整体架构**：

```
【写入】
DB(canal监听binlog) → MQ → ES同步服务 → 写ES索引（近实时，1-5s延迟）

【查询】
用户搜索 → 搜索服务 → ES查询(分词+bool+sort) → 返回高亮结果
                        ├─ 同义词扩展(奶茶→饮品)
                        ├─ 拼写纠错(edit distance)
                        └─ 热搜推荐(基于历史)
```

**ES 查询示例（商品搜索）**：

```json
POST /product/_search
{
  "query": {
    "bool": {
      "must": [{"match": {"name": "珍珠奶茶"}}],
      "filter": [
        {"term": {"category": "drink"}},
        {"range": {"price": {"gte": 10, "lte": 50}}}
      ]
    }
  },
  "sort": [
    {"_score": {"order": "desc"}},
    {"sales": {"order": "desc"}}
  ],
  "highlight": {"fields": {"name": {}}},
  "from": 0, "size": 20
}
```

**数据同步方案**：
- **同步双写**：业务代码写 DB 同时写 ES，强一致但侵入性强、性能差。
- **异步 MQ**：写 DB 发 MQ，消费者写 ES，解耦但有延迟。
- **Canal 监听 binlog**（主流）：监听 MySQL binlog 变更同步到 ES，业务无侵入。

### 真实案例

- **淘宝商品搜索**：ES 集群 + 自研相关性算法 + 个性化召回。
- **前司菜品/门店搜索**：按门店搜菜品、按品牌搜门店，ES + 同义词词典。
- **维基百科/掘金**：全文搜索，ES 高亮 + 分词。

### 对比 / 方案演进

| 方案 | 优 | 劣 | 适用 |
|------|----|----|------|
| MySQL LIKE | 简单 | 慢、无分词 | 数据量极小 |
| MySQL 全文索引 | 原生 | 中文支持差、性能一般 | 简单场景 |
| **Elasticsearch** | 全文检索强、分词、打分 | 重、写入有延迟、吃内存 | 主流 |
| Solr | 类似 ES | 生态不如ES | 老项目 |
| 自研（倒排索引） | 定制化 | 开发成本高 | 超大规模（百度） |

**演进**：MySQL LIKE（慢）→ MySQL 全文索引（中文差）→ **ES（主流）** → ES + 向量检索（语义搜索，AI时代）。

### 面试话术

「搜索我用 **Elasticsearch**。MySQL 的 `LIKE '%xx%'` 走不了索引，亿级数据全表扫描不可接受。ES 基于**倒排索引**——分词后建立'词项→文档ID列表'的映射，搜索时按词项查文档，再按 TF-IDF/BM25 打分排序，毫秒级返回。**数据同步**用 **Canal 监听 MySQL binlog** 异步同步到 ES，业务无侵入，延迟 1-5 秒。**查询**支持分词、bool 组合（must/filter）、范围过滤、聚合排序、结果高亮。**中文分词**用 IK 分词器 + 自定义词典（如茶饮行业词'芋圆''波霸'）。**扩展**：同义词扩展（奶茶→饮品）、拼写纠错（编辑距离）、热搜推荐。集群部署，分片+副本保证可用性和扩展性。」

## 2.11 文件存储 / 对象存储

### 为什么 / 痛点分析

文件上传（头像、商品图、评价晒图、合同）难点：

1. **海量小文件**：百万门店每天上传图片，文件数亿到百亿。
2. **大文件分片**：视频、合同 PDF 几百 MB 到 GB，断点续传。
3. **高可用**：文件不能丢，多副本。
4. **CDN 加速**：全国访问加速。
5. **去重**：相同图片存一份（如商品图复用）。

### 原理图解 + 代码

**整体架构**：

```
客户端 → 上传服务 → 鉴权(预签名URL) → 对象存储(OSS/S3/MinIO)
                                         ├─ 元数据(MySQL: fileId/path/size/hash/owner)
                                         └─ 多副本存储(跨可用区)
                    ↓
                CDN回源加速(全国节点)
```

**上传流程（分片上传大文件）** 🔴：

```
1. 客户端请求上传 → 服务端生成预签名URL（限时、限权）
2. 大文件分片（如每片5MB）→ 并发上传各分片 → 服务端合并
3. 断点续传：记录已上传分片，失败重传单片
4. 上传完成 → 计算文件MD5 → 查重（已存在秒传）→ 写元数据
```

**去重（秒传）**：
```
客户端上传前先算文件MD5 → 查DB是否已存在
  存在 → 直接返回已有URL（秒传，不重复存储）
  不存在 → 正常上传
```

**表设计（元数据）**：

```sql
CREATE TABLE file_meta (
  file_id BIGINT PRIMARY KEY,
  file_name VARCHAR(255),
  file_path VARCHAR(500) COMMENT 'OSS路径',
  file_size BIGINT COMMENT '字节',
  file_md5 CHAR(32) COMMENT 'MD5,去重用',
  mime_type VARCHAR(50),
  owner_id BIGINT,
  biz_type TINYINT COMMENT '1头像 2商品图 3评价 4合同',
  create_time DATETIME,
  UNIQUE KEY uk_md5 (file_md5)  -- 去重
);
```

**为什么不用文件系统/数据库存图** 🔴：
- **本地文件系统**：单机容量有限、不可扩展、单点故障。
- **DB 存 BLOB**：DB 不适合存大文件，膨胀快、备份慢、查询拖累。
- **对象存储**：天然分布式、无限扩容、多副本、HTTP 直接访问、配合 CDN。

### 真实案例

- **阿里云 OSS / AWS S3**：业界标准，前司存商品图、评价图、合同。
- **MinIO**：自建对象存储，兼容 S3 协议，私有化部署。
- **FastDFS**：早期分布式文件系统，现在多用 OSS/MinIO 替代。
- **七牛云**：图片处理+CDN 一体化。

### 对比 / 方案演进

| 方案 | 优 | 劣 | 适用 |
|------|----|----|------|
| 本地磁盘 | 简单 | 单点、不可扩 | 单机小项目 |
| NFS 共享存储 | 简单 | 性能差、单点 | 内部小规模 |
| FastDFS | 分布式 | 运维复杂、社区衰退 | 老项目 |
| **对象存储(OSS/S3/MinIO)** | 海量、高可用、CDN | 付费 | 主流 |
| DB 存 BLOB | 强一致 | DB膨胀、慢 | 绝不推荐 |

**演进**：本地磁盘 → NFS → FastDFS → **对象存储（主流）**。

### 面试话术

「文件存储我用**对象存储（OSS/S3/MinIO）+ CDN**。本机磁盘和 NFS 单点不可扩展，DB 存 BLOB 会拖垮数据库。对象存储天然分布式、无限扩容、多副本容灾、HTTP 直接访问。**上传流程**：客户端请求上传，服务端生成**预签名 URL**（限时限权）让客户端直传 OSS（不经过应用服务器，省带宽）；大文件**分片上传**（每片 5MB）支持断点续传；上传后算 MD5 查重，已存在直接秒传。**元数据**（路径/大小/hash/owner）存 MySQL 便于检索。**加速**：配合 CDN 全国节点回源，图片访问毫秒级。**安全**：私有 bucket + 预签名 URL 防盗链，敏感文件加密存储。」

## 2.12 订单系统

### 为什么 / 痛点分析

订单是电商核心（前司每笔茶饮交易都是订单）。难点：

1. **全局唯一订单号**：分布式下不重复、可读、趋势递增。
2. **防重复下单**：网络重试不能产生重复订单。
3. **状态机**：待支付/已支付/已发货/已完成/已取消，状态流转严谨。
4. **分布式事务**：下单涉及库存、优惠券、积分多服务。
5. **海量数据**：分库分表、历史归档。

### 原理图解 + 代码

**订单号设计** 🔴：

```
订单号 = 业务前缀(2位) + 时间(yyyyMMddHHmmss,14位) + 机器(2位) + 序列(4位)
例: WM20260806143025 03 0001  (前司订单,2026-08-06 14:30:25, 机器03, 序列0001)

设计原则：
  - 可读：前缀+时间一眼看出业务和下单时间
  - 趋势递增：时间在前，B+树索引友好（避免页分裂）
  - 不暴露量：不用纯自增（暴露销量），用雪花序列
  - 去中心化：雪花算法，不依赖单点DB
```

**表设计（分库分表）**：

```sql
-- 订单主表（按user_id取模分库分表）
CREATE TABLE order_main (
  id BIGINT PRIMARY KEY COMMENT '雪花ID',
  order_no VARCHAR(32) UNIQUE COMMENT '订单号(业务可读)',
  user_id BIGINT,
  store_id BIGINT,
  total_amount DECIMAL(10,2),
  pay_amount DECIMAL(10,2) COMMENT '实付(扣优惠后)',
  status TINYINT COMMENT '0待支付 1已支付 2制作中 3已完成 4已取消 5已退款',
  coupon_id BIGINT COMMENT '使用的券',
  create_time DATETIME,
  pay_time DATETIME,
  KEY idx_user_time (user_id, create_time),
  KEY idx_store_time (store_id, create_time)
);

-- 订单明细表
CREATE TABLE order_item (
  id BIGINT PRIMARY KEY,
  order_no VARCHAR(32),
  sku_id BIGINT,
  sku_name VARCHAR(100),
  quantity INT,
  unit_price DECIMAL(10,2),
  KEY idx_order (order_no)
);
```

**防重复下单（幂等）** 🔴：
- 客户端生成**幂等键**（业务唯一标识，如购物车快照 hash），请求带上。
- 服务端用幂等键去 Redis/DB 查重，存在则返回已有订单。

**下单分布式事务（核心）** 🔴：

```
方案1：强一致（2PC/TCC）—— 性能差，少用
方案2：可靠消息最终一致（主流）：
  1. 创建订单(本地事务, status=待支付)
  2. 发MQ(库存扣减消息)——用本地消息表保证消息不丢
  3. 库存服务消费MQ扣库存——失败重试
  4. 优惠券服务消费MQ核销券
  5. 任一步骤失败 → 补偿(回滚订单/库存/券)

订单状态机严格校验：
  待支付 → 已支付(支付回调) → 已完成
  待支付 → 已取消(超时/用户取消)
  已支付 → 已退款(退款流程)
  非法状态转换直接拒绝
```

**整体架构**：

```
下单请求 → 网关(限流) → 订单服务
          ├─ 幂等校验(Redis/DB)
          ├─ 创建订单(本地事务, status=待支付)
          ├─ 发MQ(扣库存/锁券)
          └─ 返回订单号
                ↓
        库存服务消费MQ → 扣库存(DB兜底WHERE num>0)
        优惠券服务消费MQ → 锁定券
                ↓
        支付回调 → 更新订单状态(已支付) → 发MQ(制作通知)
                ↓
        超时未支付 → 延时消息 → 取消订单 + 回滚库存/券
```

### 真实案例

- **茶饮 SaaS 平台订单**：每笔下单涉及库存（原料）、优惠券、积分、支付，TCC/可靠消息最终一致。
- **淘宝订单**：亿级订单，按 user_id 分库分表，历史订单归档 HBase。
- **美团外卖**：高并发下单，幂等 + 分布式事务 + 状态机。

### 对比 / 方案演进

| 方案 | 优 | 劣 |
|------|----|----|
| **V1：单库单表** | 简单 | 数据量扛不住 |
| **V2：主从读写分离** | 读扩展 | 写仍单点 |
| **V3：分库分表(ShardingSphere)** | 写扩展 | 跨库join/事务难 |
| **V4：分库分表+历史归档** | 海量数据 | 运维复杂 |

**分布式事务对比**：
- **2PC**：强一致，性能差，阻塞。
- **TCC**：最终一致，业务侵入大（Try/Confirm/Cancel 三段）。
- **Saga**：长事务，补偿机制。
- **可靠消息（本地消息表+MQ）**：主流，最终一致，解耦。

### 面试话术

「订单系统我重点设计**订单号、幂等、状态机、分布式事务**。**订单号**用'业务前缀+时间+机器+序列'格式（如 WM20260806143025030001），可读、趋势递增（索引友好）、不暴露销量、雪花算法去中心化。**防重复下单**用幂等键（购物车快照 hash），Redis 查重。**状态机**严格校验流转（待支付→已支付→已完成，非法转换拒绝）。**分布式事务**用**可靠消息最终一致**：创建订单是本地事务，扣库存、锁券通过 MQ 异步处理，用本地消息表保证消息不丢，任一失败补偿回滚。**容量上**订单按 user_id 分库分表（8 库 64 表），历史订单（如 1 年前）归档到 HBase 冷存储。超时未支付用延时消息自动取消并回滚库存券。」

## 2.13 支付系统

### 为什么 / 痛点分析

支付（微信/支付宝对接、前司收银）难点：

1. **资金安全**：绝不能错账，多一分少一分都是事故。
2. **回调可靠性**：支付渠道异步通知，必须保证回调处理成功。
3. **幂等**：支付渠道可能重复回调，不能重复处理。
4. **对账**：每天和渠道对账，发现差异补偿。
5. **退款**：逆向流程，状态严谨。

### 原理图解 + 代码

**支付核心流程**：

```
【下单支付】
1. 用户支付 → 订单服务创建支付单(pay_no, 待支付)
2. 调用微信/支付宝统一下单接口 → 返回预支付参数(prepay_id)
3. 客户端拉起支付 → 用户输密码 → 渠道扣款

【支付回调（核心）】
4. 渠道异步回调支付结果 → 支付服务
   ├─ 验签（防伪造）
   ├─ 幂等校验（同一pay_no只处理一次）
   ├─ 更新支付单状态(已支付)
   ├─ 发MQ通知订单服务更新订单状态
   └─ 返回SUCCESS给渠道（不返回渠道会重试）

【主动查询（兜底）】
5. 定时任务查询"待支付且超过X分钟"的支付单 → 主动调渠道查询接口补状态
   （防回调丢失）
```

**表设计**：

```sql
-- 支付单表
CREATE TABLE pay_order (
  id BIGINT PRIMARY KEY,
  pay_no VARCHAR(32) UNIQUE COMMENT '支付单号(幂等)',
  order_no VARCHAR(32) COMMENT '关联订单号',
  channel TINYINT COMMENT '1微信 2支付宝',
  amount DECIMAL(10,2),
  status TINYINT COMMENT '0待支付 1已支付 2已关闭 3已退款',
  channel_pay_no VARCHAR(64) COMMENT '渠道交易号',
  pay_time DATETIME,
  callback_time DATETIME,
  KEY idx_order (order_no)
);

-- 退款表
CREATE TABLE refund_order (
  id BIGINT PRIMARY KEY,
  refund_no VARCHAR(32) UNIQUE,
  pay_no VARCHAR(32) COMMENT '原支付单',
  amount DECIMAL(10,2),
  status TINYINT COMMENT '0退款中 1已退款 2退款失败',
  create_time DATETIME
);
```

**幂等设计（核心）** 🔴：
- 回调带 `pay_no`，处理前查状态，已支付直接返回 SUCCESS（不重复处理）。
- DB 层状态机：`UPDATE pay_order SET status=1 WHERE pay_no=? AND status=0`，并发只有一个成功。

**对账机制** 🔴：
- 每天凌晨拉取渠道对账单（T+1）。
- 与本地支付单逐笔比对：本地有渠道无（长款）、渠道有本地无（短款）、金额不一致。
- 差异记录告警，人工或自动补偿。

### 真实案例

- **前司收银**：对接微信/支付宝，支付回调 + 主动查询兜底 + 每日对账。
- **微信支付**：V3 接口，证书+签名，回调重试策略。
- **美团支付**：聚合支付（多渠道）+ 清结算系统。

### 对比 / 方案演进

| 方案 | 说明 |
|------|------|
| 直连渠道 | 直接对接微信/支付宝，成本低，运维各自对接 |
| 聚合支付（Ping++/收钱吧） | 统一接口对接多渠道，省心但抽成 |
| 自建支付网关 | 大公司自建，统一收银台 + 风控 + 清算 |

### 面试话术

「支付系统核心是**资金安全、回调可靠、幂等、对账**。**支付流程**：创建支付单→调渠道统一下单→客户端拉起支付→渠道异步回调。**回调处理**先验签防伪造，再做幂等（查 pay_no 状态，已处理直接返回 SUCCESS），更新支付单状态后发 MQ 通知订单服务。**回调可靠性**两手：渠道有重试机制（不返回 SUCCESS 会重试 N 次），我方定时任务主动查询超时未回调的支付单补状态。**幂等**用 DB 状态机：`UPDATE...WHERE status=0`，并发只有一个成功。**退款**是逆向流程，独立退款单表，调渠道退款接口，同样幂等。**对账**每天凌晨拉渠道 T+1 对账单逐笔比对，发现长款/短款/金额不一致告警补偿。资金类强一致，支付单主从 + 每日备份。」

## 2.14 库存系统

### 为什么 / 痛点分析

库存（电商商品库存、前司原料/包材库存、12306 余票）难点：

1. **防超卖**：并发扣减不能为负。
2. **高并发**：秒杀场景瞬时高并发扣减。
3. **多仓/多门店**：库存分布，调度。
4. **预占/释放**：下单预占库存，支付成功确认，超时释放。
5. **一致性**：缓存与 DB 一致。

### 原理图解 + 代码

**库存扣减三阶段（预占模式）** 🔴：

```
1. 下单 → 预占库存（锁定，他人不可买）
2. 支付成功 → 确认扣减（真正出库）
3. 取消/超时 → 释放库存（归还）

对应状态：可用(available) → 预占(locked) → 已出库(consumed)
                ↑________________________|
                  释放(取消时)
```

**表设计**：

```sql
CREATE TABLE stock (
  id BIGINT PRIMARY KEY,
  sku_id BIGINT COMMENT '商品/原料ID',
  store_id BIGINT COMMENT '门店ID(多门店)',
  total_stock INT COMMENT '总库存',
  available_stock INT COMMENT '可用库存',
  locked_stock INT COMMENT '预占库存',
  version INT DEFAULT 0 COMMENT '乐观锁版本',
  KEY idx_sku_store (sku_id, store_id)
);
```

**扣减方案演进** 🔴：

```
V1: DB行锁 `SELECT...FOR UPDATE` → 简单但并发排队慢
V2: DB乐观锁 `UPDATE stock SET available=available-1 WHERE id=? AND available>=1`
    → 无锁，高并发下大量失败仍打DB
V3: Redis预扣(Lua原子) + DB兜底 → 主流，秒杀场景
V4: 分库分表 + 本地缓存预判 → 超大规模
```

**Redis Lua 预扣（核心）**：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if not stock or stock < tonumber(ARGV[1]) then
    return 0  -- 库存不足
end
redis.call('DECRBY', KEYS[1], ARGV[1])
return 1     -- 预扣成功
```

**缓存与 DB 一致性**：
- Redis 预扣成功后发 MQ，消费者扣 DB 真实库存（`WHERE available>=1` 兜底）。
- Redis 宕机重建：从 DB 加载 + 重放未确认的预占。

**12306 余票特殊难点（区间票）** 🔴：

```
车次 A→B→C→D，4个区间: AB, BC, CD, AC, AD, BD...
买A→C票 → 占用 AB 和 BC 两个区间的余票
买B→D票 → 占用 BC 和 CD 两个区间的余票

建模：每个区间一个余票字段
  seat_AB=100, seat_BC=100, seat_CD=100
买A→C: seat_AB--, seat_BC--
买B→D: seat_BC--, seat_CD--  (BC被两次扣减)

查A→D余票 = min(seat_AB, seat_BC, seat_CD)
```

### 真实案例

- **前司门店原料库存**：每门店独立库存，下单扣减，预警补货。
- **淘宝商品库存**：分仓库存 + 预占模式 + Redis 预扣。
- **12306 余票**：区间票建模 + 分库分表（按车次）+ 排队削峰。
- **盒马生鲜**：门店仓库存，履约时效。

### 对比 / 方案演进

| 方案 | 优 | 劣 |
|------|----|----|
| DB 行锁 | 强一致 | 慢 |
| DB 乐观锁 | 无锁 | 高并发失败多 |
| Redis 预扣+DB 兜底 | 主流，高性能 | 最终一致 |
| TCC（Try-Confirm-Cancel） | 强一致预占释放 | 业务侵入大 |

### 面试话术

「库存系统我用**预占模式 + Redis 预扣 + DB 兜底**。库存分三态：可用、预占、已出库。**下单预占**：Redis Lua 原子扣减可用库存（判库存+扣减原子），成功后发 MQ 异步扣 DB 真实库存（`WHERE available>=1` 兜底防超卖），同时记录预占。**支付成功**确认扣减（预占转已出库）。**取消/超时**释放预占（延时消息触发，归还库存）。**为什么不直接 DB 扣**：秒杀瞬时高并发，DB 行锁排队扛不住；Redis 预扣单机 10w+ QPS，拦 99% 请求。**缓存与 DB 一致**：Redis 预扣后 MQ 异步落 DB，Redis 宕机从 DB 重建。**多门店/多仓**：库存按 sku_id+store_id 维度存储，独立扣减。**区间票**（如 12306）按区间建模，买跨区间票扣多个区间余票，查余票取区间最小值。」

## 2.15 登录 / SSO 单点登录

### 为什么 / 痛点分析

登录和 SSO（前司商家后台多系统、多端登录）难点：

1. **会话管理**：分布式下 session 如何共享。
2. **安全性**：密码加密、防暴力破解、防盗号。
3. **多系统单点登录**：一处登录处处可用（SSO）。
4. **多端互踢/共存**：手机/PC 同时登录或互踢。
5. **OAuth 第三方登录**：微信/支付宝授权登录。

### 原理图解 + 代码

**Token 机制（JWT vs Session）** 🔴：

```
【Session 模式】
登录 → 服务端创建Session(存Redis) → 返回sessionId(Cookie)
请求带sessionId → 查Redis获取用户信息
缺点：服务端有状态，扩展需共享Session

【JWT 模式（主流）】
登录 → 服务端签发JWT(Header.Payload.Signature) → 客户端存
请求带JWT(Authorization头) → 服务端验签(无状态) → 解析用户
优点：无状态、易扩展
缺点：无法主动失效（需配合黑名单）
```

**JWT 结构**：

```
Header.Payload.Signature（Base64编码，点分隔）

Header: {"alg":"HS256","typ":"JWT"}
Payload: {"userId":123,"username":"store_admin","exp":1690000000,"iat":1690000000}
Signature: HMAC-SHA256(base64(Header)+"."+base64(Payload), secretKey)

特点：Payload 可解码（不要存敏感信息），Signature 防篡改
```

**SSO 单点登录（核心）** 🔴：

```
场景：前司有订单系统、营销系统、库存系统多个子系统，一处登录全部可用

【CAS 模式（Central Authentication Service）】
1. 用户访问子系统A(未登录) → 跳SSO认证中心
2. SSO中心验证账号密码 → 生成Ticket → 写SSO域Cookie(全局会话)
3. 重定向回子系统A带Ticket → 子系统A向SSO校验Ticket → 建立本地会话
4. 用户访问子系统B → 跳SSO中心 → SSO Cookie存在 → 直接返回Ticket给B → B建本地会话
   （用户无感，不用再输密码）

【OAuth2 模式（第三方登录）】
微信登录 → 跳微信授权页 → 用户同意 → 回调带code → 服务端用code换access_token → 拉用户信息
```

**表设计**：

```sql
-- 用户表
CREATE TABLE sys_user (
  id BIGINT PRIMARY KEY,
  username VARCHAR(50) UNIQUE,
  password CHAR(64) COMMENT 'BCrypt加密',
  salt VARCHAR(32),
  phone VARCHAR(20),
  status TINYINT COMMENT '0禁用 1正常',
  last_login_time DATETIME
);

-- 登录会话（配合JWT黑名单/续期）
CREATE TABLE login_session (
  token_id VARCHAR(64) PRIMARY KEY,
  user_id BIGINT,
  device TINYINT COMMENT '1web 2app 3小程序',
  login_time DATETIME,
  expire_time DATETIME,
  KEY idx_user (user_id)
);
```

**安全性设计** 🔴：
- **密码加密**：BCrypt（带盐，抗彩虹表），不用 MD5。
- **防暴力破解**：登录失败 N 次锁定账号、IP 限流、图形验证码。
- **Token 安全**：HTTPS 传输、短期有效（如 2h）+ Refresh Token 续期、敏感操作二次验证。
- **多端互踢**：登录时清除该用户其他 Token。
- **JWT 失效**：维护 Redis 黑名单（登出/踢人时加入）。

### 真实案例

- **前司商家后台 SSO**：商家一个账号登录订单/营销/库存多个子系统，CAS 或 OAuth2。
- **微信开放平台 OAuth**：第三方应用用微信登录。
- **阿里云/钉钉**：企业 SSO，LDAP 集成。

### 对比 / 方案演进

| 方案 | 优 | 劣 |
|------|----|----|
| Cookie+Session | 简单 | 有状态、扩展难（需共享Session） |
| **JWT** | 无状态、易扩展 | 无法主动失效（需黑名单） |
| SSO(CAS) | 多系统一处登录 | 实现复杂 |
| OAuth2 | 第三方授权、标准化 | 流程复杂 |

**演进**：Session（单机）→ Session+Redis（分布式共享）→ JWT（无状态主流）→ SSO（多系统）→ OAuth2（开放授权）。

### 面试话术

「登录我用 **JWT 无状态 Token + Redis 黑名单**。登录成功签发 JWT（Header.Payload.Signature），Payload 存 userId，签名防篡改，客户端存 Token 每次请求带 Authorization 头。**为什么不用 Session**：分布式下需共享 Session（Redis），有状态扩展麻烦；JWT 无状态，服务端验签即可，易水平扩展。**JWT 缺点**是无法主动失效，配合 Redis 黑名单解决（登出/踢人时把 Token 加入黑名单，验签时检查）。**安全**：密码用 BCrypt 加盐加密（抗彩虹表），登录失败 5 次锁定，IP 限流防爆破，Token 短期有效（2h）+ Refresh Token 续期。**SSO 多系统**用 CAS 模式——认证中心统一登录，子系统通过 Ticket 建立本地会话，用户在一处登录后访问其他子系统免登。**第三方登录**用 OAuth2（微信授权码模式）。**多端**通过 device 字段区分，支持互踢。」

# 第三章 大厂开放题（字节/美团/阿里风格）

这类题没有标准答案，考的是**思维广度**和**对系统的理解**。答题要点：

1. **先澄清边界**：不要默认假设，问清楚规模、功能、约束。
2. **先全局后细节**：画高层架构，再深入核心模块。
3. **主动讲权衡**：每个选择讲为什么 + 替代方案代价。
4. **结合实际经验**：举真实项目踩坑案例。
5. **暴露瓶颈**：主动识别单点/热点并给方案。

**常见开放题清单**：

- 设计一个朋友圈（综合：Feed 流推拉 + 图片/视频存储 + 点赞评论 + 隐私）。
- 设计一个抢红包（秒杀 + 二倍均值算法）。
- 设计 12306（余票扣减 + 区间票建模 + 海量查询）。
- 设计一个监控告警系统（TSDB + 告警风暴收敛）。
- 设计一个分布式 ID 服务（雪花/Leaf + 时钟回拨）。
- 设计一个限流平台（Sentinel + 多维度规则）。
- 设计一个配置中心（长轮询 + 灰度 + 多环境隔离）。
- 设计一个抢券系统（领券预扣 + 核销幂等 + 防刷）。
- 设计亿级数据报表系统（OLAP：ClickHouse/Doris + Flink 实时）。
- 设计一个全局唯一订单号（业务前缀 + 时间 + 雪花）。
- 设计一个延迟任务平台（时间轮 + RocketMQ 延时消息）。
- 设计一个短链系统（发号器 + Base62 + 302 统计）。

**回答模板**：需求澄清 → 容量估算 → 高层架构 → 核心模块深入 → 扩展性 → 权衡。

# 第四章 答题加分技巧

1. **先问需求**：不问就开画 = 减分。问"用户量级、读写比、一致性、延迟、是否需要XX功能"。
2. **先估算**：体现"规模感知"，算 QPS/存储/机器数，数字要合理。
3. **画图要清晰**：客户端→网关→服务→存储分层，箭头标数据流。
4. **讲取舍**：每个选择讲为什么 + 放弃方案的代价（"我考虑过A方案，但因为它XX，所以选B"）。
5. **主动暴露瓶颈**：识别单点/热点（"这里 Redis 是单点，我做主从+哨兵"）。
6. **结合实际经验**："我们茶饮 SaaS 平台场景踩过坑，所以这里用 XX，当时遇到 XX 问题"。
7. **不会就说思路**：别装懂，"这块没做过，我的思路是…"，展示思考过程比硬编强。
8. **时间管理**：按 7 步节奏走，别陷细节，面试官打断就切换。
9. **使用专业术语**：QPS/TPS、最终一致、CAP、分库分表、削峰填谷、读写分离、幂等、降级熔断。
10. **画数据流**：不光画组件框图，要画出请求怎么流转（读写路径分开）。
11. **提监控**：主动说"上线后我会监控 XX 指标，告警阈值 YY"，体现运维意识。
12. **提灰度**：发布提灰度（按用户/门店灰度），体现工程严谨。
