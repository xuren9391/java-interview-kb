# 第一篇 消息队列（MQ）

## 1.1 MQ 的三大作用 🟢

### ① 为什么/痛点
单体应用里，A 调 B 是同步 RPC：A 必须等 B 返回才能继续。一旦 B 慢（或挂），A 跟着慢（或挂），**故障扩散**。高峰流量直接打到 DB，DB 抗不住就雪崩。MQ 就是中间的"蓄水池"，让生产消费解耦、异步、削峰。

### ② 原理图解
```
同步调用（无 MQ）：              异步解耦（有 MQ）：
  A → B → C （串行，RT 叠加）      A → MQ ─┬→ B
  RT = RT_A + RT_B + RT_C                  └→ C
                                          A 立即返回，B/C 异步处理
```

### ③ 真实案例（茶饮 SaaS 场景
**点单 → 发券 → 通知**：用户下单后，原本同步调用券服务发新人券、调用通知服务发短信、调用积分服务加积分，3 个下游接口累加 RT 接近 1s。改造为下单只写订单库 + 发一条 MQ，券/通知/积分各自订阅消费，**下单接口 RT 从 2s 降到 400ms**（用户最关心的核心链路只保留写库）。

### ④ 对比/边界
| 作用 | 解决问题 | 代价 |
|------|---------|------|
| 解耦 | 生产消费互不依赖 | 引入 MQ 故障点、运维成本 |
| 异步 | 写入即返回，提响应速度 | 实时性下降、需保证最终一致 |
| 削峰 | 突发流量入队，消费端按自己节奏 | 积压风险、需监控 |

**边界**：实时性要求极高（如风控拦截、支付鉴权）不适合异步化；强一致场景慎用。

### ⑤ 面试话术
「MQ 在我们项目里主要做三件事：解耦、异步、削峰。最典型的是下单链路，原本下单要同步调券、积分、通知三个下游，RT 接近 2 秒。我们把非核心的券发放、积分、通知改成发 MQ 异步消费，下单接口 RT 降到 400ms，这就是异步+解耦。大促高峰订单量是平时 10 倍，订单消息先进 Kafka 削峰，消费端按 DB 承受能力慢慢消费，不会压垮 DB，这就是削峰填谷。」

## 1.2 主流 MQ 对比 🔴🔴

### ① 为什么/痛点
不同业务对 MQ 的诉求不同：日志要吞吐、电商交易要事务和延时、金融要可靠不丢。没有银弹，必须按场景选型。

### ② 对比表
| | Kafka | RocketMQ | Pulsar | RabbitMQ |
|---|-------|----------|--------|----------|
| 来源 | LinkedIn（大数据） | 阿里（电商） | Yahoo（云原生） | Erlang |
| 吞吐 | **极高**（百万级） | 高（十万级） | 高 | 中 |
| 延迟 | ms | ms | ms | μs（低） |
| 顺序 | 分区有序 | 严格顺序（一款） | 分区有序 | 不保证 |
| 事务 | 弱 | **强**（半消息+回查） | 支持 | 弱 |
| 延时 | 无原生 | **原生**（18 等级） | 支持 | 插件 |
| 存算 | 耦合 | 耦合 | **分离**（BookKeeper） | 耦合 |
| 适用 | 日志/大数据/流 | 电商业务消息 | 云原生/多租户 | 中小项目 |

### ③ 真实案例（茶饮 SaaS 场景
项目里 **Kafka 做订单/行为日志、RocketMQ 做业务消息**（订单状态变更、支付回调、券发放）。日志量极大但允许少量丢失，用 Kafka 充分发挥吞吐；业务消息要求不丢、要延时（下单 30 分钟未支付自动取消，用 RocketMQ 延时等级 16 即 30min）。

### ④ 怎么选？🔴（选型决策树）
```
是日志/大数据/流处理？ ──是──→ Kafka（吞吐王）
      │否
是电商交易，需事务/延时/顺序？ ──是──→ RocketMQ
      │否
要多租户/存算分离/弹性扩缩？ ──是──→ Pulsar
      │否
中小项目、复杂路由、AMQP？ ──是──→ RabbitMQ
```
- **日志、大数据、流处理**：Kafka（吞吐王）。
- **业务消息（订单、交易，需事务/延时）**：RocketMQ。
- **多租户、云原生、存算分离弹性**：Pulsar（较新）。
- **中小项目、协议丰富（AMQP）、复杂路由**：RabbitMQ。

### ⑤ 面试话术
「我们公司是混合用：日志和行为数据走 Kafka，因为吞吐高、允许少量丢；业务消息像订单、支付回调、券发放走 RocketMQ，因为它原生支持事务消息和延时等级，下单 30 分钟未支付自动取消就是用 RocketMQ 延时消息。选型核心是看场景——要吞吐选 Kafka，要业务可靠性选 RocketMQ，要云原生弹性选 Pulsar。」

## 1.3 Kafka 核心架构 🔴🔴

### ① 为什么/痛点
单机单队列吞吐有上限，无法横向扩展。Kafka 用 **Topic 分区 + 副本** 的设计，让单个逻辑 topic 可以横向拆到多台机器并行读写，同时用副本保证可用性。

### ② 原理图解
```
Producer → Topic（逻辑） → Partition（物理，分区内有序） → Replica（副本）
                              ↓
        Broker（节点）← Leader / Follower（ISR 同步副本）
                              ↑
                       Consumer Group（消费者组，分区独占消费）
```

**存储结构**（这是 Kafka 高吞吐的根基）：
```
Topic: order-topic
 ├─ Partition 0  →  [msg0][msg1][msg2]...  （每个 partition 是一个目录）
 │                   ├─ 00000000000000000000.log   ← 顺序追加的日志段(Segment)
 │                   ├─ 00000000000000000000.index ← 偏移量稀疏索引
 │                   └─ 00000000000000000000.timeindex
 ├─ Partition 1  →  [msg0][msg1]...
 └─ Partition 2  →  [msg0][msg1]...

每个 Broker：  Leader(P0)  Follower(P1)  Follower(P2)   ← 副本分散在不同 broker
```

### 关键概念
- **Partition**：主题分区，**单分区内有序**。分区数 = 并发度。
- **Replica**：副本。**Leader** 负责读写，**Follower** 同步。
- **ISR（In-Sync Replicas）**：与 Leader 保持同步的副本集合，落后太多（`replica.lag.time.max.ms` 默认 10s）会被踢出。
- **Offset**：消费者在分区的消费位置。
- **Consumer Group**：组内消费者平分分区（一个分区只被组内一个消费者消费）。

### ③ 真实案例（茶饮 SaaS 场景
订单消息 topic `order-created`，按 `orderId.hashCode() % partitionCount` 路由，保证同一订单的创建/支付/取消消息进同一分区，单分区内有序。分区数设 12，对应 12 个消费者并发，单 partition 单线程消费保证顺序。

### ④ 对比/边界
- Kafka 顺序只在**单分区内**保证，跨分区不保证。
- 分区数不是越多越好：分区多 → 文件句柄多、Leader 选举慢、客户端内存多。
- 经验：单 broker 分区数建议 < 1000，集群总分区数 < 数万。

### ⑤ 面试话术
「Kafka 三层概念：Topic 逻辑分类，Partition 是物理并行单元也是有序单元，Replica 是高可用副本。读写都走 Leader，Follower 从 Leader 拉数据同步，跟不上就被踢出 ISR。消费者组里一个分区只给一个消费者，所以分区数就是并发上限。我们订单 topic 设 12 个分区，按 orderId 哈希路由，保证同一订单消息有序，又能 12 路并发消费。」

## 1.4 Kafka 高吞吐的 6 大原因 🔴🔴 必精通

### ① 为什么/痛点
大数据场景下 Kafka 要扛百万级 TPS。传统消息中间件（如 ActiveMQ）每条消息一次网络 IO + 一次磁盘随机写，性能上不去。Kafka 从磁盘、网络、内存多个层面把 IO 压到极致。

### ② 原理图解 + 关键参数
1. **顺序写磁盘**（append）：磁盘顺序写 >> 随机写（HDD 差 100 倍，SSD 也有数量级）。Kafka 只追加写日志段，不修改已写数据。
   ```
   .log 文件：  [msg0]→[msg1]→[msg2]→...   永远往后追加
   ```
2. **页缓存 PageCache**：写操作系统的 page cache，OS 异步刷盘。Kafka 不维护堆内缓存，复用 OS 缓存。重启后缓存仍在。
3. **零拷贝（sendfile）**：数据直接从内核到网卡，不进用户空间（详见 Java 核心篇零拷贝）。
   ```
   传统：磁盘→内核→用户空间→socket缓冲→网卡  （4次拷贝，4次上下文切换）
   sendfile：磁盘→内核→网卡                    （2次拷贝，2次上下文切换）
   ```
4. **批量发送**：生产者攒批 + 压缩（snappy/lz4/gzip），减少网络/IO 次数。
   - `linger.ms=5`（攒 5ms）、`batch.size=16384`（16KB）。
5. **分区并行**：水平扩展，分区数 = 并发度。
6. **Pull 模式**：消费者按自己能力拉，不压垮消费端（vs Push 模式）。批量拉（`fetch.min.bytes`）。

### ③ 真实案例（茶饮 SaaS 场景
门店行为埋点日志，每秒百万条写入 Kafka。生产端配 `linger.ms=10` + `compression.type=lz4` + `batch.size=65536`，攒批压缩后吞吐翻倍；消费者端批量拉取后写 ClickHouse，单机扛住百万级日志不丢。

### ④ 对比/边界
| 优化 | 适用 | 代价 |
|------|------|------|
| 顺序写 | 所有写 | 不支持修改/删除单条（只能标记+compaction） |
| PageCache | 大内存机器 | 进程崩溃缓存不丢（OS 管）但机器宕电丢 |
| 零拷贝 | 消费读 | 数据不进用户空间，无法在传输中改 |
| Pull | 消费端 | 实时性略差（攒批） |

### ⑤ 面试话术
「Kafka 快主要六点：第一是顺序写磁盘，只 append 不改，磁盘顺序写比随机快百倍；第二用操作系统的 PageCache 而不是 JVM 堆内存，避免 GC 且重启缓存还在；第三零拷贝 sendfile，数据从内核页缓存直接到网卡不进用户态；第四批量发送+压缩，生产者攒批用 lz4；第五分区并行，水平扩展；第六消费者 Pull 模式，按自己能力批量拉。这六点叠加让 Kafka 单机能扛百万 TPS。」

## 1.5 MQ 三大经典问题 🔴🔴🔴 必精通

### 问题一：消息可靠性（不丢失）

#### ① 为什么/痛点
MQ 链路长（生产者→网络→Broker→网络→消费者），任一环节都可能丢。丢消息=业务数据丢失（订单丢了、扣款丢了），不可接受。

#### ② 全链路三环节 + 关键参数
```
Producer → Broker → Consumer
```

**① 生产端不丢**：
- Kafka：`acks=all`（所有 ISR 确认）+ `retries=Integer.MAX_VALUE`（失败重试）+ 回调确认。
- RocketMQ：同步发送 + 重试（`retryTimesWhenSendFailed=2`）。

**② Broker 不丢**：
- Kafka：`min.insync.replicas >= 2`（至少 2 个副本）+ `acks=all` + `unclean.leader.election.enable=false`（禁止非 ISR 副本当 leader）。
- RocketMQ：同步刷盘（SYNC_FLUSH）+ 主从同步复制。

**③ 消费端不丢**：
- 关闭自动 ack，业务处理完**手动 ack**（Kafka 手动 commit offset）。
- 幂等保证重复消费安全。

```java
// Kafka 消费者手动提交 offset（业务完成后才提交）
props.put("enable.auto.commit", "false"); // 关闭自动提交
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        processBusiness(record.value()); // 先处理业务
    }
    consumer.commitSync(); // 业务成功后再提交 offset，保证 at-least-once
}
```

#### ③ 真实案例（茶饮 SaaS 场景
**支付回调消息**：第三方支付平台回调通知支付结果，必须不丢。生产端同步发送 + acks=all；Broker 同步刷盘 + 2 副本；消费端手动 ack + 业务幂等（订单号唯一约束兜底）。

#### ④ 对比/边界
可靠性越高性能越低（同步刷盘、acks=all 都拖慢）。要在可靠性和性能间权衡——日志可丢可不丢，交易不能丢。

#### ⑤ 面试话术
「消息不丢要保证三段：生产端用同步发送+acks=all+重试；Broker 配多副本+min.insync.replicas=2+关闭脏选举；消费端关自动 ack，业务处理完手动 commit。我们支付回调就是这样，三层防护保证消息必达，再叠加业务幂等兜底重复。」

### 问题二：消息重复（exactly-once）

#### ① 为什么/痛点
网络可能让 ack 丢失，生产者重发；消费者处理完业务、ack 前 crash，重启重新消费。**MQ 只能保证 at-least-once，要 exactly-once 必须业务幂等**。

#### ② 幂等方案 🔴 + 代码
1. **唯一约束**：业务 ID 唯一键，重复插报错忽略。
2. **乐观锁（版本号）**：`UPDATE ... WHERE version=v`。
3. **状态机**：业务有状态流转（订单 已支付→已发货，重复消息改不了已支付的）。
4. **去重表**：记录已处理的 msg_id，新消息先查去重表。
5. **Redis 分布式锁**：`SET msg_id NX EX`。

```sql
-- 方案1：唯一约束（券领取，user_id+activity_id 唯一）
INSERT INTO coupon_receive(user_id, activity_id, coupon_code)
VALUES(#{uid}, #{aid}, #{code})
ON DUPLICATE KEY UPDATE update_time=NOW(); -- 重复直接忽略

-- 方案3：状态机（订单状态只能往前走）
UPDATE `order` SET status='PAID', pay_time=NOW()
WHERE order_no=#{orderNo} AND status='CREATED'; -- 已支付再收到消息改不了
```

**Kafka 的事务**（exactly-once）：producer 幂等（`enable.idempotence=true`，基于 PID+seq 去重）+ 事务（consume-process-produce 原子），适合流处理。但**跨系统（如写 DB）仍需业务幂等**。

#### ③ 真实案例（茶饮 SaaS 场景
**优惠券发放幂等**：同一用户同一活动只能领一次。用 `user_id + activity_id` 数据库唯一索引，重复消息插入报 `DuplicateKeyException` 直接 catch 忽略，绝不多发券。高峰期 Redis 缓存命中 85%，少量穿透到 DB 的请求靠唯一约束兜底。

#### ④ 对比/边界
| 方案 | 实现难度 | 性能 | 适用 |
|------|---------|------|------|
| 唯一约束 | 低 | 高（DB 索引） | 插入类（领券、注册） |
| 状态机 | 低 | 高 | 状态流转类（订单） |
| 去重表 | 中 | 中（多一次查询） | 通用，但要清表 |
| Redis 锁 | 中 | 极高 | 高并发去重 |

#### ⑤ 面试话术
「消息重复的根本原因是网络不可靠导致 ack 丢失，MQ 只能保证至少一次。要 exactly-once 必须业务幂等，方案有：唯一约束（我们券领取用 user_id+activity_id 唯一索引）、状态机（订单状态只能往前走）、去重表、Redis 锁。核心思想是让重复执行和一次执行结果相同。」

### 问题三：消息顺序

#### ① 为什么/痛点
订单 创建→支付→发货，必须按顺序消费。乱序会导致"先发货后支付"的业务错误。Kafka 多分区并行消费保证不了全局有序。

#### ② 方案 🔴 + 原理图
```
全局有序（性能差）：  单分区，单消费者   →  吞吐 = 单分区上限
分区有序（推荐）  ：  按业务 key 路由到同一分区，单分区内串行消费
                    Producer 按 orderId%N 选分区
                    Partition0:[订单A创建][订单A支付][订单A发货]  ← 单线程消费，有序
                    Partition1:[订单B创建][订单B支付][订单B发货]  ← 并发，不同订单互不影响
```

- **生产端**：key hash 分区（`orderId % partitionCount`）。
- **消费端**：单分区单线程；若要并发，按 key 分发到内存队列各自串行（RocketMQ MessageQueueSelector）。
- **代价**：牺牲并行度，热点 key 成瓶颈。

```java
// Kafka Producer 按 orderId 路由（保证同订单进同分区）
ProducerRecord<String, String> record = 
    new ProducerRecord<>("order-topic", orderId, message); // 第二参是 key
producer.send(record);
```

#### ③ 真实案例（茶饮 SaaS 场景
订单状态变更消息（创建→支付→出餐→完成），用 `orderNo` 做 key 路由到同一 partition，消费端单线程消费单分区，保证同一订单状态有序。不同订单并行互不影响。

#### ④ 对比/边界
- 全局有序：单分区，吞吐瓶颈，只适合低吞吐场景。
- 分区有序：推荐方案，但要热点 key 防护（某大订单流量集中）。
- RocketMQ 严格顺序：单 broker 单队列串行，性能差，金融场景才用。

#### ⑤ 面试话术
「消息顺序的核心是局部有序而非全局有序——全局有序要单分区单消费者，吞吐极差。实际用分区有序：生产端把同一业务 key（如 orderId）路由到同一分区，消费端单线程消费单分区，这样同一订单消息有序，不同订单并行。代价是热点 key 会成瓶颈，必要时按二级 key 拆分。」

## 1.6 延时消息 🟡

### ① 为什么/痛点
很多业务有"延迟任务"需求：下单 30 分钟未支付自动取消、券领取后 7 天过期提醒。定时任务轮询 DB 效率低、有延迟。

### ② 原理图解 + 方案
```
RocketMQ 延时消息原理：
Producer → Broker（消息存到 SCHEDULE_TOPIC_XXXX，按延时等级分队列）
                ↓ 后台定时任务（每级一个 ConsumeQueue）扫描到期
            到期 → 改写回真实 topic → Consumer 可消费
```
- **RocketMQ** 原生 18 等级（1s/5s/10s/30s/1m/2m/.../2h）。
- **通用方案**：
  - Redis ZSet（score=执行时间戳）扫描。
  - **时间轮**（HashedWheelTimer，多层）——Netty、Kafka 都用。
  - MQ + 多级延迟（Kafka 无原生需自建）。

```java
// RocketMQ 延时消息（订单 30 分钟自动取消）
Message msg = new Message("OrderTimeoutTopic", "TAG", orderNo.getBytes());
msg.setDelayTimeLevel(16); // 16 = 30min（RocketMQ 延时等级表）
producer.send(msg);
```

### ③ 真实案例（茶饮 SaaS 场景
**订单超时取消**：用户下单后未支付，30 分钟后自动取消、回滚库存、退优惠券。用 RocketMQ 延时等级 16（30min），消费端收到消息检查订单状态，仍是"待支付"则取消。比定时任务轮询 DB 准时、压力小。

### ④ 对比/边界
| 方案 | 精度 | 吞吐 | 复杂度 |
|------|------|------|--------|
| RocketMQ 18 等级 | 等级固定（不能任意时间） | 高 | 低（原生） |
| Redis ZSet | 秒级 | 中 | 中 |
| 时间轮 | ms 级 | 极高 | 高（自研） |
| 定时任务轮询 | 分钟级、有延迟 | 低 | 低 |

### ⑤ 面试话术
「延时消息最常用的是 RocketMQ 原生 18 等级，原理是消息先存到内部 schedule topic，后台定时任务扫描到期再投递。我们订单 30 分钟未支付自动取消就是用它，比定时扫库准时且省 DB 压力。如果要任意时间精度，可以用 Redis ZSet 或自研时间轮（Netty 的 HashedWheelTimer）。」

---

## 1.7 消息积压处理 🔴（线上高频故障）

### ① 为什么/痛点
消费速度 < 生产速度，消息持续堆积，磁盘告警、内存爆、最终雪崩。常见原因：消费者慢（DB 慢、外部接口慢）、消费者挂了、消费逻辑死循环。

### ② 处理流程 + 关键点
```
发现积压告警
   ↓
1. 临时扩容消费者（同 group）── 注意：Kafka 消费者数 ≤ 分区数才有用！
   ├─ 消费者数 > 分区数：多余消费者空闲
   └─ 解决：先转发到新 topic（分区更多），再用更多消费者处理
   ↓
2. 根因排查
   ├─ 消费者慢：DB 慢/外部接口慢 → 优化 SQL、加缓存、异步化、批量化
   ├─ 消费者挂：OOM/异常 → 重启 + 修复 bug
   └─ 死循环：阻塞消费 → 隔离问题消息到死信队列
   ↓
3. 长期治理
   └─ 积压量监控告警、容量评估、扩容预案
```

### ③ 真实案例（茶饮 SaaS 场景
大促期间订单消息消费端写 MySQL 慢，积压 100w 条。紧急方案：先把消息转发到一个 60 分区的新 topic，再起 60 个消费者批量写库（每 100 条一批 insert），2 小时清完。根因是订单表索引不合理，后续优化索引 + 改批量写入。

### ④ 对比/边界
- Kafka 扩消费者受分区数限制；RocketMQ 队列数可动态加。
- 不能盲目重启消费者，要先确认是慢还是挂。

### ⑤ 面试话术
「积压核心是消费跟不上生产。第一步紧急扩容消费者，但 Kafka 消费者数不能超过分区数，超了就先转发到分区更多的新 topic 再扩。第二步找根因——通常是消费慢（DB 慢或外部接口慢），优化方法是批量、异步、加缓存。第三步长期治理，做积压监控告警。我们大促就遇到过，最后靠转发到 60 分区新 topic + 批量写库 2 小时清完。」

## 1.8 MQ 实战案例

### 📌 案例 1：消息丢失排查（前司）

**① 痛点/现象**：用户下单后偶尔没收到券发放通知。

**② 排查（全链路）**：
- 生产端：`acks=1`（Leader 确认即可），Leader 刚确认就宕机，Follower 还没同步 → 消息丢。

**③ 解决**：改 `acks=all` + `min.insync.replicas=2` + `unclean.leader.election.enable=false`。

**④ 话术**：「这是个经典丢消息场景。原来是 acks=1，Leader 确认就返回，但 Leader 刚确认就宕机、Follower 没同步就丢了。改成 acks=all + min.insync.replicas=2 后，必须 2 个副本都确认才算成功，杜绝这种丢失。」

---

### 📌 案例 2：消费重复导致重复扣款（前司）

**① 痛点/现象**：用户偶尔被扣两次款。

**② 排查**：消费者处理完业务、ack 前 crash → 重启重新消费 → 重复扣款。

**③ 解决**：业务幂等（msg_id 去重表 + 唯一约束）。

**④ 话术**：「消费重复是 at-least-once 的副作用。我们支付消费端处理完业务、ack 前 OOM 重启，offset 没提交，重启后重消费导致重复扣款。解决是加幂等：msg_id 写去重表 + 订单号唯一约束，重复消息直接忽略。」

---

### 📌 案例 3：消费乱序（前司）

**① 痛点/现象**：订单状态错乱（先发货后支付）。

**② 排查**：多分区并发消费，同订单消息分散到不同分区。

**③ 解决**：生产端用 `orderId` 做 key 路由到同一分区，单线程消费。

**④ 话术**：「订单状态乱序是因为多分区并发消费，同一订单消息散到不同分区。改成 Producer 用 orderId 做 key，hash 到同一分区，消费端单线程消费单分区，保证同订单有序。」

# 第二篇 分布式理论

## 2.1 CAP 定理 🔴🔴 必精通

### ① 为什么/痛点
分布式系统多节点，网络可能分区（断连）。分区发生时，要么拒绝服务保一致（CP），要么返回旧数据保可用（AP），不能既要又要。CAP 告诉你这个取舍是数学上证明的，不是工程问题。

### ② 原理图解
```
网络分区发生时：
  节点A ←──×──→ 节点B   （网络断了，互相通信不了）
  
  客户端写 A：A 要不要把数据同步给 B？
    ├─ 同步不了（分区）→ 要么 A 拒绝写（CP，保一致）
    └─ A 接受写但不一致（AP，保可用）
```

| 模型 | 含义 | 典型 |
|------|------|------|
| CP | 分区时牺牲可用性保一致性 | ZooKeeper（leader 选举期不可用）、etcd、HBase |
| AP | 分区时牺牲一致性保可用性 | Eureka、Nacos(AP)、Cassandra |
| CA | 不存在分区（单机） | 关系数据库 |

### ③ 真实案例（茶饮 SaaS 场景
注册中心选型：Nacos 默认 AP（分区时各节点都能注册返回，短暂不一致但可用），保证大促时服务发现不中断。强一致场景（如选主、配置）才用 ZK/etcd 这种 CP。

### ④ 常见误区 🔴
- "AP = 高可用" ❌。AP 指分区时仍响应（可能返回旧数据），不等于 SLA 高可用。
- "三选二" 实际是 P 必选（网络分区不可避免），C/A 二选一（分区时）。
- **注意**：CAP 的 C 是**线性一致性（强一致）**，不是 ACID 的 C（事务一致性）。
- CAP 是分区"期间"的取舍，没有分区时可以同时 CA。

### ⑤ 面试话术
「CAP 是分布式系统的铁律：一致性 C、可用 A、分区容错 P 三者分区时只能选两个。因为网络分区不可避免，P 必选，所以实际是在 CP 和 AP 间选。注册中心我们选 Nacos 默认 AP，因为服务发现短暂不一致可以接受，但不能用——大促时发现不了服务是灾难。要强一致的协调场景（选主、分布式锁）才用 ZK、etcd 这种 CP。注意 AP 不等于高可用，AP 是分区时还能响应，但可能返回旧数据。」

---

## 2.2 BASE 理论 🟡

### ① 为什么/痛点
互联网业务（电商、社交）大部分场景要的是高可用 + 最终一致，不是金融级强一致。强一致代价太高（同步阻塞、性能差），BASE 是 CAP 在 AP 方向的实践指南。

### ② 内容
CAP 在 AP 的延伸：
- **Basically Available** 基本可用：允许损失部分可用性（响应时间增加、降级、限流）。
- **Soft state** 软状态：允许中间状态（数据同步中的不一致）存在。
- **Eventually consistent** 最终一致：保证最终一致（停止写入后，所有副本最终一致）。

```
强一致：写完立刻所有节点可读到最新值  → 同步，慢
最终一致（BASE）：写完短暂不一致，一段时间后一致  → 异步，快，业务可接受
```

### ③ 真实案例（茶饮 SaaS 场景
优惠券库存跨服务同步：券服务扣减后，异步发消息同步给订单服务、积分服务。短暂时间内各服务券余量不一致，但最终（秒级）一致。这就是 BASE——牺牲强一致换可用性和性能。

### ④ 对比/边界
- 强一致：银行转账、库存扣减（金融）。
- 最终一致（BASE）：电商订单、社交、积分、缓存——大多数互联网业务。

### ⑤ 面试话术
「BASE 是 CAP 在 AP 的实践：基本可用、软状态、最终一致。互联网业务大多用 BASE，比如我们券发放，券服务扣减后异步同步给订单、积分服务，短暂不一致但秒级最终一致。强一致代价太高，业务能容忍短暂不一致就用 BASE + 补偿机制兜底。」

---

## 2.3 一致性模型 🔴

### ① 为什么/痛点
"一致性"不是非黑即白，有强弱之分。不同业务需求选不同级别，理解清楚才能做架构选型。

### ② 各模型对比
| 模型 | 含义 | 代价 | 典型 |
|------|------|------|------|
| 强一致（线性一致） | 读一定读到最新写 | 高（同步） | ZK、etcd、Spanner |
| 顺序一致 | 所有节点看到操作顺序一致，但不一定实时 | 中 | ZK 写 |
| 因果一致 | 有因果关系的操作有序 | 中 | 评论系统 |
| 最终一致 | 停止写入后最终所有副本一致 | 低 | DNS、缓存、MySQL 主从 |

**最终一致变种**：
- **读己之写**（read-your-writes）：自己写完立刻能读到（朋友圈发完能看见）。
- **单调读**（monotonic read）：不会读到比上次更旧的数据。
- **单调写**（monotonic write）：同一客户端写顺序保留。

### ③ 真实案例（茶饮 SaaS 场景
- 强一致：分布式锁（Redis/ZK）、库存扣减。
- 最终一致：券缓存（Redis）与 DB 的同步、订单服务与积分服务的数据。

### ④ 面试话术
「一致性分级：最强是线性一致，读必读到最新写，ZK/etcd 提供；中间有顺序一致、因果一致；最弱是最终一致，停止写入后最终一致，缓存、DNS、主从同步都是。业务选型：要强一致用 ZK/etcd，能容忍短暂不一致用最终一致 + 补偿。我们券缓存就是最终一致，DB 是真源，缓存秒级同步。」

# 第三篇 分布式一致性算法 🔴

## 3.1 Raft 🔴🔴 推荐重点理解（比 Paxos 易懂）

### ① 为什么/痛点
多节点要达成一致（同一份数据、同一个 leader），但节点会宕机、网络会丢包。如何在不靠谱的硬件上构建可靠的"共识"？Raft 用"选主 + 日志复制"把问题拆成三个清晰子问题，比 Paxos 好理解也好实现。etcd、Consul、TiKV、Nacos CP 都用它。

### ② 三个子问题

#### ① Leader 选举 🔴
**节点状态机**：
```
   启动/超时                   获多数票                发现更高 term
  Follower ──────→ Candidate ──────→ Leader
     ↑                                  │
     └──────────────────────────────────┘
              (收到更高 term 心跳，降级)
```
- 正常时 Leader 定期发心跳（AppendEntries）给 Follower。
- Follower 超过选举超时（election timeout，随机 150-300ms）未收到心跳 → 变 Candidate。
- Candidate：term++，给自己投票，发 RequestVote 给其他节点。
- 获**多数票** → 成为 Leader，开始发心跳。
- 🔴 **一个 term 内每个节点只投一票** → 防止多个 leader（同一 term 不会有两个 Candidate 都获多数）。
- **随机超时** → 错峰选举，避免活锁。

#### ② 日志复制 🔴
```
客户端写请求
    ↓
1. Leader 收到 → 写本地日志（未 commit）
    ↓
2. 并行复制到所有 Follower（AppendEntries）
    ↓
3. 多数 Follower 确认 → Leader commit（应用到状态机）→ 返回客户端成功
    ↓
4. Leader 下一次心跳通知 Follower commit
```
- **多数派**（quorum）：N/2 + 1。5 节点需 3 个确认。

#### ③ 安全性
- **选举限制**：Candidate 的日志必须"至少和新"（up-to-date）才能被选为 Leader → 保证 Leader 包含所有已 commit 日志。
- **commit 限制**：Leader 只 commit 当前 term 的日志（防"已 commit 被覆盖"）。

### ③ 真实案例（茶饮 SaaS 场景
Nacos 集群用 Raft（CP 模式）选主：3 节点 Nacos，1 个 Leader 处理写，2 个 Follower 同步。Leader 宕机，剩余 2 个 Follower 超时选举，获多数（2 票）成新 Leader，服务不中断。这就是为什么 Nacos CP 模式强一致但选举期短暂不可用。

### ④ 对比/边界
| 算法 | 易懂性 | 应用 | 特点 |
|------|--------|------|------|
| Raft | 易（强 leader） | etcd/Consul/TiKV | 选主+日志复制，工程友好 |
| Paxos | 难（无 leader 基础版） | Chubby/Spanner | 更基础通用 |
| ZAB | 中（类 Raft） | ZooKeeper | 崩溃恢复+广播 |

### ⑤ 面试话术
「Raft 是我重点研究的共识算法，比 Paxos 好懂。它把共识拆三个子问题：选主、日志复制、安全性。选主用随机超时+一个 term 一票防止脑裂；日志复制是 Leader 收到写请求先写本地日志，并行复制到 Follower，多数确认就 commit 再通知 Follower，这就是多数派 quorum。Nacos CP 集群就是 Raft，3 节点 1 Leader 2 Follower，Leader 宕了剩余 2 票选新主。Raft 的核心是"多数派"，容忍少数节点故障。」

---

## 3.2 Paxos 🟡（了解）

### ① 为什么/痛点
Raft 之前的经典共识算法，更基础更通用，但难理解难实现。理解 Paxos 有助于理解分布式共识的本质。

### ② 内容
- **Basic Paxos**（单值）：Proposer/Acceptor/Learner，两阶段（Prepare/Accept）。
  ```
  Prepare：Proposer 提议编号 n 给 Acceptor，Acceptor 承诺不接受更小编号
  Accept：Proposer 发 Accept(n,value)，多数 Acceptor 接受 → 决议达成
  ```
- **Multi-Paxos**（多值）：Raft 的基础，选出稳定 Leader 跳过 Prepare。
- 应用：Google Chubby、Spanner。

### ③ 面试话术
「Paxos 是共识算法鼻祖，Raft 的基础。Basic Paxos 用 Proposer/Acceptor/Learner 三角色，两阶段 Prepare/Accept 达成单值共识。Multi-Paxos 选稳定 leader 跳过 Prepare 处理多值。它太复杂难实现，所以工程上多用 Raft（同源但更简单）。」

---

## 3.3 ZAB 协议 🟡

### ① 为什么/痛点
ZooKeeper 需要自己的共识协议（保证写强一致 + 主备切换），ZAB（ZooKeeper Atomic Broadcast）就是为 ZK 定制的，比 Raft 早。

### ② 内容
ZooKeeper 用，类似 Raft。
- 两阶段：**崩溃恢复**（选主）+ **消息广播**（两阶段提交变体）。
- **ZXID**（事务 ID）= epoch（32bit）+ counter（32bit）。
- epoch 类似 Raft term，counter 保证单 Leader 内有序。

```
消息广播（类似 2PC 但半数即可）：
  Leader ──Proposal──→ 所有 Follower
  Follower ──ACK──→ Leader
  Leader 收到半数 ACK ──Commit──→ 所有 Follower
```

### ③ 面场话术
「ZAB 是 ZK 的共识协议，类似 Raft 但更早。两阶段：崩溃恢复选主 + 消息广播写数据。ZXID = epoch + counter，epoch 类似 Raft term 标识主周期，counter 保证单 Leader 内有序。和 Raft 比，ZAB 的广播是"半数 ACK 就 commit"（2PC 变体），不是等多数确认。」

# 第四篇 分布式事务 🔴🔴 必精通

## 4.1 各种方案对比

### ① 为什么/痛点
微服务下，一次业务操作跨多个服务多个库（下单=订单服务建订单+库存服务扣库存+券服务扣券），任一服务失败要全部回滚。单库的 ACID 不管用了，要分布式事务方案。

### ② 对比表
| 方案 | 一致性 | 性能 | 复杂度 | 适用 |
|------|--------|------|--------|------|
| **2PC**（XA） | 强一致 | 差（同步阻塞） | 中 | 传统数据库、银行 |
| **3PC** | 强一致 | 差 | 高 | 很少用 |
| **TCC** | 强一致（业务层） | 好 | 高（3 方法） | 金融、核心交易 |
| **SAGA** | 最终一致 | 好 | 中（补偿复杂） | 长事务、多服务 |
| **本地消息表** | 最终一致 | 好 | 低 | 互联网主流 |
| **事务消息**（RocketMQ） | 最终一致 | 好 | 中 | 解耦场景 |
| **Seata AT** | 最终一致（默认） | 好 | 低（无侵入） | 主流微服务 |

### ③ 真实案例（茶饮 SaaS 场景选型
- **券发放 + 订单创建**（跨服务）：用本地消息表，最终一致。
- **核心交易**（支付扣款）：TCC，强一致。
- **下单链路**（订单+库存+券多服务）：Seata AT，无侵入低复杂度。

### ④ 话术
「分布式事务方案很多，核心是强一致 vs 最终一致的取舍。强一致（2PC/TCC）性能差、复杂；互联网业务多用最终一致（本地消息表、事务消息、Seata AT）。我们项目：券发放用本地消息表，下单多服务用 Seata AT，支付扣款用 TCC。」

---

## 4.2 2PC（两阶段提交）🟡

### ① 为什么/痛点
最经典的分布式事务方案，用一个协调者统一指挥所有参与者提交或回滚，保证强一致。

### ② 流程
```
阶段一 Prepare：
  协调者 → 各参与者："准备提交"
  各参与者：锁资源、写 undo/redo → 回 yes/no
阶段二 Commit/Rollback：
  全部 yes → 协调者发 commit
  任一 no → 协调者发 rollback
```

### ③ 问题
- **同步阻塞**：参与者锁资源等协调者指令，整个事务期间都不能干别的。
- **协调者单点**：协调者挂了，参与者一直阻塞。
- **参与者超时不一致**：协调者发了 commit 但部分参与者没收到 → 数据不一致。
- **性能差**：两轮网络 + 全程锁资源。

### ④ 面试话术
「2PC 是最经典的分布式事务，分 Prepare 和 Commit 两阶段，协调者统一指挥。优点强一致，缺点致命：同步阻塞（参与者全程锁资源）、协调者单点（挂了全卡死）、超时不一致。所以互联网基本不用，只有传统银行、XA 场景才用。」

---

## 4.3 TCC（Try-Confirm-Cancel）🔴

### ① 为什么/痛点
2PC 锁资源太久。TCC 把"锁资源"改成"业务层预留资源"（如冻结余额），不锁数据库，性能好但业务侵入大。

### ② 流程 + 代码
```
Try：预留资源（如冻结余额、预占库存）
  ├─ 成功 → Confirm
  └─ 失败 → Cancel
Confirm：真正扣减（用预留资源）
Cancel：释放预留
```

```java
// TCC 三个方法示例（扣款）
@TwoPhaseBusinessAction(name = "deductBalance", commitMethod = "confirm", rollbackMethod = "cancel")
public boolean tryDeduct(BusinessActionContext ctx, @BusinessActionContextParameter String userId, BigDecimal amount) {
    // Try：冻结金额（不真扣，标记冻结）
    accountService.freeze(userId, amount);
    return true;
}
public boolean confirm(BusinessActionContext ctx) {
    // Confirm：把冻结的真正扣掉
    accountService.deductFrozen(ctx.getActionContext("userId"), ctx.getActionContext("amount"));
    return true;
}
public boolean cancel(BusinessActionContext ctx) {
    // Cancel：解冻
    accountService.unfreeze(ctx.getActionContext("userId"), ctx.getActionContext("amount"));
    return true;
}
```

### ③ 三大坑（必答）
- **幂等**：Confirm/Cancel 可能被重试（网络问题），必须幂等。
- **空回滚**：Try 未执行但 Cancel 调用（Try 超时，全局回滚）→ Cancel 要判断 Try 是否执行过。
- **悬挂**：Cancel 先于 Try 到达（Cancel 后迟到的 Try 又来）→ Try 要判断是否已 Cancel。

### ④ 对比/边界
- **业务侵入大**，每操作写 3 个方法。
- 适合核心金融交易（支付、转账）。

### ⑤ 面试话术
「TCC 是业务层的两阶段：Try 预留资源、Confirm 确认、Cancel 回滚。优点不锁数据库性能好、强一致；缺点业务侵入大、要处理三大坑——幂等（Confirm/Cancel 重试）、空回滚（Try 没执行但 Cancel 来了）、悬挂（Cancel 后 Try 才到）。我们支付扣款用 TCC，因为是核心交易要强一致，但只用在少数核心场景。」

---

## 4.4 Seata 🔴🔴 主流

### ① 为什么/痛点
TCC 业务侵入大，2PC 性能差。Seata AT 模式做到了"无侵入 + 最终一致"，拦截 SQL 自动生成补偿，是微服务分布式事务的事实标准。

### ② 三种模式 + AT 原理

#### AT 模式（默认，无侵入）：基于本地事务 + undo log
```
一阶段（业务执行）：
  拦截 SQL → 执行本地事务（自动提交）
              + 记录 undo log（前后镜像，存入 undo_log 表）
              + 记录全局锁（行锁，key = 表名+主键）
二阶段提交：
  异步删 undo log（已成功，无需补偿）
二阶段回滚：
  根据 undo log 反向补偿（用前镜像还原数据）
```

- **隔离性**：全局锁实现写隔离；读默认 RC（要 RR 加 @GlobalLock）。

#### TCC 模式：手写 Try/Confirm/Cancel。
#### SAGA 模式：长事务，正向 + 补偿。

### 角色
```
   TM(@GlobalTransactional 发起)
    │ 申请全局事务 XID
    ↓
   TC（独立部署 Seata-Server，协调器）
    │ 分支注册/提交/回滚
    ↓
   RM（每个微服务的 DB，资源管理器）
```
- **TC**（Transaction Coordinator）：事务协调器，独立部署（Seata-Server）。
- **TM**（Transaction Manager）：事务管理器，发起方（@GlobalTransactional）。
- **RM**（Resource Manager）：资源管理器，参与方（每个数据库/服务）。

### ③ 真实案例（茶饮 SaaS 场景踩坑
跨服务下单（订单服务 + 库存服务 + 券服务），用 Seata AT。偶发库存扣了订单没建。排查：库存服务的 RM 没正确配置（数据源代理没生效）→ 全局事务回滚时库存 undo 没执行。**解决**：确保所有参与服务的 DataSource 被 Seata 代理（`@EnableAutoDataSourceProxy` 或启动参数）。

### ④ 对比/边界
| 模式 | 一致性 | 侵入 | 适用 |
|------|--------|------|------|
| AT | 最终一致 | 无（自动） | 主流微服务、增删改 |
| TCC | 强一致 | 高（3 方法） | 金融核心 |
| SAGA | 最终一致 | 中（补偿） | 长流程事务 |

### ⑤ 面试话术
「Seata 是微服务分布式事务主流，我们用 AT 模式无侵入。原理：一阶段拦截 SQL 执行本地事务同时记 undo log（前后镜像）和全局锁；二阶段成功就异步删 undo log，失败就根据 undo log 反向补偿。三个角色：TC 独立部署协调、TM 发起（@GlobalTransactional）、RM 是各服务 DB。我踩过坑——库存服务数据源代理没生效导致回滚失败，后来确保所有服务都配了代理。AT 适合增删改多的业务，但要强一致就上 TCC。」

---

## 4.5 本地消息表（互联网主流）🔴🔴

### ① 为什么/痛点
跨服务要保证"本地业务 + 发消息"原子（业务成功消息必发，业务失败消息不发）。直接业务后发消息，消息发失败就数据不一致。

### ② 流程
```
1. 业务表 + 消息表 在【同一个本地事务】里写
   → 保证业务和消息同时成功/失败
2. 定时任务扫描消息表，投递 MQ
3. 消费方处理完 ack，回调更新消息表状态
4. 失败重试 + 业务幂等
```

### ③ 真实案例（茶饮 SaaS 场景
**优惠券发放**：用户领券，券服务在同一个本地事务里写 `coupon_receive`（业务表）+ `coupon_message`（消息表）。定时任务每秒扫 `coupon_message` 未发送的，投递 MQ 通知订单/积分服务。消费方处理完回调更新消息状态为"已发送"。**优**：实现简单、最终一致、可靠（消息表持久化）。**劣**：消息表耦合业务、定时扫描有延迟（可改 binlog 监听即时投递）。

### ④ 面试话术
「本地消息表是互联网最常用的最终一致方案。核心思想：把业务数据和消息放同一个本地事务，保证原子；定时任务扫消息表投递 MQ；消费方处理完更新消息状态；失败重试 + 业务幂等。我们券发放就用它——券表和消息表同事务写，定时扫表投 MQ 通知订单积分服务。优点简单可靠，缺点是定时扫描有延迟，可以改 binlog 监听即时投递。」

---

## 4.6 RocketMQ 事务消息 🔴🔴

### ① 为什么/痛点
和本地消息表解决同一问题（本地业务+发消息原子），但不用业务表耦合消息表，由 MQ 原生支持。

### ② 流程
```
1. Producer 发"半消息"（消费者看不到）→ Broker 存储
2. 执行本地事务
3. 本地事务成功 → commit（消息可见）；失败 → rollback（删除）
4. 异常（无 commit/rollback）→ Broker 【回查】Producer → 根据本地事务状态决定
```

```java
// RocketMQ 事务消息
TransactionMQProducer producer = new TransactionMQProducer("group");
producer.setTransactionListener(new TransactionListener() {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            doLocalBusiness(); // 执行本地事务（如扣库存）
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 回查：根据业务表状态判断本地事务是否成功
        return isBusinessDone(msg) ? LocalTransactionState.COMMIT_MESSAGE 
                                   : LocalTransactionState.ROLLBACK_MESSAGE;
    }
});
producer.sendMessageInTransaction(msg, null); // 发事务消息
```

### ③ 对比/边界（vs 本地消息表）
| | 本地消息表 | 事务消息 |
|---|----------|---------|
| 业务侵入 | 有（要建消息表） | 低（实现回查接口） |
| 依赖 | 通用 MQ | RocketMQ |
| 实时性 | 定时扫描有延迟 | 实时 |
| 复杂度 | 低 | 中 |

### ④ 面试话术
「RocketMQ 事务消息解决"本地事务+发消息"原子问题。流程：先发半消息（消费者看不到）→ 执行本地事务 → 成功 commit 失败 rollback → 异常没回执就 Broker 回查。本质是用半消息 + 回查机制替代本地消息表，业务侵入更小、实时性更好。我们订单状态变更用事务消息保证订单库和下游通知一致。」

# 第五篇 分布式锁 🔴🔴 必精通

## 5.1 三种实现对比

### ① 为什么/痛点
多节点部署下，单机锁（synchronized/Lock）只锁单 JVM，跨节点失效。秒杀扣库存、抢券、定时任务防重复执行，都要跨节点的分布式锁。

### ② 对比表
| 实现 | 一致性 | 性能 | 可重入 | 可靠性 |
|------|--------|------|--------|--------|
| Redis（Redisson） | AP（高可用，可能不一致） | 高 | 支持（hash 计数） | 中（主从切换可能丢锁） |
| ZooKeeper | CP（强一致） | 中 | 支持（节点计数） | 高 |
| MySQL（唯一约束） | 强 | 低 | 难 | 高 |

### ③ 选型（前司）
- **高并发抢券**：Redis（Redisson），性能优先，业务幂等兜底。
- **选主、配置变更**：ZK，强一致。

### ④ 面试话术
「分布式锁三种实现：Redis、ZK、MySQL。Redis 性能最高但是 AP，主从切换可能丢锁；ZK 强一致可靠但性能不如 Redis；MySQL 用唯一约束，简单但性能差并发弱。选型看场景——高并发抢券我们用 Redis（Redisson 看门狗续期）+ 业务幂等兜底；要强一致的选主、配置用 ZK。」

---

## 5.2 Redis 分布式锁演进 🔴🔴

### ① 为什么/痛点
从简单 SET NX 到 Redisson 看门狗，是一步步踩坑演进出来的。面试常考演进过程和每步解决的问题。

### ② 演进 4 步

#### v1 简单版
```bash
SET key value NX PX 30000   # NX 不存在才设，PX 过期
```
**问题**：业务没执行完锁就过期 → 误删别人锁。

#### v2 加唯一 value + Lua
```lua
-- 加锁：value 用 UUID（标识自己）
-- 解锁：Lua 脚本判断 value 一致才删（保证"判断+删除"原子）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

#### v3 Redisson 看门狗 🔴
- 默认锁 30s，后台**看门狗线程**每隔 10s（1/3 周期）检查持有者还活着就续期。
- 可重入：hash 结构，key=锁名，field=线程ID，value=重入次数。
- 公平锁、读写锁、信号量都支持。

```java
// Redisson 加锁（看门狗自动续期）
RLock lock = redissonClient.getLock("coupon:lock:" + couponId);
try {
    // 不传过期时间，触发看门狗自动续期（默认30s，每10s续一次）
    lock.lock(); 
    // 业务逻辑（扣减券库存）
    deductCoupon(couponId);
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock(); // 只解锁自己持有的
    }
}
```

```
看门狗续期原理：
  线程获锁(30s) → 业务执行中...
       ↑              ↓
       └── 看门狗每10s检查：持有者还在？→ 是 → 续期到30s
                          → 否 → 不续（业务完成或宕机）
```

### ③ 真实案例（茶饮 SaaS 场景
**秒杀抢券**：高并发抢限量券，用 Redisson 分布式锁锁 `couponId`，防止超卖。锁里扣减 Redis 库存 + 异步落库。看门狗保证业务执行期间锁不丢。叠加业务幂等（用户+活动唯一约束）兜底极小概率丢锁。

### ④ 面试话术
「Redis 分布式锁演进有四个阶段：v1 SET NX PX 简单但有业务没完锁过期误删问题；v2 加唯一 value+Lua 解锁保证判断删除原子；v3 Redisson 看门狗——默认30s每10s续期，还有可重入（hash+计数）。我们抢券就用 Redisson，lock 不传过期时间触发看门狗自动续期，叠加业务幂等兜底。注意 Redis 是 AP，主从切换可能丢锁，强一致场景要 Redlock 或 ZK。」

---

## 5.3 Redlock（多节点）争议 🔴🔴

### ① 为什么/痛点
Redis 主从异步复制，主库加锁后宕机、从库晋升但锁没同步 → 锁丢失 → 并发。antirez 提出 Redlock 试图解决，但被 Martin Kleppmann 猛烈批评。

### ② Redlock 算法
```
向 N（奇数，如5）个【独立】Master 节点申请锁：
  client → 同时向 5 个独立 master 加锁
  获多数（3）成功，且耗时 < 锁有效期 → 加锁成功
  否则 → 向所有节点释放锁，加锁失败
```

### ③ Martin Kleppmann 批评 🔴
1. **GC 暂停**：客户端持锁后 GC 停顿，锁超时但客户端不知情，其他客户端获锁 → 并发。
2. **时钟漂移**：依赖各节点时钟，NTP 跳变会破坏假设。
3. **正确性 vs 性能**：为性能牺牲了正确性，不如直接用 ZK/etcd。

### ④ 结论
强一致场景用 ZK/etcd；高并发性能优先用 Redis，容忍极小概率失败 + 业务幂等兜底。

### ⑤ 真实案例（茶饮 SaaS 场景
**Redis 主从切换丢锁**：高并发抢券偶尔超发。排查：主库加锁 → 主库宕机 → 从库（锁未同步）晋升 → 锁丢失 → 并发。解决：业务幂等兜底（券领取唯一约束）；强一致场景改用 Redlock 或 ZK；Redis 主从同步配置 `WAIT` 命令等待同步。

### ⑥ 面试话术
「Redlock 是 antirez 解决 Redis 主从丢锁的方案——向多个独立 master 加锁，多数成功才算成功。但 Martin Kleppmann 批评它三点：GC 暂停会让客户端持锁不自知、依赖时钟漂移会破坏假设、为性能牺牲正确性。我们项目实际不用 Redlock，而是 Redis 单主 + 业务幂等兜底（券领取唯一约束），强一致场景才上 ZK。我的观点是 Redlock 理论上有缺陷，工程上用幂等兜底更实际。」

---

## 5.4 ZK 分布式锁 🔴

### ① 为什么/痛点
Redis 锁是 AP 有丢锁风险，强一致场景（选主、防重复执行）需要 CP 的锁。ZK 基于临时顺序节点实现，天然 CP。

### ② 原理
```
/lock
 ├─ seq-0001  ← 最小序号，获锁
 ├─ seq-0002  ← 监听 seq-0001 删除
 └─ seq-0003  ← 监听 seq-0002 删除（不是监听所有！）
```
- **临时顺序节点**：`/lock/seq-0001`、`/lock/seq-0002`...
- **最小序号获锁**。
- 其余节点**监听前一个节点删除事件**（不是监听所有）→ **避免羊群效应**（一个节点释放，所有等待者被唤醒争抢）。
- 客户端断开 → 临时节点自动删除 → 释放锁 + 通知后继。
- CP 特性，强一致可靠，但写性能不如 Redis。

### ③ 避免羊群效应（必答）
如果所有等待者都监听同一个节点（如 `/lock`），锁释放时所有等待者被唤醒争抢 = 羊群效应。改成**每个等待者只监听前一个节点**，前一个释放才唤醒下一个，串行化避免惊群。

### ④ 真实案例（茶饮 SaaS 场景
定时任务防多节点重复执行（如每天凌晨清算券）。用 ZK 锁：所有节点启动时创建临时顺序节点，最小序号的执行任务，其余监听前驱。Leader 宕机临时节点删除，下一个自动获锁，保证始终只有一个节点执行。

### ⑤ 面试话术
「ZK 分布式锁用临时顺序节点：所有客户端在 /lock 下创建顺序节点，最小序号获锁，其余监听前一个节点删除。关键是监听前一个而不是所有——避免羊群效应（一个释放全唤醒争抢）。客户端断开会话临时节点自动删除释放锁。ZK 是 CP 强一致可靠，但写性能不如 Redis，适合选主、定时任务防重这种要强一致的场景。」

---

# 第六篇 分布式 ID 🔴🔴

## 6.1 需求

### ① 为什么/痛点
分库分表后，单库自增 ID 会重复；UUID 无序导致 B+ 树索引碎片化；业务需要全局唯一、趋势递增、高性能、不暴露业务量（信息安全）的 ID。

### ② 五大要求
全局唯一、趋势递增（索引友好）、高性能、高可用、信息安全（不能暴露业务量）。

---

## 6.2 方案对比

### ② 对比表
| 方案 | 唯一 | 递增 | 性能 | 依赖 | 缺点 |
|------|------|------|------|------|------|
| UUID | ✅ | ❌ 随机 | 高 | 无 | 长度长、索引差、无序 |
| 数据库自增 | ✅ | ✅ | 低 | DB | 单点、瓶颈 |
| **号段模式**（美团 Leaf-segment） | ✅ | ✅ | 高 | DB | 可推测量（可改进） |
| **雪花算法**（Snowflake） | ✅ | ✅ | 极高 | 时钟 | 时钟回拨 |
| Leaf-snowflake | ✅ | ✅ | 极高 | ZK | 复杂 |
| Redis INCR | ✅ | ✅ | 高 | Redis | 持久化风险 |

### ③ 真实案例（茶饮 SaaS 场景选型
- **订单号**：雪花算法（高性能、趋势递增、不暴露真实订单量）。
- **券码**：业务规则生成（带活动标识）+ DB 唯一约束。
- 不用 UUID：订单表数据量大，UUID 无序导致索引碎片严重。

### ④ 面试话术
「分布式 ID 方案我熟悉的有：UUID（无序索引差，不用）、数据库自增（单点瓶颈）、号段模式（美团 Leaf，DB 取号段缓存本地）、雪花算法（时间戳+机器ID+序列号，性能极高）、Redis INCR（持久化风险）。我们订单号用雪花算法，因为高性能、趋势递增、不暴露订单量。雪花要处理时钟回拨，我们记录上次时间戳，回拨小等待大报错。」

## 6.3 雪花算法 🔴🔴 必精通

### ① 为什么/痛点
需要高性能（不依赖外部）、趋势递增（索引友好）、不暴露业务量的全局 ID。雪花用"时间戳 + 机器 + 序列"组合，本地生成无网络开销。

### ② 64 位结构
```
| 1bit 符号(0) | 41bit 时间戳(ms) | 10bit 机器ID | 12bit 序列号 |
```
- 41 bit 时间戳：可用约 69 年。
- 10 bit 机器：1024 台（可拆 5 机房 × 12 机器）。
- 12 bit 序列：同 ms 内 4096 个。

```java
public class SnowflakeIdGenerator {
    private final long epoch = 1288834974657L; // 起始时间戳
    private final long machineIdBits = 10L;
    private final long sequenceBits = 12L;
    private final long maxMachineId = ~(-1L << machineIdBits); // 1023
    private final long machineIdShift = sequenceBits;
    private final long timestampShift = sequenceBits + machineIdBits;
    
    private long machineId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;
    
    public synchronized long nextId() {
        long currentTimestamp = System.currentTimeMillis();
        // 🔴 时钟回拨处理
        if (currentTimestamp < lastTimestamp) {
            long offset = lastTimestamp - currentTimestamp;
            if (offset <= 5) {
                try { Thread.sleep(offset); } catch (InterruptedException e) {}
                currentTimestamp = System.currentTimeMillis();
                if (currentTimestamp < lastTimestamp) {
                    throw new RuntimeException("时钟回拨超阈值，拒绝生成ID");
                }
            } else {
                throw new RuntimeException("时钟回拨过大，报警");
            }
        }
        if (currentTimestamp == lastTimestamp) {
            sequence = (sequence + 1) & ~(-1L << sequenceBits);
            if (sequence == 0) { // 序列耗尽，等下一 ms
                currentTimestamp = tilNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }
        lastTimestamp = currentTimestamp;
        return ((currentTimestamp - epoch) << timestampShift)
                | (machineId << machineIdShift)
                | sequence;
    }
    private long tilNextMillis(long last) {
        long t = System.currentTimeMillis();
        while (t <= last) t = System.currentTimeMillis();
        return t;
    }
}
```

### ③ 时钟回拨问题 🔴🔴
- **现象**：服务器时间回退（NTP 同步、人为调整）→ 时间戳变小 → 可能生成重复 ID。
- **解决**：
  - 拒绝服务（回拨超阈值报警）。
  - 等待（睡眠到回拨后）。
  - 用历史最大时间戳。
  - Leaf-snowflake 用 ZK 分配 workerId + 记录上次时间戳（回拨小则等待，大则报错）。

### ④ 真实案例（茶饮 SaaS 场景
**雪花算法时钟回拨导致重复 ID**：订单号偶尔重复。排查：服务器 NTP 同步触发时钟回拨 → 雪花生成重复 ID。解决：记录上次时间戳，回拨超 5ms 等待，超 10ms 报警拒绝服务（或切到备用 worker）。

### ⑤ 面试话术
「雪花算法 64 位：1 符号位 + 41 时间戳（ms，69年）+ 10 机器ID（1024台）+ 12 序列号（同 ms 4096 个）。性能极高本地生成无依赖。最大坑是时钟回拨——NTP 同步或人为调时导致时间戳变小生成重复 ID。解决是记录上次时间戳，回拨小（5ms 内）等待，大就报错拒绝。我们订单号用雪花，线上踩过时钟回拨重复的坑，加了时间戳校验解决。Leaf-snowflake 用 ZK 分配 workerId + 持久化上次时间戳更彻底。」

---

## 6.4 美团 Leaf 🟡

### ① 为什么/痛点
雪花要管 workerId 和时钟回拨；号段模式要降低 DB 压力。Leaf 两种模式都覆盖。

### ② 内容
- **Leaf-segment**：DB 存 `max_id, step`，应用每次取一个号段（如 1-1000），用完再取。双 buffer 预加载避免等待。
  ```
  DB:  biz_tag | max_id | step
       order   | 1000   | 1000
  应用取号段：UPDATE 设置 max_id=max_id+step，返回旧 max_id 到新 max_id
  双 buffer：用到 10% 时异步预加载下一个号段
  ```
- **Leaf-snowflake**：ZK 持久顺序节点分配 workerId，解决时钟回拨。

### ③ 面试话术
「美团 Leaf 两种模式：Leaf-segment 是号段模式，DB 存 max_id 和 step，应用每次取一个号段（如 1000 个）缓存本地，双 buffer 预加载避免取号等待，降低 DB 压力；Leaf-snowflake 用 ZK 分配 workerId + 记录上次时间戳解决时钟回拨。号段模式缺点是 ID 可被推测量，可加随机步长改善。」

# 第七篇 注册中心与配置中心 🟡

## 7.1 注册中心对比

### ① 为什么/痛点
微服务需要知道"服务实例在哪"（IP:port），实例会动态上下线，要一个中心化的注册发现机制。

### ② 对比
- **Nacos**：阿里，AP+CP 双模式，注册+配置一体，UI 友好，主流。
- **Eureka**：Netflix，AP，停更。
- **ZooKeeper**：CP，通用协调（锁、选主、配置），重。
- **Consul**：HashiCorp，CP，带健康检查 + 服务网格。
- **etcd**：CNCF，CP，K8s 用的，Raft。

### ③ 真实案例（茶饮 SaaS 场景
用 Nacos：AP 模式注册服务（高可用优先），CP 模式存配置（强一致）。门店服务、订单服务、券服务都注册到 Nacos，相互通过 Nacos 服务发现调用。

### ④ 面试话术
「注册中心我们用 Nacos，AP+CP 双模式，注册用 AP（高可用优先），配置用 CP（强一致）。为什么不选 ZK？ZK 是 CP，选举期不可用，注册中心这个场景下短暂不一致能接受但不能用，所以选 AP（Nacos 默认 AP、Eureka）。Eureka 停更了不考虑。」

---

## 7.2 服务发现：推 vs 拉

### ① 对比
- **推**（Nacos）：服务端变更主动推客户端，实时。
- **拉**（Eureka）：客户端定时拉（30s），有延迟。
- **长轮询**（Nacos 配置）：客户端 hold 请求 30s，配置变更立即返回。

### ② 面试话术
「服务发现两种模式：推（Nacos，服务端变更主动推，实时）和拉（Eureka，客户端定时拉 30s，有延迟）。配置中心多用长轮询——客户端 hold 请求 30s，配置变更立即返回，兼顾实时和性能。Nacos 配置中心就是长轮询。」

---

## 7.3 健康检查

### ① 内容
- 客户端心跳（Nacos 临时实例 5s）。
- 服务端 TCP/HTTP 探测（Nacos 持久实例、Consul）。

### ② 面试话术
「健康检查两种：客户端心跳（Nacos 临时实例 5s 一次，超时摘除）和服务端探测（Consul TCP/HTTP 主动探）。Nacos 区分临时实例（心跳）和持久实例（服务端探），灵活。」

# 第八篇 ZooKeeper 🟡

## 8.1 数据模型

### ① 为什么/痛点
需要一个"协调服务"——存配置、做注册、选主、加锁。ZK 用树形命名空间 + Watcher 机制，提供通用的分布式协调能力。

### ② 内容
- **树形命名空间**（Znode）：路径如 `/app/service/provider1`。
- Znode 类型：**持久/临时** × **顺序/非顺序**（组合 4 种）。
- 临时节点：会话结束自动删除（做锁、注册）。
- 顺序节点：自动加序号后缀（做队列、选主）。

```
/（根）
├── app1
│   ├── config        （持久，存配置）
│   ├── services
│   │   ├── provider1 （临时，注册）
│   │   └── provider2 （临时，注册）
│   └── lock
│       ├── seq-0001  （临时顺序，分布式锁）
│       └── seq-0002
└── app2
```

---

## 8.2 核心 API 与监听（Watcher）

### ① 内容
- getData/getChildren/exists + watch：**一次性触发**（3.6+ 支持持久递归 watch）。
- 典型应用：配置（节点存配置 + watch）、注册（临时子节点 + watch 父节点）、选主（临时顺序节点 + watch 前驱）、分布式锁。

### ② 面试话术
「ZK 核心：树形 Znode + Watcher 监听。Znode 四种类型：持久/临时 × 顺序/非顺序。临时节点会话结束自动删（做注册、锁），顺序节点自动加序号（做选主、队列）。Watcher 是一次性触发，3.6 才支持持久递归。典型应用：配置中心、注册中心、选主、分布式锁，Dubbo 早期和 Kafka 元数据都用 ZK。」

---

## 8.3 ZK 典型场景

- 注册中心（Dubbo 早期、Kafka 元数据）。
- 分布式锁（Curator InterProcessMutex）。
- Leader 选举。
- 配置中心（小规模）。
- 队列（顺序节点）。

# 第九篇 实战案例汇总

## 📌 案例 4：分布式事务踩坑（Seata AT）

**① 痛点/现象**：跨服务下单（订单服务 + 库存服务），偶发库存扣了订单没建。

**② 排查**：用 Seata AT，但库存服务的 RM 没正确配置（数据源代理没生效）→ 全局事务回滚时库存 undo 没执行。

**③ 解决**：确保所有参与服务的 DataSource 被 Seata 代理（`@EnableAutoDataSourceProxy` 或启动参数）。

**④ 话术**：「Seata AT 踩坑——库存服务数据源代理没生效，导致回滚时 undo log 没执行，库存扣了没回滚。教训是上 Seata 必须确保每个参与服务都配了数据源代理，启动时验证 RM 注册成功。」

---

## 📌 案例 5：Redis 分布式锁主从切换丢锁

**① 痛点/现象**：高并发抢券，偶尔超发。

**② 排查**：主库加锁 → 主库宕机 → 从库（锁未同步）晋升 → 锁丢失 → 并发。

**③ 解决**：
- 业务幂等兜底（券领取唯一约束）。
- 强一致场景改用 Redlock 或 ZK。
- Redis 主从同步配置 `WAIT` 命令等待同步。

**④ 话术**：「Redis 主从异步复制导致丢锁——主加锁后宕机，从没同步就晋升，锁丢了。我们三层兜底：业务幂等（券领取唯一约束，重复直接忽略）、Redis WAIT 等同步、强一致场景上 ZK。教训是 Redis 锁不能单独保证可靠，必须配业务幂等。」

---

## 📌 案例 6：消息积压导致系统雪崩

**① 痛点/现象**：消费端 DB 慢，MQ 积压 100w 条，磁盘告警。

**② 排查**：消费速度 < 生产速度，持续堆积。

**③ 解决**：
- 紧急：临时扩容消费者（先转发到新 topic 更多分区）。
- 根因：优化消费逻辑（批量化、异步写 DB）。
- 监控：积压量告警。

**④ 话术**：「积压 100w 是因为消费写库慢。紧急转发到 60 分区新 topic + 60 消费者批量写，2 小时清完。根因是 SQL 索引差，优化后正常。监控一定要做积压量告警，提前发现。」

---

## 📌 案例 7：雪花算法时钟回拨导致重复 ID

**① 痛点/现象**：订单号偶尔重复。

**② 排查**：服务器 NTP 同步触发时钟回拨 → 雪花生成重复 ID。

**③ 解决**：记录上次时间戳，回拨超 5ms 等待，超 10ms 报警拒绝服务（或切到备用 worker）。

**④ 话术**：「雪花时钟回拨生成重复订单号，排查发现是 NTP 同步触发。解决是记录上次时间戳，回拨小等待大报错。长期方案是 Leaf-snowflake 用 ZK 分配 workerId + 持久化上次时间戳，更彻底。」
