# 第一篇 消息队列（MQ）

## 1.1 MQ 的三大作用 🟢
1. **解耦**：生产者消费者互不依赖。
2. **异步**：写入即返回，提升响应速度。
3. **削峰填谷**：突发流量先入队，消费端按自己节奏处理。

## 1.2 主流 MQ 对比 🔴🔴

| | Kafka | RocketMQ | Pulsar | RabbitMQ |
|---|-------|----------|--------|----------|
| 来源 | LinkedIn（大数据） | 阿里（电商） | Yahoo（云原生） | Erlang |
| 吞吐 | **极高**（百万级） | 高（十万级） | 高 | 中 |
| 延迟 | ms | ms | ms | μs（低） |
| 顺序 | 分区有序 | 严格顺序（一款） | 分区有序 | 不保证 |
| 事务 | 弱 | **强**（半消息+回查） | 支持 | 弱 |
| 延时 | 无原生 | **原生**（18 等级） | 支持 | 插件 |
| 存算 | 耦合 | 耦合 | **分离**（BookKeeper） | 耦合 |
| 适用 | 日志/大数据/流 | 电商业务消息 | 云原生/多租户 | 中小项目 |

### 怎么选？🔴
- **日志、大数据、流处理**：Kafka（吞吐王）。
- **业务消息（订单、交易，需事务/延时）**：RocketMQ。
- **多租户、云原生、存算分离弹性**：Pulsar（较新）。
- **中小项目、协议丰富（AMQP）、复杂路由**：RabbitMQ。

## 1.3 Kafka 核心架构 🔴🔴

```
Producer → Topic（逻辑） → Partition（物理，分区内有序） → Replica（副本）
                              ↓
        Broker（节点）← Leader / Follower（ISR 同步副本）
                              ↑
                       Consumer Group（消费者组，分区独占消费）
```

### 关键概念
- **Partition**：主题分区，**单分区内有序**。分区数 = 并发度。
- **Replica**：副本。**Leader** 负责读写，**Follower** 同步。
- **ISR（In-Sync Replicas）**：与 Leader 保持同步的副本集合，落后太多会被踢出。
- **Offset**：消费者在分区的消费位置。
- **Consumer Group**：组内消费者平分分区（一个分区只被组内一个消费者消费）。

## 1.4 Kafka 高吞吐的 6 大原因 🔴🔴 必精通

1. **顺序写磁盘**（append）：磁盘顺序写 >> 随机写（HDD 差 100 倍，SSD 也有数量级）。
2. **页缓存 PageCache**：写操作系统的 page cache，OS 异步刷盘。Kafka 不维护堆内缓存，复用 OS 缓存。
3. **零拷贝（sendfile）**：数据直接从内核到网卡，不进用户空间（详见 Java 核心篇零拷贝）。
4. **批量发送**：生产者攒批 + 压缩（snappy/lz4/gzip），减少网络/IO 次数。
5. **分区并行**：水平扩展，分区数 = 并发度。
6. **Pull 模式**：消费者按自己能力拉，不压垮消费端（vs Push 模式）。

## 1.5 MQ 三大经典问题 🔴🔴🔴 必精通

### 问题一：消息可靠性（不丢失）

**全链路三环节**：
```
Producer → Broker → Consumer
```

**① 生产端不丢**：
- Kafka：`acks=all`（所有 ISR 确认）+ `retries`（失败重试）+ 回调确认。
- RocketMQ：同步发送 + 重试。

**② Broker 不丢**：
- Kafka：`min.insync.replicas >= 2`（至少 2 个副本）+ `acks=all` + `unclean.leader.election.enable=false`（禁止非 ISR 副本当 leader）。
- RocketMQ：同步刷盘（SYNC_FLUSH）+ 主从同步复制。

**③ 消费端不丢**：
- 关闭自动 ack，业务处理完**手动 ack**（Kafka 手动 commit offset）。
- 幂等保证重复消费安全。

### 问题二：消息重复（exactly-once）

**原因**：网络导致 ack 丢失 → 重发；消费者重启 offset 未提交。

**本质**：网络不可靠，**MQ 只能保证 at-least-once（至少一次）**。要 exactly-once 必须业务幂等。

**幂等方案** 🔴：
1. **唯一约束**：业务 ID 唯一键，重复插报错忽略。
2. **乐观锁（版本号）**：`UPDATE ... WHERE version=v`。
3. **状态机**：业务有状态流转（订单 已支付→已发货，重复消息改不了已支付的）。
4. **去重表**：记录已处理的 msg_id，新消息先查去重表。
5. **Redis 分布式锁**：`SET msg_id NX EX`。

**Kafka 的事务**（exactly-once）：producer 幂等 + 事务（consume-process-produce 原子），适合流处理。但**跨系统（如写 DB）仍需业务幂等**。

### 问题三：消息顺序

**场景**：订单 创建→支付→发货，必须按顺序消费。

**方案** 🔴：
- **单分区有序**：同一业务 key（如同 orderId）路由到**同一分区/队列**，单线程消费。
- **生产端**：key hash 分区（`orderId % partitionCount`）。
- **消费端**：单分区单线程；若要并发，按 key 分发到内存队列各自串行（RocketMQ MessageQueueSelector）。
- **代价**：牺牲并行度，热点 key 成瓶颈。

## 1.6 延时消息 🟡

- **RocketMQ** 原生 18 等级（1s/5s/10s/30s/1m/2m/.../2h）。
- 原理：消息先存 `SCHEDULE_TOPIC_XXXX`，后台定时任务到点重新投递。
- **通用方案**：
  - Redis ZSet（score=执行时间戳）扫描。
  - **时间轮**（HashedWheelTimer，多层）。
  - MQ + 多级延迟（Kafka 无原生需自建）。

## 1.7 消息积压处理 🔴（线上高频故障）

1. **临时扩容消费者**（同 group），注意 Kafka 消费者数 ≤ 分区数才有用。
2. **紧急方案**：先消费转发到新 topic（分区更多），再用更多消费者处理。
3. **根因排查**：消费者慢（DB 慢/外部接口慢）→ 优化处理逻辑 / 异步化 / 批量化。
4. **监控告警**：积压量监控，提前发现。

## 1.8 MQ 实战案例

### 📌 案例 1：消息丢失排查

**现象**：用户下单后偶尔没收到消息通知。
**排查**（全链路）：
- 生产端：`acks=1`（Leader 确认即可），Leader 刚确认就宕机，Follower 还没同步 → 消息丢。
**解决**：改 `acks=all` + `min.insync.replicas=2` + `unclean.leader.election.enable=false`。

### 📌 案例 2：消费重复导致重复扣款

**现象**：用户偶尔被扣两次款。
**排查**：消费者处理完业务、ack 前 crash → 重启重新消费 → 重复扣款。
**解决**：业务幂等（msg_id 去重表 + 唯一约束）。

### 📌 案例 3：消费乱序

**现象**：订单状态错乱（先发货后支付）。
**排查**：多分区并发消费，同订单消息分散到不同分区。
**解决**：生产端用 `orderId` 做 key 路由到同一分区，单线程消费。

# 第二篇 分布式理论

## 2.1 CAP 定理 🔴🔴 必精通

一个分布式系统在**一致性 C、可用 A、分区容错 P** 三者中**最多满足两个**。由于网络分区 P 不可避免，实际是在 **CP** 和 **AP** 间选择。

| 模型 | 含义 | 典型 |
|------|------|------|
| CP | 分区时牺牲可用性保一致性 | ZooKeeper（leader 选举期不可用）、etcd、HBase |
| AP | 分区时牺牲一致性保可用性 | Eureka、Nacos(AP)、Cassandra |
| CA | 不存在分区（单机） | 关系数据库 |

**注意**：CAP 的 C 是**线性一致性（强一致）**，不是 ACID 的 C（事务一致性）。
**分区时**选 CP 还是 AP，看业务能否容忍**短暂不一致**。

**常见误区** 🔴：
- "AP = 高可用" ❌。AP 指分区时仍响应（可能返回旧数据），不等于 SLA 高可用。
- "三选二" 实际是 P 必选，C/A 二选一（分区时）。

## 2.2 BASE 理论 🟡
CAP 在 AP 的延伸：
- **Basically Available** 基本可用：允许损失部分可用性。
- **Soft state** 软状态：允许中间状态。
- **Eventually consistent** 最终一致：保证最终一致。

大多数互联网业务（电商、社交）用 BASE + 最终一致，而非强一致。

## 2.3 一致性模型 🔴
- **强一致（线性一致）**：读一定读到最新写。代价高（同步）。
- **顺序一致**：所有节点看到操作顺序一致，但不一定实时。
- **因果一致**：有因果关系的操作有序。
- **最终一致**：停止写入后最终所有副本一致。变种：读己之写、单调读、单调写。

# 第三篇 分布式一致性算法 🔴

## 3.1 Raft 🔴🔴 推荐重点理解（比 Paxos 易懂）

**解决的问题**：多节点达成一致（选主、日志复制）。etcd、Consul、TiKV、Nacos CP 都用它。

### 三个子问题

**① Leader 选举** 🔴
- 节点状态：**Follower / Candidate / Leader**。
- 正常时 Leader 定期发心跳（AppendEntries）给 Follower。
- Follower 超过选举超时（election timeout，随机 150-300ms）未收到心跳 → 变 Candidate。
- Candidate：term++，给自己投票，发 RequestVote 给其他节点。
- 获**多数票** → 成为 Leader，开始发心跳。
- 🔴 **一个 term 内每个节点只投一票** → 防止多个 leader（同一 term 不会有两个 Candidate 都获多数）。
- **随机超时** → 错峰选举，避免活锁。

**② 日志复制** 🔴
```
1. Leader 收到写请求 → 写本地日志（未 commit）
2. 并行复制到所有 Follower（AppendEntries）
3. 多数 Follower 确认 → Leader commit（应用到状态机）→ 返回客户端成功
4. Leader 下一次心跳通知 Follower commit
```
- **多数派**（quorum）：N/2 + 1。5 节点需 3 个确认。

**③ 安全性**
- **选举限制**：Candidate 的日志必须"至少和新"（up-to-date）才能被选为 Leader → 保证 Leader 包含所有已 commit 日志。
- **commit 限制**：Leader 只 commit 当前 term 的日志（防"已 commit 被覆盖"）。

## 3.2 Paxos 🟡（了解）
- 更基础、更通用，但复杂。
- **Basic Paxos**（单值）：Proposer/Acceptor/Learner，两阶段（Prepare/Accept）。
- **Multi-Paxos**（多值）：Raft 的基础，选出稳定 Leader 跳过 Prepare。
- 应用：Google Chubby、Spanner。

## 3.3 ZAB 协议 🟡
ZooKeeper 用，类似 Raft。
- 两阶段：**崩溃恢复**（选主）+ **消息广播**（两阶段提交变体）。
- **ZXID**（事务 ID）= epoch（32bit）+ counter（32bit）。
- epoch 类似 Raft term，counter 保证单Leader内有序。

# 第四篇 分布式事务 🔴🔴 必精通

## 4.1 各种方案对比

| 方案 | 一致性 | 性能 | 复杂度 | 适用 |
|------|--------|------|--------|------|
| **2PC**（XA） | 强一致 | 差（同步阻塞） | 中 | 传统数据库、银行 |
| **3PC** | 强一致 | 差 | 高 | 很少用 |
| **TCC** | 强一致（业务层） | 好 | 高（3 方法） | 金融、核心交易 |
| **SAGA** | 最终一致 | 好 | 中（补偿复杂） | 长事务、多服务 |
| **本地消息表** | 最终一致 | 好 | 低 | 互联网主流 |
| **事务消息**（RocketMQ） | 最终一致 | 好 | 中 | 解耦场景 |
| **Seata AT** | 最终一致（默认） | 好 | 低（无侵入） | 主流微服务 |

## 4.2 2PC（两阶段提交）🟡

```
阶段一 Prepare：
  协调者 → 各参与者："准备提交"
  各参与者：锁资源、写 undo/redo → 回 yes/no
阶段二 Commit/Rollback：
  全部 yes → 协调者发 commit
  任一 no → 协调者发 rollback
```
**问题**：同步阻塞、协调者单点、参与者超时不一致、性能差。

## 4.3 TCC（Try-Confirm-Cancel）🔴

```
Try：预留资源（如冻结余额）
Confirm：真正扣减（用预留资源）
Cancel：释放预留
```
- **业务侵入大**，每操作写 3 个方法。
- 要处理：**幂等**（Confirm/Cancel 可能重试）、**空回滚**（Try 未执行但 Cancel 调用）、**悬挂**（Cancel 先于 Try 到达）。
- 适合核心金融交易。

## 4.4 Seata 🔴🔴 主流

### 三种模式
- **AT 模式**（默认，无侵入）：基于本地事务 + undo log。
  - **一阶段**：拦截 SQL → 执行本地事务 + 记录 undo log（前后镜像）+ 记录**全局锁**。
  - **二阶段提交**：异步删 undo log。
  - **二阶段回滚**：根据 undo log 反向补偿。
  - **隔离性**：全局锁实现写隔离；读默认 RC（要 RR 加 @GlobalLock）。
- **TCC 模式**：手写 Try/Confirm/Cancel。
- **SAGA 模式**：长事务，正向 + 补偿。

### 角色
- **TC**（Transaction Coordinator）：事务协调器，独立部署（Seata-Server）。
- **TM**（Transaction Manager）：事务管理器，发起方（@GlobalTransactional）。
- **RM**（Resource Manager）：资源管理器，参与方（每个数据库/服务）。

## 4.5 本地消息表（互联网主流）🔴🔴

```
1. 业务表 + 消息表 在【同一个本地事务】里写
   → 保证业务和消息同时成功/失败
2. 定时任务扫描消息表，投递 MQ
3. 消费方处理完 ack，回调更新消息表状态
4. 失败重试 + 业务幂等
```
**优**：实现简单、最终一致、可靠（消息表持久化）。
**劣**：消息表耦合业务、定时扫描有延迟（可改 binlog 监听即时投递）。

## 4.6 RocketMQ 事务消息 🔴🔴

```
1. Producer 发"半消息"（消费者看不到）→ Broker 存储
2. 执行本地事务
3. 本地事务成功 → commit（消息可见）；失败 → rollback（删除）
4. 异常（无 commit/rollback）→ Broker 【回查】Producer → 根据本地事务状态决定
```
**本质**：解决"本地事务 + 发消息"的原子问题。

# 第五篇 分布式锁 🔴🔴 必精通

## 5.1 三种实现对比

| 实现 | 一致性 | 性能 | 可重入 | 可靠性 |
|------|--------|------|--------|--------|
| Redis（Redisson） | AP（高可用，可能不一致） | 高 | 支持（hash 计数） | 中（主从切换可能丢锁） |
| ZooKeeper | CP（强一致） | 中 | 支持（节点计数） | 高 |
| MySQL（唯一约束） | 强 | 低 | 难 | 高 |

## 5.2 Redis 分布式锁演进 🔴🔴

**v1 简单版**：
```bash
SET key value NX PX 30000   # NX 不存在才设，PX 过期
```
**问题**：业务没执行完锁就过期 → 误删别人锁。

**v2 加唯一 value + Lua**：
```lua
-- 加锁：value 用 UUID（标识自己）
-- 解锁：Lua 脚本判断 value 一致才删（保证"判断+删除"原子）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**v3 Redisson 看门狗** 🔴：
- 默认锁 30s，后台**看门狗线程**每隔 10s（1/3 周期）检查持有者还活着就续期。
- 可重入：hash 结构，key=锁名，field=线程ID，value=重入次数。
- 公平锁、读写锁、信号量都支持。

## 5.3 Redlock（多节点）争议 🔴🔴

**antirez 提出**：向 N（奇数，如 5）个**独立** Master 节点申请锁，**多数（3）成功**才算成功。

**Martin Kleppmann 批评** 🔴：
1. **GC 暂停**：客户端持锁后 GC 停顿，锁超时但客户端不知情，其他客户端获锁 → 并发。
2. **时钟漂移**：依赖各节点时钟，NTP 跳变会破坏假设。
3. **正确性 vs 性能**：为性能牺牲了正确性，不如直接用 ZK/etcd。

**结论**：强一致场景用 ZK/etcd；高并发性能优先用 Redis，容忍极小概率失败 + 业务幂等兜底。

## 5.4 ZK 分布式锁 🔴

- **临时顺序节点**：`/lock/seq-0001`、`/lock/seq-0002`...
- **最小序号获锁**。
- 其余节点**监听前一个节点删除事件**（不是监听所有）→ **避免羊群效应**（一个节点释放，所有等待者被唤醒争抢）。
- 客户端断开 → 临时节点自动删除 → 释放锁 + 通知后继。
- CP 特性，强一致可靠，但写性能不如 Redis。

# 第六篇 分布式 ID 🔴🔴

## 6.1 需求
全局唯一、趋势递增（索引友好）、高性能、高可用、信息安全（不能暴露业务量）。

## 6.2 方案对比

| 方案 | 唯一 | 递增 | 性能 | 依赖 | 缺点 |
|------|------|------|------|------|------|
| UUID | ✅ | ❌ 随机 | 高 | 无 | 长度长、索引差、无序 |
| 数据库自增 | ✅ | ✅ | 低 | DB | 单点、瓶颈 |
| **号段模式**（美团 Leaf-segment） | ✅ | ✅ | 高 | DB | 可推测量（可改进） |
| **雪花算法**（Snowflake） | ✅ | ✅ | 极高 | 时钟 | 时钟回拨 |
| Leaf-snowflake | ✅ | ✅ | 极高 | ZK | 复杂 |
| Redis INCR | ✅ | ✅ | 高 | Redis | 持久化风险 |

## 6.3 雪花算法 🔴🔴 必精通

**64 位结构**：
```
| 1bit 符号(0) | 41bit 时间戳(ms) | 10bit 机器ID | 12bit 序列号 |
```
- 41 bit 时间戳：可用约 69 年。
- 10 bit 机器：1024 台（可拆 5 机房 × 12 机器）。
- 12 bit 序列：同 ms 内 4096 个。

**时钟回拨问题** 🔴🔴：
- 服务器时间回退（NTP 同步、人为调整）→ 时间戳变小 → 可能生成重复 ID。
**解决**：
- 拒绝服务（回拨超阈值报警）。
- 等待（睡眠到回拨后）。
- 用历史最大时间戳。
- Leaf-snowflake 用 ZK 分配 workerId + 记录上次时间戳（回拨小则等待，大则报错）。

## 6.4 美团 Leaf 🟡
- **Leaf-segment**：DB 存 `max_id, step`，应用每次取一个号段（如 1-1000），用完再取。双 buffer 预加载避免等待。
- **Leaf-snowflake**：ZK 持久顺序节点分配 workerId，解决时钟回拨。

# 第七篇 注册中心与配置中心 🟡

## 7.1 注册中心对比
- **Nacos**：阿里，AP+CP 双模式，注册+配置一体，UI 友好，主流。
- **Eureka**：Netflix，AP，停更。
- **ZooKeeper**：CP，通用协调（锁、选主、配置），重。
- **Consul**：HashiCorp，CP，带健康检查 + 服务网格。
- **etcd**：CNCF，CP，K8s 用的，Raft。

## 7.2 服务发现：推 vs 拉
- **推**（Nacos）：服务端变更主动推客户端，实时。
- **拉**（Eureka）：客户端定时拉（30s），有延迟。
- **长轮询**（Nacos 配置）：客户端 hold 请求 30s，配置变更立即返回。

## 7.3 健康检查
- 客户端心跳（Nacos 临时实例 5s）。
- 服务端 TCP/HTTP 探测（Nacos 持久实例、Consul）。

# 第八篇 ZooKeeper 🟡

## 8.1 数据模型
- **树形命名空间**（Znode）：路径如 `/app/service/provider1`。
- Znode 类型：**持久/临时** × **顺序/非顺序**（组合 4 种）。
- 临时节点：会话结束自动删除（做锁、注册）。
- 顺序节点：自动加序号后缀（做队列、选主）。

## 8.2 核心 API 与监听（Watcher）
- getData/getChildren/exists + watch：**一次性触发**（3.6+ 支持持久递归 watch）。
- 典型应用：配置（节点存配置 + watch）、注册（临时子节点 + watch 父节点）、选主（临时顺序节点 + watch 前驱）、分布式锁。

## 8.3 ZK 典型场景
- 注册中心（Dubbo 早期、Kafka 元数据）。
- 分布式锁（Curator InterProcessMutex）。
- Leader 选举。
- 配置中心（小规模）。
- 队列（顺序节点）。

# 第九篇 实战案例汇总

## 📌 案例 4：分布式事务踩坑（Seata AT）

**现象**：跨服务下单（订单服务 + 库存服务），偶发库存扣了订单没建。
**排查**：用 Seata AT，但库存服务的 RM 没正确配置（数据源代理没生效）→ 全局事务回滚时库存 undo 没执行。
**解决**：确保所有参与服务的 DataSource 被 Seata 代理（`@EnableAutoDataSourceProxy` 或启动参数）。

## 📌 案例 5：Redis 分布式锁主从切换丢锁

**现象**：高并发抢券，偶尔超发。
**排查**：主库加锁 → 主库宕机 → 从库（锁未同步）晋升 → 锁丢失 → 并发。
**解决**：
- 业务幂等兜底（券领取唯一约束）。
- 强一致场景改用 Redlock 或 ZK。
- Redis 主从同步配置 `WAIT` 命令等待同步。

## 📌 案例 6：消息积压导致系统雪崩

**现象**：消费端 DB 慢，MQ 积压 100w 条，磁盘告警。
**排查**：消费速度 < 生产速度，持续堆积。
**解决**：
- 紧急：临时扩容消费者（先转发到新 topic 更多分区）。
- 根因：优化消费逻辑（批量化、异步写 DB）。
- 监控：积压量告警。

## 📌 案例 7：雪花算法时钟回拨导致重复 ID

**现象**：订单号偶尔重复。
**排查**：服务器 NTP 同步触发时钟回拨 → 雪花生成重复 ID。
**解决**：记录上次时间戳，回拨超 5ms 等待，超 10ms 报警拒绝服务（或切到备用 worker）。
